# Проект: поиск объектов на карте

Проектный документ.
Формат карты: [`map-format-v4.md`](../map-format-v4.md) (индекс поиска — раздел 21), клавиатура: [`user-guide.md`](../user-guide.md).

- [x] «Простой поиск» (категория → ближайшие объекты, без нового формата карты)
- [x] «Умный поиск» (ввод текста: категория и/или начало названия, список уточняется по мере набора; POI, улицы, реки,
водоёмы и землепользование). Умный поиск строится поверх простого: расстояния, переход на карту и цель навигации общие.
Замеры на железе и на карте Беларуси - в списке задач ниже.

**Что есть в карте (проверено по `features.csv`, `purrgo_bin_writer.py`, `purrgo_osmparser.py`).**

- `pois.idx`: три секции LOD, и в LOD 0 лежат **все** POI (`lod >= 0`), в LOD 1 и 2 только более важные.
  Для поиска всегда обходится секция LOD 0. Узел листа: bbox (у POI вырожденный, `xmin==xmax`, `ymin==ymax`,
  координата = градусы × 10⁷), `Type`, `v1 = 0`, `v2` = номер записи в `pois.db`.
- `pois.db`: DBF, заголовок 129 Б, запись 117 Б (validity 1, osm_id 12, code 4, name 100); запись `v2`
  находится по смещению `129 + (v2 - 1) * 117`. Координат в `.db` нет, обратной ссылки на узел тоже нет.
- Название: `name:ru > name:be > int_name > short_name:en > name:en > short_name > name`. Пробелы заменены на `_`,
  стоп-слова («кафе», «ресторан», «улица», «hotel»…) переносятся
  в конец («Пушкин кафе»). У POI без названия в имя подставляется значение OSM-тега (`camp_site`, `clothes`),
  то есть безымянный объект от именованного по `.db` не отличить.
  В V3 компилятор обрезал название до 22 символов (20 + `..`) для малого экрана; в V4 название хранится целиком
  (поле 100 Б, размер записи не меняется), а сокращение при выводе делает прошивка (`map-format-v4.md`, раздел 10.6).
  Поэтому в поиске доступны хвост длинного названия и перенесённое в конец стоп-слово.
- Код `Type` — класс отрисовки, а не OSM-тег. POI-коды (диапазон 128..191, см. `map-format-v4.md`, раздел 8.1.1, и `tools/map-compiler/features.csv`; прежние коды 11..36 заменены): 128 населённые пункты, 129 малые населённые пункты (то же, что 128), 130 полиция, 131 магазины и рынок, 132 медицина, 133 еда, 134 хижины (альпийский домик, лесная избушка), 135 кемпинг и зона отдыха, 136 одежда и обувь, 137 спорт и туризм, 138 компьютеры и связь, 139 велосипеды, 140 автосервис, 141 замки, руины, форты, маяки, 142 туалет, 143 питьевая вода, колодец, родник, 144 прочее (брод), 145 АЗС, 146 транспорт, 147 авиация, 149 бар и паб, 150 душ, 151 банк и банкомат, 152 препятствия (барьеры, не искать), 153 достопримечательности, смотровые, горячие источники, 154 вулкан, 155 перевал, 156 пожарные, 157 культовые сооружения, 159 укрытия, 160 строительные магазины, 161 хозмаги, 162 памятники и мемориалы, 163 искусство, 164 водопад, 165 стоянка автодомов, 166 жильё (место для пикника, обычно можно поставить палатку), 167 жильё (отель, мотель, B&B, гостевой дом, хостел). Коды 148 и 158 не заняты.
- Клавиатура En/Ru (`keyboard.h`, `ui_keyboard.c`, `PURRGO_KBD_TEXT_MAX` = 48, кодировка PurrGO-256) подключена к умному
  поиску (`APP_STATE_SEARCH`) и к поиску по книге. На экране карты все четыре кнопки заняты, вход в поиск — через главное меню.

### Простой поиск (категория → ближайшие)

Без изменений формата карты и компилятора: нужны только `pois.idx` и `pois.db`.

**Поведение.** MENU_MAIN → SEARCH → список категорий → список из ближайших 32 объектов категории
(иконка, название, расстояние, направление) → выбор строки переводит на карту с центром в объекте.

**Категории** (таблица в прошивке: название «RU / EN», маска кодов `Type`; на экране 176 px помещается
около 29 символов 5×7, поэтому названия двуязычные и язык интерфейса не нужен):

| Категория | Коды |
|---|---|
| Жильё / Lodging | 134, 135, 159, 165, 166, 167 |
| Еда и напитки / Food | 133, 149 |
| Магазины / Shops | 131, 136, 137, 138, 139, 140, 160, 161 |
| Здоровье / Health | 132 |
| Вода / Water | 143 |
| Туалеты и душ / Toilets, showers | 142, 150 |
| АЗС / Fuel | 145 |
| Транспорт / Transport | 146, 147 |
| Банки и банкоматы / Money | 151 |
| Экстренные службы / Emergency | 130, 156 |
| Достопримечательности / Sights | 141, 153, 154, 157, 162, 163, 164 |
| Перевалы / Passes | 155 |
| Населённые пункты / Towns | 128, 129 |

Коды 144 (прочее) и 152 (препятствия) в категории не входят. Ограничение: категория = код отрисовки, поэтому «хостел» от «отеля»,
а «кемпинг» от «укрытия» не отличить, а в «Достопримечательностях» вместе вершины, храмы и памятники.
Тонкое деление даёт только умный поиск (подтипы).

**Алгоритм ядра** (модуль `src/core/map/poi_search.c`, без float, без выделения памяти, опрос порциями,
чтобы не блокировать кнопки):

1. Начало отсчёта: GNSS, если есть фикс; иначе последняя известная позиция; иначе центр вида карты. Источник
   (`GNSS` / `LAST` / `MAP`) показывать в заголовке списка.
2. Обход LOD 0 `pois.idx` по bbox квадрата вокруг начала отсчёта; в листе проверять `Type` по маске.
   Радиус растёт 1 → 2 → 4 → … → 64 км, пока не набрано N результатов или не достигнут предел.
   Пересчёт на каждом шаге читает верхние узлы заново, но их держит LRU-кэш секторов.
3. Расстояние: `dy = Δlat`, `dx = Δlon · cos(lat0)` (таблица `cos` Q15 по градусам, `lat0` — широта начала
   отсчёта), `d² = dx² + dy²` в int64. Единица координаты = 10⁻⁷° ≈ 1,112 см; метры = `sqrt(d²) · 1112 / 10⁸`
   (целочисленный корень только для подписи). Направление: 8 румбов по знакам и отношению `|dx|` и `|dy|`.
   Сначала сверить `geo.c` и `navigation.c`, чтобы не дублировать готовые функции.
4. Топ-N по `d²`: вставка в массив фиксированного размера, без `qsort`. Память: 32 записи × ≈16 Б ≈ 0,5 КБ.
5. Названия читать из `pois.db` только для строк на экране, `_` заменять на пробел, длинное название сокращать по ширине строки (`map-format-v4.md`, раздел 10.6.1); для безымянных
   (имя совпадает с OSM-значением) на этом этапе показывать как есть.

**Проблема в коде.** `map_idx_parse_node()` привязана к отрисовке (`gfx`, `params`, `cam`). Нужно выделить из
неё обход дерева с колбэком на лист (`visit(bbox, type, v2)`), общий для рендера и поиска. Рендер при этом
не должен замедлиться: сравнить время кадра до и после (профиль из P2).

**UI.** Подсостояния `APP_STATE_MENU_POI_CATEGORY` и `APP_STATE_MENU_POI_RESULTS` (как `WPT_SELECT`):
UP / DOWN / SELECT / BACK, 1 bit, вывод списка по правилам полного и частичного обновления, как у остальных
меню. Выбор строки: `map_controller` центрирует карту, автоследование выключается, остаётся перекрестие
центра карты. Длинный SELECT назначает объект целью навигации (WAYPOINT, как MAP CENTER).

**Задачи.**

  через `map_idx_draw_leaf()`. Host-тесты `test_map.c` проходят; сравнение кадра и время кадра - на железе.

  имён. Файлы `pois.idx` и `pois.db` берутся у карты (`purrgo_map_poi_files()`), отдельных слотов ФС поиск не занимает
  (всего слотов 14, слой POI уже держит два).

### Умный поиск (категория и/или начало названия, список уточняется)

Ищутся не только POI, но и **улицы и дороги** (`roads`), **реки и ручьи** (`waterways`), **водоёмы и болота** (`water`) и
**землепользование** (`landuse`: леса, парки, кладбища, районы...). Слой объекта задаёт его код `Type`, названия лежат в
`*.db` слоя, поэтому индекс общий (`map-format-v4.md`, раздел 21), а запись указывает на запись `.db` нужного слоя.

Требования: ввод слов-категорий на русском и английском («жильё», «hotel», «еда», «река», «парк»…), ввод первых
букв названия, список по расстоянию, уточнение на каждом символе, выбор → карта центрируется на объекте.
Запрос из двух частей работает как И: «кафе пуш» = категория «кафе» и название на «пуш».

**Почему нужен новый файл.** Название и координата лежат в разных файлах без обратной ссылки, `.db` — 117 Б
на запись, а линейное чтение десятков МБ с SD по SPI (10 МГц) на каждый символ недопустимо. Стоп-слова
переносятся в конец имени («Пушкин кафе»), поэтому «кафе» в начале имени искать нельзя. Нужен индекс,
отсортированный по ключу названия, с позицией в записи.

**Файл `search.idx`** (опционален; нет файла → доступен только простой поиск; описан в спецификации (`map-format-v4.md`, раздел 21) как
необязательный файл V4, `tests/audit_maps.py` проверяет только его PGO-заголовок). PGO-контейнер, новый `file_type`,
дальше:

Точный формат заголовка, записи, словаря и правила проверки — в `map-format-v4.md`, раздел 21; ниже обзор.

- Заголовок: magic `SRCH`, версия, размер записи, число записей в секциях, смещения секций,
  словарь категорий.
- Запись 32 Б: `lon` i32, `lat` i32, `db_idx` (`v2`) u32, `code` u8, `subtype` u8, `flags` u8
  (бит «вторичная запись слова», бит «безымянный»), `key_len` u8, `key[16]` — свёрнутый ключ.
- Секция NAME: все записи, отсортированы по `key`. Для каждого слова названия (разделители `_`, `-`, `(`)
  добавляется своя запись (до 4 слов на имя, `flags` = «вторичная»), поэтому ищется и «пуш», и «кафе».
  Размер секции оценить как N × 32 Б × ≈1,7 по числу узлов `pois.idx` карты из CI.
- Секция CAT: записи отсортированы по (`subtype`, Morton-код координаты), в ней по одной записи на объект.
  Для категорийных запросов читается подряд только участок нужных подтипов.
- Безымянные POI (имя = OSM-значение) попадают в CAT и не попадают в NAME.
- Улицы, реки, водоёмы и землепользование: только объекты с названием. У линии одна **точка привязки** (средняя вершина),
  у полигона - вершина внешнего контура, ближайшая к центру BBox: на неё центрируется карта. Чтобы улица из тысяч отрезков
  не давала тысячи строк, объекты слоя с одинаковым названием и точкой привязки в одной клетке 0.05° сливаются в одну запись
  (только в индексе, `.db` не меняются). Слова-ключи словаря («улица», «река») вторичными записями не индексируются.
  В заголовке `search.idx` четыре поля `*_records` (число записей `.db` слоя) защищают от индекса другой карты.

**Ключ.** Нормализация: нижний регистр, Ё → Е, `_` → пробел, `..` в конце отбрасывается; кириллица и
латиница в PurrGO-256 (`docs/font-encoding.md`: кириллица 0x80..0xBF, Ё/ё 0xF0/0xF1). Одна и та же
функция в компиляторе (Python) и в прошивке (C): таблица свёртки 256 Б генерируется скриптом из шрифта,
проверка по аналогии с `tests/check_pgo_text_table.py`, общие тестовые векторы. Ключ длиннее 16 байт не
различает хвост: после 16-го символа проверять полное имя из `pois.db` только у кандидатов.

**Подтипы и словарь.** Новый файл `tools/map-compiler/search_categories.csv`:
`Group;Subtype;Keywords_RU;Keywords_EN;OSM_Tags`. `OSM_Tags` — то же выражение, что в `features.csv`
(`tourism=hostel`), по нему компилятор присваивает подтип узлу. Группа = набор подтипов («жильё»: отель,
хостел, кемпинг, гостевой дом, укрытие). Словарь (слово → маска подтипов, синонимы RU / EN) записывается
в заголовок `search.idx`: можно расширять без перепрошивки. Правила `Enabled = 0` в карте отсутствуют и
поэтому не ищутся; чтобы искать без отрисовки, потребуется колонка «только поиск» в `features.csv`.

**Разбор запроса.**

1. Нормализация, разбиение на слова.
2. Слово — категория, если оно совпадает с ключевым словом словаря целиком или как префикс от 3 букв.
   Остальные слова — префиксы названия (первое из них идёт в запрос, остальные проверяются на полное
   имя кандидата).
3. Только категория → секция CAT. Есть слово-префикс названия → бинарный поиск диапазона в NAME
   (нижняя и верхняя границы по 16-байтному ключу), в потоке отфильтровать по маске подтипов, если она есть.
4. Префикс из одного символа не ищется (нужно 2 байта и больше); если в запросе есть категория, однобайтное слово названия
   просто не учитывается, пока человек печатает.
5. Единственное слово, которое только начало ключевого слова («пар»), ищется и как категория, и как название.

**Отбор и порядок.** Один поток по диапазону, в RAM только массив топ-32 по `d²` (и копия показанного списка: пока считается
новый запрос, на экране прежний); дубликаты по (слой, `db_idx`) схлопываются. Участок подтипа в CAT до 1024 записей читается
целиком, больший - по квадрату вокруг начала отсчёта: клетки квадродерева, интервалы кода Мортона, бинарный поиск и чтение
подряд, радиус 1 → 4 → 16 → 64 км. Каталог диапазонов в `search.idx` не нужен, пока замер на карте Беларуси не покажет обратное.

**Инкрементальность.** Если новый запрос продолжает предыдущий, бинарный поиск начинается внутри
предыдущего диапазона `[lo, hi)`. Порционный опрос (≈256 записей за вызов) прерывается на нажатие кнопки:
новый символ отменяет текущий расчёт.

**UI.** Состояние `APP_STATE_SEARCH` (`search_screen.c`, `ui_search.c`): сверху поле ввода клавиатуры, под ним строка
состояния (`Searching...`, `N found, from GNSS`, `Type 2+ letters`) и 8 строк результатов, внизу сетка клавиш. Запрос уходит
в поиск через 0,6 с после последней клавиши; пока считается новый запрос, виден прежний список. Список перерисовывается
частичным обновлением только изменившихся строк (`ui_rows`). Кнопки: долгое K3 - фокус в список (в списке K1 / K2 вверх и вниз,
K3 - показать на карте, долгое K3 - цель, K4 - к клавиатуре), долгое K4 - выход. При входе файлы карты закрываются
(`purrgo_map_shutdown()`): поиску нужны слоты ФС (`search.idx` и одна база названий), карта откроет файлы при следующей
отрисовке. Вход - отдельный пункт главного меню SMART SEARCH; SEARCH остаётся простым поиском по категориям (выбор из списка, без
набора текста) и от `search.idx` не зависит. Нет `search.idx` или он не прошёл проверку - SMART SEARCH ничего не открывает.
Последний запрос не запоминается.
