# Проект: поиск объектов на карте

Проектный документ.
Формат карты: [`map-format-v3.md`](../map-format-v3.md), клавиатура: [`user-guide.md`](../user-guide.md).

- [ ] «Простой поиск» (категория → ближайшие объекты, без нового формата карты)
- [ ] «Умный поиск» (ввод текста: категория и/или начало названия, список уточняется по мере набора). Умный поиск строится
поверх простого: список результатов, расстояния, переход на карту и тесты общие.

**Что есть в карте (проверено по `features.csv`, `purrgo_bin_writer.py`, `purrgo_osmparser.py`).**

- `pois.idx`: три секции LOD, и в LOD 0 лежат **все** POI (`lod >= 0`), в LOD 1 и 2 только более важные.
  Для поиска всегда обходится секция LOD 0. Узел листа: bbox (у POI вырожденный, `xmin==xmax`, `ymin==ymax`,
  координата = градусы × 10⁷), `Type`, `v1 = 0`, `v2` = номер записи в `pois.db`.
- `pois.db`: DBF, заголовок 129 Б, запись 117 Б (validity 1, osm_id 12, code 4, name 100); запись `v2`
  находится по смещению `129 + (v2 - 1) * 117`. Координат в `.db` нет, обратной ссылки на узел тоже нет.
- Название: `name:ru > name:be > int_name > short_name:en > name:en > short_name > name`. Пробелы заменены на `_`,
  длиннее 22 символов обрезается до 20 + `..`, стоп-слова («кафе», «ресторан», «улица», «hotel»…) переносятся
  в конец («Пушкин кафе»). У POI без названия в имя подставляется значение OSM-тега (`camp_site`, `clothes`),
  то есть безымянный объект от именованного по `.db` не отличить.
- Код `Type` — класс отрисовки, а не OSM-тег. POI-коды: 11 населённые пункты, 12 прочее мелкое (в основном
  выключено), 13 полиция и пожарные, 14 магазины и рынок, 15 медицина, 16 еда, 17 жильё, 18 кемпинг и укрытия,
  19 одежда и обувь, 20 спорт и туризм, 21 компьютеры и связь, 22 велосипеды, 23 стройка и автосервис,
  24 достопримечательности и природа (музей, памятник, вершина, смотровая, водопад, храм…), 25 туалет,
  26 питьевая вода, колодец, родник, 27 прочее (парковка, брод, пляж), 28 АЗС, 29 транспорт, 30 авиация,
  31 перевал, 32 бар и паб, 33 душ, 34 банк и банкомат, 36 барьеры (не искать).
- Клавиатура En/Ru готова (`keyboard.h`, `ui_keyboard.c`, `PURRGO_KBD_TEXT_MAX` = 48, кодировка PurrGO-256), но
  в `app_fsm` не подключена. На экране карты все четыре кнопки заняты, вход в поиск — через главное меню.

### Простой поиск (категория → ближайшие)

Без изменений формата карты и компилятора: нужны только `pois.idx` и `pois.db`.

**Поведение.** MENU_MAIN → SEARCH → список категорий → список из ближайших 32 объектов категории
(иконка, название, расстояние, направление) → выбор строки переводит на карту с центром в объекте.

**Категории** (таблица в прошивке: название «RU / EN», маска кодов `Type`; на экране 176 px помещается
около 29 символов 5×7, поэтому названия двуязычные и язык интерфейса не нужен):

| Категория | Коды |
|---|---|
| Жильё / Lodging | 17, 18 |
| Еда и напитки / Food | 16, 32 |
| Магазины / Shops | 14, 19, 20, 21, 22, 23 |
| Здоровье / Health | 15 |
| Вода / Water | 26 |
| Туалеты и душ / Toilets, showers | 25, 33 |
| АЗС / Fuel | 28 |
| Транспорт / Transport | 29, 30 |
| Банки и банкоматы / Money | 34 |
| Экстренные службы / Emergency | 13 |
| Достопримечательности / Sights | 24 |
| Перевалы / Passes | 31 |
| Населённые пункты / Towns | 11 |

Коды 12, 27, 36 в категории не входят. Ограничение: категория = код отрисовки, поэтому «хостел» от «отеля»,
а «кемпинг» от «укрытия» не отличить, а в «Достопримечательностях» вместе вершины, храмы и памятники.
Тонкое деление даёт только умный поиск (подтипы).

**Алгоритм ядра** (новый модуль `src/core/poi_search.c`, без float, без выделения памяти, опрос порциями,
чтобы не блокировать кнопки):

1. Начало отсчёта: GNSS, если есть фикс; иначе последняя известная позиция; иначе центр вида карты. Источник
   (`GNSS` / `LAST` / `MAP`) показывать в заголовке списка.
2. Обход LOD 0 `pois.idx` по bbox квадрата вокруг начала отсчёта; в листе проверять `Type` по маске.
   Радиус растёт 1 → 2 → 4 → … → 64 км, пока не набрано N результатов или не достигнут предел.
   Пересчёт на каждом шаге читает верхние узлы заново, но их держит LRU-кэш секторов.
3. Расстояние: `dy = Δlat`, `dx = Δlon · cos(lat0)` (таблица `cos` Q15 по градусам, `lat0` — широта начала
   отсчёта), `d² = dx² + dy²` в int64. Единица координаты = 10⁻⁷° ≈ 1,112 см; метры = `sqrt(d²) · 1112 / 10⁸`
   (целочисленный корень только для подписи). Направление: 8 румбов по знакам и отношению `|dx|` и `|dy|`.
   Сначала сверить `geo.c` и `navigation.c`, чтобы не дублировать готовые функции.
4. Топ-N по `d²`: вставка в массив фиксированного размера, без `qsort`. Память: 32 записи × ≈16 Б ≈ 0,5 КБ.
5. Названия читать из `pois.db` только для строк на экране, `_` заменять на пробел; для безымянных
   (имя совпадает с OSM-значением) на этом этапе показывать как есть.

**Проблема в коде.** `map_idx_parse_node()` привязана к отрисовке (`gfx`, `params`, `cam`). Нужно выделить из
неё обход дерева с колбэком на лист (`visit(bbox, type, v2)`), общий для рендера и поиска. Рендер при этом
не должен замедлиться: сравнить время кадра до и после (профиль из P2).

**UI.** Подсостояния `APP_STATE_MENU_POI_CATEGORY` и `APP_STATE_MENU_POI_RESULTS` (как `WPT_SELECT`):
UP / DOWN / SELECT / BACK, 1 bit, вывод списка по правилам полного и частичного обновления, как у остальных
меню. Выбор строки: `map_controller` центрирует карту, автоследование выключается, остаётся перекрестие
центра карты. Длинный SELECT назначает объект целью навигации (WAYPOINT, как MAP CENTER).

  оставить, `_` заменять на пробел; позже компилятор помечает такие записи отдельным флагом (см. умный поиск).

### Умный поиск (категория и/или начало названия, список уточняется)

Требования: ввод слов-категорий на русском и английском («жильё», «hotel», «еда», «магазин»…), ввод первых
букв названия, список по расстоянию, уточнение на каждом символе, выбор → карта центрируется на объекте.
Запрос из двух частей работает как И: «кафе пуш» = категория «кафе» и название на «пуш».

**Почему нужен новый файл.** Название и координата лежат в разных файлах без обратной ссылки, `.db` — 117 Б
на запись, а линейное чтение десятков МБ с SD по SPI (10 МГц) на каждый символ недопустимо. Стоп-слова
переносятся в конец имени («Пушкин кафе»), поэтому «кафе» в начале имени искать нельзя. Нужен индекс,
отсортированный по ключу названия, с позицией в записи.

**Файл `search.idx`** (опционален; нет файла → доступен только простой поиск; описать в спецификации как
необязательное расширение V3 и добавить в `tests/audit_maps.py`). PGO-контейнер, новый `file_type`,
дальше:

- Заголовок: magic `SRCH`, версия, размер записи, число записей в секциях, смещения секций,
  словарь категорий.
- Запись 32 Б: `lon` i32, `lat` i32, `db_idx` (`v2`) u32, `code` u8, `subtype` u8, `flags` u8
  (бит «вторичная запись слова», бит «безымянный»), `key_len` u8, `key[16]` — свёрнутый ключ.
- Секция NAME: все записи, отсортированы по `key`. Для каждого слова названия (разделители `_`, `-`, `(`)
  добавляется своя запись (до 4 слов на имя, `flags` = «вторичная»), поэтому ищется и «пуш», и «кафе».
  Размер секции оценить как N × 32 Б × ≈1,7 по числу узлов `pois.idx` карты из CI.
- Секция CAT: записи отсортированы по (`subtype`, Morton-код координаты), в ней по одной записи на объект.
  Для категорийных запросов читается подряд только участок нужных подтипов.
- Безымянные POI (имя = OSM-значение) попадают в CAT и не попадают в NAME.

**Ключ.** Нормализация: нижний регистр, Ё → Е, `_` → пробел, `..` в конце отбрасывается; кириллица и
латиница в PurrGO-256 (`docs/font-encoding.md`: кириллица 0x80..0xBF, Ё/ё 0xF0/0xF1). Одна и та же
функция в компиляторе (Python) и в прошивке (C): таблица свёртки 256 Б генерируется скриптом из шрифта,
проверка по аналогии с `tests/check_pgo_text_table.py`, общие тестовые векторы. Ключ длиннее 16 байт не
различает хвост: после 16-го символа проверять полное имя из `pois.db` только у кандидатов.

**Подтипы и словарь.** Новый файл `tools/map-compiler/search_categories.csv`:
`Group;Subtype;Keywords_RU;Keywords_EN;OSM_Tags`. `OSM_Tags` — то же выражение, что в `features.csv`
(`tourism=hostel`), по нему компилятор присваивает подтип узлу. Группа = набор подтипов («жильё»: отель,
хостел, кемпинг, гостевой дом, укрытие). Словарь (слово → маска подтипов, синонимы RU / EN) записывается
в заголовок `search.idx`: можно расширять без перепрошивки. Правила `Enabled = 0` в карте отсутствуют и
поэтому не ищутся; чтобы искать без отрисовки, потребуется колонка «только поиск» в `features.csv`.

**Разбор запроса.**

1. Нормализация, разбиение на слова.
2. Слово — категория, если оно совпадает с ключевым словом словаря целиком или как префикс от 3 букв.
   Остальные слова — префиксы названия (первое из них идёт в запрос, остальные проверяются на полное
   имя кандидата).
3. Только категория → секция CAT. Есть слово-префикс названия → бинарный поиск диапазона в NAME
   (нижняя и верхняя границы по 16-байтному ключу), в потоке отфильтровать по маске подтипов, если она есть.
4. Префикс из одного символа: радиус ограничить (например 50 км) или требовать от двух символов, решить по
   замеру скорости SD.

**Отбор и порядок.** Один поток по диапазону, в RAM только массив топ-N (N = 32…64) по `d²`; дубликаты по
`db_idx` схлопываются, при равенстве — по названию. Если для подтипа записей слишком много, добавить
каталог тайлов (по Morton-диапазонам) и читать только ближние. Сначала измерить на реальной карте.

**Инкрементальность.** Если новый запрос продолжает предыдущий, бинарный поиск начинается внутри
предыдущего диапазона `[lo, hi)`. Порционный опрос (≈256 записей за вызов) прерывается на нажатие кнопки:
новый символ отменяет текущий расчёт.

**UI.** Состояние `APP_STATE_SEARCH`: сверху строка запроса с указанием начала отсчёта, ниже 6–8 строк
результатов, внизу компактная клавиатура. Список обновляется частичным обновлением области результатов
после паузы 0,7–1 с после последнего нажатия (частичное обновление E-Ink ≈ 1,3 с); если список не
изменился, обновления нет. Кнопки: длинный K3 переключает фокус между клавиатурой и списком (в списке
K1 / K2 вверх и вниз, K3 выбор), длинный K4 — выход. Последний запрос хранится в RAM.
