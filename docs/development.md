# PurrGO — разработка: сборка, тесты, эмуляторы

Для разработчика. Что делает устройство - [`user-guide.md`](user-guide.md), устройство ПО - [`architecture.md`](architecture.md),
железо - [`hardware.md`](hardware.md), результаты замеров - [`measurements/`](measurements/README.md).

## Сборка

Инициализация сабмодулей:

```sh
git submodule update --init --recursive
```

Проект собирается из **корня репозитория**. Что именно собирать (PC-эмулятор или
прошивку STM32, Debug или Release) выбирается **CMake-пресетом** из
[`CMakePresets.json`](CMakePresets.json), а не выбором папки проекта.

| Пресет | Что собирается | Окружение |
|---|---|---|
| `win-mingw-debug`, `win-mingw-release` | PC-эмулятор (SDL2) | Windows, MSYS2 ucrt64 (`C:/msys64/ucrt64`) |
| `linux-gcc-debug`, `linux-gcc-release` | PC-эмулятор (SDL2) | Linux, GCC, Ninja, `libsdl2-dev` |
| `linux-gcc-test` | Только ядро + host-тесты, ASan/UBSan (без SDL2) | Linux, GCC, Ninja |
| `stm32u5-debug`, `stm32u5-release` | Прошивка STM32U585 | `arm-none-eabi-gcc` в `PATH`, Ninja |
| `web-release` | Эмулятор в браузере (WebAssembly) | Emscripten, см. раздел «Web-эмулятор» ниже |

Пресеты, неподходящие для текущей ОС, в списке не показываются.

### Visual Studio Code

Откройте корень репозитория (или `purrgo.code-workspace`), установите расширение
CMake Tools и выберите пресет в строке состояния. Для STM32 расширение
STM32Cube for VS Code предоставляет `cube-cmake` (см. `.vscode/settings.json`).
Отладка прошивки — конфигурация `Cortex Debug: OpenOCD (PurrGO)`: она берёт `.elf`
активного пресета.

### Командная строка

```sh
cmake --preset stm32u5-debug
cmake --build --preset stm32u5-debug
```

Уровень логирования UART/stderr (`include/purrgo/logger.h`) выбирается кэш-переменной
`PURRGO_LOG_LEVEL`: 0 NONE, 1 ERROR, 2 WARN, 3 INFO, 4 DEBUG. По умолчанию Release собирается
с уровнем 1 (только ошибки, светодиод PC13 не мигает), остальные типы сборки - с 3. Пример:
`cmake --preset stm32u5-release -DPURRGO_LOG_LEVEL=3`.

Другие параметры сборки прошивки:

| Параметр | Назначение |
|---|---|
| `-DPURRGO_HW_TEST=SD_SPEED\|EINK_4GRAY\|EINK_PARTIAL` | Аппаратный тест вместо навигатора, см. [`docs/hardware.md`](docs/hardware.md) |
| `-DPURRGO_TRACK_DIAG=ON` | Диагностическая запись трека (каждая эпоха GNSS), см. раздел [«Полевой тест фильтров трека»](#полевой-тест-фильтров-трека) |
| `-DPURRGO_WERROR=ON` | Предупреждения - ошибки (кроме `-Wconversion`) |

Результат сборки: `out/build/<пресет>/`. Прошивка — `out/build/stm32u5-*/PurrGO_STM32U5.elf`,
эмулятор — `out/build/<пресет>/emulator/purrgo_emulator`.

Платформу выбирает переменная `PURRGO_PLATFORM` (`pc` | `stm32u5`), которую задаёт
пресет. Без пресета `cmake -S . -B build` собирает PC-эмулятор.

### STM32CubeMX

CubeMX-проект находится в `stm32/` (`PurrGO_STM32U5.ioc`, `Core/`, `Drivers/`, ...).
Перегенерация кода обновляет `cmake/stm32cubemx/CMakeLists.txt` и
`cmake/gcc-arm-none-eabi.cmake` в этой папке — они подхватываются автоматически.
`stm32/CMakeLists.txt` (пользовательский, CubeMX его не перезаписывает)
подключается из корневого `CMakeLists.txt` и самостоятельно не конфигурируется.

## Тестирование

Host-тесты проверяют переносимое ядро на ПК, без железа и без SDL2. Код запускается под
AddressSanitizer и UndefinedBehaviorSanitizer; платформенный слой подменяется фейковой ФС
с внедрением сбоев (`tests/host/fake_fs.c`).

```sh
cmake --preset linux-gcc-test
cmake --build --preset linux-gcc-test
ctest --preset linux-gcc-test
```

Без CMake (только `gcc`, из корня репозитория): `sh tests/host/run.sh`.

Тесты сгруппированы по подсистемам. Что именно проверяет каждый, написано в комментарии в начале `tests/host/test_*.c`
(так список не расходится с кодом).

| Подсистема | Тесты |
|---|---|
| GNSS | `test_gnss` (кольцевой буфер, разбор NMEA на записанном логе), `test_gnss_receiver` (UBX-кадры, UBX-CFG-VALSET), `test_gnss_ubx` (UBX-расширения M10: PVT, ODO, hAcc, SEC-SIG, MON-RF/VER, [`docs/gnss-ubx.md`](gnss-ubx.md)), `test_gnss_link` (поиск скорости и её смена), `test_gnss_diag`, `test_gnss_pps` |
| Карта и графика | `test_map` (парсер Map Format V3, фаззинг), `test_map_mlp_stream`, `test_geometry_clip`, `test_gfx_fast_paths` |
| Экран и интерфейс | `test_marker_pan_battery`, `test_ui_refresh_fixes`, `test_display_eink` (очередь E-Ink поверх `epd4g`, нужен сабмодуль), `test_keyboard`, `test_pgo_text` |
| Трек и время | `test_time_logger`, `test_track_filter`, `test_track_diag`, `test_tracker_mode`, `test_negative_altitude` |
| Навигация | `test_navigation`, `test_waypoint`, `test_wpt_layer`, `test_route` |
| Питание | `test_power_off_screen`, `test_power_sequence`, `test_power_source`, `test_supply_low` |
| Читалка | `test_pgb`, `test_book_reader`, `test_book_search`, `test_book_resume_track` |
| Хранилище и ошибки | `test_sd_spi`, `test_refact_critical` |

Python-проверки в CI: `tests/check_pgo_text_table.py` (таблица PurrGO-256 в прошивке и компиляторе совпадает) и
`python3 -m unittest tests/test_book_compiler.py` (конвертер книг). `tests/audit_maps.py` (аудит бинарных файлов карты)
запускается вручную и рекурсивно проверяет все карты в каталоге: `python3 tests/audit_maps.py <каталог с картами>`.

Тесты на железе (SD, дисплей, ток, время кадра) в этот набор не входят.

## CI

`.github/workflows/ci.yml` на каждый push и pull request: host-тесты (ASan/UBSan), сборка
PC-эмулятора, сборка прошивки STM32 (с выводом использования RAM/FLASH), `cppcheck`
(блокирующий) и `clang-tidy` (информативный, набор проверок в `.clang-tidy`).

### Флаги сборки

Код проекта (`src/core`, `src/platform`, `emulator`, пользовательские файлы прошивки)
собирается с `-Wall -Wextra -Wshadow -Wformat=2 -Wconversion -Wdouble-promotion`
(`cmake/PurrgoWarnings.cmake`); сторонний и сгенерированный CubeMX код - без них. Опция
`-DPURRGO_WERROR=ON` превращает предупреждения в ошибки (кроме `-Wconversion`). Для
прошивки `-ffunction-sections -fdata-sections -fstack-usage`, `--gc-sections` и
`--print-memory-usage` задаёт CubeMX-тулчейн; для ПК секции добавляются тем же файлом.

## Аппаратные тесты (замеры на железе)

Замеры из [`TODO.md`](../TODO.md) выполняются отдельной сборкой: после инициализации периферии CubeMX `main()` вызывает
один тест и в главный цикл навигатора не попадает. Тест выбирается параметром CMake:

```
cmake --preset stm32u5-release -DPURRGO_HW_TEST=SD_SPEED
cmake --build --preset stm32u5-release
```

Пустое значение (`-DPURRGO_HW_TEST=`) возвращает обычную прошивку. Допустимо: `SD_SPEED`, `EINK_4GRAY`,
`EINK_PARTIAL` (последние два включают прежние `PURRGO_EINK_SELFTEST_*`). Результаты идут в UART1 строками
`HWTEST ...` независимо от `PURRGO_LOG_LEVEL`, поэтому тесты можно собирать и в Release. Реализация:
`stm32/common/Src/hw_test.c`, список имён: `PURRGO_HW_TEST_NAMES` в `stm32/CMakeLists.txt`.

**`SD_SPEED`.** Карта только читается (ничего не записывается). Замеры по `DWT->CYCCNT`:

- A: сырое последовательное чтение 1 МиБ секторами по 1 / 2 / 8 / 32 за команду (CMD17 или CMD18);
- B: случайное чтение одного сектора, 512 обращений: среднее, минимум, максимум;
- C: FatFs, самый большой файл `0:/PURRGO/MAPS`: последовательное чтение блоками 512 Б / 4 КБ / 16 КБ и
  случайные `f_lseek` + `f_read` 512 Б без CLMT и с CLMT (заодно видно `CLMT ok` / `CLMT off`).

Скорость печатается в МБ/с и в процентах от предела SPI (`f_spi / 8`). Параметры (`-D` через
`CMAKE_C_FLAGS` или `target_compile_definitions`): `PURRGO_HWTEST_SD_SEQ_SECTORS`, `PURRGO_HWTEST_SD_RANDOM_READS`,
`PURRGO_HWTEST_SD_START_SECTOR`, `PURRGO_HWTEST_SD_FILE_BYTES`, `PURRGO_HWTEST_SD_FILE` (путь к файлу).
Частота SPI берётся из `PURRGO_SD_SPI_RUN_PRESCALER` (`sd_card.c`, по умолчанию `/4` = 20 МГц), поэтому сравнение `/8` и `/4`
делается двумя сборками с разным значением. Результат прогонов на плате: [`measurements/SD-speed-test-result.txt`](measurements/SD-speed-test-result.txt).

### Проверка дисплея на железе

1. `PURRGO_EINK_SELFTEST_4GRAY` — 4 полосы серого, шахматка, градиент; картинка без мусора.
2. `PURRGO_EINK_SELFTEST_PARTIAL` — самотест частичного обновления через тот же путь, что у приложения
   (`display_init`, gfx, `display_refresh_region` + `display_flush`). Сцены выбираются маской
   `PURRGO_EINK_TEST_SCENES` (по умолчанию `0x3F`), ход пишется в UART строками `EINKTEST ...`:
   S1 — 1-bit меню, области как в приложении, пауза 0,6 с; S2 — то же, пауза 2,5 с (панель засыпает между
   шагами); S3 — 1-bit меню, частичное обновление всего экрана; S4 — 4 gray меню; S5 — 1-bit карта
   с маркёром и треком; S6 — 4 gray карта с маркёром и треком. В каждой сцене: полное обновление,
   10 шагов частичных, выдержка 3 с, полное обновление того же кадра (эталон), выдержка 3 с.
   Лимит «частичных подряд до полного» на время теста отключён. Сравнивать кадр до и после эталона:
   любое отличие — артефакт частичных обновлений. На хосте тот же самотест прогоняется на модели
   1-bit контроллера (`eink_selftest_host`, `eink_selftest_host_swap`) и сверяет «стекло» с framebuffer.
3. Сцены S7 (1 bit) и S8 (4 gray), маска `-DPURRGO_EINK_TEST_SCENES=0xC0U`: 40 частичных подряд в худшем
   случае (одни и те же пиксели меняются на каждом шаге); после 10, 20, 30 и 40 шагов кадр держится 4 с
   (строка `checkpoint N partials`), в конце эталонное полное обновление.
4. Приложение: запуск → карта; открытие меню (вход в 1-bit: одно полное мигание); перемещение курсора
   по главному меню MENU (частичное без мигания); возврат на карту; движение маркера
   (частичное 4 gray); выключение из карты и из меню (экран выключения в 4 gray).
5. Ток в простое после засыпания панели — пока не измерялся.

Результаты прогонов: [`measurements/eink-selftest.md`](measurements/eink-selftest.md).

Лимиты `PURRGO_EINK_MONO_PARTIALS_BEFORE_FULL` и `PURRGO_EINK_GRAY_PARTIALS_BEFORE_FULL` по умолчанию равны
значениям библиотеки (`EPD4G_*PARTIALS_BEFORE_FULL` = 10): библиотека сама выполняет полное обновление
вместо одиннадцатого частичного. Питание панели она тоже снимает сама через
`EPD4G_AUTO_POWEROFF_MS` = 500 мс простоя. Чем больше лимит, тем
реже мигание всего экрана; поднимать можно не выше проверенного.

Параметры в `display_eink.c` (переопределяются `-D`): `PURRGO_EINK_SPI_PRESCALER`,
`PURRGO_EINK_GRAY_PARTIALS_BEFORE_FULL`, `PURRGO_EINK_MONO_PARTIALS_BEFORE_FULL`,
`PURRGO_EINK_GRAY_FULL_MODE` (`EPD4G_FULL_FAST` ~3 с / `EPD4G_FULL_DEEP` ~5 с),
`PURRGO_EINK_MONO_FULL_MODE`, `PURRGO_EINK_SLEEP_AFTER_MS`.

## Эмулятор на ПК: GNSS и время

Эмулятор (`emulator`) получает GNSS одним из двух способов:

- по умолчанию (`USE_MOCK_GNSS=ON`) - встроенный генератор NMEA;
- с реального приёмника через последовательный порт: сконфигурируйте с `-DUSE_MOCK_GNSS=OFF`
  и запустите `purrgo_emulator COM3` (`COM3` замените на порт приёмника, скорость 9600).

Так GNSS pipeline проверяется на реальном приёмнике до проверки на STM32.

Mock ведёт точку не по прямой, а по ломаной траектории, похожей на путь пешехода: курс держится
на отрезке 15-45 с, затем меняется (изгиб 5-45° или изредка угол 70-110°, поворот растянут на
несколько секунд), скорость гуляет около 5 км/ч, к позиции добавлен шум около 0.7 м. Позиция
считается из курса и скорости, одометр растёт на реально пройденный путь. Генератор
псевдослучайных чисел детерминированный: путь повторяется от запуска к запуску.

Единственный источник времени ядра - `purrgo_system_time_ms()` (на ПК это монотонные
миллисекунды, `src/platform/pc/system_time.c`); эмулятор передаёт в `purrgo_app_tick()`
именно его. Смешивать его с другими часами (например `SDL_GetTicks()`) нельзя: ядро
сравнивает отметки времени, и фикс GNSS ложно сбрасывается по таймауту.

Стартовую точку mock-приёмника можно задать при конфигурации. Например, берег Мёртвого
моря (отрицательная высота):

```sh
cmake --preset linux-gcc-debug -DPURRGO_MOCK_LAT_1E7=315590000 \
      -DPURRGO_MOCK_LON_1E7=354731666 -DPURRGO_MOCK_ALT_M=-430
```

## Web-эмулятор (WebAssembly + GitHub Pages)

PC-эмулятор (`emulator`) собирается в WebAssembly через Emscripten и запускается в браузере,
в том числе на смартфоне. Ядро (`src/core`) и платформенный слой (`src/platform/pc`) те же, что
в десктопной сборке; отличается только обвязка:

| Что | Десктоп | Браузер |
|-----|---------|---------|
| Окно, рендер | SDL2 (системный) | SDL2 из портов Emscripten, `<canvas>` |
| Основной цикл | `while` + `SDL_Delay` | `emscripten_set_main_loop` (requestAnimationFrame) |
| Кнопки K1-K4 | нарисованы в окне SDL, клавиши 1-4 | HTML-кнопки страницы (`web/shell.html`), клавиши 1-4, 5 = K1+K4 |
| Файлы | диск, пути `../../../../tests/data/...` | MEMFS: `/maps`, `/books`, `/routes`, `/waypts`, `/tracks`, `/PURRGO.CFG` |
| GNSS | mock или COM-порт | только mock (старт задаётся при сборке) |

Настройки (`PURRGO.CFG`) и треки живут в памяти вкладки и теряются при перезагрузке страницы.

### Публикация на GitHub Pages

1. Один раз: **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. Workflow `.github/workflows/pages.yml` запускается при push в `main` (если менялись эмулятор,
   ядро, компилятор карт и т. п.) или вручную: **Actions → Web emulator → Run workflow**.
3. Сайт появится по адресу `https://<владелец>.github.io/<репозиторий>/`.

Что делает workflow:

1. Скачивает PBF (Geofabrik), вырезает область `bbox` (`osmium extract`), прогоняет
   `purrgo_osm_optimizer.py` и `purrgo_map_compiler.py`. Результат кэшируется
   (ключ: PBF URL + bbox + код компилятора), поэтому PBF скачивается не при каждой сборке.
2. Кладёт карту в `web-root/maps`, примеры книг (`tests/host/data/sample*.pgb`) в `web-root/books`.
3. Собирает эмулятор пресетом `web-release` с `-DPURRGO_WEB_PRELOAD_DIR=web-root`:
   содержимое `web-root` упаковывается в `index.data` и монтируется в корень виртуальной ФС.
4. Публикует `index.html`, `index.js`, `index.wasm`, `index.data`.

Параметры ручного запуска: `pbf_url`, `bbox` (`lon_min,lat_min,lon_max,lat_max`) и стартовая точка
имитации GNSS (`mock_lat`, `mock_lon`; она должна лежать внутри bbox). Размер образа `index.data`
растёт вместе с областью карты и скачивается браузером целиком при открытии страницы, поэтому
bbox лучше держать в пределах города.

### Локальная сборка

Нужен [emsdk](https://emscripten.org/docs/getting_started/downloads.html) (проверено на 4.0.9)
и переменная окружения `EMSDK`:

```sh
# каталог с содержимым виртуальной ФС: maps/ (файлы карты прямо в maps/), books/ ...
cmake --preset web-release -DPURRGO_WEB_PRELOAD_DIR=/путь/к/web-root \
      -DPURRGO_MOCK_LAT_1E7=539006000 -DPURRGO_MOCK_LON_1E7=275590000
cmake --build out/build/web-release
cd out/build/web-release/emulator && python3 -m http.server 8000
# открыть http://localhost:8000/index.html
```

`file://` не подходит: браузер не даёт загрузить `.wasm` и `.data` с локального диска.
Без `PURRGO_WEB_PRELOAD_DIR` эмулятор запустится, но карты не найдёт.

### Ограничения

- Только имитация GNSS: реальная геопозиция браузера не подключена.
- Своя карта сейчас подключается только пересборкой (через `bbox` в workflow).
- Эмуляция E-Ink упрощённая: частота обновления и серые уровни как в десктопном эмуляторе,
  но без физики ghosting-а.

## Полевой тест фильтров трека

Цель: на реальных данных проверить пороги `track_logger.c` — качество фикса (`fix_type` ≥ 3,
HDOP ≤ 5, ≥ 4 спутников), стоянка (< 0,5 уз), выброс (> 500 м/с) и прореживание
(`FILTER_STANDARD` / `FILTER_EXPEDITION`: шаг, отклонение, хорда, таймаут).

Записанные до сих пор треки (`tools/battery-calibrate/`) уже прошли фильтры, поэтому отброшенные
точки в них не видны. Для теста нужна диагностическая сборка: она пишет **каждую** эпоху GNSS и
помечает, какие фильтры обычная сборка применила бы.

### Что пишется в точку

```xml
<trkpt lat="53.6999993" lon="28.4000336">
  <ele>100</ele>
  <time>2026-11-12T08:30:01Z</time>
  <fix>3d</fix>                  <!-- none / 2d / 3d / dgps: PVT (UBX) или GSA (NMEA) -->
  <sat>9</sat>                   <!-- спутников в решении: PVT numSV или GGA -->
  <hdop>0.90</hdop>              <!-- только NMEA (GSA/GGA): в PVT HDOP нет, остаётся включённым -->
  <extensions>
    <gpxtpx:TrackPointExtension>   <!-- Garmin TrackPointExtension v2 -->
      <gpxtpx:speed>0.08</gpxtpx:speed>    <!-- скорость над землёй, м/с -->
      <gpxtpx:course>84.40</gpxtpx:course> <!-- курс, градусы; только при надёжном курсе -->
    </gpxtpx:TrackPointExtension>
    <pg:hacc>3.52</pg:hacc>      <!-- hAcc, м; только с UBX-NAV-PVT (PURRGO_GNSS_UBX=1) -->
    <pg:bat>100</pg:bat><pg:vbat>4793</pg:vbat>
    <pg:sacc>0.120</pg:sacc>     <!-- sAcc, м/с; только диагностическая сборка и только с PVT -->
    <pg:rej>6</pg:rej>           <!-- только диагностическая сборка, маска ниже -->
  </extensions>
</trkpt>
```

`<fix>`, `<sat>`, `<hdop>`, `gpxtpx:speed` пишутся и в обычной сборке (тег пропускается, если приёмник
значение не прислал). `pg:sacc` и `pg:rej` — только в диагностической; `pg:rej` — сумма битов:

| бит | значение | причина |
|---|---|---|
| 1 | `fix_type` < 3 | нет 3D-фикса |
| 2 | HDOP > 5,0 | только когда hAcc неизвестна (нет PVT): при PVT HDOP не ограничивает, бит не ставится |
| 4 | спутников < 4 | |
| 8 | стоянка | скорость < 0,5 уз |
| 16 | выброс | скачок быстрее 500 м/с от опорной точки |
| 32 | прореживание | трек не изменился заметно |
| 64 | hAcc > порога | оценка точности UBX выше `PURRGO_GNSS_TRACK_MAX_HACC_M` (20 м); при известной hAcc бит 2 (HDOP) не ставится |

`pg:rej="0"` — обычная сборка записала бы эту точку. Примеры: `6` = HDOP > 5 и мало спутников;
`32` = точка на прямой, пропущена прореживанием.

При UBX позиция, скорость, `fix_type`, число спутников и hAcc/sAcc берутся из одного кадра PVT и
согласованы между собой. HDOP приходит из NMEA (GGA/GSA) отдельно и может отставать от них на
эпоху; для сверки порогов это несущественно. Если PVT перестал приходить (NMEA-резерв после
`PURRGO_GNSS_PVT_HOLD_EPOCHS` эпох), hAcc/sAcc в точках пропадают, а фильтр качества снова
работает по HDOP.

### Подготовка

1. Собрать прошивку с `PURRGO_TRACK_DIAG`:
   `cmake --preset stm32u5-release -DPURRGO_TRACK_DIAG=ON` (после смены опции пересоздайте каталог
   сборки или очистите кэш). Если собираете не через CMake — в начале `src/core/track_logger.c`
   замените значение по умолчанию на `#define PURRGO_TRACK_DIAG 1` (после теста верните 0).
2. microSD с запасом: диагностическая запись ≈ 0,9 МБ в час. Батарея заряжена; напряжение и заряд
   тоже пишутся в точки, это заодно полезные данные.
3. Время в `<time>` — UTC (из GNSS). Записывайте время начала и конца сценариев в UTC (или с
   поправкой на пояс): по ним вы потом вырежете сценарии из файла.
4. Режим логгера выбирается в меню (LOG). Для сценариев A–E ставьте **STANDARD**. Смена режима
   «на лету» продолжает тот же файл, а `pg:rej` считается по режиму, действовавшему в момент точки;
   поэтому сценарий F лучше писать отдельным файлом (например, выключить запись через OFF и снова
   включить нужный режим, либо перезапустить устройство). Режим TRACKER (SCREEN OFF) пишет как
   EXPEDITION.

### Сценарии

Для каждого пишите в блокноте время начала и конца (с точностью до минуты) и что делали.

| | сценарий | длительность | что проверяет |
|---|---|---|---|
| A | **Стоим на открытом месте.** Устройство лежит неподвижно на ровной поверхности под открытым небом (крыша машины, парапет). Не трогать. | 30–60 мин | дрейф позиции и скорости на стоянке: порог 0,5 уз, шаг 5 м, таймаутные точки |
| B | **Стоим при плохом приёме.** Подоконник внутри здания, двор-колодец или под густыми кронами. | 20–30 мин | hAcc ≤ 20 м (при UBX; без PVT — HDOP ≤ 5), ≥ 4 спутников, `fix_type`; скачки позиции при плохом приёме, выбросы |
| C | **Ходьба по маршруту** ~2–3 км в обычном темпе, так как носите устройство: прямые, повороты 90°, один «шпиль» 180°, **прогулка к точке и обратно по той же тропе**, 2–3 остановки по 1–2 мин. | 30–45 мин | прореживание на пешем ходу: шаг, допуск 5 м, поворот/разворот, остановки |
| D | **Ходьба при плохом приёме** (лес, городские улицы между высокими домами) — желательно тот же маршрут C. | 30 мин | шум координат на ходу против допуска 5 м |
| E | **Холодный старт и потеря сигнала.** Включить после нескольких часов выключенного состояния на открытом месте, не ждать фикса — сразу идти; затем зайти в подъезд/подземный переход/тоннель на 1–3 мин и выйти. | 15 мин | первый фикс (ошибочная опорная точка), восстановление приёма, скачки после потери сигнала, порог 500 м/с |
| F | (по желанию) **Повтор C в EXPEDITION** по тому же маршруту, отдельным файлом. | 30–45 мин | допуск 10 м, хорда 1 км, таймаут 15 мин |
| G | **Велосипед** (основной режим применения; модель динамики — Portable): 20–30 мин по ровной дороге и по грунтовке со сменой скорости 3–10 м/с, 90°-повороты, остановка на перекрёстке. Отдельно — медленная езда/ведение велосипеда рядом. | 30 мин | прореживание на 5–10 м/с (на такой скорости точка раз в ~1 с уже заметный шаг; хорда 250 м = 25–50 с), срез углов, порог стоянки при остановках, поведение Portable на медленном ходу |

Если выберете одно — C (или G, если трек почти всегда будет велосипедным) и A дают больше всего.
Сценарии с транспортом уже есть (LIION/ZINK), повторять их не нужно. Если собираетесь сравнить
модель динамики (Portable и Pedestrian, `-DPURRGO_GNSS_DYNMODEL=PURRGO_GNSS_DYN_PEDESTRIAN`),
записывайте C отдельными файлами с каждой моделью: сглаживание приёмника меняет шум координат, на
который настроены допуски прореживания.

### Разбор

С карты забрать `TRACKS/*.gpx` и запустить

```
python3 tools/track-analyze/analyze_diag.py TRACKS/XXXXXXXX.gpx --from 2026-11-12T08:30 --to 2026-11-12T09:00
```

(`--from/--to` — UTC, вырезают один сценарий; можно передать несколько файлов). Отчёт:

1. сколько точек отбросил бы каждый фильтр;
2. распределения `fix`, спутников, HDOP, hAcc, sAcc и доля эпох за порогами;
3. шаг позиции за 1 с по группам HDOP и (3a, только UBX) по группам hAcc;
4. шаг позиции за 1 с по скорости приёмника;
5. самые быстрые скачки между эпохами;
6. итог прореживания: записанных точек, интервал, отклонение ломаной от **всех** эпох.

Как читать:

- **hAcc (UBX) и HDOP / спутники.** Порог (`PURRGO_GNSS_TRACK_MAX_HACC_M`, 20 м) разумен, если в
  сценариях A, C, G доля эпох выше него мала, а в B — заметна и именно за ним шаг позиции (п. 3а)
  выходит за допуск прореживания. Если p95 шага заметно больше уже при hAcc 5–10 м — порог слишком
  мягкий. Для HDOP (только без PVT) логика та же по п. 3. Если в точках без hAcc прореживание пишет
  заметно больше точек на прямой, чем с hAcc — допуск прореживания имеет смысл связать с hAcc. При 3D-фиксе приёмнику нужно ≥ 4 спутников, так что `спутников < 4` почти
  дублирует `fix_type`; если в данных он ничего не добавляет, фильтр можно убрать.
- **Стоянка.** Порог верен, если в сценарии A скорость приёмника держится ниже него, а в C при
  обычном шаге — выше. В п. 4 шаг на «стоячих» скоростях должен быть шумом (сравним с шагом в A), а
  на скоростях выше порога — расти. Сравните скорость на стоянке с sAcc (п. 2): если sAcc сравним с
  порогом (0,26 м/с), скорость ниже порога ничего не гарантирует. Если в A скорость иногда выше 0,5 уз — порог поднять; если на
  медленном ходу (C, остановки и разворот у вьюпойнта) настоящее движение попадает ниже порога —
  опустить.
- **Выброс.** В сценариях A–D бит 16 должен быть нулевым; в E смотрите, какие скачки после потери
  сигнала и первого фикса отбросил фильтр и записалась ли после них опорная точка.
- **Прореживание.** В п. 6 для C/D: отклонение p99 порядка допуска (5 м) — норма; сильно больше — допуск
  или предельная хорда велики; записанных точек слишком много (доля эпох > 15–20 %) — шум GNSS при
  ходьбе заставляет писать точки на прямой, допуск надо поднять. Если разворот «туда и обратно» в C
  потерян (на пике нет точки) — это ошибка, пришлите файл.

Файлы (или вывод скрипта по сценариям) можно прислать, и я предложу правки порогов.
