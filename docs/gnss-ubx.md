# UBX-расширения GNSS (u-blox M10, SPG 5.10 / 5.30)

Переключатель сборки: `PURRGO_GNSS_UBX` в `include/purrgo/hardware_config.h`
(`-DPURRGO_GNSS_UBX=0` - только NMEA, `1` - с UBX; по умолчанию 1 для приёмника UBX).
Модуль G10A-F30 - u-blox M10 (UBX-M10050-KB, L1). Установленный экземпляр сообщает
`ROM SPG 5.10`, протокол 34.10 (документ в `docs/datasheets/GNSS_modules/U-blox M10`);
более новые прошивки - SPG 5.30, протокол 34.30. Ключи ниже есть в обеих, кроме SEC-SIG.
Документ SPG 7.0x (протокол 52, L1+L5) для этого модуля не подходит.

## Что включено при `PURRGO_GNSS_UBX=1`

| Сообщение | Ключ `CFG-MSGOUT-*_UART1` | Зачем |
|---|---|---|
| UBX-NAV-PVT | `0x20910007` | время, позиция, скорость, курс, hAcc/vAcc/sAcc; главнее RMC/GGA/GSA |
| UBX-NAV-ODO | `0x2091007F` | дистанция трека (нужен `CFG-ODO-USE_ODO`, по умолчанию выключен) |
| UBX-SEC-SIG | `0x20910635` | глушение и спуфинг; только SPG 5.30+, в 5.10 нет (NAK), по умолчанию выключено (`PURRGO_GNSS_SEC_SIG`) |
| UBX-MON-RF | `0x2091035A` | CW-помеха (`cwSuppression`), AGC, `jammingState` (флаги), шум; антенна у G10A-F30 всегда `DONTKNOW` |
| UBX-NAV-DOP | `0x20910039` | HDOP/VDOP/PDOP (без NMEA их больше неоткуда взять) |
| UBX-NAV-STATUS | `0x2091001B` | `spoofDetState` (флаги 2, биты 4..3) - спуфинг вместо SEC-SIG (`PURRGO_GNSS_NAV_STATUS`) |
| UBX-NAV-SAT | `0x20910016` | C/N0 спутников решения (`svUsed`): средний и максимум (`PURRGO_GNSS_NAV_SAT`) |
| CFG-ITFM-ENABLE | `0x1041000D` | не сообщение, а ключ: включает монитор помех, без него `jammingState` всегда 0 (`PURRGO_GNSS_ITFM`) |
| CFG-TP-LEN_TP1, CFG-TP-LEN_LOCK_TP1 | `0x40050004`, `0x40050005` | длина импульса 0: таймпульс (1PPS) включён, но без импульсов, светодиод PPS не мигает (`PURRGO_GNSS_TIMEPULSE`) |
| UBX-MON-VER | опрос | версия прошивки в лог (только при `PURRGO_GNSS_POLL_VERSION` = 1) |

## SIG и RF без SEC-SIG (SPG 5.10)

В SPG 5.10 сообщения `UBX-SEC-SIG` нет (там только `SEC-UNIQID`), а предупреждение в описании `MON-RF` о
том, что `jammingState` устарел и всегда 0, относится к версиям с SEC-SIG (5.30+). Поэтому:

- **JAM** - `UBX-MON-RF`, флаги, биты 1..0: 0 неизвестно (монитор выключен, ещё не готов или антенна
  отключена), 1 нет помех, 2 предупреждение (помеха видна, фикс есть), 3 критично (помеха и нет фикса).
  Монитор (ITFM) по умолчанию выключен, включается `CFG-ITFM-ENABLE` = 1 (кадр `ITFM`). Опорный спектр
  он снимает после первого хорошего фикса, до этого состояние 0 (`JAM --`). Пороги оставлены по
  умолчанию (`CFG-ITFM-BBTHRESHOLD` 3 дБ, `CFG-ITFM-CWTHRESHOLD` 15 дБ), `CFG-ITFM-ANTSETTING` - 0
  (неизвестно: у G10A-F30 встроенная антенна, есть ли в ней МШУ, неизвестно).
- **SPF** - `UBX-NAV-STATUS`, `flags2`, биты 4..3: 0 неизвестно, 1 нет признаков, 2 признаки, 3 несколько
  признаков. Детектор в модуле включён всегда, но обнаруживает смену настоящих сигналов на поддельные;
  состояние 1 не означает, что спуфинга нет. Заполняет ли поле именно ROM 5.10 на G10A-F30, по
  документам не подтверждено - проверить по логу (`spoof=0` постоянно - не заполняет).
- Если приходит `UBX-SEC-SIG` (SPG 5.30+, `PURRGO_GNSS_SEC_SIG=1`), строка SIG берётся из него.
- **Антенна.** Супервайзеру антенны нужны внешняя схема и свободные PIO (`ANT_DETECT`, `ANT_SHORT_N`,
  `ANT_OFF_N`, MAX-M10S Integration manual, разд. 3.3.1); у G10A-F30 выводов шесть и антенна встроена,
  поэтому `antStatus` всегда `DONTKNOW`. Состояние антенны, CW/AGC и C/N0 на экране не выводятся (строку RF
  из Trip computer убрали как малоинформативную); `UBX-MON-RF` по-прежнему нужен для JAM.

Нагрузка: NAV-STATUS 24 байта и (если включить `PURRGO_GNSS_NAV_SAT`) NAV-SAT `16 + 12 * N` байт в секунду
(N - все известные спутники; при 20 около 260 байт) - примерно 3 % канала 115200 бод; буфер разборщика `PURRGO_UBX_MAX_PAYLOAD` = 800 байт
(до 64 спутников, +416 байт RAM). Сравнить ток с флагами `PURRGO_GNSS_ITFM`, `PURRGO_GNSS_NAV_STATUS`,
`PURRGO_GNSS_NAV_SAT` = 0 и 1 (см. TODO, P1).

## NMEA на UART приёмника

По умолчанию (`PURRGO_GNSS_UBX_NMEA=0`) NMEA выключен полностью: меньше нагрузка на UART (около
300-500 байт/с) и нет текста между бинарными кадрами. Порядок:

1. Включение: модуль на заводской настройке (NMEA, 38400). `gnss_link` ищет скорость UART **по NMEA**
   (или по кадру UBX, см. ниже), при необходимости меняет скорость модуля.
2. Связь установлена: уходит настройка. Базовый кадр, как и раньше, включает GGA/RMC/GSA (1 Гц) и
   выключает остальное; затем PVT, ODO, MON-RF, NAV-DOP, (NAV-STATUS, NAV-SAT, ITFM), одометр, модель динамики.
3. Отдельным VALSET `CFG-UART1OUTPROT-NMEA` (`0x10740002`) = 0 - после остальной настройки и до PSM
   (кадры PSM по-прежнему самые последние). Ответ ACK/NAK приходит в UBX и при выключенном NMEA.

Если модуль ответил NAK на этот кадр (`GNSS: config "NMEA off" rejected by module`), остаётся
сокращённый NMEA (GGA/RMC/GSA): он разбирается как запасной путь, как и NMEA до настройки.

### Энергосбережение приёмника (PSM)

Настройка идёт отдельными UBX-CFG-VALSET в конце серии, чтобы NAK называл точный шаг. Сводка (ключи -
Interface Description SPG 5.10, группа `CFG-PM`; поведение - Integration Manual MAX-M10S, раздел 3.6):

| Профиль | Режим | Кадры (имена групп в логе) | Слои |
|---|---|---|---|
| Навигация (карта, путевой компьютер) | PSMCT (`PURRGO_GNSS_PSM` = 2) | `Signals` (SBAS и BeiDou выключены), `PSM no-off` (DONOTENTEROFF = 1), `PSM mode` (OPERATEMODE = 2) | RAM (в BBR приёмник PSMCT отклонил) |
| Трекер с отключённым дисплеем | цикл по EN (`PURRGO_GNSS_TRACKER_MODE` = 3, по умолчанию): приёмник включается раз в `PURRGO_GNSS_TRACKER_PERIOD_S` = 15 с на время поиска фикса, полная мощность (профиль `TRACKER_EN`); при слабом небе остаётся включённым в PSMCT (профиль `TRACKER_CT`, период `PURRGO_GNSS_TRACKER_CT_PERIOD_S` = 10 с) | навигационный набор без `NAV-SAT`, без кадра скорости UART (38400 бод), `OPERATEMODE` = 0 (FULL) в `TRACKER_EN` и PSMCT в `TRACKER_CT` | RAM и BBR (кроме `OPERATEMODE`: только RAM); после EN = High повторно не отправляется |
| Трекер, режимы-альтернативы | PSMCT с периодом 10 с (`PURRGO_GNSS_TRACKER_MODE` = 1); PSMOO с периодом 15 с (= 2, эксперимент) | PSMCT: серия навигации с `CFG-RATE-MEAS` = 10000 мс; PSMOO: см. ниже | PSMCT: RAM; PSMOO: RAM и BBR |

**Почему в PSM выключаются BeiDou и SBAS.** BeiDou B1C (заводской набор G10A-F30) в PSM не поддерживается, B1I
несовместим с GLONASS L1OF, SBAS в PSM не принимается. Первый запуск с заводским набором: кадр PSM отклонён (NAK,
`PSM state 0`).

**Набор систем (`PURRGO_GNSS_SIGNALS`).** В PSM работают GPS, Galileo, QZSS и либо GLONASS, либо BeiDou B1I (вместе
они несовместимы). Режим 0 оставляет GLONASS (`SBAS_ENA` = 0, `BDS_ENA` = 0), режим 2 заменяет его на B1I: кадр
`Signals` выключает `GLO_ENA` (`0x10310025`) и `BDS_B1C_ENA` (`0x1031000F`), затем включает `BDS_B1_ENA` (`0x1031000D`)
и `BDS_ENA` (`0x10310022`); при PSM в него добавляется `SBAS_ENA` = 0. Ограничения взяты из Integration Manual MAX-M10S
(UBX-20053088, раздел 3.6.2: B1C и SBAS в PSM) и сноски 1 даташита G10A-F30 (B1I и B1C/GLONASS L1OF). Даташит MAX-M10S,
табл. 15: ток слежения в PSM у GPS+GAL+GLO и GPS+GAL+BDS B1I одинаков (5 мА), холодный старт 23 с с GLONASS и 27 с с B1I.
На G10A-F30 режим 2 не проверялся: при NAK кадра `Signals` приёмник остаётся на заводском наборе.

**Трекер: цикл по EN (`PURRGO_GNSS_TRACKER_MODE` = 3, по умолчанию).** Прошивка сама включает приёмник (EN = High) раз
в период, ждёт фикс, записывает точку и выключает (EN = Low). Решение принято по тестам `GNSS_BBR`
([`gnss-retention.md`](gnss-retention.md)): EN = Low стирает RAM приёмника, но BBR, эфемериды и время остаются, поэтому
старт горячий; на хорошем небе `rx-ttff` около 1 с, включённое время на точку около 3-4 с (загрузка 0,3 с + время до
`fixOK`) против постоянных ~7 мА в PSMCT. Сам автомат (когда включать, как долго ждать, как удлинять паузы) - чистая логика
без привязки к железу: `purrgo/gnss_duty.h`, `src/core/gnss/gnss_duty.c`, тест `tests/host/test_gnss_duty.c`.

- **Включение.** `purrgo_gnss_restart_profile(PURRGO_GNSS_PROFILE_TRACKER_EN)`: связь ищется и остаётся на заводской скорости
  38400 (скорость UART не переключается: при коротком включении это не окупается и добавляет отказы). Набор сообщений
  как в навигации, но без `NAV-SAT`; `OPERATEMODE` = FULL.
- **Настройка шлётся один раз, а не после каждого включения** (`PURRGO_GNSS_TRACKER_EN_BBR` = 1). Она пишется в слои RAM и
  BBR (набор систем, сообщения, NMEA выключен, модель движения и т. д.; только `OPERATEMODE` - в RAM: PSMCT в BBR приёмник
  отклоняет, а после EN = Low RAM пуста, то есть полная мощность). EN = Low стирает RAM, но BBR остаётся
  ([`gnss-retention.md`](gnss-retention.md), 4.2), поэтому модуль включается уже настроенным. Решает первый кадр после включения
  (`gnss_io.c`, `link_on_state`), без таймеров: модуль может молчать секунды, а МК спать в Stop 2, и таймер по NAV-PVT давал
  ложное «BBR потерян» (лог `BBR_and_RAM.log`: настройка уходила дважды). (1) Первое включение после перезапуска МК отправляет
  настройку всегда (BBR мог остаться от другой версии прошивки) и не выключает модуль ещё `PURRGO_GNSS_EN_CFG_SETTLE_MS` (200 мс)
  после передачи. (2) Дальше связь найдена по кадру UBX без единого предложения NMEA - NMEA в BBR выключен, значит, настройка
  на месте: `GNSS: after EN only UBX (...): settings kept in BBR, config not sent`. (3) Связь найдена по предложению NMEA - BBR
  пуст (потеря резервного питания, раздел 4.1 `gnss-retention.md`): `GNSS: after EN NMEA (...): BBR settings lost, sending
  config`, настройка отправляется сразу. Повтор через `PURRGO_GNSS_CONFIG_RETRY_MS` пропускается и если ответов ACK ещё нет, но
  `NAV-PVT` уже идёт. `PURRGO_GNSS_TRACKER_EN_BBR` = 0 возвращает прежнее поведение: настройка только в RAM после каждого
  включения.
- **Фикс принят**, когда пришло новое решение (растёт `fix_seq`: устаревшее решение прошлого цикла не считается) с
  `gnssFixOK` и типом не хуже `PURRGO_GNSS_DUTY_MIN_FIX_TYPE` (3 - 3D; тип 0, «не передан», допускается), и точность `hAcc` не хуже
  `PURRGO_GNSS_DUTY_ACCEPT_HACC_M` (30 м). Если точность хуже, ждём лучшей не дольше `PURRGO_GNSS_DUTY_HOLD_MS` (3 с), потом
  принимаем любой фикс. Принял - сразу EN = Low. Логгер получает те же решения, что и раньше.
- **Период** `PURRGO_GNSS_TRACKER_PERIOD_S` (15 с) считается между началами включений: пауза = период минус время работы, не
  меньше `PURRGO_GNSS_DUTY_MIN_PAUSE_S` (1 с).
- **Таймаут** `PURRGO_GNSS_DUTY_FIX_TIMEOUT_S` (25 с) при горячем старте. **Он не растёт при промахах**: в горячем состоянии
  долгое ожидание значит плохое небо и только тратит ток. Исключение - холодный старт: первое включение без известного фикса, фикс
  старше `PURRGO_GNSS_DUTY_COLD_AGE_S` (2 ч, эфемериды устарели) или приёмник сообщил, что не знает времени (RTC сброшен, BBR пуст):
  один раз разрешается `PURRGO_GNSS_DUTY_COLD_TIMEOUT_S` (90 с, измеренный холодный старт 65-82 с).
- **Промахи.** Таймаут без фикса: EN = Low, пауза после первого промаха равна периоду, после каждого следующего подряд
  удваивается (30, 60, 120, 240 с) до `PURRGO_GNSS_DUTY_BACKOFF_MAX_S` (300 с); принятый фикс возвращает период. Так в
  помещении приёмник включается всё реже (рабочий цикл 25 с из 325 с).
- **Слабое небо: приёмник не выключается.** Поиск при слабом небе занимает 9-14 с (4-5 спутников) и стоит ~13 мА, а непрерывный
  PSMCT - ~7 мА: граница около 8 с на период 15 с. Если `PURRGO_GNSS_DUTY_SLOW_COUNT` (3) фикса подряд пришли дольше
  `PURRGO_GNSS_DUTY_SLOW_FIX_S` (8 с), автомат переходит в непрерывный режим: профиль `TRACKER_CT` (PSMCT, решения раз в
  `PURRGO_GNSS_TRACKER_CT_PERIOD_S` = 10 с, EN остаётся High). Выход: нет фикса `PURRGO_GNSS_DUTY_CONT_LOSS_S` (60 с) - как
  промах, с паузой; либо через `PURRGO_GNSS_DUTY_CONT_RETRY_S` (10 мин) снова пробуется цикл по EN. `PURRGO_GNSS_DUTY_SLOW_COUNT` = 0
  выключает этот режим.
- **Сон МК.** Главный цикл спит в Stop 2 не дольше срока автомата (`purrgo_gnss_tracker_wait_ms`: следующее включение, таймаут
  фикса, конец ожидания точности), а не по общему пределу `PURRGO_STOP2_MAX_MS`, чтобы 15 с выдерживались точно.
- **Срок действия фикса** в ядре (`gnss_fix_timeout_ms`) в этом режиме = последняя пауза + таймаут + 10 с
  (`purrgo_gnss_tracker_fix_timeout_ms`): растёт вместе с паузами и в непрерывном режиме равен `CONT_LOSS_S` + 10 с.
- **Вход и выход.** Вход: приёмник перезапускается по EN с профилем `TRACKER_EN` (EN = Low на 200 мс), первый старт считается
  горячим, если при входе был действующий фикс. Выход (K1+K4): автомат останавливается, приёмник снова перезапускается по EN, но
  уже с профилем навигации (115200 бод, PSMCT, полный набор сообщений). Слой BBR хранит настройку трекера (те же ключи,
  что у навигации, кроме `NAV-SAT`, и без `OPERATEMODE`/скорости UART): навигация перекрывает её своей настройкой в RAM, а
  связь после EN = High находится по кадрам UBX (NMEA в BBR выключен). Вход и выход пишутся в лог: `Tracker mode: entered ...`
  и `Tracker mode: left`.
- **Линии UART при EN = Low** остаются в Hi-Z (`PURRGO_GNSS_OFF_TX_HIZ` = 1), см. [`hardware.md`](hardware.md).

Если модуль остался в BBR с настройкой от прошлых прошивок (например, PSMOO с `OPERATEMODE` = 1 из слоя BBR), после EN = Low он
вернёт её при старте: такой BBR нужно очистить (профиль навигации `NAV_AFTER_TRACKER` в режиме PSMOO делает это сам; иначе -
фаза `FLASH`/очистка теста `GNSS_BBR`, `cleanup_receiver()`).

**PSMCT и PSMOO в трекере (режимы 1 и 2).** Режим ON/OFF (PSMOO, `PURRGO_GNSS_TRACKER_MODE` = 2) в рабочей прошивке был
нестабилен. Логи с SD (17.11.2026): за 48 с трекера приёмник четыре раза возвращался к заводскому состоянию - 38400 бод, NMEA,
мигающий PPS (`GNSS RX error` -> `RX error storm` -> `listening for NMEA at 38400 baud`), в том числе на улице при хорошем фиксе
(9 спутников, hAcc 5 м). Настройка принималась (ACK на `UART baud`, `PSMOO params`, `PSMOO mode`). Один цикл "off" ->
пробуждение она пережила, сброс случился примерно через 1,4 с после начала поиска; причина не установлена. Аппаратный тест
`GNSS_BBR` ([`gnss-retention.md`](gnss-retention.md)) режим PSMOO сам по себе выдержал (24 цикла «off» -> пробуждение, настройка
в BBR цела, NMEA не возвращался, ошибок UART 0), и BBR живёт даже при выключенном устройстве, так что остаются подозрения на
Stop 2 с пробуждением по RXNE, восстановление связи в `gnss_link`, остальные кадры настройки и просадку питания при пробуждении.
В тесте PSMOO ещё и держал модуль включённым 7-9 с за цикл при `ONTIME` = 2 с. Режимы оставлены как альтернативы: PSMCT
(= 1) - решения раз в 10 с (предел PSMCT), приёмник не уходит в "off"; PSMOO (= 2) - период `PURRGO_GNSS_TRACKER_PERIOD_S`
(15 с), `PURRGO_GNSS_TRACKER_ONTIME_S`, вся настройка и `UART baud` в слоях RAM и BBR, кадры `PSMOO params` и `PSMOO mode`.

**Что сохраняет модуль.** RAM стирается при `EN` = Low, в «off» PSMOO и при любом сбросе; BBR (настройка, эфемериды,
альманах, время) переживает `EN` = Low, «off» PSMOO и программный сброс, стирается аппаратным сбросом
(`UBX-CFG-RST` 0x00); слой Flash у модуля есть и переживает оба сброса. Подробности, методика и цифры (в том числе время
до фикса после `EN` = Low): [`gnss-retention.md`](gnss-retention.md).

Ядро в трекере: в режимах 1 и 2 фикс считается действующим `PURRGO_GNSS_TRACKER_FIX_TIMEOUT_MS` (два периода + 30 с), в
режиме 3 срок задаёт автомат (см. выше); логгер получает каждое решение один раз, монитор не пишет «нет данных» между
решениями. В режимах 1 и 2 без неба (в помещении) поиск идёт непрерывно, в режиме 3 приёмник включается всё реже.

**Выход из трекера (K1+K4) в режимах 1 и 2** (в режиме 3 приёмник перезапускается по EN, см. выше). Приёмник будится байтами `0xFF` на RX (любой фронт - источник пробуждения), через 300 мс
уходит настройка навигации (слой RAM: решения раз в секунду, PM-ключи возвращают PSMCT или полную мощность; в режиме
PSMOO добавляется кадр `PM BBR clean` - `UBX-CFG-VALDEL`, который удаляет из слоя BBR параметры PSMOO); через `PURRGO_GNSS_CONFIG_RETRY_MS` - повтор. Если питание выключается из трекера, настройка навигации отправляется перед EN = Low (на случай, если BBR
переживёт отключение).

**Шторм ошибок приёма.** Пять ошибок приёма UART за три секунды (FE, NE, ORE) считаются штормом: модуль, скорее всего,
сбросил настройку и снова шлёт NMEA на заводской скорости (признак - мигает светодиод PPS, который прошивка гасит), а
МК слушает на рабочей. Сначала связь переустанавливается мягко (заново подбор скорости UART и настройка текущего профиля,
навигации или трекера), если шторм повторился в течение 30 с - выключением модуля по EN на 200 мс. В логе: `GNSS: RX error
storm ... restarting the link`, затем `power cycling the module (EN)`. В окне шторма в лог пишутся только первые две ошибки.
Строка `RF jam` при смене состояния помех пишется не чаще раза в 10 с (в трекере - раз в минуту): раньше при слабом
сигнале состояние дребезжало, и лог заполнялся.

Откуда теперь берутся данные: время, позиция, высота, скорость, курс, тип фикса, число спутников,
hAcc/vAcc/sAcc - из UBX-NAV-PVT; HDOP/VDOP/PDOP - из UBX-NAV-DOP; таймаут потери фикса считается по
PVT. Число спутников "в поле зрения" (GSV) в мониторе больше недоступно: показываются спутники в
решении (`sv` из PVT).

Что учитывает отсутствие NMEA:

- **`gnss_link`**: после сброса одного МК (модуль не обесточен) NMEA у модуля уже выключен, поэтому
  модулем считается и корректный кадр UBX (верная контрольная сумма), не только предложение NMEA.
  После выключения питания по EN модуль возвращается к заводской настройке (NMEA, 38400), и всё
  проходит заново (настройка навигации хранится только в слое RAM, `PURRGO_GNSS_UBX_LAYERS`; профиль EN трекера пишет ещё и
  в BBR, см. выше).
- **Монитор** (`gnss_monitor`): связь определяется по кадрам UBX, состояние фикса - по PVT
  (`UBX OK, no fix yet ...`, `FIX after ... s, sats used=..`).
- **Разбор NMEA** в ядре остаётся: он нужен сборкам `PURRGO_GNSS_UBX=0`, модулю до настройки и запасному
  пути при NAK. В режиме без NMEA через него не проходит ни один байт после настройки.

`-DPURRGO_GNSS_UBX_NMEA=1` оставляет NMEA включённым (GGA/RMC/GSA, 1 Гц) рядом с UBX, как раньше:
для отладки (u-center, внешние программы). Тогда пока приходит PVT, он главнее RMC/GGA/GSA (NMEA даёт
HDOP/VDOP и запасной путь, после `PURRGO_GNSS_PVT_HOLD_EPOCHS` эпох RMC без PVT решением снова владеет NMEA).

Настройка уходит отдельными `UBX-CFG-VALSET` (базовая NMEA, по одному на каждое
сообщение PVT/ODO/MON-RF/NAV-DOP, одометр, модель динамики, выключение NMEA) и (при `PURRGO_GNSS_POLL_VERSION` = 1) опросом MON-VER: модуль применяет
VALSET целиком или отклоняет целиком, поэтому NAK по одному кадру не отменяет остальные.
Ответы ACK/NAK приходят в порядке отправки, поэтому отказ пишется в лог с именем группы:
`GNSS: config "NAV-ODO" rejected by module (NAK)` (имена: `NMEA/rate`, `NAV-PVT`, `NAV-ODO`,
`MON-RF`, `NAV-DOP`, `SEC-SIG`, `NAV-STATUS`, `NAV-SAT`, `ITFM`, `ODO enable/profile`, `DYNMODEL`, `TIMEPULSE quiet` или `TIMEPULSE off`, `NMEA off`). Сопоставление считается от последнего вызова
настройки; поздний ответ на команду смены скорости UART (gnss_link) может сдвинуть счёт на один.

## Диагностика в логе

По умолчанию периодические строки и опрос версии выключены (`PURRGO_GNSS_LOG_PERIODIC` = 0,
`PURRGO_GNSS_POLL_VERSION` = 0), чтобы не забивать лог; включаются через `#define` в `hardware_config.h`
или `-D`.

- `GNSS: u-blox SW ... HW ...`, `FWVER`, `PROTVER` - ответ на опрос MON-VER (`PURRGO_GNSS_POLL_VERSION` = 1).
- `GNSS: PVT fixType=.. fixOK=.. sv=.. validTime=.. hAcc=.. mm pDOP=..` - раз в 5 с (уровень INFO, `PURRGO_GNSS_LOG_PERIODIC` = 1):
  видно, есть ли уже время без позиции. Импульсы таймпульса (1PPS) выключены (длина 0, `PURRGO_GNSS_TIMEPULSE`); по заводской
  настройке он выдаётся, как только приёмник синхронизировался по времени GNSS, позиция для этого не нужна,
  поэтому мигание светодиода PPS не означало 3D-фикс.
- Только в сборке Debug (`PURRGO_LOGD`, уровень 4) и при `PURRGO_GNSS_LOG_PERIODIC` = 1, раз в 5 с и сразу при смене `jammingState`/`spoofDetState`:
  `GNSS: RF jam=.. ant=../.. noise=.. agc=.. cw=..`, `GNSS: STATUS gpsFix=.. flags=0x.. psm=.. spoof=..`,
  `GNSS: SAT listed=.. used=.. cno avg=.. max=.. dBHz`. По ним на железе видно, какие значения выдаёт
  именно эта прошивка (`jam=0` при включённом ITFM после фикса или `spoof=0` постоянно - не поддержано).

## Данные и обновление

Модуль выдаёт всё раз в `PURRGO_GNSS_UPDATE_PERIOD_MS` (1000 мс). Ядро берёт решение и снимок
путевого компьютера (`purrgo_trip_computer_update`) раз в секунду; экран Trip computer
перерисовывается, только когда изменилось показанное (километры с шагом 10 м, hAcc с шагом 0,1 м,
состояния).

Экран Trip computer (строки ниже блока SUN):

- `TRP:` дистанция с начала записи трека (одометр модуля; при старте нового файла трека
  отправляется `UBX-NAV-RESETODO`; если отправить не удалось, отсчёт идёт от текущего значения);
- `ACC:` `H3.5 m V5.2 m` - hAcc / vAcc;
- `SIG:` `JAM OK SPF OK` - глушение и спуфинг (SEC-SIG, а в SPG 5.10 - MON-RF и NAV-STATUS, см. выше);
  глушение `WARN!` - предупреждение, `CRIT!` - помеха и нет фикса; спуфинг `IND!` - признаки,
  `AFF!!` - подтверждён; `--` - источник не сообщил состояние.

`---` - данных нет (сообщение не приходило дольше 3,5 с, нет фикса или сборка без UBX).

## GPX

Заголовок содержит `xmlns="http://www.topografix.com/GPX/1/1"` и пространство имён
`gpxtpx` = Garmin TrackPointExtension **v2** (в v1 нет скорости и курса):

```xml
<extensions>
  <gpxtpx:TrackPointExtension>
    <gpxtpx:speed>2.49</gpxtpx:speed>    <!-- м/с -->
    <gpxtpx:course>45.00</gpxtpx:course> <!-- градусы, только при надёжном курсе -->
  </gpxtpx:TrackPointExtension>
  <pg:hacc>3.52</pg:hacc>                <!-- м, только с PVT -->
  <pg:bat>100</pg:bat><pg:vbat>4793</pg:vbat>
</extensions>
```

`pg:spd` (сотые доли узла) заменён на `gpxtpx:speed` (м/с); `tools/track-analyze/analyze_diag.py`
читает оба варианта.

## Курс из PVT

`headMot` при стоянке случаен, поэтому курс считается надёжным только при скорости >= 0,5 м/с
и `headAcc` <= 45 градусов.
