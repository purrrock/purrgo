# Формат карты PurrGO — техническая спецификация V4

**Статус:** нормативная спецификация, **черновик** (компилятор и прошивка пока работают с V3; см. раздел 0.3 и приложение A)

Документ определяет бинарный формат карты PurrGO V4 и правила, которым должны следовать совместимый компилятор карт и парсер прошивки.

Формат состоит из трёх файлов в контейнере PGO на каждый слой:

* `.idx` — пространственный индекс (блочная раскладка, **новое в V4**);
* `.mlp` — векторная геометрия;
* `.db` — атрибуты объектов;

и одного необязательного файла уровня пакета:

* `search.idx` — индекс для поиска POI (**новое в V4**, раздел 21).

Классификация объектов определяется файлом `features.csv`; словарь подтипов для поиска — файлом `search_categories.csv` (раздел 21.8).

Все многобайтные целые поля хранятся в порядке **Little-Endian**, если явно не указано иное.

Документ основан на [`map-format-v3.md`](map-format-v3.md). Разделы, текст которых не изменился, сохранили номера V3, поэтому ссылки вида «раздел 10» или «раздел 8.1.1» остаются верными.

Обоснование решений: [`design/pgo-v4.md`](design/pgo-v4.md) (блочная раскладка индекса) и [`design/poi-search.md`](design/poi-search.md) (поиск POI).

Растровые тайлы карты формат V4 не использует, и места под них в формате не зарезервировано.

# 0. ОБЛАСТЬ ПРИМЕНЕНИЯ И ОТЛИЧИЯ ОТ V3

## 0.1. Что изменилось

| Область | V3 | V4 |
| ------- | -- | -- |
| Раскладка дерева `.idx` | обход в глубину, дети перемешаны со своими поддеревьями | **блочная раскладка**: все дети узла образуют один блок 512 Б, блоки упорядочены по уровням (разделы 5–7) |
| Доступ к поддереву | относительный пропуск `v3_jump` | абсолютное смещение блока детей `child_block` |
| Magic SQT | `SQT\x01` | `SQT\x02` |
| Заголовок SQT | 16 байт, сразу за ним узлы | один сектор заголовка 512 Б (раздел 5.1) |
| Ветвление (fan-out) | 14 детей на узел | 18 навигационных или 20 листовых узлов на блок (раздел 6.1) |
| Выравнивание | нет | секции LOD и блоки начинаются со смещений файла, кратных 512 |
| `.db` POI | текст: «безымянный POI → `v2 = 0`» | у каждого POI есть запись, `v2 ≥ 1` (раздел 10.5; компилятор V3 уже так делал) |
| Поле названия | не описано | правила выбора и кодирования названия описаны (раздел 10.6); название **не сокращается до 22 символов**, предел поля 100 байт |
| Поиск | нет | необязательный `search.idx` (раздел 21), тип файла `4` |

## 0.2. Что не изменилось

* заголовок контейнера PGO (раздел 1), кроме нового типа файла `4` и правил выравнивания для `.idx`;
* координаты (раздел 2);
* записи геометрии `.mlp` и смысл `v1` (раздел 3);
* размер навигационного узла (28 байт), раскладка и размер узла данных (25 байт);
* `features.csv`, коды объектов и их диапазоны (разделы 8.1 и 9);
* раскладка DBF в `.db`: заголовок 129 Б, запись 117 Б, поле названия 100 Б (разделы 10.1–10.4);
* `map.name` (раздел 11);
* инварианты слоёв и геометрии (раздел 13).

## 0.3. Совместимость

* Читатель V3 отвергает `.idx` версии V4 на проверке magic SQT и не должен пытаться его разбирать.
* Версия файла `.idx` определяется по magic его секций SQT: `SQT\x01` — V3, `SQT\x02` — V4. Все три секции одного файла имеют одинаковый magic. Переходная прошивка может поддерживать обе версии и выбирать парсер для файла по magic секции LOD 0.
* Пакет карты компилируется целиком как V3 или целиком как V4. Смешивать файлы слоёв V3 и V4 в одном пакете нельзя.
* `.mlp` и `map.name` побайтно одинаковы в пакетах V3 и V4, собранных из одних исходных данных. `.db` имеет ту же раскладку, но названия в нём больше не сокращаются до 22 символов (раздел 10.6).
* `search.idx` необязателен. Читатель, который его не знает, игнорирует файл (раздел 11.4.1).

# 1. КОНТЕЙНЕР PGO

Каждый файл `.idx`, `.mlp`, `.db` и `search.idx` начинается с **заголовка PGO** фиксированного размера 32 байта.

## 1.1. Раскладка заголовка

| Смещение | Размер | Тип       | Поле                 | Описание                                       |
| -------: | -----: | --------- | -------------------- | ---------------------------------------------- |
| `0x00`   |      3 | `char[3]` | Magic                | Строго `PGO` (`50 47 4F`)                      |
| `0x03`   |      1 | `uint8`   | Тип файла            | `1` = `.idx`, `2` = `.mlp`, `3` = `.db`, `4` = `search.idx` |
| `0x04`   |      4 | `uint32`  | Размер payload       | Размер файла минус 32                          |
| `0x08`   |      4 | `uint32`  | Смещение LOD 0       | Абсолютное смещение секции LOD 0 в `.idx`      |
| `0x0C`   |      4 | `uint32`  | Смещение LOD 1       | Абсолютное смещение секции LOD 1 в `.idx`      |
| `0x10`   |      4 | `uint32`  | Смещение LOD 2       | Абсолютное смещение секции LOD 2 в `.idx`      |
| `0x14`   |      4 | `uint32`  | Резерв 1             | Зарезервировано; должно быть нулём             |
| `0x18`   |      4 | `uint32`  | Резерв 2             | Зарезервировано; должно быть нулём             |
| `0x1C`   |      4 | `uint32`  | Резерв 3             | Зарезервировано; должно быть нулём             |

Payload начинается со смещения:

```text
0x20
```

Размер payload:

```text
Размер payload = Размер файла - 32
```

`uint32` допускает файлы примерно до 4 ГиБ; текущая реализация ограничивает размер payload значением `0xFFFFFFFF`.

## 1.2. Тип файла

```text
1 = .idx
2 = .mlp
3 = .db
4 = search.idx
```

Остальные значения зарезервированы для будущих расширений.

## 1.3. Смещения LOD

Для `.idx` три поля LOD содержат **абсолютные смещения в байтах от начала файла**:

```text
Смещение LOD 0 → начало секции LOD 0
Смещение LOD 1 → начало секции LOD 1
Смещение LOD 2 → начало секции LOD 2
```

Они позволяют прошивке сразу перейти к выбранному LOD.

В V4 смещения LOD кратны 512, первое из них равно `0x200`, секции идут друг за другом в порядке LOD 0, LOD 1, LOD 2 без промежутков (раздел 4.1). Секция LOD простирается до следующего смещения LOD; последняя — до конца файла.

Для `.mlp`, `.db` и `search.idx` эти поля сейчас не используются и должны быть нулями.

## 1.4. Зарезервированные поля

Смещения `0x14`–`0x1F` зарезервированы для будущих расширений.

Текущий компилятор записывает в них нули.

Текущая прошивка должна считать их непрозрачными и не придавать им никакого смысла.

## 1.5. Проверка заголовка

Парсер обязан:

1. проверить magic `PGO`;
2. проверить, что тип файла равен `1`, `2`, `3` или `4`;
3. прочитать размер payload;
4. проверить, что заявленный payload помещается в файл;
5. для `.idx` проверить, что каждое смещение LOD лежит внутри файла, кратно 512, не меньше `0x200`, и что LOD 0 < LOD 1 < LOD 2;
6. отвергнуть неверные или неподдерживаемые заголовки до разбора payload.

# 2. ПРЕДСТАВЛЕНИЕ КООРДИНАТ

Все координаты карты хранятся как знаковые 32-битные целые с фиксированной точкой и точностью:

```text
10⁻⁷ градуса
```

Перевод из географических координат:

```text
целая_координата = географическая_координата × 10⁷
```

Пример:

```text
55.7558000° → 557558000
37.6173000° → 376173000
```

Порядок координат:

```text
X = долгота
Y = широта
```

В `.idx` и `.mlp` не хранятся координаты с плавающей точкой.

Путь карты и навигации на STM32 работает с этими целыми координатами. Для разбора бинарной карты и пространственного обхода арифметика с плавающей точкой не нужна.

# 3. ФАЙЛ ГЕОМЕТРИИ (`.MLP`)

Файл `.mlp` хранит упорядоченные координаты линейных и полигональных объектов.

Файл состоит из заголовка PGO и записей геометрии.

```text
+-------------------------+
| Заголовок PGO (32 Б)    |
+-------------------------+
| Запись геометрии        |
+-------------------------+
| Запись геометрии        |
+-------------------------+
| ...                     |
+-------------------------+
```

## 3.1. Локальный заголовок записи геометрии

Каждая запись геометрии начинается с 8-байтного локального заголовка.

| Смещение | Размер | Тип      | Порядок байт  | Описание                                          |
| -------: | -----: | -------- | ------------- | ------------------------------------------------- |
| `0x00`   |      4 | `uint32` | Big-Endian    | Порядковый номер записи геометрии, с 1            |
| `0x04`   |      4 | `uint32` | Little-Endian | Длина тела записи геометрии в байтах              |

Тело записи следует сразу за локальным заголовком.

## 3.2. Тело записи геометрии

Длина тела в точности равна значению в локальном заголовке.

| Смещение | Размер           | Тип          | Описание                        |
| -------: | ---------------: | ------------ | ------------------------------- |
| `0x00`   |               16 | `int32[4]`   | BBox `[minx, miny, maxx, maxy]` |
| `0x10`   |                4 | `int32`      | `num_parts`                     |
| `0x14`   |                4 | `int32`      | `num_points`                    |
| `0x18`   |  `num_parts × 4` | `uint32[]`   | массив `parts`                  |
| далее    | `num_points × 8` | `int32[2][]` | Точки `[X,Y]`                   |

Все координаты хранятся с точностью `10⁻⁷` градуса.

`parts` содержит **индексы точек**, а не длины контуров.

Для геометрии с `num_parts` частями каждый `parts[i]` указывает первую точку части `i`.

## 3.3. Указатель на геометрию (`v1`)

Для обычного узла данных `v1` указывает на соответствующую геометрию в `.mlp`.

`v1` — смещение **относительно начала payload `.mlp`**, то есть относительно смещения файла `0x20`.

Он указывает на начало **тела записи геометрии**, а не на 8-байтный локальный заголовок.

Поэтому:

```text
абсолютное смещение в файле .mlp = 0x20 + v1
```

Например, если:

```text
v1 = 8
```

указатель ссылается на первый байт тела первой записи геометрии.

8-байтный локальный заголовок в `v1` не входит.

Текущий компилятор реализует это так:

```text
v1 = смещение_записи_геометрии_в_payload + 8
```

## 3.4. Топология полигонов

Мультиполигон хранится так же, как вся остальная геометрия.

* все кольца сводятся в один массив `points`;
* `num_parts` задаёт число колец;
* `parts` содержит индекс начальной точки каждого кольца;
* кольца должны быть замкнуты;
* первая и последняя точки кольца должны совпадать.

Правила обхода:

```text
Внешние кольца   → по часовой стрелке (CW)
Внутренние кольца → против часовой стрелки (CCW)
```

Простой полигон состоит из одной замкнутой части.

Кольца заполняются по правилу чётности-нечётности (even-odd), поэтому внутреннее кольцо является дыркой (например, остров в озере).

### 3.4.1. Ограничения

Одна запись геометрии содержит не более `2000` точек суммарно по всем частям и не более `32` частей. Прошивка отвергает запись большего размера целиком, и объект не рисуется. Компилятор пропускает линии и мультиполигоны длиннее `1999` точек, поэтому каждый записанный им объект укладывается в предел.

### 3.4.2. Построение мультиполигонов в компиляторе

* кольца отношения собираются из его участков (ways): замкнутые участки берутся как есть, незамкнутые склеиваются по общим концам;
* участок с пустой ролью — внешнее кольцо;
* кольцо, которое нельзя замкнуть (неполные данные на краю выгрузки), отбрасывается;
* внутреннее кольцо сохраняется, только если оно лежит внутри одного из собранных внешних колец; отношение без замкнутого внешнего кольца ничего не производит, поэтому острова никогда не записываются без своего озера;
* для воды мультиполигон заменяет отдельный полигон своего внешнего участка независимо от того, дублирует ли отношение теги участка или не несёт их вовсе (старый стиль разметки). Иначе сплошной полигон закрыл бы дырки.

# 4. ПРОСТРАНСТВЕННЫЙ ИНДЕКС (`.IDX`)

Файл `.idx` обеспечивает пространственный поиск и отсечение по BBox.

PurrGO сейчас определяет:

```text
LOD 0
LOD 1
LOD 2
```

Каждый LOD хранится как независимая секция SQT.

Пространственный индекс — иерархическое дерево, построенное алгоритмом пакетной загрузки **Sort-Tile-Recursive (STR)**. В V4 дерево хранится **блоками**: дети одного навигационного узла лежат вместе в одном блоке 512 байт, поэтому читатель получает всех детей узла одним чтением сектора и по их BBox решает, в какие поддеревья спускаться.

Индекс содержит только сведения, нужные для пространственного обхода и получения объектов. Теги OSM и текстовые описания в `.idx` не хранятся.

## 4.1. Раскладка файла

```text
+-----------------------------+ 0x000
| Заголовок PGO (32 байта)    |
+-----------------------------+ 0x020
| нулевое заполнение          |
+-----------------------------+ 0x200   ← смещение LOD 0
| секция LOD 0                |
+-----------------------------+         ← смещение LOD 1
| секция LOD 1                |
+-----------------------------+         ← смещение LOD 2
| секция LOD 2                |
+-----------------------------+ конец файла
```

Правила:

* байты `0x20..0x1FF` — нули;
* смещение LOD 0 равно `0x200`; LOD 1 и LOD 2 следуют без промежутков в этом порядке;
* каждое смещение LOD кратно 512;
* размер каждой секции LOD кратен 512; поэтому размер файла кратен 512;
* `Размер payload` определяется как в V3: размер файла минус 32.

Выравнивание по 512 байт считается от начала файла, а не от начала payload. Файлы читаются с тома FAT, кластеры которого выровнены по секторам, поэтому блок 512 байт по смещению файла, кратному 512, занимает ровно один сектор SD.

# 5. СЕКЦИИ LOD (SQT)

Секция LOD состоит из одного **сектора заголовка**, за которым идут **блоки**. И то и другое имеет размер 512 байт. Адрес блока — абсолютное смещение файла, кратное 512.

```text
начало секции S
+---------------------------+ S
| Сектор заголовка (512 Б)  |
+---------------------------+ S + 512
| Корневой блок             |
+---------------------------+ S + 1024
| Блоки уровня depth-2      |   (в порядке из раздела 7.3)
| ...                       |
| Листовые блоки            |
+---------------------------+ S + section_size
```

## 5.1. Сектор заголовка SQT

| Смещение | Размер | Тип       | Описание                                                          |
| -------: | -----: | --------- | ----------------------------------------------------------------- |
| `0x00`   |      4 | `char[4]` | Magic: `SQT\x02`                                                  |
| `0x04`   |      4 | `uint32`  | Топология: `2` (блочное дерево)                                   |
| `0x08`   |      4 | `uint32`  | Глубина дерева: число уровней узлов; `0` для пустого LOD          |
| `0x0C`   |      4 | `uint32`  | Число корневых узлов (`root_count`)                               |
| `0x10`   |      4 | `uint32`  | Размер блока в байтах: `512`                                      |
| `0x14`   |      4 | `uint32`  | Размер секции в байтах: сектор заголовка + все блоки              |
| `0x18`   |      2 | `uint16`  | Максимум навигационных узлов в блоке (`nav_fanout`): `18`         |
| `0x1A`   |      2 | `uint16`  | Максимум узлов данных в блоке (`leaf_fanout`): `20`               |
| `0x1C`   |    484 | `uint8[]` | Резерв; должен быть нулями                                        |

Читатель V4 требует `Размер блока = 512`, `nav_fanout ≤ 18` и `leaf_fanout ≤ 20`. Поля нужны для того, чтобы следующая ревизия могла изменить размер блока без смены раскладки заголовка; V4 других значений не допускает.

`Размер секции` должен быть кратен 512 и равен расстоянию до следующего смещения LOD (для LOD 2 — до конца файла).

## 5.2. Пустой LOD

Пустой LOD состоит только из сектора заголовка:

```text
depth = 0
root_count = 0
section_size = 512
```

Корневого блока у него нет.

## 5.3. Корневой блок

Корневой блок непустого LOD начинается со смещения `S + 512`. Он содержит `root_count` навигационных узлов (`1 ≤ root_count ≤ 18`) уровня `depth - 1`.

`depth` — число уровней навигационных узлов. Корневые узлы имеют уровень `depth - 1`; нижние узлы имеют уровень `0`, и их дети — узлы данных (раздел 6.3).

# 6. БЛОКИ И УЗЛЫ

## 6.1. Блок

Блок имеет размер ровно 512 байт. Он содержит непрерывный массив записей, начиная с нулевого байта блока; байты после последней записи — нули.

Блоки бывают двух видов:

| Вид                  | Записи                  | Размер записи | Макс. записей | Занято байт |
| -------------------- | ----------------------- | ------------: | ------------: | ----------: |
| Навигационный блок   | навигационные узлы      |       28 байт |            18 |         504 |
| Листовой блок        | узлы данных             |       25 байт |            20 |         500 |

Вид блока и число его записей в самом блоке не хранятся. Их задаёт узел, который на него указывает: `v1` навигационного узла (уровень) выбирает вид, а `v2` (число детей) даёт число записей (раздел 6.3). Вид и число записей корневого блока следуют из заголовка SQT: это навигационный блок с `root_count` записей.

В каждом блоке есть хотя бы одна запись.

## 6.2. Навигационный узел

Навигационный узел представляет пространственный кластер и указывает на блок с его детьми.

Его бинарный размер — **28 байт** (как в V3).

Бинарная раскладка:

```text
<IiiiiII
```

| Смещение | Размер | Тип        | Описание                                                    |
| -------: | -----: | ---------- | ----------------------------------------------------------- |
| `0x00`   |      4 | `uint32`   | `child_block` — абсолютное смещение файла блока с детьми    |
| `0x04`   |     16 | `int32[4]` | BBox кластера `[xmin,ymin,xmax,ymax]`                       |
| `0x14`   |      4 | `uint32`   | `v1` — уровень дерева                                       |
| `0x18`   |      4 | `uint32`   | `v2` — число детей                                          |

Все координаты BBox хранятся с точностью `10⁻⁷` градуса.

Единственное отличие от узла V3 — первое поле: `v3_jump` (размер поддерева детей в байтах) заменён на `child_block` (см. раздел 7).

## 6.3. Уровень и число детей

Для:

```text
v1 = 0
```

узел указывает на **листовой блок** с `v2` узлами данных, `1 ≤ v2 ≤ 20`.

Для:

```text
v1 > 0
```

узел указывает на **навигационный блок** с `v2` навигационными узлами, `1 ≤ v2 ≤ 18`, каждый уровня `v1 - 1`.

Таким образом, дерево однородно на каждом уровне: все записи одного блока одного вида, а все навигационные узлы одного блока имеют один уровень.

Узлы корневого блока имеют уровень `depth - 1`. Поэтому их `v1` равен `depth - 1` у всех.

# 7. `child_block`

`child_block` — абсолютное смещение файла блока, содержащего детей навигационного узла.

Оно ни от чего не отсчитывается: читатель переходит на это смещение и читает 512 байт.

## 7.1. Ограничения

Для навигационного узла, лежащего в блоке по смещению `B`, в секции `[S, S + section_size)`:

1. `child_block` кратен 512;
2. `S + 1024 ≤ child_block` и `child_block + 512 ≤ S + section_size`;
3. `child_block > B` — блок детей всегда лежит после блока, который на него ссылается.

Ограничение 3 делает дерево ациклическим по построению: парсер, идущий по указателям `child_block`, не может зациклиться, а число вложенных чтений ограничено `depth`.

Парсер обязан отвергнуть узел, нарушающий эти ограничения, либо у которого `v1` или `v2` выходят за пределы раздела 6.3, либо `v1` не равен ожидаемому уровню.

## 7.2. Обход

Для отсечения не нужен пропуск поддеревьев. Поддерево пропускается тем, что его блок не читается:

```text
visit_block(offset, level, count):        # level = уровень записей (Nav) или -1 (лист)
    прочитать 512 байт по offset
    для каждой записи e среди первых count:
        если e.bbox не пересекает видимую область:
            continue                       # для поддерева не читается ничего
        если листовой блок:
            передать e в отрисовку
        иначе:
            visit_block(e.child_block, e.v1 - 1, e.v2)    # e.v1 = 0 → листовой блок с e.v2 записями
```

Корневой вызов: `visit_block(S + 512, depth - 1, root_count)`.

Между детьми одного блока читателю не нужен `seek`: после чтения блока все BBox его записей уже в памяти.

## 7.3. Физический порядок блоков

Порядок блоков внутри секции нормативен, чтобы на него могли полагаться парсеры и инструменты.

Блоки сгруппированы по уровню узлов, которые они содержат:

```text
группа 0: корневой блок                          (узлы уровня depth-1)
группа 1: навигационные блоки узлов уровня depth-2
...
группа depth-1: навигационные блоки узлов уровня 0
группа depth:   листовые блоки                   (узлы данных)
```

Правила:

1. Группы идут в порядке возрастания номера выше, одна за другой, без промежутков. У дерева с `depth = 1` группы — корневой блок и листовые блоки.
2. На каждый блок, кроме корневого, ссылается ровно один навигационный узел, и каждый навигационный узел ссылается ровно на один блок.
3. Блоки группы идут в порядке ссылающихся на них узлов: k-й блок группы `g + 1` — блок детей k-го навигационного узла группы `g`, где узлы считаются в порядке их блоков и, внутри блока, в порядке записей.
4. Из правила 3 следует, что блоки детей узлов одного блока идут подряд: для записей `i` и `i + 1` одного блока `child_block[i + 1] = child_block[i] + 512`. Читатель может прочитать детей блока одним многосекторным запросом.
5. Порядок узлов внутри блока — порядок, выданный алгоритмом STR (раздел 14). Для читателя он смысла не имеет.
6. Все байты вне записей и заголовков (хвосты блоков, хвост сектора заголовка) — нули.

Поэтому верхние уровни дерева лежат в начале секции, рядом друг с другом. Блоки одного уровня, принадлежащие одному поддереву, расположены рядом.

## 7.4. `v3_jump` удалён

В V4 нет `v3_jump`. Нет относительного пропуска поддерева, нет размера поддерева и нет компенсации прыжка. Всё, что V3 говорил о «пропуске поддеревьев», заменено разделом 7.2.

## 7.5. Пример (справочно)

LOD с 50 узлами данных (один слой из трёх кластеров по 20, 20 и 10) и началом секции `S = 0x200`:

```text
0x200  сектор заголовка  depth=1, root_count=3, block_size=512, section_size=0xA00
0x400  корневой блок     3 навигационных узла, уровень 0:
                           child_block=0x600  v2=20
                           child_block=0x800  v2=20
                           child_block=0xA00  v2=10
0x600  листовой блок     20 узлов данных (500 байт) + 12 нулевых байт
0x800  листовой блок     20 узлов данных (500 байт) + 12 нулевых байт
0xA00  листовой блок     10 узлов данных (250 байт) + 262 нулевых байта
0xC00  конец секции (= следующее смещение LOD или конец файла)
```

# 8. УЗЕЛ ДАННЫХ

Узел данных представляет один картографический объект.

Его бинарный размер — **25 байт**.

Бинарный формат:

```text
<iiiiBII
```

| Смещение | Размер | Тип        | Описание                         |
| -------: | -----: | ---------- | -------------------------------- |
| `0x00`   |     16 | `int32[4]` | BBox `[xmin,ymin,xmax,ymax]`     |
| `0x10`   |      1 | `uint8`    | `Type` — код объекта PurrGO      |
| `0x11`   |      4 | `uint32`   | `v1` — указатель на геометрию    |
| `0x15`   |      4 | `uint32`   | `v2` — номер записи в DB         |

## 8.1. Код объекта

`Type` — числовой `Code` из `features.csv`.

Прошивка по этому числовому коду определяет класс объекта PurrGO и стиль отрисовки.

Исходные теги OSM прошивке не нужны.

### 8.1.1. Диапазоны кодов

Поле `Type` — `uint8`. Пространство кодов разделено на фиксированные диапазоны, по одному на слой:

| Диапазон    | Слой / назначение | Классы                                                            |
| ----------: | ----------------- | ----------------------------------------------------------------- |
|    `0..31`  | `roads`           | `NO_CLASS` (0), `ROAD_*`, `RAILWAY`                               |
|   `32..63`  | `waterways`       | `WATERWAY_MAJOR` (32), `WATERWAY_MINOR` (33)                      |
|   `64..95`  | `water`           | `WATER` (64), `WETLAND` (65), `GLACIER` (66)                      |
|  `96..127`  | `landuse`         | `LANDUSE_NATURAL` (96), `LANDUSE_HUMAN` (97), `SAND` (98)         |
| `128..191`  | `pois`            | `POI_BIG` (128), `POI_SMALL` (129), прочие классы POI (130..)     |
| `192..223`  | значки интерфейса | номера значков `purrgo_poi_icons`, в картах никогда не хранятся   |
| `224..255`  | резерв            | не используются ни одним слоем                                    |

Правила:

- Правило в `features.csv` должно использовать код из диапазона своего `Layer`. Компилятор это проверяет (в том числе для выключенных правил) и останавливается с ошибкой в противном случае.
- Новый класс добавляется в конец диапазона своего слоя: следующий свободный код после наибольшего из используемых. Код, который появлялся в скомпилированных картах, никогда не переназначается другому классу.
- Несколько правил могут разделять один код (один класс, много тегов OSM). Код `4` — существующее исключение: его используют правила и `ROAD_NORMAL`, и `ROAD_MINOR`.
- Номера `192..223` прошивка использует для значков интерфейса (цель, путевая точка, перекрестие; позже батарея, антенна и подобное). Это не коды объектов: карта не должна их содержать, а компилятор никогда их не назначает. Новый значок интерфейса получает следующий свободный номер этого диапазона.
- Коды `224..255` зарезервированы на будущее (например, новые слои). Код без стиля прошивка трактует как «не рисовать».
- Значки POI индексируются самим кодом, см. 9.6.

Карта, скомпилированная по прежнему назначению кодов (`WATER` = 10, `LANDUSE_*` = 8/9, `POI_*` = 11..36, `WATERWAY_*` = 37/38, `WETLAND` = 39, `GLACIER` = 40, `SAND` = 41), несовместима с текущей прошивкой: вода, землепользование и POI не будут нарисованы. Такие карты нужно перекомпилировать. Коды дорог и железной дороги (`1..7`) не менялись.

Например:

```text
features.csv

2;ROAD_NORMAL;DARK_GRAY_SEMITHICK_LINE;1;roads;highway=primary;Главная дорога;1;
```

даёт:

```text
Type = 2
```

Смысл кода определяется соответствующей строкой `features.csv`.

Текстовые поля `PG_class`, `STYLE`, `LOD`, `Layer` и `OSM_Tags` в узле данных не хранятся.

## 8.2. `v1`

Для линейных и полигональных объектов:

```text
v1 = смещение тела геометрии в payload .mlp
```

Для нативных POI:

```text
v1 = 0
```

См. [раздел 3.3](#33-указатель-на-геометрию-v1).

## 8.3. `v2`

Для объектов со связанной записью атрибутов:

```text
v2 = номер записи DB
```

Для слоёв без файла `.db`:

```text
v2 = 0
```

Точные правила индексации `.db` определены в разделе 10.

# 9. КЛАССИФИКАЦИЯ ОБЪЕКТОВ (`features.csv`)

`features.csv` — исходная таблица классификации, которую использует компилятор карт.

Формат:

```text
Code;PG_class;STYLE;LOD;Layer;OSM_Tags;Description;Enabled;Icon
```

## 9.1. Поля

| Поле          | Тип           | Описание                                            |
| ------------- | ------------- | --------------------------------------------------- |
| `Code`        | целое         | Числовой код объекта PurrGO, хранимый в узлах данных |
| `PG_class`    | идентификатор | Семантический класс объекта PurrGO                  |
| `STYLE`       | идентификатор | Стиль отрисовки                                     |
| `LOD`         | целое         | LOD, в котором хранится объект                      |
| `Layer`       | идентификатор | Целевой слой                                        |
| `OSM_Tags`    | выражение     | Выражение над тегами OSM для сопоставления          |
| `Description` | текст         | Описание для человека                               |
| `Enabled`     | `0/1`         | Активно ли правило                                  |
| `Icon`        | идентификатор | Идентификатор значка POI                            |

Пример:

```text
Code;PG_class;STYLE;LOD;Layer;OSM_Tags;Description;Enabled;Icon

1;ROAD_MAJOR;DARK_GRAY_THICK_LINE;2;roads;highway=motorway;Автомагистраль;1;
2;ROAD_NORMAL;DARK_GRAY_SEMITHICK_LINE;1;roads;highway=primary;Главная дорога;1;
3;ROAD_MINOR;DARK_GRAY_LINE;0;roads;highway=residential;Жилая улица;1;
64;WATER;WATER_FILL;1;water;natural=water;Водоем;1;
32;WATERWAY_MAJOR;WATER_THICK_LINE;2;waterways;waterway=river;Река;1;
129;POI_SMALL;DARK_GRAY_CIRCLE;0;pois;amenity=pharmacy;Аптека;1;cross
```

Точный набор классов объектов и стилей определяется текущим `features.csv`.

## 9.2. Сопоставление правил

Правила проверяются строго сверху вниз.

**Побеждает первое подходящее включённое правило.**

Поэтому более конкретные правила должны стоять перед более общими.

Пример:

```text
128;POI_BIG;...;place=city, capital=yes;Столица;1;circle
128;POI_BIG;...;place=city;Город;1;circle
```

Объект, подходящий под оба правила, классифицируется по первому.

Это правило также разрешает конфликты между логическими категориями, такими как `landuse` и `POI`.

Отдельного этапа переназначения нет, то есть нет:

```text
Remap_Code
Remap_Color
Remap_LOD
```

## 9.3. Выключенные правила

Если:

```text
Enabled = 0
```

правило игнорируется компилятором.

Объекты по такому правилу не создаются.

## 9.4. Классы объектов

`PG_class` задаёт семантическую классификацию PurrGO.

Примеры:

```text
NO_CLASS
ROAD_MAJOR
ROAD_NORMAL
ROAD_MINOR
ROAD_UNPAVED
ROAD_PATH
RAILWAY
LANDUSE_NATURAL
LANDUSE_HUMAN
WATER
WATERWAY_MAJOR
WATERWAY_MINOR
POI_BIG
POI_SMALL
```

Классы слоя `waterways` (`WATERWAY_MAJOR`, `WATERWAY_MINOR`) — линейные водные объекты. `WETLAND` и `GLACIER` — полигоны слоя `water`, которые прошивка рисует горизонтальной штриховкой (болото) и мелким узором-снежинкой (ледник) вместо сплошной чёрной заливки воды. `SAND` — полигон слоя `landuse` (пляж, песок, дюна, галька, осыпь), который прошивка рисует точечным узором вместо светло-серой заливки. Их коды перечислены в 8.1.1.

Бинарная карта хранит только числовой `Code`.

## 9.5. Стили отрисовки

`STYLE` определяет стиль отрисовки объекта.

Примеры:

```text
DARK_GRAY_THICK_LINE
DARK_GRAY_SEMITHICK_LINE
DARK_GRAY_LINE
DARK_GRAY_DOTTED_LINE
DARK_GRAY_DASHED_LINE
RAILWAY_LINE
WATER_THICK_LINE
WATER_LINE
LIGHT_GRAY_FILL
DARK_GRAY_FILL
WATER_FILL
DARK_GRAY_CIRCLE
DARK_GRAY_BIG_CIRCLE
```

Названия стилей в `.idx` как строки не хранятся.

Водные стили чёрные: `WATER_FILL` — чёрная заливка полигона с тёмно-серым контуром 1 px; `WATER_THICK_LINE` — простая чёрная линия 3 px (реки, каналы); `WATER_LINE` — простая чёрная линия 1 px (ручьи). У водных линий нет обводки.

## 9.6. Значки POI

`Icon` сейчас — метаданные, связанные с определениями POI.

Примеры:

```text
circle
cross
shop
cup
house
fuel
transport
airplane
attraction
```

Растровые ресурсы значков в формат карты не встраиваются.

Прошивка рисует POI значком 11×11 `purrgo_poi_icons[Type]` (`src/core/map/purrgo_poi_icons.c`): номер значка равен коду объекта, поэтому значки POI занимают номера `128..191`. Значки интерфейса (цель навигации `192`, путевая точка `193`, перекрестие центра карты `194`) используют диапазон `192..223`. Новый класс POI получает следующий свободный код в `128..191`, и его значок рисуется под тем же номером.

В режиме кружков прошивка рисует `POI_BIG` большим кругом, а любой другой код POI — малым.

Поле `Icon` сохранено для будущей поддержки нативных значков.

# 10. БАЗА АТРИБУТОВ (`.DB`)

Файл `.db` хранит текстовые атрибуты, например названия объектов.

Он содержит базу данных **dBase III (DBF)**, упакованную в контейнер PGO.

Payload DBF начинается со смещения файла:

```text
0x20
```

## 10.1. Заголовок DBF

Текущий формат использует:

```text
Magic byte       = 0x03
Размер заголовка = 129 байт (0x0081)
Размер записи    = 117 байт (0x0075)
```

Число записей хранится как 4-байтное значение little-endian.

Заголовок DBF содержит ровно три описателя полей:

```text
osm_id
code
name
```

Описатель каждого поля занимает 32 байта.

Терминатор заголовка:

```text
0x0D
```

## 10.2. Раскладка записи

Каждая обычная запись занимает 117 байт:

```text
+----------+------------+----------+----------------------+
| Признак  | osm_id     | code     | name                 |
| 1 байт   | 12 байт    | 4 байта  | 100 байт             |
+----------+------------+----------+----------------------+
```

Признак обычной записи:

```text
0x20
```

Смещение названия внутри записи — 17 байт, длина поля названия — 100 байт. Прошивка использует эти константы напрямую: запись `v` лежит в файле по смещению `32 + 129 + (v - 1) × 117`.

## 10.3. Фиктивная запись стандартного слоя

Стандартные слои карты используют специальную фиктивную запись из нулей с номером 1.

Фиктивная запись:

```text
117 байт 0x00
```

Именованные объекты используют:

```text
v2 = 2
v2 = 3
...
```

Таким образом:

```text
v2 = 1
```

обозначает фиктивную запись.

## 10.4. Слои без названий

Если стандартный слой не содержит именованных объектов, создание его файла `.db` можно пропустить.

Все объекты этого слоя тогда используют:

```text
v2 = 0
```

## 10.5. База POI

`.db` слоя POI использует ту же трёхполевую структуру DBF, но **не содержит** стандартной фиктивной записи.

Поэтому:

```text
v2 = 1
```

— первая физическая запись POI.

**У каждого узла данных POI `v2 ≥ 1`.** Компилятор записывает по одной записи на каждый POI, в том числе на POI без собственного названия (раздел 10.6). Для POI значение `v2 = 0` не производится; читатель должен трактовать `v2 = 0` как «записи нет».

В тексте V3 говорилось, что безымянные POI используют `v2 = 0`. Компилятор V3 так никогда не делал: он назначает запись каждому POI. V4 приводит текст в соответствие с реальным поведением.

В `.db` нет координат и нет обратной ссылки на узел `.idx`. Связь в обратном направлении (запись → положение) существует только в `search.idx` (раздел 21).

## 10.6. Поле названия

Поле `name` записи хранит название объекта в PurrGO-256 (`docs/font-encoding.md`), по одному байту на символ, дополненное до 100 байт. Компилятор формирует его так; правила нормативны для компилятора, и на них опирается `search.idx`.

1. **Выбор.** Первое непустое значение из тегов `short_name:ru`, `name:ru`, `short_name:be`, `name:be`, `int_name`, `short_name:en`, `name:en`, `short_name`, `name` (в таком порядке).
2. **Стоп-слова.** Если название начинается со стоп-слова (улица, площадь, кафе, hotel и подобные слова на русском, белорусском и английском; список в `purrgo_osmparser.py`), слово переносится в конец: `Кафе Пушкин` становится `Пушкин кафе`. Первая буква оставшейся части — заглавная, перенесённое слово — строчное.
3. **Пробелы.** Каждый пробел заменяется на `_`.
4. **Длина.** Название длиннее 100 байт обрезается до первых 98 символов (хвостовые `_` убираются) и дополняется `..`. **Для малого экрана название при компиляции не сокращается**: сокращение при выводе — задача читателя (раздел 10.6.1).
5. **POI без названия.** POI без тега названия получает в качестве названия значение первого тега своего правила `features.csv` (`camp_site`, `clothes`), обрезанное по правилу 4, без правила стоп-слов.
6. **Барьеры.** POI по правилу с тегом `barrier=…` без названия сохраняет пустое название.

Следствия, на которые опираются другие части формата:

* стоп-слово обычно стоит в **конце** названия, а не в начале;
* POI, названный по правилу 5, нельзя отличить по `.db` от POI, который действительно так называется; `search.idx` помечает такие POI флагом `UNNAMED` (раздел 21.4);
* названия слоёв `roads`, `landuse` и `water` подчиняются правилам 1–4.

### 10.6.1. Сокращение при выводе (справочно)

Компилятор V3 обрезал названия длиннее 22 символов до 20 символов плюс `..`, потому что название нужно было только для вывода на малый экран. Теперь название служит ещё и для поиска, и обрезка потеряла бы хвост названия и перенесённое в конец стоп-слово. Поэтому сокращение перенесено в читателя:

* подпись на карте: не более 22 символов; более длинное название выводится как первые 20 символов плюс `..` (внешний вид карты остаётся таким же, как в V3);
* строка списка (например, результатов поиска): сколько помещается по ширине экрана (около 29 символов шрифта 5×7 на экране 176 px), с тем же правилом `..`;
* при выводе `_` заменяется пробелом.

Читателю для вывода достаточно прочитать из поля начало нужной длины (прошивка уже читает только `max_len - 1` байт). Полное поле нужно только поиску для проверки хвоста названия.

### 10.6.2. Почему поле остаётся 100 байт

Вопрос, нужно ли увеличить поле названия из-за поиска, решён так: **не нужно**.

* Ограничение 22 символа было политикой компилятора, а не пределом поля: поле и так занимает 100 байт. Пока компилятор резал названия до 22 символов, 78 байт каждой записи не использовались; теперь они доступны поиску.
* Названия OSM длиннее 100 символов практически не встречаются, а такие названия обрезаются с признаком `..` (правило 4).
* Размер записи, смещение названия и размер заголовка DBF жёстко заданы в прошивке (раздел 10.2) и в заголовке DBF. Записи фиксированного размера, поэтому размер `.db` от длины названий не зависит: изменение политики ничего не стоит по размеру файла.
* Увеличение поля потребовало бы менять размер записи, заголовок и все константы прошивки и дало бы выигрыш только для названий, которые и так длиннее 100 символов.

Для ключей поиска предел названия не критичен: ключ строится по словам и занимает 16 байт на слово (раздел 21.7).

# 11. МЕТАДАННЫЕ КАРТЫ (`map.name`)

Каждый пакет карты PurrGO должен содержать файл `map.name`.

В отличие от `.idx`, `.mlp` и `.db`, `map.name` — текстовый файл, **не обёрнутый в бинарный заголовок PGO**.

Файл использует **строгий JSON** и содержит название карты и географический центр карты.

## 11.1. Структура JSON

Обязательная структура:

```json
{"centerLat":55.7558,"centerLon":37.6173,"mapName":"Moscow"}
```

Три обязательных поля:

| Поле        | Тип JSON | Описание                                |
| ----------- | -------- | --------------------------------------- |
| `centerLat` | число    | Широта центра карты в десятичных градусах |
| `centerLon` | число    | Долгота центра карты в десятичных градусах |
| `mapName`   | строка   | Название карты для человека             |

Порядок координат:

```text
centerLat = широта
centerLon = долгота
```

В отличие от координат в `.idx` и `.mlp`, координаты в `map.name` хранятся прямо как десятичные градусы в числах JSON.

## 11.2. Центр карты

`centerLat` и `centerLon` — центр, вычисленный по **общему BBox всех слоёв карты**, входящих в пакет.

Их используют просмотрщик карт на ПК и прошивка как начальный центр карты/камеры.

Центр — только метаданные. Он не заменяет пространственные BBox, хранимые в `.idx`.

## 11.3. Представление JSON

Текущий пакет карты PurrGO использует компактный JSON без лишних пробелов.

Компилятору следует сериализовать объект с разделителями JSON, эквивалентными:

```python
json.dumps(data, separators=(',', ':'))
```

Поэтому предпочтительное представление:

```json
{"centerLat":55.7558,"centerLon":37.6173,"mapName":"Moscow"}
```

а не:

```json
{
    "centerLat": 55.7558,
    "centerLon": 37.6173,
    "mapName": "Moscow"
}
```

Компактное представление сохраняет файл небольшим и совместимо с текущими требованиями к разбору JSON в прошивке.

## 11.4. Структура пакета карты

Полный пакет карты имеет такую структуру:

```text
<map>/
├── map.name
├── landuse.idx
├── landuse.mlp
├── landuse.db
├── water.idx
├── water.mlp
├── water.db
├── waterways.idx
├── waterways.mlp
├── waterways.db
├── roads.idx
├── roads.mlp
├── roads.db
├── pois.idx
├── pois.db
└── search.idx        (необязательный, раздел 21)
```

Файлы слоёв, не содержащих данных, могут быть опущены по правилам слоёв, определённым в других местах этой спецификации. Сам файл `map.name` обязателен.

### 11.4.1. Необязательные слои и совместимость

Слой `waterways` необязателен. Компилятор записывает `waterways.idx`, `waterways.mlp` и `waterways.db` только если исходные данные содержат хотя бы один включённый линейный водный объект; пустые фиктивные файлы для него не создаются.

Добавление нового слоя не меняет бинарный формат: структуры контейнера PGO, `.idx`, `.mlp` и `.db` те же, и версия формата остаётся V4. Читатель открывает файлы слоёв по имени и должен игнорировать файлы слоёв, которые не использует. Поэтому пакет с `waterways.*` корректен для читателя, не знающего этого слоя, а пакет без него корректен для читателя, который его знает.

`search.idx` необязателен так же: компилятор записывает его, только если запрошен индекс поиска, читатель, не знающий файла, его игнорирует, а читатель, знающий файл, работает и без него (тогда доступен только простой поиск).

## 11.5. Связь с бинарными файлами карты

`map.name` — метаданные уровня пакета:

```text
                    Пакет карты
                         │
             ┌───────────┴───────────┐
             │                       │
         map.name              Бинарные слои
             │                       │
       ┌─────┴─────┐          ┌──────┼──────┐
       │           │          │      │      │
    mapName     центр        .idx   .mlp    .db
```

`map.name` не содержит данных объектов, геометрии, данных пространственного индекса или записей атрибутов.

# 12. СЛОЙ POI

POI — точечные объекты, и записи геометрии `.mlp` им не нужны.

Узел данных POI хранит свою точку прямо в BBox:

```text
xmin == xmax
ymin == ymax
```

Координаты используют то же представление с фиксированной точкой:

```text
координата = градусы × 10⁷
```

Для POI:

```text
v1 = 0
```

Поле `Type` объекта определяет класс POI PurrGO.

Метаданные `Icon` происходят из `features.csv`, но текущая отрисовка использует нативное представление POI.

# 13. ИНВАРИАНТЫ ГЕОМЕТРИИ СЛОЁВ

Компилятор гарантирует, что тип геометрии согласован с целевым слоем.

Текущий контракт слоёв:

| Слой        | Геометрия                  |
| ----------- | -------------------------- |
| `roads`     | только линии               |
| `landuse`   | только полигоны            |
| `water`     | только полигоны            |
| `waterways` | только линии               |
| `pois`      | только точки               |

Прошивка может полагаться на этот инвариант и не обязана определять тип геометрии динамически.

Линейные водные объекты (реки, ручьи, каналы) поэтому хранятся в отдельном слое `waterways` и никогда в `water`. `waterways` использует ту же запись геометрии, что и `roads`: незамкнутая ломаная из одной части. Правила ориентации и замкнутости колец для него не применяются. Как и `roads`, слой не подписывается, а его `.db` можно опустить, если в нём нет именованных объектов (раздел 10.4).

Нарушение означает неверную карту, созданную компилятором.

# 14. ПОСТРОЕНИЕ ИНДЕКСА STR

Пространственный индекс `.idx` строится алгоритмом пакетной загрузки Sort-Tile-Recursive (STR), после чего сериализуется блоками.

Концептуально:

1. сгруппировать объекты по LOD;
2. отсортировать объекты по X центроида;
3. разделить их на пространственные полосы;
4. отсортировать каждую полосу по Y центроида;
5. разбить объекты на кластеры;
6. сформировать навигационные узлы;
7. вычислить охватывающие BBox;
8. повторять шаги 2–7 для навигационных узлов предыдущего уровня, пока в слое не останется не более `nav_fanout` узлов; этот слой становится корневым блоком;
9. назначить блоки и вычислить `child_block` (раздел 14.2);
10. сериализовать сектор заголовка и блоки секции LOD.

## 14.1. Ветвление (fan-out)

Ветвление выбрано так, чтобы полный блок помещался в один сектор:

```text
Навигационный блок:   18 × 28 байт = 504 байта   (nav_fanout  = 18)
Листовой блок:        20 × 25 байт = 500 байт    (leaf_fanout = 20)
```

Кластер узлов данных (уровень 0) имеет не более 20 детей. Кластер навигационных узлов (уровень ≥ 1) имеет не более 18 детей. В корневом слое не более 18 узлов.

В компиляторе это заменяет единственную константу `CHUNK_SIZE = 14` из V3 двумя константами.

## 14.2. Назначение блоков

После построения дерева компилятор:

1. упорядочивает узлы каждого уровня в порядке полос STR (в порядке их создания);
2. задаёт корневому блоку смещение `S + 512`;
3. назначает смещения остальных блоков группа за группой в порядке раздела 7.3, по 512 байт на блок;
4. записывает `child_block` в каждый навигационный узел;
5. заполняет нулями неиспользуемые байты каждого блока.

Одинаковую секцию LOD нельзя скопировать байтами из другого LOD, как это делал компилятор V3 для LOD с одинаковым числом объектов, потому что смещения внутри секции зависят от её положения в файле. Каждый LOD строится или перебазируется отдельно.

## 14.3. Размер (справочно)

Блок дополняется до 512 байт, даже если он не полон, поэтому `.idx` растёт по сравнению с V3. Проектная оценка — в 1,3–1,5 раза (для Беларуси около +25–30 МБ). Оценку нужно проверить с помощью `sim_map_io.py` на карте из CI.

# 15. МОДЕЛЬ КОМПИЛЯЦИИ КАРТЫ

Полный процесс компиляции:

```text
Данные OpenStreetMap
        │
        ▼
   Объекты OSM
        │
        ▼
   features.csv
        │
        │ первое подходящее включённое правило
        ▼
 Определение объекта PurrGO
        │
        ├── Code
        ├── PG_class
        ├── STYLE
        ├── LOD
        └── Layer
        │
        ├─────────────────┐
        ▼                 ▼
  Геометрия              POI
        │                 │
        ▼                 ▼
      .mlp              .idx
        │                 │
        └──────┐    ┌─────┘
               ▼    ▼
                 .db
```

Для обычных линейных и полигональных объектов:

1. определить `Code`;
2. определить `LOD`;
3. определить `Layer`;
4. вычислить целочисленный BBox;
5. записать геометрию в `.mlp`;
6. назначить `v1` на тело геометрии;
7. создать соответствующий узел данных;
8. назначить `v2`, если есть запись атрибутов;
9. вставить узел данных в пространственный индекс LOD.

Для нативных POI:

1. определить `Code`;
2. определить `LOD`;
3. определить `Layer = pois`;
4. вычислить координаты точки;
5. создать BBox узла данных нулевой площади;
6. задать `v1 = 0`;
7. назначить `v2` (у каждого POI есть запись, раздел 10.5);
8. вставить узел данных в пространственный индекс LOD.

Дополнительно, после компиляции `pois.db` и `pois.idx` (чтобы `v2` каждого POI был известен), компилятор записывает `search.idx` (раздел 21): назначает подтипы по `search_categories.csv`, режет названия на слова и записывает секции NAME и CAT и словарь.

# 16. МОДЕЛЬ РАЗБОРА В ПРОШИВКЕ

Прошивка не разбирает теги OSM.

Она работает с:

```text
.idx
.mlp
.db
```

и соответствующими числовыми определениями объектов PurrGO. Если есть `search.idx`, код поиска дополнительно использует его (раздел 21).

Концептуально:

```text
.idx
 │
 └── Узел данных
      │
      ├── BBox
      ├── Type ───────────────┐
      ├── v1 ──→ .mlp         │
      └── v2 ──→ .db          │
                              ▼
                   Определение объекта
                              │
                              ├── PG_class
                              ├── STYLE
                              └── параметры отрисовки
```

Пространственный обход выполняется по целочисленным BBox.

Для каждого блока парсер читает 512 байт одним запросом и проверяет BBox всех записей из ОЗУ. Навигационный узел, BBox которого не пересекает текущую видимую область, пропускается тем, что его `child_block` не читается. Узел данных, прошедший пространственную проверку, передаётся в отрисовку.

Парсеру следует держать по одному буферу 512 байт на уровень вложенности (не более `depth` буферов) или, если не хватает стека, копировать только те записи, которые прошли проверку, перед спуском.

Переходная прошивка читает `.idx` V3 и V4 и выбирает обход по magic SQT (раздел 0.3).

# 17. ИНВАРИАНТЫ БИНАРНОГО ФОРМАТА

Следующие свойства нормативны для V4:

1. Все контейнеры PGO имеют заголовок 32 байта.
2. Magic PGO — ровно `PGO`.
3. `.idx`, `.mlp`, `.db` и `search.idx` используют типы файлов `1`, `2`, `3` и `4`.
4. Все многобайтные целые — Little-Endian, если явно не указано иное.
5. Порядковые номера записей геометрии `.mlp` — Big-Endian.
6. Координаты — знаковые `int32` с точностью `10⁻⁷` градуса.
7. Узлы данных `.idx` — ровно 25 байт.
8. Навигационные узлы `.idx` — ровно 28 байт.
9. `v1` обычного узла данных указывает на тело геометрии в `.mlp` относительно начала payload `.mlp`.
10. Локальный заголовок `.mlp` в цель `v1` не входит.
11. Секции SQT начинаются с magic `SQT\x02`, топологии `2` и сектора заголовка 512 байт.
12. Смещения LOD, размеры секций и блоки кратны 512; первое смещение LOD — `0x200`.
13. Блок содержит не более 18 навигационных узлов или 20 узлов данных; неиспользуемые байты блока — нули.
14. `child_block` — абсолютное смещение блока с детьми, и `child_block` больше смещения блока, в котором лежит узел.
15. Блоки хранятся в порядке раздела 7.3; блоки детей узлов одного блока идут подряд.
16. Пустые LOD по-прежнему содержат сектор заголовка SQT 512 байт.
17. POI не используют записи геометрии `.mlp`.
18. Координаты POI представлены BBox узла данных нулевой площади.
19. У каждого узла данных POI `v2 ≥ 1`.
20. Сопоставление правил OSM использует семантику «побеждает первое совпадение».
21. Выключенные правила `features.csv` игнорируются.
22. Теги OSM и текстовые определения объектов в `.idx` не хранятся.
23. Тип геометрии определяется целевым слоем.
24. Поле названия в `.db` занимает 100 байт; при компиляции название не сокращается до 22 символов.
25. Зарезервированные поля заголовка PGO и зарезервированные байты заголовка SQT не имеют текущей семантики времени выполнения и равны нулю.

# 18. СВЯЗИ МЕЖДУ ФАЙЛАМИ

Связь между тремя бинарными файлами:

```text
.idx
 │
 ├── Узел данных.Type ────→ features.csv / определение объекта PurrGO
 │
 ├── Узел данных.v1 ──────→ тело геометрии в .mlp
 │
 └── Узел данных.v2 ──────→ запись .db
```

Для нативных POI:

```text
.idx
 │
 ├── Узел данных.Type ────→ определение POI
 ├── Узел данных.BBox ────→ координаты точки
 ├── v1 = 0
 └── v2 ──────────────────→ запись POI в .db
```

Для необязательного индекса поиска:

```text
search.idx
 │
 ├── record.db_idx ───────→ запись pois.db (= v2 узла данных POI в pois.idx)
 ├── record.lon, lat ─────→ точка POI (= BBox узла данных POI)
 └── record.code ─────────→ определение POI (= Type узла данных)
```

Такое разделение сохраняет компактность бинарного представления времени выполнения и оставляет классификацию, специфичную для OSM, компилятору карт на ПК.

# 19. ОГРАНИЧЕНИЯ РЕАЛИЗАЦИИ

Бинарный формат карты рассчитан на прошивку с ограниченными ресурсами.

Реализации на STM32 следует:

* использовать целые типы фиксированной ширины;
* работать прямо с координатами с фиксированной точкой;
* избегать арифметики с плавающей точкой в рабочем пути карты и навигации;
* избегать динамического выделения памяти там, где это практично;
* полагаться на инварианты геометрии и слоёв, которые гарантирует компилятор;
* отвергать некорректные бинарные структуры, а не пытаться их восстановить.

Компилятор на стороне ПК не подчиняется ограничению на арифметику времени выполнения STM32 и может использовать арифметику с плавающей точкой там, где её требуют алгоритмы компиляции.

# 21. ИНДЕКС ПОИСКА (`search.idx`)

## 21.1. Назначение и статус

`search.idx` позволяет искать POI по части названия и по слову-категории («кафе», «hotel»), не читая весь `pois.db`. Без него название и положение POI дёшево связать нельзя: в `pois.db` нет координат, а в `pois.idx` нет названий.

Файл **необязателен**:

* нет файла → доступен только простой поиск (категория по коду объекта, ближайшие объекты); ему нужны только `pois.idx` и `pois.db`;
* файл, не прошедший проверку (раздел 21.10), игнорируется, как будто его нет; это никогда не фатальная ошибка карты.

`search.idx` — файл уровня пакета рядом с `pois.idx` и `pois.db` (раздел 11.4). Компилятор записывает его в том же запуске, что и `pois.*`.

## 21.2. Раскладка файла

```text
+------------------------------+ 0x000
| Заголовок PGO (32 байта)     |   Тип файла = 4
+------------------------------+ 0x020
| Заголовок SRCH (64 байта)    |
+------------------------------+ 0x060   ← dict_offset
| Словарь                      |
+------------------------------+
| нулевое заполнение до 512    |
+------------------------------+         ← name_offset (кратно 512)
| секция NAME                  |
| (нули до границы 512)        |
+------------------------------+         ← cat_offset  (кратно 512)
| секция CAT                   |
| (нули до границы 512)        |
+------------------------------+ конец файла
```

В заголовке PGO `Тип файла` равен `4`; три поля смещений LOD и резервные поля — нули. `Размер payload` — размер файла минус 32.

Обе секции начинаются со смещения, кратного 512, и дополняются нулями до кратного 512, поэтому бинарный поиск затрагивает целые секторы SD (16 записей на сектор). Секция с нулём записей имеет `count = 0`, а её смещение указывает на конец предшествующих данных (по-прежнему кратно 512, не за концом файла).

## 21.3. Заголовок SRCH

Заголовок начинается со смещения файла `0x20`. Смещения в таблице отсчитываются от этой позиции.

| Смещение | Размер | Тип       | Описание                                                                         |
| -------: | -----: | --------- | -------------------------------------------------------------------------------- |
| `0x00`   |      4 | `char[4]` | Magic: `SRCH`                                                                    |
| `0x04`   |      2 | `uint16`  | Версия: `1`                                                                      |
| `0x06`   |      2 | `uint16`  | Размер записи: `32`                                                              |
| `0x08`   |      4 | `uint32`  | Флаги: `0`                                                                       |
| `0x0C`   |      4 | `uint32`  | `db_records` — число записей в `pois.db`, для которого построен индекс           |
| `0x10`   |      4 | `uint32`  | `name_offset` — абсолютное смещение файла секции NAME                            |
| `0x14`   |      4 | `uint32`  | `name_count` — число записей в NAME                                              |
| `0x18`   |      4 | `uint32`  | `cat_offset` — абсолютное смещение файла секции CAT                              |
| `0x1C`   |      4 | `uint32`  | `cat_count` — число записей в CAT                                                |
| `0x20`   |      4 | `uint32`  | `dict_offset` — абсолютное смещение файла словаря: `0x60`                        |
| `0x24`   |      4 | `uint32`  | `dict_size` — размер словаря в байтах                                            |
| `0x28`   |      4 | `uint32`  | `range_offset` — резерв под каталог диапазонов; в версии 1 равен `0`             |
| `0x2C`   |      4 | `uint32`  | `range_count` — резерв под каталог диапазонов; в версии 1 равен `0`              |
| `0x30`   |     16 | `uint8[]` | Резерв; должен быть нулями                                                       |

Размер заголовка — 64 байта. Читатель, обнаруживший `Версия ≠ 1` или `Размер записи ≠ 32`, игнорирует файл.

## 21.4. Запись

Обе секции используют одну и ту же 32-байтную запись. Бинарная раскладка:

```text
<iiIBBBB16s
```

| Смещение | Размер | Тип         | Описание                                                               |
| -------: | -----: | ----------- | ---------------------------------------------------------------------- |
| `0x00`   |      4 | `int32`     | `lon` — долгота, `10⁻⁷` градуса                                        |
| `0x04`   |      4 | `int32`     | `lat` — широта, `10⁻⁷` градуса                                         |
| `0x08`   |      4 | `uint32`    | `db_idx` — номер записи POI в `pois.db` (`v2` узла данных POI)         |
| `0x0C`   |      1 | `uint8`     | `code` — код объекта `Type` POI (раздел 8.1.1, диапазон `128..191`)    |
| `0x0D`   |      1 | `uint8`     | `subtype` — подтип поиска (раздел 21.8); `0` = нет                     |
| `0x0E`   |      1 | `uint8`     | `flags`                                                                |
| `0x0F`   |      1 | `uint8`     | `key_len` — число значащих байт `key`, `0..16`                         |
| `0x10`   |     16 | `uint8[16]` | `key` — нормализованный ключ (раздел 21.7), дополненный нулевыми байтами |

`lon`, `lat`, `db_idx` и `code` — копии BBox, `v2` и `Type` узла данных POI в `pois.idx`.

`flags`:

| Бит | Имя         | Значение                                                                          |
| --: | ----------- | --------------------------------------------------------------------------------- |
|   0 | `SECONDARY` | только NAME: ключ — слово названия, не первое                                     |
|   1 | `UNNAMED`   | только CAT: у POI нет собственного названия (раздел 10.6, правила 5 и 6)          |
|   2 | `KEY_TRUNC` | нормализованное слово было длиннее 16 байт; в `key` первые 16                     |
| 3–7 | —           | резерв; должны быть нулями                                                        |

Сравнение ключей для упорядочивания и поиска — побайтовое беззнаковое сравнение 16 байт `key` (`memcmp`) независимо от `key_len`. Поскольку в ключах нет нулевых байт (раздел 21.7), более короткий ключ идёт перед любым более длинным, который с него начинается.

## 21.5. Секция NAME

NAME — индекс названий POI по словам.

**Содержимое.** Для каждого именованного POI (название не подставлено по правилу 5 раздела 10.6 и не пусто) компилятор записывает:

* одну **первичную** запись для первого слова названия (`SECONDARY = 0`);
* одну **вторичную** запись (`SECONDARY = 1`) для каждого следующего слова, не более 3 вторичных записей на POI.

Слова вырезаются из названия, как описано в разделе 21.7. Вторичное слово короче 2 байт после нормализации не индексируется. Слово, ключ которого совпадает с ключом более раннего слова того же POI, повторно не индексируется.

У всех записей одного POI одинаковые `lon`, `lat`, `db_idx`, `code` и `subtype`. `subtype` равен `0`, если ни одно правило `search_categories.csv` не подошло POI.

**Порядок.** Записи отсортированы по `key` (раздел 21.4), затем по `db_idx`, затем первичная перед вторичной.

**Использование.** Все названия, содержащие слово, начинающееся с префикса `p` (`1 ≤ |p| ≤ 16`), образуют один непрерывный диапазон записей: от первой записи с `key ≥ p`, дополненным `0x00`, до первой записи с `key > p`, дополненным `0xFF`. POI может встретиться в диапазоне дважды (два слова с одним префиксом); читатель сливает дубликаты по `db_idx`.

Поскольку стоп-слово названия хранится в его конце (раздел 10.6, правило 2), оно, как правило, оказывается вторичной записью: название `Пушкин кафе` находится и по `пуш` (первичная запись), и по `кафе` (вторичная запись).

Название теперь не сокращается при компиляции (раздел 10.6), поэтому слова из хвоста длинного названия тоже индексируются (первые 4 слова).

Компилятор может не включать классы POI, которые не являются осмысленной целью поиска (например, барьеры, код `152`). Читатель не должен считать, что каждый POI из `pois.idx` есть в `search.idx`.

## 21.6. Секция CAT

CAT — индекс POI по категории (подтипу).

**Содержимое.** Одна запись на каждый искомый POI с `subtype ≠ 0`, включая безымянные POI (`UNNAMED = 1`, `key_len = 0`). Для именованного POI `key` — ключ его первого слова (раздел 21.7); `SECONDARY` равен `0`.

**Порядок.** Записи отсортированы по `subtype`, затем по коду Мортона точки, затем по `db_idx`.

Код Мортона — 64-битное значение, вычисляемое по точке так:

```text
X = lon + 1 800 000 000      (как uint32)
Y = lat +   900 000 000      (как uint32)
morton = побитовое чередование X и Y: бит i числа X → бит 2·i, бит i числа Y → бит 2·i + 1
```

Код не хранится; читатель вычисляет его по `lon` и `lat` записи, когда нужно.

**Использование.** Записи одного подтипа идут подряд, поэтому запрос по категории читает один участок записей. Внутри участка порядок Мортона держит близкие объекты близко в файле, поэтому запрос объектов около точки может сузить участок бинарным поиском по коду Мортона ограничивающего квадрата и затем отфильтровать по расстоянию. Нужен ли поверх этого каталог диапазонов (`range_offset`), решается после замера на реальной карте (приложение A).

## 21.7. Нормализация ключа

Ключ вычисляется по байтам PurrGO-256 (`docs/font-encoding.md`), в той же кодировке, что и поле `name` в `pois.db`. Компилятор и прошивка обязаны использовать одну и ту же функцию; она задаётся таблицей из 256 байт, генерируемой из таблицы шрифта и проверяемой так же, как `tests/check_pgo_text_table.py`.

**Свёртка.** Каждый байт `b` названия заменяется:

| Входные байты   | Результат               | Смысл                                              |
| --------------- | ----------------------- | -------------------------------------------------- |
| `0x41..0x5A`    | `b + 0x20`              | латиница: верхний регистр → нижний                 |
| `0x80..0x9F`    | `b + 0x20`              | кириллица: верхний регистр → нижний                |
| `0xC0..0xCF`    | `b + 0x10`              | расширенная кириллица: верхний регистр → нижний    |
| `0xF0`, `0xF1`  | `0xA5`                  | `Ё`, `ё` → `е`                                     |

**Байты слова.** После свёртки байт является *байтом слова*, если он входит в один из диапазонов:

```text
0x30..0x39    цифры
0x61..0x7A    латинские буквы
0xA0..0xBF    кириллические буквы
0xD0..0xDF    расширенные кириллические буквы
0xE0..0xEF    коды глифов расширенной латиницы
```

Любой другой байт (управляющие коды, пробел, `_`, `-`, `(`, `)`, `.`, `,`, кавычки, `0xF2..0xFF` и так далее) — **разделитель**.

**Слова.** Название режется на слова по разделителям; пустые слова отбрасываются. Для ключа слово не длиннее 16 байт: более длинное слово обрезается до первых 16 байт и выставляется `KEY_TRUNC`. Первое слово — первичное.

**Алфавит ключей.** Ключ содержит только байты слова, поэтому в нём никогда нет `0x00` и `0xFF`.

Латинские буквы с диакритикой PurrGO-256 уже объединил в один код глифа (`Č Ć Ç` → `0xE4`); ключ их не различает. Завершающее `..` у сокращённого названия (раздел 10.6, правило 4) состоит из разделителей и пропадает.

Та же нормализация применяется к тексту, набранному пользователем. `Ё` и `Е` в запросе не различаются.

## 21.8. Подтипы и словарь

**Подтип** — класс тоньше, чем код объекта: `tourism=hostel` и `tourism=hotel` имеют один код, но разные подтипы. Номера подтипов — `1..255`; `0` означает «нет». Номер подтипа, который появлялся в скомпилированных картах, никогда не назначается другому классу.

### 21.8.1. `search_categories.csv`

Файл — вход компилятора (как `features.csv`) и в пакет карты не входит. Он лежит в `tools/map-compiler/`.

```text
Group;Subtype;Keywords_RU;Keywords_EN;OSM_Tags
```

| Поле          | Описание                                                                                  |
| ------------- | ----------------------------------------------------------------------------------------- |
| `Group`       | идентификатор набора подтипов (например, жильё: отель, хостел, кемпинг, гостевой дом, укрытие) |
| `Subtype`     | номер подтипа `1..255`; в строке группы пусто                                             |
| `Keywords_RU` | слова категории на русском через запятую                                                  |
| `Keywords_EN` | слова категории на английском через запятую                                               |
| `OSM_Tags`    | то же выражение, что `OSM_Tags` в `features.csv` (`tourism=hostel`); в строке группы пусто |

Строка с заполненным `Subtype` назначает подтип POI и задаёт ключевые слова этого подтипа. **Строка группы** (`Subtype` и `OSM_Tags` пусты) задаёт ключевые слова, которые означают все подтипы группы.

Компилятор назначает подтип POI по **первой подходящей строке** сверху вниз, проверяя теги OSM объекта. POI, не подошедший ни под одну строку, получает `subtype = 0`.

Правила с `Enabled = 0` в `features.csv` не создают POI в карте и поэтому не могут быть найдены. Поиск объектов, которые не рисуются, требует отдельного механизма (раздел 22).

### 21.8.2. Словарь

Словарь перечисляет ключевые слова и подтипы, которые обозначает каждое слово. Он хранится по `dict_offset`, поэтому словарь можно расширять перекомпиляцией карты, не меняя прошивку.

| Смещение | Размер | Тип      | Описание                         |
| -------: | -----: | -------- | -------------------------------- |
| `0x00`   |      2 | `uint16` | Число ключевых слов `n`          |
| `0x02`   |      2 | `uint16` | Размер записи: `48`              |
| `0x04`   |      4 | `uint32` | Резерв; должен быть нулём        |

За заголовком следуют `n` записей по 48 байт, так что `dict_size = 8 + 48 · n`:

| Смещение | Размер | Тип         | Описание                                                                |
| -------: | -----: | ----------- | ----------------------------------------------------------------------- |
| `0x00`   |     16 | `uint8[16]` | нормализованное ключевое слово (одно слово, раздел 21.7), дополненное нулевыми байтами |
| `0x10`   |     32 | `uint8[32]` | маска подтипов: бит `s mod 8` байта `s div 8` установлен для подтипа `s` |

Записи отсортированы по ключевому слову (побайтово, как ключи), слова уникальны: если одно нормализованное слово встречается в нескольких строках (в том числе в русском и английском списках), их маски объединяются по OR. Маска слова из строки группы содержит все подтипы группы. Бит 0 — ноль. Ключевое слово длиннее 16 байт недопустимо.

## 21.9. Семантика запроса (справочно)

Формат рассчитан на следующее использование; точный интерфейс описан в `design/poi-search.md`.

1. Текст нормализуется и режется на слова (раздел 21.7).
2. Слово — **слово категории**, если оно совпадает с ключевым словом словаря или является его префиксом длиной не менее 3 байт. Маски подтипов всех подошедших слов объединяются по OR. Все остальные слова — **префиксы названия**.
3. Только слова категории → читаются участки секции CAT для подтипов маски.
4. Есть хотя бы один префикс названия → первый префикс выбирает диапазон в NAME (раздел 21.5); записи фильтруются по маске подтипов, если она есть, а остальные префиксы названия проверяются по полному названию из `pois.db` у кандидатов. Запрос из двух частей — это И: «кафе пуш» — категория «кафе» и слово названия на «пуш».
5. Результат — ближайшие объекты: дубликаты по `db_idx` сливаются, в массиве фиксированного размера хранятся первые N по расстоянию.
6. Если новый запрос продолжает предыдущий, диапазон поиска предыдущего запроса можно сужать, а не начинать заново.

Префикс из одного байта может выбрать большую часть секции NAME; ограничить радиус или потребовать два байта — решение прошивки (приложение A).

## 21.10. Проверка

Читатель проверяет `search.idx` перед использованием и игнорирует файл, если любая проверка не прошла:

1. заголовок PGO корректен, `Тип файла = 4`, payload помещается в файл;
2. `Magic = SRCH`, `Версия = 1`, `Размер записи = 32`;
3. `name_offset`, `cat_offset` и `dict_offset` лежат внутри файла, `name_offset` и `cat_offset` кратны 512, а секции расположены после словаря в порядке словарь, NAME, CAT без перекрытий;
4. `name_offset + 32 · name_count` и `cat_offset + 32 · cat_count` не превышают размер файла;
5. `db_records` равно числу записей в `pois.db`, чтобы не использовался индекс, построенный для другого `pois.db`;
6. `range_offset = 0` и `range_count = 0`;
7. `dict_size = 8 + entry_size · n`, и словарь помещается в файл.

Читатель, читающий записи по одной, дополнительно отвергает запись с `db_idx = 0` или `db_idx > db_records`, `key_len > 16` или с выставленными резервными битами флагов.

Аудит карты (`tests/audit_maps.py`) дополнительно проверяет порядок обеих секций, уникальность и порядок записей словаря, то, что каждый `db_idx` встречается в `pois.idx` с теми же координатами и кодом, и то, что ключ каждой записи можно пересчитать по её записи в `pois.db`.

## 21.11. Размер (справочно)

```text
NAME   = число именованных POI × 32 байта × ≈1,7   (одна первичная и в среднем ≈0,7 вторичной записи)
CAT    = число POI с subtype ≠ 0 × 32 байта
dict   = 8 + 48 × число ключевых слов
```

Размеры для карты Беларуси нужно измерить на карте из CI. Они определяют, оставлять ли запись 32 байта (приложение A).

# 22. ТОЧКИ РАСШИРЕНИЯ

Следующие расширения в V4 не входят. Формат оставляет под них место, то есть их можно добавить без смены версии V4 файлов `.idx`:

* **Каталог диапазонов** в `search.idx`: поля заголовка `range_offset` и `range_count` (раздел 21.3). Он перечислял бы диапазоны кода Мортона подтипа, чтобы запрос по категории читал только ближние участки.
* **POI только для поиска**: POI, которые не рисуются на карте, но находятся поиском (колонка `features.csv`, отдельная отметка в `search.idx`).
* **Транслитерация** (`kafe` → `Кафе`): может выполняться в читателе дополнительными ключами в NAME либо преобразованием перед запросом; таблица ключей раздела 21.7 при этом расширяется.
* **Улицы из `roads.db`**: ещё одна секция `search.idx` для названий дорог; нужна обратная ссылка от названия дороги к геометрии.
* **Общие секции LOD**: два смещения LOD указывают на одну секцию, когда LOD равны. Читатель V4, вычисляющий конец секции по следующему смещению LOD, это не поддерживает; поле `section_size` сектора заголовка зарезервировано для этой цели.
* **Упаковка блоков**: несколько малых блоков в одном секторе. Правило 4 раздела 7.3 (блоки детей подряд) исключает её в V4.

# ПРИЛОЖЕНИЕ A. ОТКРЫТЫЕ ВОПРОСЫ ЧЕРНОВИКА

Это приложение удаляется, когда вопросы будут решены.

1. **Заголовок SQT.** `docs/design/pgo-v4.md` меняет только magic. Этот черновик дополнительно расширяет заголовок до сектора 512 байт с размером блока, размером секции и пределами ветвления (раздел 5.1), чтобы адрес каждого блока оставался выровненным, а заголовок проверялся по реальной протяжённости секции.
2. **Выравнивание `.idx`.** Смещения LOD кратны 512, первый LOD начинается с `0x200`; 480 байт после заголовка PGO — заполнение (раздел 4.1).
3. **Блоки детей подряд** (раздел 7.3, правило 4) в этом черновике нормативны. Они позволяют читать детей блока многосекторным чтением, но исключают упаковку и совместное использование блоков.
4. **Ветвление** 18 (навигационные) и 20 (листовые), как в проектном документе. Неполный блок стоит целого сектора.
5. **Проверить в прошивке:** текст V3 говорил «безымянный POI → `v2 = 0`», а компилятор записывал запись на каждый POI. V4 следует компилятору (раздел 10.5). Нужно проверить, что код прошивки нигде не зависит от `v2 = 0` для POI.
6. **Длина названия.** Поле `name` остаётся 100 байт, меняется политика компилятора: название не сокращается до 22 символов (раздел 10.6). Нужно изменить `_sanitize_name_cached` и `_resolve_name` в `purrgo_osmparser.py` и добавить сокращение при выводе в прошивке: буфер `name_buf[64]` в `map_idx.c` сейчас сам по себе ограничит подпись до 63 символов, а подписи карты должны оставаться не длиннее 22 символов (раздел 10.6.1).
7. **Параметры индекса поиска**, которые решаются после замера: размер записи 32 или 16 байт, каталог диапазонов, минимальная длина префикса в один байт.
8. **`search_categories.csv`:** соглашение о строках групп и 256-битная маска подтипов ключевого слова (раздел 21.8) — предложения этого черновика.
9. **Безымянные POI.** Флаг `UNNAMED` выставляется для обоих видов безымянных POI (подставленное значение тега и пустое название); пустые — это барьеры, и по ним поиск не ведётся.
