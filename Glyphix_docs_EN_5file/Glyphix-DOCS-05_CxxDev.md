# Application installation process

Glyphix is an application framework for embedded devices. After a device leaves the factory, the end user or manufacturer still needs to add apps to the device—just like installing apps on a phone. But on resource-constrained MCUs, what exactly "installing an app" means, and how the framework finds and launches it, is not as well-known as it is on mobile phones.

This document will introduce the complete process of installing → starting → uninstalling an application package on the device, and explain how directory configuration affects the search, update and uninstallation of applications.

## "Install app" on device

A Glyphix application is delivered as a `.pkg` file - this is a read-only resource container that contains the application's manifest (`manifest.json`), JavaScript code, images and other resources. There is no unpacking when the application is running, and the framework reads files directly from `.pkg` on demand.

**Installing** an application essentially does two things: put the `.pkg` file into a directory on the device that will be scanned by the framework, and register its package name into the package database. After registration, the framework can find the corresponding `.pkg` through the package name and start it.**Uninstall** is the reverse operation: delete the `.pkg` file, clean up the data generated by the application, and log out from the database.

::: tip resource bundle format
Use the complete `.pkg` resource file when running, rather than the unzipped directory. This bundle mode is also common in game engines, because the application resource bundle will only read but not write. The bundle mode can reduce the fragmentation of the file system and avoid a bunch of small files from overly occupying the inode of the file system.
:::

There are two roles involved here, and this tutorial is geared toward the latter:
- **Application Developer**: Write applications in JavaScript, build `.pkg` files through the `gx build` command and deliver them.
- **Platform Developer**: Integrate the Glyphix runtime on the device, configure the directory where the application is stored, and call the installation and startup interface in C++.What you get is a `.pkg` file, and the goal is to make it run.

::: tip
This tutorial assumes that you already have a working Glyphix platform skeleton (`Application` + `JsVM` + `AppletKit`).If you haven't already, refer to the `examples/emulator` examples that come with the SDK.
:::

## Preparation

Before starting, please make sure the following conditions are in place:

- A working Glyphix platform. The minimal skeleton is as follows, and all subsequent operations are performed in this context.
- A `.pkg` file to be installed. You can get it from the application developer, or build a sample application yourself using `gx build`.This tutorial assumes that the file name is `com.example.demo.pkg` and the package name is `com.example.demo` (the package name is written in the application's [`manifest.json`](/framework/application/manifest.md#package)).
- A writable partition on the device, used to store `.pkg` files and application runtime data.`/data` is used below to represent this partition.

A simple Glyphix platform skeleton looks like this (this is not pseudocode, it's that simple):

```cpp
#include "gx_application.h"
#include "gx_appletkit.h"
#include "gx_jsvm.h"
#include "gx_widget.h"

using namespace gx;

int main() {
Application app{new MyPlatform}; // Platform adaptation, need to be connected according to the device
JsVM vm; // JavaScript runtime
Widget window; //The parent window of all applications
AppletKit kit(&window, "/pkgs.db"); // The second parameter is the package database path
//...The configuration and installation code of this tutorial is written here
return app.exec();
}
```

::: The second parameter of tip `AppletKit`
It points to a "package database" file (such as `/pkgs.db`).`AppletKit` uses it to record information about installed applications. You can get a `PackageDatabase` object through `kit.database(ADBT_Applet)` to query the list of installed applications, which will be used later.
:::

## Tell the framework where to place the application

Before installing any application, you must first tell Glyphix the locations of two directories: **application package directory** (storage `.pkg` files) and **application data directory** (storage data generated when the application is run).The two have different responsibilities, so don't confuse them.

### Application package directory

Application package directories are managed by `EnvPath::packages()`.It is a list, each entry in the list points to a directory where `.pkg` is stored. This list bears multiple semantics at the same time, and understanding them is the basis for all subsequent configurations:

- **Search**: When the framework needs to load a resource like `pkg://com.example.demo/...`, it will traverse the list **from front to back** and look for `com.example.demo.pkg` in each directory. The first hit will be loaded.
- **Installation**: When calling the installation interface, the new package is **fixedly written to the last directory** in the list.
- **Uninstall**: When uninstalling, scan from front to back and delete from the first directory containing the package.

Because installation always falls at the end of the list, and search and uninstallation start from the head of the list, the order of the directories in the list determines their role: the directory at the front is suitable for applications that "come with the factory and do not want to be overwritten"; the directory at the back is suitable for applications that are "subsequently installed by the user."

::: important precondition
Before calling the installation interface, the `packages()` list must have at least one directory, and the last directory in the list (the installation target) must exist and be writable. Otherwise the installation will fail directly.
:::

The configuration method is to append directories to the list during the platform initialization phase:

```cpp
#include "gx_environment.h"
using namespace gx;

// Called after Application construction and before installation/startup
EnvPath::packages().emplace_back("/data/apps");
```

### Application data directory

When the application is running, it requires writable space to store cache, files, temporary data, etc. These directories are configured with `EnvPath::setEntry(role, path)`, with each role corresponding to a purpose. Their semantic contract is as follows:

| Role | Meaning | Typical Path |
|:---|:---|:---|
| `AppletCache` | Application writable cache, the framework can clean and rebuild when space is tight | `/data/cache` |
| `AppletFiles` | Application private files, persisted, not automatically cleaned | `/data/files` |
| `AppletMass` | Large file storage (such as media resources), large capacity | `/data/mass` |
| `AppletTemp` | Temporary files, which can be cleaned after the application exits | `/data/temp` |
| `AppletStorage` | Application persistent storage | `/data/storage` |
| `LoggingDirectory` | Framework log directory | `/logs` |

**Data Isolation**: The framework creates independent subdirectories for each application in the above directory by package name. For example, the private files of application `com.example.demo` fall under `/data/files/com.example.demo/`.You don't need to manually manage these subdirectories, the framework automatically creates and cleans them during installation and uninstallation.

In addition, there is a special role `GlobalPackage`, which points to a globally shared `.pkg` (such as `/global.pkg`). All applications can read public resources such as fonts and icons through the `pkg:///...` protocol. It does not belong to an application and is usually burned with the firmware.

Configuration example:

```cpp
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
```

::: tip timing
`EnvPath` is reset to the default configuration when `Application` is constructed, so custom configuration should be done immediately after `Application` is constructed and before any `installPackage`/`launch` calls. Late configuration can lead to unexpected behavior.
:::

### Configuration example

Combining the two types of directories, the minimum usable initialization fragment is as follows:

```cpp
Application app;
// Application package directory: at least one writable directory
EnvPath::packages().emplace_back("/data/apps");
// Application data directory: adjusted according to the actual partition of the device
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");

JsVM vm;
Widget window;
AppletKit kit(&window, "/pkgs.db");
```

## Install an application

Before calling `installPackage`, you need to confirm:

1. The `EnvPath::packages()` list is not empty, and its last directory exists and is writable.
2. `AppletKit` is constructed (installation requires writing to the package database it manages).
3. The `.pkg` file to be installed already exists in the device file system (for example, at `/tmp/com.example.demo.pkg`).
4. If using the default version verification strategy (`NormalVerify`), the device's vendor/product ID should have been configured; otherwise the installation will return `InvalidDevice` due to device ID verification failure.

### Call installation

The installation interface is `AppletKit::installPackage(fileUri, policy)`, the first parameter is the `.pkg` file path, the second is the verification policy, which can be omitted (default `NormalVerify`):

```cpp
auto status = kit.installPackage("/tmp/com.example.demo.pkg");
if (status != AppletKit::ValidPackage) {
LogError() << "install failed:" << AppletKit::packageStatusMessage(status);
return;
}
LogInfo() << "install ok";
```

The return value is `PackageStatus`, which has several common meanings:

| Status | Meaning |
|:---|:---|
| `ValidPackage` | Installation successful |
| `FileNotExists` | `.pkg` file path does not exist |
| `InvalidPackage` | The package is corrupt or the manifest is unreadable |
| `InvalidVersion` | The version does not meet the verification policy |
| `InvalidDevice` | Device vendor/product ID does not match |
| `FileIOError` | The copy failed, usually because the installation directory is not writable or there is insufficient space |

The verification strategy `PackageVerify` determines how strict the framework is on installing packages:

| Policy | Version Verification | Device ID Verification |
|:---|:---|:---|
| `NormalVerify` (default) | The new version must not be lower than the installed version | Required |
| `UpgradeOnly` | Must be strictly higher than the installed version | Required |
| `IgnoreVersion` | Skip | Required |
| `NoVerify` | Skip all, as long as the package is legal | Skip |

::: tip
If you encounter `InvalidDevice` or `InvalidVersion` during first installation and debugging, you can temporarily use `AppletKit::NoVerify` to eliminate verification interference, confirm that there is no problem with the installation process itself, and then restore the official strategy.
:::

### What will the installation do?

`installPackage` guarantees the following external effects:

- Verify that the `.pkg` file is legal and check the version and device ID according to the selected policy.
- If an application with the same name is running, it will be terminated first to avoid file occupation or data conflicts.
- Copy the `.pkg` file to the last directory in the `packages()` list, with the file name `<package-name>.pkg`.If a file with the same name already exists, it will be overwritten.
- Register the application in the package database, recording its installation path and `pkg://<package-name>` access URI.
- If the application manifest declares a URI scheme (for example, registering itself as a handler of the `ime` input method), register it as well.
- Emit a "package changed" notification to make other parts of the framework aware of the new application.

::: important package verification capability
`AppletKit::installPackage()` itself has no file integrity or signature verification capabilities. Equipment manufacturers need to develop relevant functions by themselves, verify the `.pkg` file before calling `installPackage()`, and ensure the consistency of file system power-off protection, rollback, etc. during the installation process. The framework only ensures that the installation is completed under the premise that the `.pkg` file is legal, readable, and writable.
:::

### Watchlist

After the installation returns `ValidPackage`, you can verify the effect in the following ways:

- You should see the file: `/data/apps/com.example.demo.pkg` in the installation directory.
- `kit.database(ADBT_Applet)->contains("com.example.demo")` should return `true`.
- The list returned by `kit.installedApplets()` should contain `"com.example.demo"`.

```cpp
EXPECT_TRUE(File::exists("/data/apps/com.example.demo.pkg"));
EXPECT_TRUE(kit.database(ADBT_Applet)->contains("com.example.demo"));
EXPECT_NE(std::find(kit.installedApplets().begin(),
kit.installedApplets().end(),
"com.example.demo"),
kit.installedApplets().end());
```

## Start and observe

Installation just puts the package in place. To actually display the application, you need to call `AppletKit::launch(name)`, where `name` is the package name in the manifest:

```cpp
Applet *applet = kit.launch("com.example.demo");
if (!applet)
LogError() << "launch failed";
```

`launch` returns a pointer to the application object, or `nullptr` on failure. After success, the application will enter the foreground.

::: tip dependency description
Whether `launch()` allows the application to actually display depends on the JavaScript engine, window system, platform graphics adaptation, and the readiness of the application's own code. If `launch()` returns non-empty but the screen is blank, the problem is usually with the other system mentioned above and not with the installation process.
:::

After successful startup, you can verify:

- The application interface appears in the window (depends on the system readiness mentioned above).
- After the application runs and writes data, its private directory appears: `/data/files/com.example.demo/`.
- Resources in the application package can be accessed through `pkg://com.example.demo/<asset-path>` (can be operated through the `File` class).

## Uninstall an application

The uninstall interface is `AppletKit::removePackage(package)`. Pass in the package name and return `bool` to indicate whether the package file is found and deleted:

```cpp
if (!kit.removePackage("com.example.demo"))
LogError() << "uninstall failed: package not found";
```

The effects of uninstalling external guarantees:

- If the application is running, end it first.
- Remove the `.pkg` file from the first directory in the `packages()` list that contains the package.
- Delete the subdirectories of the application in each data directory (`<package-name>/` under `AppletCache`/`AppletFiles`/`AppletTemp`/`AppletStorage`).
- Unregister the application from the package database.

Verify after uninstallation:

- `/data/apps/com.example.demo.pkg` in the installation directory has disappeared.
- Data subdirectories such as `/data/files/com.example.demo/` have been cleared.
- `kit.installedApplets()` no longer contains `"com.example.demo"`.

## Advanced: System pre-installed application directory

Many devices need to distinguish between two types of applications: system applications that are pre-installed at the factory and cannot be uninstalled, and user applications that are subsequently installed by the user and can be uninstalled. This layering can be achieved with two directories by taking advantage of the sequential semantics of the `packages()` list.

### Usage scenarios

Factory-installed applications (such as system dials, settings applications) are usually burned into read-only flash memory and should not be uninstalled or overwritten by users. Applications installed by users should be in a writable partition and can be added or deleted at any time. If only one directory is used to mix the two, subsequent application update or uninstall management will become complicated.

### Recommended layout

Append two directories to `packages()`, the order is sensitive, the pre-installed read-only directory is first, and the user-writable directory is last:

```cpp
EnvPath::packages().emplace_back("/system/apps"); // Read-only preinstalled, put in front
EnvPath::packages().emplace_back("/data/apps"); // Writable user installation, placed after
```

Looking back at the [Application Package Directory](#Application Package Directory) in the first step, the semantics of the three operations under this layout are as follows:

- **Search** from front to back, with pre-installed directories in front, and factory applications hit first to ensure stable loading.
- **Installation** writes the last directory in the list, which is the user area. Newly installed applications will not pollute the pre-installed directory.
- **Uninstall** remove from front to back, from the first directory containing the package.

### Protection mechanism: calling side whitelist

Sequential semantics only determine the storage path of the application and start the search process, and cannot prevent users from uninstalling pre-installed applications. The built-in <code>AppletKit&#8203;::&#8203;removePackage</code> has no concept of "pre-installed" or "protected".Therefore, the device's uninstallation entry should be implemented by native code, in which a whitelist of pre-installed package names is maintained and intercepted before calling `removePackage`: if the whitelist is hit, uninstallation is refused.

No whitelist is required on the installation side. The installation channels of device manufacturers (app stores, preset push, etc.) are themselves controlled, and the legitimacy of application package names is guaranteed by the signature mechanism, which is not the responsibility of this layer; and due to the masking of forward resolve (see "Known Limitations" below), runtime upgrades of pre-installed applications cannot take effect, and there is no need to additionally prevent overwritten installations. Therefore installation can be done directly by calling `kit.installPackage`.

A native way to uninstall the wrapping layer:

```cpp
#include "gx_hashset.h"

class PackageManager {
public:
PackageManager(AppletKit &kit, HashSet<String> preinstalled)
: m_kit(kit), m_preinstalled(std::move(preinstalled)) {}

auto install(const String &packageUri) {
return m_kit.installPackage(packageUri);
}

bool uninstall(const String &packageName) {
if (m_preinstalled.count(packageName)) {
LogWarning() << "refuse to uninstall protected package:" << packageName;
return false;
}
return m_kit.removePackage(packageName);
}

private:
AppletKit&m_kit;
HashSet<String> m_preinstalled;
};
```

::: tip Read-only mounting and whitelisting
Mounting premounted partitions read-only is still recommended (to prevent accidental writes), but it is not a dependency on unmount protection. Even if the preinstalled directory is writable, the whitelist will block it before calling `removePackage`.

The permission field of `EnvPath::Entry` does not participate in the decision-making of the application package directory, and only restricts the access of JavaScript code to the application data directory.
:::

### Restore factory settings

Taking advantage of the separation of the pre-installed directory and the user directory, restoring factory settings can be achieved by deleting all `.pkg` files in the user directory and resetting `pkgs.db`; the pre-installed packages in the system directory are not affected. Runtime installation is fixedly written to `packages().back()` (user directory) and never overwrites the pre-installed copy in the system directory. Therefore, after clearing the user directory and resetting the database, pre-installed applications can still be parsed and loaded by `pkg://` normally.

Optionally, you can "uninstall updates of pre-installed applications" - that is, delete the updated copy of a pre-installed application in the user directory and roll it back to the factory version in the system directory. This capability is currently only possible and has not yet been officially supported.

### Known limitations

The following framework behaviors require the native business layer to actively avoid or pay attention to:

1. **The app store upgrade of pre-installed apps cannot be implemented**.The current resource resolution of `pkg://<name>` performs forward traversal on the `packages()` list, while the runtime installation always writes `packages().back()` (user directory).If you try to upgrade a pre-installed application through runtime installation, the new version will land in the user directory, but will be obscured by the old version in the system directory due to forward hits, and will never take effect. This upgrade capability is yet to be realized.
2. **There is no concept of "protected" in uninstallation**.`removePackage` only locates according to "the first successful deletion", and will delete the package in any directory without any distinction. There is no "whether it is a pre-installed package" mark. Whitelist interception must be implemented by the native caller, and the framework does not provide this judgment.
3. **Uninstalling the dial package did not clean the database**.`removePackage` only logs out from the application table (`ADBT_Applet`) and does not clean up the database entries of the dial package (`ADBT_Dial`), leaving stale records. This is a to-do item of the framework. If the native uninstallation logic needs to support the dial, it needs to be handled by itself.
4. **The permission field of the application package directory entry is invalid**.The permission of `EnvPath::Entry` does not participate in the search/installation/uninstallation decisions of the `packages()` list, and only restricts the access of JavaScript code to the application data directory. It cannot be used to express "Installation is prohibited in this directory".

## Platform initialization template

The complete `EnvPath` configuration of three typical scenarios is given below, which can be copied directly and adjusted according to the device path. All configuration must be done after `Application` is constructed and before <code>AppletKit&#8203;::&#8203;launch</code>/`installPackage`.

### Host emulator

The simplest configuration, single directory storage application:

```cpp
os::chroot(".");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::packages().emplace_back("/apps");
```

### Embedded target (single partition)

A device with only one writable partition, where applications and data are co-located:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::packages().emplace_back("/data/apps");
```

### Devices with preinstalled partitions

Separate the pre-installed read-only partition from the user-writable partition:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/system/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");

// Order sensitive: pre-installed read-only directories come first, user-writable directories come last
EnvPath::packages().emplace_back("/system/apps");
EnvPath::packages().emplace_back("/data/apps");
```

After completing the configuration, you can follow steps two and three to install and start the application. It is recommended to use `AppletKit::NoVerify` to install a simple sample package when running for the first time, confirm that `.pkg` appears under `/data/apps`, `launch` returns non-empty, and then gradually restore the formal verification strategy and pre-installed layout.

# Asynchronous development example

If you feel that [Asynchronous Function Development](async.md) has too many chapters and is not intuitive enough, this document will provide some typical and simpler examples to help you deal with some common asynchronous development scenarios.

These scenarios are not extremely complex, but focus on:
- A typical asynchronous calling pattern, focusing on cross-thread and cross-language calling relationships;
- These scenarios may be more trivial, there are a large number of system APIs that need to be connected, and they are more sensitive to code expansion;
- There are typical C API interaction requirements, rather than the standard C++ interface.

You can find complete implementations of these scenarios in the SDK examples and run them directly on your PC.

## Scenario: Connecting to the C alarm clock interface

A common asynchronous pattern in embedded systems is "C callback": the caller submits a task and passes in a function pointer as a completion notification. After the operation is completed, the callback is called by the worker thread.

:::important async only supports threading model
The asynchronous functionality of the Glyphix framework only supports ordinary thread contexts and cannot be used in interrupts. If your asynchronous context is an interrupt handler, you should have a thread to relay it.
:::

Here is an alarm clock service as an example. The C asynchronous interface it provides is like this:

```c
// Take alarm_async_create as an example, other operations are similar in form
void alarm_async_create(AlarmService *svc, uint32_t interval_ms, ...,
alarm_create_cb_t done_cb, void *done_ctx);

// The function pointer type of the completion callback, which is called in the worker thread
typedef void (*alarm_create_cb_t)(alarm_err_t err, alarm_id_t id, void *ctx);
```

The following explains how to bridge this type of typical C callback interface to JavaScript Promise.

### Multiple operations share the Session type

The alarm clock service has a batch of operations such as `create`, `cancel`, `setEnabled`, `update`, `snooze`, `getInfo`, `list`, `count` and so on. If you define a separate client class for each operation, a large number of template instantiations will be generated.

For this kind of scenario where "the actual logic is completed in the C layer, and only parameters are passed on the C++ side", you can define a lightweight client that only contains error code mapping, so that all operations share a `ResultSession` instantiation:

```cpp
struct AlarmClient {
//Convert the alarm_err_t of the C layer into a readable error string,
// Provided to the catch on the JavaScript side when Promise is rejected.
static const char *errorMessage(async::Status status) {
switch (status.value()) {
case ALARM_OK: return "ok";
case ALARM_ERR_NOT_FOUND: return "not_found";
case ALARM_ERR_TABLE_FULL: return "table_full";
case ALARM_ERR_INVALID_ARG: return "invalid_arg";
default: return "unknown_error";
}
}
};

// All alarm clock operations share this Session type
using AlarmSession = async::ResultSession<AlarmClient>;
```

`AlarmClient` does not need to implement the `resolve()` method because the default thread pool executor is not used here. The actual asynchronous operation is completed by the worker thread of the alarm clock service, and the C++ side is only responsible for delivering the results back to the UI thread.

### Basic binding mode

Take `alarm.create()` as an example to show the complete binding process:

```cpp
static JsValue jsAlarmCreate(JsCtx ctx) {
auto *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1 || !ctx.arg(0).isObject())
return JsValue{};

//Read parameters from the options object passed in from JavaScript
const JsValue &opts = ctx.arg(0);
uint32_t intervalMs = static_cast<uint32_t>(opts["interval"].toInt());
String label = opts["label"].toString();
alarm_repeat_t mask = parseRepeatMask(opts["repeat"]);

// Create a session and extract resolve/reject callbacks from the options object (supports two asynchronous styles)
auto *session = async::make<AlarmSession>(applet);
session->setResolver(opts);

// C callback: called in the worker thread, notifies JavaScript across threads through resolve()
auto done = +[](alarm_err_t err, alarm_id_t id, void *data) {
auto *s = static_cast<AlarmSession *>(data);
s->resolve(err == ALARM_OK
? async::Result<int>(id) // Success: resolve the newly created alarm clock ID
: async::Status(err)); // Failure: reject, error message comes from errorMessage()
};

// Call the asynchronous alarm clock creation interface of the C service, passing in the callback and session pointer
alarm_async_create(AppletAlarmService::instance(),
intervalMs, mask, label.c_str(), /*...*/,
onAlarmFired, nullptr, done, session);
// Return the Promise object to JavaScript, the framework will automatically resolve it when resolve() is called
return session->promise();
}
```

Here are a few fixed routines that can be copied and used directly:

- `async::make<AlarmSession>(applet)` creates a session and binds it to the current Applet to meet life cycle requirements.
- `session->setResolver(opts)` allows the same set of code to support asynchronous calls of [callback style and Promise style](/api/README.md#Quick Application Asynchronous Interface).
- `+[](... void *data)` converts lambda to a normal function pointer via unary `+`, satisfying the type requirements for C callbacks.
- Pass `session` as `void *` transparently to the C API, convert it back in the callback and call `resolve()`.
- `resolve()` is thread-safe. It encapsulates the result as an event and delivers it back to the UI thread, and then drives the resolution of the Promise.

::: tip uses lambda expressions to write callbacks
In C, the callback function is usually a static function. You can use the C++ lambda expression to directly nest the callback function, for example:
```cpp
auto done = +[](alarm_err_t err, alarm_id_t id, ...) { ... }
alarm_async_create(..., done, session);
```
This avoids defining a large number of separate static functions, and the code is more compact and clear.
:::

The structure of the rest of the operations (`cancel`, `setEnabled`, `snooze`, etc.) is exactly the same, only the parameter reading and the C API call differ:

```cpp
static JsValue jsAlarmCancel(JsCtx ctx) {
auto *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1)
return JsValue{};

alarm_id_t id = ctx.arg(0).toInt();

auto *session = async::make<AlarmSession>(applet);
session->setResolver(ctx.arg(0));

auto done = +[](alarm_err_t err, void *data) {
// When there is no return value, use resolve<void>
static_cast<AlarmSession *>(data)->resolve<void>(async::Status(err));
};
alarm_async_cancel(AppletAlarmService::instance(), id, done, session);

return session->promise();
}
```

:::important Don't miss parameter checking
`session->setResolver(ctx.arg(0))` relies on a check of `ctx.argc()`.If the number of parameters is not checked at the beginning of the function, then the number of parameters must be checked when calling `setResolver()`:
```cpp
session->setResolver(ctx.argc() ? ctx.arg(0) : JsValue{});
```
:::

### Register type conversion for custom C structures

`alarm.getInfo()` returns an `alarm_info_t` structure, which needs to be converted into a JavaScript object. To do this, first specialize `js_cast<T>` in the `gx` namespace:

```cpp
template<> JsValue gx::js_cast<alarm_info_t>(const alarm_info_t &info) {
JsValue obj = JsVM::current().newObject();
obj["id"] = info.id;
obj["label"] = info.label;
obj["interval"] = double(info.interval_ms);
obj["repeatMask"] = info.repeat_mask;
obj["enabled"] = bool(info.enabled);
obj["remaining"] = double(info.remaining_ms);
obj["fireCount"] = int(info.fire_count);
obj["snooze"] = int(info.snooze_ms);
obj["snoozed"] = bool(info.snoozed);
return obj;
}
```

After specialization is completed, just pass the structure instance directly to `resolve()` in the binding function:

```cpp
auto done = +[](alarm_err_t err, const alarm_info_t *info, void *data) {
auto *s = static_cast<AlarmSession *>(data);
if (err != ALARM_OK || !info) {
//Exception path, return error status to trigger reject, error message comes from errorMessage()
s->resolve<alarm_info_t>(async::Status(err));
return;
}
s->resolve<alarm_info_t>(*info); // The framework automatically calls js_cast in the UI thread
};
alarm_async_get_info(AppletAlarmService::instance(), id, done, session);
```

::: tip
`js_cast()` is called by the framework after the result is returned to the UI thread and is not executed in the worker thread. This means that UI thread-specific APIs such as `JsVM::current()` can be used safely inside `js_cast()`.
:::
For the case where `alarm.list()` returns an array, `std::vector<int>` can be constructed directly and resolved without defining additional type conversion:

```cpp
auto done = +[](alarm_err_t /*err*/, const alarm_id_t *ids, int count, void *data) {
auto *s = static_cast<AlarmSession *>(data);
s->resolve<std::vector<int>>(std::vector<int>{ids, ids + count});
};
alarm_async_list(AppletAlarmService::instance(), done, session);
```

### Alarm trigger callback: send event back to JavaScript

When the alarm is triggered, the C layer calls the `alarm_fire_cb_t` callback from the worker thread. This scenario is somewhat different from the previous "query results" and requires a specially designed event notification mechanism.

#### Why not use JavaScript callback function

Intuitively, it seems reasonable to have the application pass a callback function when registering the alarm:

```javascript
// ❌ This does not work in the alarm clock scenario
alarm.create({ interval: 60000, onFired: (event) => { /* ... */ } })
```

The problem is that alarms span the application life cycle: after the alarm is created, the application may be killed at any time before the alarm is triggered; many devices also support triggering the alarm after restarting.

A JavaScript callback function (`JsValue`) is only valid within the JavaScript runtime of the current application instance. Once the application is closed, this runtime is destroyed along with all `JsValue`.At this point, the C++ side has no way to keep this JavaScript callback, let alone call it when the alarm is triggered.

This is not just a problem with alarm clocks. **Any event that may be triggered across application lifetimes cannot be resolved through JavaScript callbacks**, such as scheduled tasks, offline message push, background download completion notifications, etc.

#### Use agreed method names instead of callback references

The simplest solution is: instead of the application "registering a callback", the system actively **starts** the application when an event occurs, and calls the processing method on the application object with the agreed method name.

This is consistent with the idea of ​​application lifecycle functions (`onCreate`, `onShow`, etc.) - the system starts the application on demand and calls known entry methods instead of holding pre-registered callbacks. The application side can implement the corresponding method according to the agreement:

```javascript
// app.js — Processing methods exported by application model objects (implemented by convention)
export default {
onAlarmFired(event) {
// event: { id, label, interval, ... }
console.log('alarm fired:', event)
}
}
```

Implementation on the C++ side: First read the snapshot in the worker thread, then switch back to the main thread to start the application and call the method:

```cpp
static void onAlarmFired(alarm_id_t id, void * /*user_data*/) {
//Read the snapshot in the worker thread to avoid cross-thread access to the alarm clock table
alarm_info_t info{};
alarm_get_info(id, &info);

// Switch back to the main thread and then operate JavaScript
App()->postTask([info] {
auto *svc = AppletAlarmService::instance();
// Use launch() to launch (or wake up) the target application, even if it is not currently running
auto *applet = AppletKit::instance()->launch(svc->alarmAppletName);
if (!applet) return;

auto &vm = JsVM::current();
//Call the agreed method on the app.js exported object, and the event parameter is the JavaScript object of the alarm clock information
JsValue event = js_cast(info);
applet->modelObject().callMethod("onAlarmFired", {event}).reportError();
});
}
```

A few key points:

- **Don't** directly manipulate `JsValue` or call any JavaScript API in the worker thread, they can only be used in the UI thread.
- Use `App()->postTask()` to deliver the closure to the main event loop for execution. This is the easiest way to switch back to the main thread.
- Use `AppletKit::launch()` instead of looking for an existing instance; `launch()` will restart the app if it does not exist, or return an existing instance if the app is already running.
- `.reportError()` on the return value of `callMethod()` will print possible JavaScript exceptions to the log instead of silently ignoring them.

::: tip Conventional method names are the simplest way to handle events.
This pattern can be understood as: the exported object of app.js is the "entry point collection" exposed by the application to the system. The system calls the methods in it when needed, just like calling `onCreate` and `onShow`.

This method is not very general, but it is basically sufficient for controlled system applications, and it is simple to implement and does not require complex persistence and callback management mechanisms.
:::

### Register library loader

After all binding functions are written, they need to be "assembled" into a [library object](native-module.md#library-loader) that can be imported by JavaScript and registered in the framework.

The library loader is a C++ function that is triggered when the application calls `app.loadLibrary('vendor.alarm')` and is responsible for creating and returning a JavaScript object containing all exported methods:

```cpp
static JsValue libAlarmLoader(Applet *applet) {
// You can check the application package name here to deny unauthorized application access. Fields can also be checked.
if (!applet || applet->objectName() != "com.vendor.alarm")
return JsValue{};

JsValue lib = JsVM::current().newObject();

// Mount the binding function to the library object. The attribute name is the method name called on the JavaScript side.
lib["create"] = jsAlarmCreate;
lib["cancel"] = jsAlarmCancel;
lib["list"] = jsAlarmList;
lib["count"] = jsAlarmCount;
// ...
return lib;
}
```

Then register the loader with `AppletKit` during the initialization phase:

```cpp
AppletKit kit{&window};
kit.setLibraryLoader("vendor.alarm", libAlarmLoader);
```

The JavaScript side is imported through `app.loadLibrary()`, and the return value is the library object returned by the loader:

```javascript
const alarm = app.loadLibrary('vendor.alarm')

const id = await alarm.create({ interval: 60000, label: 'Get up' })
```

#Asynchronous function development

In embedded systems, many operations are time-consuming - reading flash memory, accessing the network, waiting for the hardware to respond. If these operations are performed on the UI thread (which is also the rendering thread), it will freeze the UI and cause the application to become unresponsive.

Glyphix solves this problem by seamlessly integrating asynchronous operations with JavaScript’s `Promise` mechanism. The C++ side is responsible for the true asynchronous logic (usually in another thread or via events), the JavaScript side waits for the result via `async/await` or `.then()`, and the UI remains fluid during the wait.

## Core Mechanism

The core of asynchronous functionality is the "Session" model. When a JavaScript asynchronous call is initiated, the C++ side creates a **session object** (`AsyncSession`) and immediately returns a `Promise` to JavaScript; when the operation is completed, the session drives the resolution (resolve or reject) of the `Promise`, and the `then/catch` or `await` on the JavaScript side is subsequently executed.

The session object is bound to the `Applet` that initiated the call. The session is automatically cleaned up when the application exits, and developers do not need to manually manage memory.

The implementation of the asynchronous framework is in `gx_async.h` and is encapsulated in the `gx::async` namespace. The framework provides several useful facilities:
- **`async::ResultSession`**: used for single asynchronous query, suitable for scenarios such as reading files and initiating network requests.
- **`async::make_timeout()`**: used to create a single timer and add a timeout function to a single session.
- **`async::Signal<T>`**: used for global event broadcast, suitable for scenarios such as device status changes and external event notifications.

## Single query ResultSession

`async::ResultSession<T>` is suitable for "initiating a query and waiting for a single result" scenario, such as reading a file or initiating a network request. It is the most commonly used asynchronous pattern and works like an asynchronous function call.

### Working model

The complete life cycle of a `ResultSession` is as follows:

1. **Create**: The module function creates a session through `async::make<ResultSession<T>>(applet)`, and the session is automatically bound to the current `Applet`.
2. **Configuration**: Access the client object through `session->client()` and set the pure C++ parameters required for the task.
3. **Submit**: Call `session->request(resolver)` to submit the task and immediately return a `Promise` to JavaScript.
4. **Execution**: The framework forwards the client's `resolve()` method to the **asynchronous executor** (default is the background thread pool) for execution.
5. **Return**: After `resolve()` returns, the result is **automatically scheduled back to the UI thread**, driving the resolve or reject of `Promise`.
6. **Cleanup**: The session object is automatically destroyed after the report is completed, or automatically cleaned up when the `Applet` exits.

:::Isolation requirements for important Client classes
The client class (i.e. template parameter `T`) runs in an asynchronous context and must not hold or access any objects that interact with JavaScript, including any UI thread-specific objects such as `JsValue`, `Applet*`, etc.

The client class should be a **pure C++ data processing unit**, holding only the value type data required to perform the task (such as `String`, `int`, or a custom structure, etc.), and completing all work in the `resolve()` method. All interactions between the UI thread and asynchronous threads are handled automatically by the framework.
:::

### Basic usage
First, define a client class and implement the `resolve()` method. This method is called in an asynchronous context, returning the result wrapped in `async::Result<T>`:

```cpp
#include "gx_async.h"
#include "gx_file.h"

using namespace gx;

//Client class: pure C++ data processing, does not hold any JS objects
class ReadTextClient {
public:
void setPath(const String &path) { m_path = path; }

// Called in an asynchronous context and return the operation result
async::Result<String> resolve() {
File file(m_path);
if (!file.open(File::ReadOnly | File::Text))
return async::Status(300); // IO error
int size = int(file.size());
String text(size);
text.resize(file.read(text.data(), size));
return text; // Success: return file content
}

// Optional: Custom error message (used when Promise is rejected)
static const char *errorMessage(async::Status status) {
switch (status.value()) {
case 300: return "io error";
default: return "unknown error";
}
}

private:
String m_path; // Absolute path that has passed security verification
};
```

Then, create the session and return a `Promise` in the module function. Note: You must use `Applet::resolveUri()` to perform security verification on the path passed in by JavaScript instead of directly trusting the string provided by the application:

```cpp
static JsValue readText(JsCtx ctx) {
Applet *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1 || !ctx.arg(0).isObject())
return {};

// ✅ Security: Verify and convert the path through resolveUri
auto uri = applet->resolveUri(ctx.arg(0)["uri"].toString());
if (uri.empty())
return {}; // URI verification failed, access denied

using Session = async::ResultSession<ReadTextClient>;
auto *session = async::make<Session>(applet);
session->client().setPath(uri); // Pass in the verified safe path

//Submit an asynchronous task and pass in the complete options object to be compatible with the quick app callback interface
session->request(ctx.arg(0));
return session->promise();
}
```

::: tip Why pass in `ctx.arg(0)`?
`request()` receives the entire `options` object passed in from the JavaScript side, that is, `ctx.arg(0)`, which is used to automatically adapt to the two [calling styles] of the quick application asynchronous interface (/api/README.md#Quick application asynchronous interface):

- If `options` contains any attribute of `success`, `fail` or `complete`, it is determined to be **callback style** and the corresponding function is called directly. `request()` does not return a meaningful value;
- Otherwise, it is determined to be **Promise style**, a new `Promise` will be created, and `session->promise()` will return the object for the caller to `await`.

This allows the same C++ implementation to support both the quick application standard callback interface and the modern Promise/async-await interface without any additional code. If you are sure that only the Promise style is supported, you can also pass in an empty value `{}`.
:::

:::danger Don't skip URI validation
Directly using a string passed in JavaScript as a file path is a serious security vulnerability:

```cpp
// ❌ Danger!Bypassing the path security check of the sandbox
session->client().setPath(ctx.arg(0)["uri"].toString());
```

Malicious applications can access file systems outside the sandbox through path traversal (such as `../../etc/passwd`).All paths from JavaScript must be sanitized by `Applet::resolveUri()`, which will detect path traversal attacks, cross-application unauthorized access and illegal URI formats, and return an empty string if validation fails.
:::

Usage on JavaScript side:

```javascript
import file from '@system.file'

async function loadConfig() {
try {
const text = await file.readText({
uri: 'internal://files/config.json'
})
console.log('config:', text)
} catch (err) {
console.error('read failed:', err.message)
}
}
```

### Errors and status codes

`async::Status` encapsulates an integer status code, `0` (ie `async::OK`) indicates success, and other values ​​are business-defined error codes:

```cpp
// Success: return value directly, status code is automatically OK
return async::Result<String>{std::move(content)};
// Failure: only the status code is returned, the value part is ignored
return async::Status(404);
// Carry both partial results and non-OK status (such as HTTP 206 Partial Content)
return async::Result<ByteArray>{
std::move(partialData),
async::Status(206)
};
```
When `resolve()` returns an error status, the `Promise` is rejected and the JavaScript `catch` block receives an error object containing the `message` and `code` fields.`message` static method from `errorMessage()` of client class.

`errorMessage()` supports multiple signatures, which will be automatically recognized by the framework:

```cpp
// Form 1: Receive Status (recommended, concise)
static const char *errorMessage(async::Status status);

// Form 2: Receive the complete Result and generate messages based on the value and status
static String errorMessage(const async::Result<MyType> &result);
```

If the client class does not define `errorMessage()`, the framework will use the default `"unknown async error"`.

### Value types and JavaScript conversion

The value returned by `resolve()` will not be passed to JavaScript as is. The framework automatically converts the C++ type to `JsValue` through the `js_cast()` function, and then drives the resolve of `Promise`.This process is completed within the framework and looks "transparent", but in fact it relies on a set of **implicit conventions**: only types that implement `js_cast()` specialization can be converted correctly. For custom enumerations, structures and other types, the conversion relationship needs to be explicitly established, otherwise the compilation will fail.

#### Built-in supported types

The following types can be used directly as type parameters of `Result<T>` without additional work:

| C++ type | Corresponding JavaScript type | Remarks |
| --- | --- | --- |
| `int`, `double`, `float` | `number` | Direct mapping of numerical values |
| `bool` | `boolean` | Boolean direct mapping |
| `String`, `StringView`, `const char *` | `string` | String direct mapping |
| `ByteArray` | `ArrayBuffer` | Binary data |
| `JsonValue` | `object` / `array` | JSON object or array |
| [`std::vector<T>`](https://en.cppreference.com/w/cpp/container/vector) | `Array` | Array, element recursive conversion (`T` itself also needs to be convertible) |
| `JsValue` | Any | Pass directly without conversion |
| `void` (i.e. `Result<void>`) | `undefined` | No return value |

These types have built-in `js_cast<T>()` specialization in the JsVM framework. Some of them are types that can be directly constructed by `JsValue`, and some of them implement conversion logic through specialization.

#### Add conversion support for custom types

If the type used is not in the above list, the compiler will report an error indicating that `JsValue` cannot be constructed. There are two ways to solve it:

**Method 1: Define `operator JsValue()` member function**

This is suitable for custom structures whose definitions can be modified. The advantage is that the conversion logic is built into the type definition and is tightly coupled:

```cpp
struct DeviceInfo {
String model;
int version;

// Convert the structure to a JavaScript object
// Note: The conversion is executed on the UI thread, and there is a valid JsVM context at this time
operator JsValue() const {
JsVM &vm = JsVM::current();
JsValue obj = vm.newObject();
obj["model"] = JsValue(model);
obj["version"] = JsValue(version);
return obj;
}
};
```

Once defined, `Result<DeviceInfo>` can be used directly:

```cpp
async::Result<DeviceInfo> resolve() {
return DeviceInfo{"ModelX", 3}; // The framework automatically calls operator JsValue()
}
```

APIs such as `JsVM::current()` and `vm.newObject()` used internally by `operator JsValue()` belong to the JsVM bridging layer. For details, see [Native Module Development Documentation](./native-module.md#Creating and Returning Objects).

**Method 2: [Specialization](https://en.cppreference.com/w/cpp/language/template_specialization) `js_cast<T>`** in the `gx` namespace

Suitable for cases where the original type definition cannot be modified (such as a type or enumeration from an external definition):

```cpp
// Declare the specialization before using it if necessary
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x);

//Specify within the gx namespace
template<>
JsValue gx::js_cast<ConnectionState>(const ConnectionState &x) {
switch (x) {
case ConnectionState::Connected: return "connected";
case ConnectionState::Connecting: return "connecting";
case ConnectionState::Disconnected: return "disconnected";
default: return "unknown";
}
}
```

After specialization, both `Result<ConnectionState>` and `Signal<ConnectionState>` work normally.

::: tip A simple way to enumerate integers
If the enumeration value corresponds directly to an integer, manual conversion to `int` in `resolve()` is the least labor-intensive way, without any specialization:

```cpp
async::Result<int> resolve() {
return async::Result<int>{int(myEnum)};
}
```
:::

#### Runtime conversion overhead
`js_cast()` is executed only after the asynchronous result is posted back to the UI thread, and does not run in the asynchronous thread. The time overhead of conversion occurs entirely in the UI thread. For complex structures, it needs to be fast enough to avoid frame freezes. The actual costs of each type are as follows:

- **Zero-overhead types**: `int`, `double`, `bool`, `String`, `const char *` are directly mapped through the `JsValue` constructor, no additional copies or heap allocations. The `operator JsValue()` method and the `js_cast<T>` specialization are also inlined at compile time, without virtual calls or levels of indirection.
- **Linear cost type**: `std::vector<T>` needs to call `setIndex()` element by element, and the cost is proportional to the number of elements. If the return structure is an object with fixed fields, it is preferable to use `operator JsValue()` to manually construct the JS object, which is more efficient and easier to read than an array.
- **Tree traversal type**: `JsonValue` recursively traverses the entire tree during conversion and constructs JavaScript nodes one by one. It is the most expensive of the built-in types. If the data structure is known at compile time, it is often faster to construct the object directly with `operator JsValue()` without the construction cost of `JsonValue` itself.
- **Custom structure**: If you use `operator JsValue()` or `js_cast()` specialization, the conversion performance depends on the conversion cost of each member type, that is, the complexity of constructing the object.

::: tip Simple judgment criteria
If your asynchronous data structure is simple (numeric values, simple struct objects, or small `JsonValue`), then the conversion overhead usually does not affect UI smoothness.
:::

#### No serialization middle layer

Some asynchronous frameworks require that when data is passed between the worker thread and the UI thread, the results must be serialized into JSON or other self-describing formats, and then deserialized in the UI thread. This is to achieve "type erasure" transfer between threads, but at the cost of each call having to bear the splicing, transmission and parsing overhead of strings (or binary data streams).Even worse is the possibility of constructing multiple copies of the data (serialized intermediate data, original data, etc.).

The async framework** does not rely on a serialization middle layer.** Results are moved between threads as native C++ values via `async::Result<T>`, bypassing the serialization process entirely:

```
worker thread UI thread
resolve(Result<MyType>{...}) → js_cast(result.value()) → JsValue (JavaScript)
↑
Direct memory movement, no JSON strings
```

`js_cast()` is only executed after the result has been safely returned to the UI thread, and its job is to map C++ values to the JavaScript engine's internal representation, not to act as an inter-thread communication protocol.

If you actively choose to use `JsonValue` as the type parameter of `Result<T>` (used to alleviate template code bloat), then you introduce the **construction and tree traversal** overhead of `JsonValue` instead of string serialization. `JsonValue` itself is also an in-memory tree structure, not a text format.

#### Template code size

`ResultSession<T>` is a template class, and the compiler will generate a separate code for each different client type `T`.However, the framework has extracted most of the logic unrelated to `T` (such as `Promise` management, event delivery, `Applet` life cycle binding) into the non-template base class `detail::ResultSession`, so the actual additional code amount for each `T` is mainly concentrated in the thin `Resolver` adaptation layer.

But if there are a large number of fine-grained client types in the project that are only used once, the cumulative number of instantiations will still bring considerable code growth.

A common compression method is to use `JsonValue` as a type erasure medium to merge multiple scattered small functions into a single client type:

```cpp
// Before merging: each operation is an independent client class + independent template instantiation
struct GetVersionClient { ... }; // ResultSession<GetVersionClient>
struct GetModelClient { ... }; // ResultSession<GetModelClient>
struct GetSerialClient { ... }; // ResultSession<GetSerialClient>

//After merging: share the same template instantiation and only differentiate operations at runtime
struct DeviceQueryClient {
enum Kind { Version, Model, Serial } kind;

// Here the demonstration uses switch dispatch, but in fact, function pointers can also be used. But don't use BaseClient
// Rewriting resolve() with derived classes to achieve polymorphism will cause more virtual table expansion than the function pointer solution.
async::Result<JsonValue> resolve() {
switch (kind) {
case Kind::Version: return JsonValue{getVersion()};
case Kind::Model: return JsonValue{getModel()};
case Kind::Serial: return JsonValue{getSerial()};
}
}
};

// The three module functions share the instantiation of ResultSession<DeviceQueryClient>
static JsValue getVersion(JsCtx ctx) {
using Session = async::ResultSession<DeviceQueryClient>;
auto *session = async::make<Session>(applet);
session->client().kind = DeviceQueryClient::Version;
return session->request(ctx.arg(0));
}
```

The cost of this approach is that the return type degenerates to `JsonValue` and requires additional conversion runtime overhead (see above).Therefore, it is suitable for scenarios where the amount of data is small and the number of functions is large, and a small amount of runtime overhead is exchanged for meaningful code volume gains. For large data volumes or performance-sensitive operations, separate strongly typed client classes should still be maintained.

### Custom asynchronous context

By default, `session->request()` submits `resolve()` to the framework's **asynchronous executor** - usually a background thread pool. But some scenarios require the use of different asynchronous contexts, such as custom event loops or AIO multiplexing mechanisms, and they do not want to occupy additional thread resources.
At this time, you can skip `request()` and directly control the asynchronous execution process manually. The client class does not need to implement the `resolve()` execution function. The key is: **After completing the work in the asynchronous context, call `session->resolve()` to post the results back to the UI thread**.

```cpp
// Client class: No need to implement resolve() because the default thread pool is not used
struct FirmwareCheckClient {
// Only define errorMessage() for error description
static const char *errorMessage(async::Status status) {
switch (status.value()) {
case 1: return "firmware not found";
case 2: return "check failed";
default: return "unknown error";
}
}
};

static JsValue checkFirmwareUpdate(JsCtx ctx) {
Applet *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1) return {};

using Session = async::ResultSession<FirmwareCheckClient>;
auto *session = async::make<Session>(applet);
auto version = ctx.arg(0).asString();

// Manually set resolver (do not call request, do not use the default thread pool)
session->setResolver(ctx.arg(0));
JsValue promise = session->promise();

//Submit to custom hardware driver thread
HardwareDriver::checkUpdate(
version,
// The callback may be on any thread - the framework will automatically schedule it back to the UI thread
[session](bool available) {
session->resolve<bool>(available);
},
[session](int errorCode) {
session->resolve<bool>(async::Status(errorCode));
}
);

return promise;
}
```

The core difference here:
- `request()` completes the two actions of "setting resolver" and "submitting to asynchronous executor" at the same time;
- In manual mode, you need to call `setResolver()` yourself to set the response target, and then push the result or error status through `session->resolve()` at any time.

`resolve()` is thread-safe. It encapsulates the result as an event and delivers it back to the UI thread, and then completes the resolution of `Promise`.

::: tip when to use custom context
- The underlying driver already provides a callback interface, and you don’t want to create additional threads: `resolve` directly in the driver callback.
- Requires integration with existing AIO/epoll event loop: `resolve` in event completion callback.
- Need to be executed serially (for example, operations must be in order): use your own task queue to schedule, and `resolve` after completion.

As long as it is guaranteed to call `session->resolve()` once in the end, the framework does not care which thread the result is delivered from.
:::

### Value type semantics

Since the `async::Result<T>` value returned by `resolve()` (or actively posted by a custom asynchronous context) will be posted to the UI thread and then converted to `JsValue`, the data type `T` must be movable. Built-in supported types all meet this requirement. For custom types:
- If a structure contains only members of built-in supported types, the C++ standard guarantees that it is movable.
- If you use a raw pointer and control its ownership yourself, then you need to implement the [move constructor](https://en.cppreference.com/w/cpp/language/move_constructor) correctly.
- [Trivial Type](https://en.cppreference.com/w/cpp/named_req/TrivialType) (such as pure C structures, enumerations, etc.) satisfy value type semantics by default.

It should be noted that non-trivial types usually contain resources on the heap, and the following writing may face memory peak problems:

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(data); // There will be a complete copy of data
```
This is because the parameters of `session->resolve()` are passed by value. When `data` is passed in, the [copy constructor](https://en.cppreference.com/w/cpp/language/copy_constructor) will be called, resulting in a complete copy. This can double memory usage if `data` is large. This type of compilation warning will appear at this time:
```
'...' is deprecated:
avoid use copy semantics of Result<T> if T is not trivially copyable
```
The correct approach is to explicitly enable move semantics using [`std::move()`](https://en.cppreference.com/w/cpp/utility/move):

```cpp
auto *session = getFetchLargeDataSession();
std::vector<uint32_t> data = fetchDataFromNetwork(url);
session->resolve<decltype(data)>(std::move(data)); // Use move semantics
```

### Timeout control

For asynchronous operations that may be unresponsive for long periods of time, use `async::make_timeout()` to add timeout protection to the session.`Promise` will be automatically rejected after timeout to prevent the JavaScript side from hanging permanently.

The following code snippet shows a basic example of how to use timeout control with network requests:

```cpp
static JsValue fetchData(JsCtx ctx) {
Applet *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1) return {};

String url = ctx.arg(0)["url"].asString();
int timeoutMs = ctx.arg(0)["timeout"].asInt(5000);

using Session = async::ResultSession<HttpClient>;
auto *session = async::make<Session>(applet);
session->client().setUrl(url);
session->setResolver(ctx.arg(0));
JsValue promise = session->promise();

//Create timeout protection: automatically reject Promise after timeout
auto handle = async::make_timeout(session, timeoutMs,
[](Session *s) {
// Timeout processing: ongoing asynchronous operations should be canceled here
s->fulfill(async::Status(408)); // 408 Request Timeout

});

//Move handle to asynchronous execution context
NetworkDriver::fetch(url,
[handle = std::move(handle)](auto &response) {
// If timed out, resolve will be safely ignored
handle->resolve<String>(std::move(response.body));
});

return promise;
}
```

#### How it works

Key workflow of `make_timeout()`:

1. Move the client data of `session` to an inner class, and `session->client()` must not be accessed again.
2. Start a single timer and return the `SharedRef<SingleTimer>` handle.
3. **Normal path**: Call `handle->resolve()` before timeout, and internally atomically take away the session ownership and deliver the result event. Afterwards, when the timer triggers, it is found that the session is empty and no processing is performed.
4. **Timeout path**: Triggered regularly, **execute the callback on the UI thread**, and the developer calls `session->fulfill()` in the callback to deliver the error status; after the callback returns, the timer is responsible for `delete session`.
5. **Application exit**: When the `Applet` is destroyed, the timer is automatically unbound, the session is deleted, and the callback will not be triggered.

This mechanism is particularly suitable for scenarios where asynchronous operations do not have a built-in timeout mechanism, such as the implementation of certain network requests. As we all know, implementing timeout protection correctly is a bit tricky, and you have to properly handle race conditions and lifecycle safety issues on all paths.

`make_timeout()` relies on these premises to ensure safety:
- The client type (i.e. the `T` in `ResultSession<T>`) must be **movable**, which is a legacy restriction.
- Asynchronous operations must support safe cancellation in the UI thread, which means removing the task listener and releasing the reference to `handle`.

#### Callback thread and `fulfill()`

The timeout callback (the third argument to `make_timeout()`) **always executes** on the UI thread because it is triggered by a timer (`Timer`) and timer events are dispatched by the main event loop.

This determines that `session->fulfill()` can only be used in callbacks but not `session->resolve()`:

| Method | Callable thread | Impact on session |
| --- | --- | --- |
| `resolve(result)` | Any thread | Deliver the Consume event, and the session will be deleted after being processed by the UI thread |
| `fulfill(result)` | **UI thread only** | Distribute results directly, **not delete** session |

The timeout path of `make_timeout()` is the responsibility of the timer itself to `delete session` after the callback ends. If `session->resolve()` is called in the callback, it will also deliver an event to delete the session, forming a **double free** with the `delete` of the timer, resulting in undefined behavior.`fulfill()` only delivers results and does not touch the session life cycle, so it is the only safe choice in callbacks.

`fulfill()` accepts `async::Result<R>` or directly `async::Status` (short for when there is no result value):

```cpp
auto handle = async::make_timeout(session, 5000, [](Session *s) {
s->fulfill(async::Status(408)); // Only fill error status
// Or carry value and status:
s->fulfill(async::Result<String>{"partial", async::Status(206)});
// ❌ Do not call s->resolve(), it will form a double release with the timer's delete session
});
```

::: tip
The judgment rule is simple: where is the ownership of the session, and who is responsible for deleting it?
- **Normal path**: `handle->resolve()` takes over the session ownership atomically internally, and the session is deleted after the Consume event is processed.
- **Timeout callback**: timer takes over session ownership and is deleted after the callback ends. Therefore, only `fulfill()` can be used in callbacks to deliver results.
:::

#### Access client data

If the timeout callback needs to read client data to determine error policy, use the extended callback signature `(Session *, const T &)`.**Don't** call `session->client()` in a callback - the client has been moved into the timer:

```cpp
auto handle = async::make_timeout(session, 3000,
[](Session *s, const HttpClient &client) { // auto &client can also be used
// ✅ Access client data through the second parameter
LogWarn() << "request timeout: " << client.url();
s->fulfill(async::Status(408));
}
);
```
#### Resource life cycle management

When the timeout occurs, you need to cancel the ongoing asynchronous task in the callback to release the reference to `handle`.`SingleTimer` uses reference counting to manage lifetime - if an asynchronous operation holds a reference to `handle` but never completes, a memory leak will occur:

```cpp
auto task = AioTask::create();
auto handle = async::make_timeout(session, 5000,
[task](auto *s) {
task->cancel(); // Cancel the task and release the reference to handle
s->fulfill(async::Status(408)); // reject Promise
});

//Task completion callback holds handle reference
task->start([handle = std::move(handle)](auto &result) {
handle->resolve(result);
});
```

::: important
The `handle` returned by `make_timeout()` must also be referenced by the asynchronous task (captured by the lambda in the above example) to ensure that the timer is not destroyed before the task completes. Otherwise, the timeout callback and Promise reject will be triggered immediately, causing the task to fail to complete normally.
:::

This memory leak is caused by two reasons:
1. **async framework leak**: `handle` reference is forgotten, resulting in the related session object not being released.
2. **Underlying task leak**: The asynchronous task itself is blocked in an unfinished state, and related resources will not be cleaned up.

### Automatic cleanup when the application exits

When an `Applet` is destroyed (for example, the user closes the application and the system reclaims resources), all asynchronous sessions bound to the `Applet` will be automatically cleaned up:

- The session's `unbind()` method is called, which closes the session and releases the `Promise` reference.
- If `make_timeout` is being used, the timer will also be unbound and the session held internally will be deleted.
- The `Promise` on the JavaScript side will never be resolved or rejected - but the JavaScript environment itself is being destroyed at this time, so this is safe.

This means you don't need to manually track and cancel asynchronous tasks - the framework guarantees that the following will not happen:
- Posting to a destroyed `Applet` results in accessing a dangling pointer.
- Execute callbacks in a released JavaScript context.
- Asynchronous session leaks after app exits.

Specifically, when the background thread calls `resolve()` to deliver the result to the UI thread, the handler function checks whether `applet()` is still valid. If the `Applet` has been destroyed causing `applet()` to return `nullptr`, the framework safely discards the result without performing any JavaScript operations.

::: tip Safe return in asynchronous context
Since `resolve()` is pure data delivery (via the event queue), calling `resolve()` in a background thread will not crash even if the `Applet` has been destroyed. The background thread does not need to care about the alive state of `Applet`, this is the responsibility of the framework.
:::

The only thing to note is that if you derive `ResultSession` and introduce other `JsValue` member variables, you need to clean up these members in `unbind()` to avoid memory leaks:

```cpp
class MySession : public async::ResultSession<MyClient> {
public:
void unbind() override {
m_callbacks = {}; // Clean up any held JsValue to avoid leaks
async::ResultSession::unbind(); // Call base class cleanup
}

private:
JsValue m_callbacks; // Members that need to be cleaned manually
};
```

::: important `ResultSession` life cycle extended
If there are still unfinished asynchronous sessions when the application exits, the framework will only clean up resources related to the application (such as `Promise` references, binding relationships, etc.), but **will not destroy the session object itself**, which means that the life cycle of `ResultSession` is extended until the asynchronous operation is completed.

This itself is to ensure memory safety, but it will cause some resources to be released late. Therefore, asynchronous tasks must be completed within a limited time and cannot be suspended indefinitely.
:::

## Global event broadcast async::Signal

If a C++ event needs to be broadcast to multiple applications (rather than to a specific caller), use `async::Signal<T>`.It "multicasts" underlying hardware or system events to all JavaScript listeners that subscribe to it.

The positioning of `async::Signal<T>` and `ResultSession` is different:

| Features | ResultSession | Signal |
| --- | :---: | :---: |
| Communication direction | One-to-one (caller → result) | One-to-many (event source → all subscribers) |
| Number of triggers | Single | Multiple times |
| Binding Object | Single Applet | Cross-Applet |
| Applicable scenarios | Asynchronous queries, requests | System events, status changes |

### Basic usage

Suppose there is a battery lighting change event that needs to notify all subscribers:

```cpp
//Define a global signal, usually a member variable of the corresponding service
async::Signal<int> batteryChanged;

//Trigger signal when hardware event occurs (can be called in any thread)
void onBatteryLevelChanged(int newLevel) {
batteryChanged(newLevel); // Notify all subscribers
}
```

#### Bind & Unbind

This module function allows the JavaScript side to subscribe to the signal, and it also returns a binding ID for the JavaScript side to unsubscribe:

```cpp
static JsValue subscribeBatteryChange(JsCtx ctx) {
if (ctx.argc() < 1 || !ctx.arg(0).isFunction())
return {};
// Must be in a valid applet environment to subscribe
auto *applet = Applet::current(ctx.vm());
if (applet == nullptr) return {};

// Bind the slot to the application and automatically unsubscribe when the application exits
auto *slot = batteryChanged.connect(ctx.arg(0));
return applet->bindObject(slot); // Return slot ID for JavaScript to cancel
}
```

You also need to implement an unsubscribe module function. Regardless of the `async::Signal` type, the implementation of the unbinding function is very fixed:

```cpp
static JsValue unsubscribeBatteryChange(JsCtx ctx) {
auto *applet = Applet::current(ctx.vm());
if (applet && ctx.argc()) {
// slotId defaults to 0 and can be safely ignored without performing any action
auto slotId = ctx.arg(0).toInt();
//After unbinding the slot from the applet, you need to delete the slot object
delete applet->unbindObject<async::Slot>(slotId);
}
return {};
}
```

#### JavaScript export

Just define a [Native Module](./native-module.md) to export these functions:

```cpp
static JsModule *createBatteryModule(JsVM &vm) {
auto mod = vm.newObject();
// The battery module usually also has functions such as getLevel(), which will not be expanded here.
mod["subscribe"] = subscribeBatteryChange;
mod["unsubscribe"] = unsubscribeBatteryChange;
return mod;
}
// Don't forget to import the module with GX_JSVM_MODULE_IMPORT
GX_JSVM_MODULE(vendor_battery, "vendor.battery", createBatteryModule)
```

::: tip Reuse the `unsubscribe` function
Since the implementation of the unbinding function is very general, you can define a general `unsubscribe` function and then import it into each module multiple times for use.
:::

JavaScript side:

```js
import battery from '@vendor.battery'

const sid = battery.subscribe((level) => {
console.log('battery level:', level)
})

// Called when you need to cancel the subscription
battery.unsubscribe(sid)
```

### Signal transmission mode

`Signal` supports two delivery modes, controlled by the second parameter:

```cpp
// Normal mode (default): Notify all subscribers
batteryChanged(newLevel, async::NormalSignal);

// Skip invisible applications: only notify applications visible in the foreground to reduce unnecessary consumption
batteryChanged(newLevel, async::SkipInvisible);
```

`SkipInvisible` mode is suitable for events that are only meaningful when the UI is visible (such as interface refresh notifications).For events that require background awareness (such as low battery warnings), the default `NormalSignal` should be used.

### Signal value type

The type parameter `T` of `Signal<T>` follows exactly the same conversion rules as `ResultSession`: when the signal is fired, the framework converts the C++ value into the parameter of the JavaScript callback through the same `js_cast()` mechanism. Built-in types such as `int`, `bool`, `String`, `JsonValue`, etc. can be used directly; if you need to pass a custom structure or enumeration, please refer to the methods in the [Value Types and JavaScript Conversion](#Value Types and -javascript-Conversion) section.

## Thread safety instructions

The thread safety model of asynchronous frameworks follows the following rules:

- **`resolve()` is thread-safe**: `ResultSession::resolve()` and `SingleTimer::resolve()` can be called from any thread. They deliver results to the UI thread through the event system and do not directly operate JavaScript objects.
- **`JsValue` is not thread-safe**: `JsValue` manages lifecycle based on reference counting, and its reference counting operations are non-atomic.`JsValue` must not be created, copied, destroyed or accessed in an asynchronous thread. This is why client classes must not hold `JsValue`.
- **`Promise` resolution is executed on the UI thread**: No matter which thread `resolve()` is called from, the final JavaScript `Promise` callback is always executed on the UI thread, ensuring the safety of UI operations.
- **`async::Signal` notifications are dispatched on the UI thread**: Although `async::Signal::operator()` can be called across threads, JavaScript callbacks are always executed on the UI thread.

If the client class needs to share state with the UI thread (such as providing a cancellation flag), use atomic operations such as [`std::atomic`](https://en.cppreference.com/w/cpp/atomic/atomic) or a mutex to protect the shared data:

```cpp
class CancellableClient {
public:
void cancel() { m_cancelled.store(true); }

async::Result<String> resolve() {
for (int i = 0; i < 100 && !m_cancelled.load(); ++i) {
// Execute step-by-step tasks and periodically check the cancellation flag
processChunk(i);
}
if (m_cancelled.load())
return async::Status(499); // Client cancels
return std::move(m_result);
}

private:
std::atomic_bool m_cancelled{false};
String m_result;
};
```

In particular, many value types of the Glyphix framework can be safely passed across threads in this asynchronous framework, such as:
- `String`: can be assigned and accessed directly in multiple threads without additional synchronization mechanism.
- `JsonValue`: This class is also a value type and has the same thread safety features as `String`.
- `ByteArray`: similar to `String`, supports cross-thread use.
- `SharedRef<T>`: The reference-counted smart pointer itself can be passed across threads, but the thread safety of managed object `T` depends on its definition.
- Non-owned types such as `String::View` cannot be used across threads.

This is why in all the previous examples we always capture and pass types such as `String` directly across the asynchronous context, and no special processing is required to use them. There is no need to use synchronization mechanisms such as mutex for protection.

::: important
The above types of thread safety actually depend on the specific async framework memory model, which means that they are not automatically thread safe in all scenarios. The asynchronous framework in this document guarantees this, but cannot be generalized to every situation.
:::

# C++ learning suggestions

This document is not a C++ tutorial, but provides quick learning suggestions for developers who are ready to read the documents in this directory.

It assumes that you have been developing in C for a long time and are familiar with MCUs, RTOS, drivers, LVGL or similar embedded frameworks; you should have a lot of programming experience, but may not be familiar with the C++ knowledge required by Glyphix.

::: tip
If your goal is to develop Native Modules, asynchronous functions or Native Widgets, please read this article first before continuing to read [Object System](./object-system.md) and other chapters. This can avoid many problems of "you can understand the code, but just can't write it".
:::

## C++ capability subset

The Glyphix project disables some C++ features so developers don't need to learn them at all:

- Disable **RTTI**: `dynamic_cast` and `typeid`, a set of runtime type identification mechanisms, cannot be used. When safe downward conversion is required, please use [`dyn_cast`](object-system.md#dynamic type conversion) directly.
- Disable **Exceptions**: No need to learn `try` / `catch` / `throw` as the main path. Error handling prefers return values, status codes, object states, and explicit checks. This is similar to C's error handling habits.


In addition, Glyphix's runtime has some special constraints, which are mainly caused by the fragmentation and compatibility limitations of the MCU system:
1. Concurrency tools of the C++ standard library such as `std::thread` and `std::mutex` are not available on MCU.
2. Time libraries such as `std::chrono` are also not available on MCU.
3. Do not use static local variables (function-local static). The atomic initialization guaranteed since C++11 is **most likely unreliable** on MCU.
4. Do not use global variables (objects) with heap allocation because the global construction phase on the MCU may be uncontrolled and heap memory may not be available.

Among them, 3 and 4 are very common situations and should be paid special attention to.

## Required C++ knowledge

The following content is sufficient to support most of the documents in this directory.

### Classes and Object-Oriented Programming

At least you need to be able to read and write code like this:

```cpp
class MyWidget : public Widget {
public:
explicit MyWidget(Widget *parent = nullptr)
: Widget(parent) {}

void setValue(int value);
int value() const;
};
```

You need to understand:

- The difference between classes and structures (not much difference, mainly the default access rights)
- The meaning of public inheritance (generally only public inheritance is used)
- Constructor and initialization list
- Member functions, **`const` member functions**
- When to override a base class interface and when to just declare a normal member function

This knowledge will appear directly in [Object System](./object-system.md), [Control Development Guide](./widget.md) and [Control Registration and Export](./widget-export.md).

### Pointers, references and `const`

If you're familiar with C, this is the easiest part to "think you already know", but C++ usage is more rigorous than C.

Points that must be truly mastered:

- The difference between `T *` and `T &`
- When to pass pointers and when to pass references
- Meaning of **`const T *`**, `T *const`, **`const T &`**
- Why `const` member functions are common
- Why objects shouldn't be handled arbitrarily by bytes like in C

In Glyphix, this knowledge is directly related to interface design and lifecycle security.

### Life cycle and resource management

This is the most important section when migrating from C to C++.

You need to establish this habit:

- Objects are automatically destroyed when they leave the scope
- The constructor is responsible for establishing valid state
- The destructor is responsible for releasing resources
- Don’t put “clean up resources” at the end of the function and finish it manually
- Don't treat complex objects as ordinary memory blocks with `memset` / `memcpy`


A large number of Glyphix's facilities and features are built on C++'s object lifecycle model, which includes topics such as RAII.

### Basic usage of templates

This part does not require a deep understanding, but you must at least be able to understand it:

- `Signal<int>`
- `Pointer<Label>`
- `SharedRef<MyData>`
- `async::ResultSession<Client>`
- `std::vector<T>`

And know that "templates are code generation mechanisms with type parameters", not some advanced trick that only library authors touch.

In the Glyphix documentation, templates mainly appear in two forms:

- **Generic container/tool types**, such as `Signal<T>`, `Pointer<T>`
- **Specialization points**, such as adding `js_cast<T>` for custom types

Developers should at least understand basic terms such as "template parameters", "instantiation", and "specialization", and be able to read the declaration and use of template types. But it is not required to be able to define your own template classes or functions.

### lambda expression

In modern C++, lambda is a very practical way of writing one-time functions. You must at least be able to read:

```cpp
mod["double"] = [](JsCtx ctx) -> JsValue {
return ctx.arg(0).asInt(0) * 2;
};
```

and:

```cpp
int factor = readScaleFactorFromConfig();
mod["scale"] = [factor](JsCtx ctx) -> JsValue {
return ctx.arg(0).asInt(0) * factor;
};
```

First, you should be familiar with the basic syntax and capture mechanism of lambda, and focus on understanding:

- lambda is an anonymous function object
- Capture-free lambdas can often be used as ordinary function pointers
- Lambda with capture will carry state
- Once the lambda is held asynchronously, it becomes very important to capture the object's lifetime

This directly affects the code security in [Native Module Development](./native-module.md) and [Asynchronous Development Examples](./async-examples.md).

::: tip lambda is very common
Lambdas actually completely occupy the callback function niche, which means they are everywhere. In some ways, lambdas are probably the most important C++ syntax point.

**Captureless** lambda expressions are almost identical to C function pointers, except that the syntax is different and can alleviate the "naming difficulty".
:::

### Minimum working set of the standard library

There is no need to systematically learn the entire set of STL, but it is recommended to familiarize yourself with these most common components:

- `std::vector`
- `std::array`
- `std::move`
- Basic algorithms `<algorithm>`, iterators and ranges `for`

::: tip associated container
Glyphix has its own implementation of `HashMap` and `HashSet`, which are very similar to `std::unordered_map`.However, it is not recommended to use associative containers such as `std::map`, `std::unordered_map`, because their performance is poor, and the code bloat of `std::map` is obvious.
:::

### C and C++ interop

If you want to connect to the underlying SDK, this part will almost certainly be used.

At least you must be able to:

- The role of `extern "C"`
- C callback function pointer

You will see a very typical pattern in [Asynchronous Development Examples](./async-examples.md): the C API is responsible for true asynchronous execution, and the C++ layer only does parameter packaging, life cycle management and result return.

::: tip Difficulty Expectation
This part isn't difficult, but it's easy to make linking errors. You may need to learn to solve various problems caused by `extern "C"` when mixing C/C++ header files.
:::

# Global resource migration guide

This article is aimed at Glyphix downstream integration projects, helping you upgrade the global resource loading method in historical projects to the latest solution, obtain a global resource layout that is easy to manage and edit, and no longer rely on the manufacturer's packaging or conversion tool support.
In the early days, Glyphix used the `global.pkg` binary archive package to manage global resources (font files, font mapping tables, etc.). Later, it gradually evolved to directly use unpackaged resource files. Finally, the format of the font mapping file was also converted from binary to standard JSON <version-badge since="0.9" />.If the entry code you maintain still uses the old writing method, you can upgrade according to this article.

::: tip
Using the old model has problems such as maintenance trouble and difficulty in managing and editing global resources. It is recommended to upgrade immediately.
:::

## Remove `global.pkg`

### Old code characteristics

If you have any of the following patterns in your entry code, you are using `global.pkg`:

```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
static String globalUri(const String &path) { return "pkg:///" + path; }
```

The effect of these two lines is to route all `pkg:///` protocol resource requests to the `/global.pkg` file inside the binary archive package.

Why it needs to be removed:
- Every time you change resources such as fonts, you must re-run the packaging tool to generate a `.pkg` file
- It is not possible to directly view or replace individual files inside `.pkg` during debugging, and it is difficult to check the content.
- The packaging process relies on special tools, increasing communication and maintenance costs

### Migration operation

**Step one: Extract the resources in `global.pkg`.**

If you no longer have the `.pkg` source file, you can extract the contents from `global.pkg` (use the Glyphix command line tool or request the original resource file).Usually the following needs to be solved:

```
fonts/
NotoSans-Regular.ttf
NotoSansSC-Regular.ttf
...
font-faces ← font mapping file (will be upgraded to JSON later)
```

Place the extracted directory into your project resources directory, such as `/fonts/`.

**Step 2: Remove `global.pkg` related code.**

1. Delete the entire line `EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg")`
2. Delete wrapper functions such as `globalUri()`
3. Change all resource references of `pkg:///xxx` to direct file paths, that is, `/xxx`

**Step 3: Modify the font loading code.**

Assume your initialization code originally looked like:

```cpp
static String globalUri(const String &path) { return "pkg:///" + path; }

static void setupFont(const String &fontMap) {
String uri = globalUri(fontMap);
FontFaceMap &map = App()->fontManager()->faces();
if (!map.readFile(uri))
LogError() << "Failed to load font face map: " << fontMap;
}

int main() {
Application app;
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");

// ...
}
```

Use the file path directly instead (without the `globalUri()` function and `GlobalPackage` registration):

```cpp
static void setupFont(const String &fontMap) {
auto &map = App()->fontManager()->faces();
if (!map.readFile(fontMap))
LogError() << "Failed to load font face map: " << fontMap;
}

int main() {
Application app;
setupFont("/fonts/font-faces");
// ...
}
```

At this point the resource layout becomes:

```
/fonts/
font-faces ← binary format
NotoSans-Regular.ttf
...
```

At this stage you are still using the binary font-faces file, which will be upgraded to JSON in the next section.

## Use JSON font mapping file instead

### Old code characteristics

```cpp
FontFaceMap &map = App()->fontManager()->faces();
map.readFile("/fonts/font-faces");
```

`readFile` reads a custom binary format file. This binary file cannot be edited manually and must be converted from a CSS file using a packaging tool.

### JSON format description

Now we directly use JSON files to describe the font mapping relationship. You just need to create a `font-faces.json` file with the following format:

```json
{
"font-faces": [
{
"family": "sans-serif",
"weight": 400,
"style": "normal",
"urls": [
"NotoSans-Regular.ttf",
"NotoSansSC-Regular.ttf",
"NotoSansJP-Regular.ttf"
]
},
{
"family": "sans-serif",
"weight": 700,
"style": "normal",
"urls": [
"NotoSans-Bold.ttf"
]
},
{
"family": "serif",
"weight": 400,
"style": "normal",
"urls": [
"NotoSerif-Regular.ttf"
]
}
]
}
```

Field description:

| Field | Type | Required | Default value | Description |
|------|------|------|--------|------|
| `family` | String | Yes | - | Font family name, such as `sans-serif`, `serif` |
| `weight` | Integer | No | 400 | CSS font weight value (100-900), 400 is regular, 700 is bold |
| `style` | string | no | normal | font style, optional `italic` or `oblique` |
| `urls` | string array | yes | - | font file path, relative to the directory where the JSON file is located |

The key fields are further explained below.

**weight field**

Weight directly fills in the CSS font weight value, which will be rounded to the nearest standard value:

- `100` Thin
- `400` Regular (default value, just leave it blank)
- `700` Bold
- `900` Black

**urls path resolution**

Paths in `urls` are resolved relative to the directory where the JSON file is located. For example, the JSON file is located in `/fonts/font-faces.json`, then writing `"fonts/NotoSans-Regular.ttf"` in `urls` will eventually be parsed as `/fonts/fonts/NotoSans-Regular.ttf`.

Therefore, it is recommended that the JSON file be placed directly in the same directory as the font file, so that the URL can directly write the file name. For example, the directory layout is:

```
/fonts/
font-faces.json
NotoSans-Regular.ttf
NotoSansSC-Regular.ttf
NotoSans-Bold.ttf
```

At this time, the JSON content is as shown in the above code.

### Code modification

Replace `readFile` in the initialization code with `readJSON`:

```cpp
#include "gx_fontmanager.h"

static void setupFont() {
auto &map = App()->fontManager()->faces();
if (!map.readJSON("/fonts/font-faces.json"))
LogError() << "Failed to load font-faces.json";
App()->setFont(Font("sans-serif", 24));
}

int main() {
Application app;
setupFont();
// ...
}
```

For this API call change, the rest of the code does not need to be modified. Afterwards, you can directly edit `font-faces.json` to add or delete fonts or adjust the mapping relationship without any conversion tools.

## FAQ

**How to deal with the same family having multiple variants such as Regular, Bold, Italic, etc.?**

Add a separate entry for each variant in the `font-faces` array, differentiated by `weight` and `style`:

```json
{
"font-faces": [
{
"family": "sans-serif",
"weight": 400,
"style": "normal",
"urls": ["NotoSans-Regular.ttf"]
},
{
"family": "sans-serif",
"weight": 700,
"style": "normal",
"urls": ["NotoSans-Bold.ttf"]
},
{
"family": "sans-serif",
"weight": 400,
"style": "italic",
"urls": ["NotoSans-Italic.ttf"]
}
]
}
```

MCU projects usually only use Regular `sans-serif` fonts with `normal` weight, and the system will automatically fall back.

**Can multiple files be placed in the `urls` array?When is it needed?**

Can. When a font family needs to cover multilingual characters, put multiple font files into the same `urls` array. For example, `sans-serif` needs to support Latin letters, Chinese, Japanese and Korean characters, and Arabic at the same time:

```json
{
"family": "sans-serif",
"weight": 400,
"style": "normal",
"urls": [
"NotoSans-Regular.ttf",
"NotoSansSC-Regular.ttf",
"NotoSansJP-Regular.ttf",
"NotoSansArabic.ttf"
]
}
```

When the engine renders text, it looks for character glyphs in these files in order, and the first matching glyph is used.

**Do the font files have to be placed in the same directory as JSON?**

no. Paths in `urls` are resolved relative to the directory where the JSON file is located, you can use relative paths to place fonts in subdirectories. You can also use absolute paths, which are not affected by the JSON directory.

**Can I pass in JSON string directly in the code?**

Can. Use the two-argument overloaded version:

```cpp
map.readJSON("/fonts/", R"({
"font-faces": [
{"family": "sans-serif", "urls": ["NotoSans-Regular.ttf"]}
]
})");
```

The first parameter is baseUri, which is used to resolve relative paths in `urls`.

Native Module is a bridge between C++ and application layer JavaScript code. When you need to expose system capabilities to applications - such as reading sensor data, calling third-party SDKs, and accessing system capabilities, you need to write a Native Module.

The Glyphix framework has implemented many built-in modules through this mechanism, such as file system (`@system.file`), routing (`@system.router`), etc. You can add exclusive capabilities to your device in the same way.

Writing a Native Module requires the use of three sets of concepts: **JsVM bridging layer** provides type conversion and function calling capabilities between C++ and JavaScript; **Module registration macro** assembles C++ code into JavaScript `import` modules; **Applet sandbox** provides application-level context and resource life cycle management for modules. This chapter unfolds step by step in this order.

::: warning security risk
When you plan to develop "system-level extensions" for Glyphix, don't overlook that this also represents a high security risk. A little carelessness may introduce vulnerabilities, causing malicious applications to exploit these capabilities to attack the system or other applications. Be sure to follow secure coding practices, limit module permissions and access scope, and conduct adequate security testing.

## JsVM bridging layer

Before writing specific modules, you need to understand the interaction tools between C++ and JavaScript. The JsVM bridge layer is the infrastructure for the entire Native Module. It provides the `JsValue` type system and the `JsCallContext` calling context, enabling C++ code to create, read and manipulate JavaScript values.

### `JsValue` type system

`JsValue` is a C++ type representing JavaScript values in the framework, covering all JavaScript basic types. It uses reference counting to manage the life cycle and can be assigned and copied directly like C++ value types such as `int` and `String`.

Create JavaScript values from C++:

```cpp
JsValue undefined; // undefined
JsValue boolVal{true}; // boolean
JsValue intVal{42}; // number (integer)
JsValue floatVal{3.14}; // number (floating point)
JsValue strVal{"hello"}; // string
```

These constructors are implicit, so module functions can directly `return "hello"` or `return 42` without manual wrapping.

When reading C++ values ​​from `JsValue`, use the `as*` family of methods. They return specified default values when types do not match, avoiding manual type checking:

```cpp
int count = value.asInt(0); // Returns 0 if not a number
double ratio = value.asNumber(1.0); // If not a number, return 1.0
String label = value.asString(); // If it is not a string, return an empty string
```

If you need to perform type conversion according to JavaScript semantics (for example, convert any value to a Boolean), use the `to*` series of methods:

```cpp
bool enable = value.toBoolean(); // Any value can be converted to bool
int num = value.toInt(); // Convert to integer according to ECMAScript specification
String str = value.toString(); // Convert to string according to ECMAScript specification
```

When you need to determine the specific type of a value, use the `is*` series of methods:

```cpp
value.isUndefined() // Whether it is undefined
value.isNumber() // Whether it is a number
value.isString() // Whether it is a string
value.isObject() // Whether it is an object
value.isArray() // Whether it is an array
value.isFunction() // Whether it is a function
```

### `JsCallContext` context

Every C++ function called by JavaScript has a fixed signature:

```cpp
JsValue myFunction(JsCtx ctx);
```

`JsCtx` is an alias for `const JsCallContext &`.`JsCallContext` provides three core capabilities:

- **`ctx.argc()`**: Get the number of parameters passed in by JavaScript;
- **`ctx.arg(index)`**: Get the `index`th parameter (return `const JsValue &`);
- **`ctx.vm()`**: Get the current JavaScript engine instance (`JsVM &`).

A typical parameter reading pattern:

```cpp
static JsValue setVolume(JsCtx ctx) {
// Be sure to check the number of parameters first, and then verify the type, otherwise ctx.arg(0) may be out of bounds
if (ctx.argc() < 1 || !ctx.arg(0).isNumber())
return JsValue(); // The parameter is illegal and returns undefined

int level = ctx.arg(0).asInt(0);
level = std::max(0, std::min(100, level));
audioSetVolume(level);
return JsValue(true); // Return success flag
}
```

Many built-in module functions receive an object parameter. This is a flexible convention that allows parameters to have default values and facilitates future expansion:

```js
// JavaScript side call
setConfig({ brightness: 80, contrast: 50 })
```

Read object properties through `operator[]` on the C++ side:

```cpp
static JsValue setConfig(JsCtx ctx) {
if (ctx.argc() < 1) return {}; // Remember to check the number of parameters

JsValue params = ctx.arg(0);
int brightness = params["brightness"].asInt(100);
int contrast = params["contrast"].asInt(50);
// ...
return {}; // return undefined
}
```

### Export function as `JsValue`

Module functions do not have to be named static functions.`JsValue` can be constructed from any callable object: **uncaptured lambda** will be automatically parsed into a function pointer, with the same efficiency as a named function; **captured lambda** is packaged as a callable object, suitable for closing the module-level runtime state in a factory function:

```cpp
static JsValue createMathModule(JsVM &vm) {
JsValue mod = vm.newObject();

// No capture lambda: automatically degenerates into a function pointer, no additional overhead
mod["double"] = +[](JsCtx ctx) -> JsValue {
return ctx.arg(0).asInt(0) * 2;
};

// Lambda with capture: Read the configuration once when the module is created, and use it directly in subsequent calls
int factor = readScaleFactorFromConfig();
mod["scale"] = [factor](JsCtx ctx) -> JsValue {
return ctx.arg(0).asInt(0) * factor;
};

return mod;
}
```

The advantage of the Lambda form is that relevant logic can be written nearby in the factory function, avoiding a large number of short named functions scattered throughout the file. For functions that have simple logic and do not need to be reused on the C++ side, it is recommended to use lambda first.

### Create and return objects

In many scenarios it is necessary to return a result object containing multiple fields. Use `JsVM::newObject()` to create a new JavaScript object, and then set the properties through `operator[]`:

```cpp
static JsValue getSystemInfo(JsCtx ctx) {
JsValue result = ctx.vm().newObject();
result["model"] = "GX-Watch-2";
result["firmware"] = "2.1.0";
result["memory"] = 512; // KB
return result;
}
```

`JsVM` also provides other factory methods, such as `newArray()`, `newArrayBuffer()`, `newPromise()`, etc., to create various JavaScript types as needed.

###Exception and error handling

If a module function encounters an error, a JavaScript exception can be thrown via `JsVM::newError()`:

```cpp
static JsValue setConfig(JsCtx ctx) {
if (ctx.argc() < 1)
return ctx.vm().newError("missing parameters");
// ...
}
```

However, we generally do not use exceptions in simple scenarios such as function parameter checking, because the exception information text will occupy the amount of code. For non-critical errors, it is usually more appropriate to return `undefined` or `false`.

### Function interoperability

If you need to actively execute a JavaScript function or object method in C++, you can use `JsValue::call()` or `callMethod()`.This is as simple as calling a JavaScript function directly in C++, passing parameters through the initialization list and getting the return value:

```cpp
static JsValue printDemo(JsCtx ctx) {
JsVM &vm = ctx.vm();
JsValue obj = vm.newObject();
obj["value"] = 42;

// Call the method of the console object, equivalent to console.log("Object is:", obj) in JS
auto result = vm.globalObject()["console"]
.callMethod("log", {"Object is:", obj});

// print() can be used to directly output the contents of JsValue to the console to facilitate debugging
result.print(); // undefined

// If you only care about the execution and not the return value, and want to print a warning when an error occurs:
result.reportError(); // Returns a bool value indicating whether it is an exception

return {}; // return undefined
}
```

If you are calling an independent function object passed in as a parameter (rather than a method attached to the object), you need to use `call()` and specify the `this` binding object. You can usually use the global object `globalObject()`:

```cpp
static JsValue doMathAndCallback(JsCtx ctx) {
if (ctx.argc() < 1 || !ctx.arg(0).isFunction()) return JsValue();

auto &callback = ctx.arg(0); // You can get a reference here to avoid reference counting overhead
// This is the this object when the JS function is called. If it is {}, it is equivalent to undefined
JsValue thisObj = ctx.vm().globalObject();
// Equivalent to callback.call(globalThis, 10, 20) in JS
JsValue result = callback.call(thisObj, { 10, 20 });

return result;
}
```

::: warning Dangerous anti-pattern: leaked asynchronous callbacks
If your original intention is to store the `callback` passed in from JavaScript for a long time, such as passing it to the underlying hardware and using it to subscribe to events, please be careful:

```cpp
// ❌ Error demonstration: will cause memory leak!
static JsValue onButtonPress(JsCtx ctx) {
auto callback = callback = ctx.arg(0);
// Get the JavaScript callback directly from the parameter and capture it in a lambda, passing it to the underlying driver
HardwareButton::onPress([callback]() mutable {
callback.call({}, {...});
});
return {};
}
```

This is a classic **serious pitfall**: `JsValue` has lifecycle management based on reference counting. Once this closure is persisted with the global state by the underlying driver and does not provide an explicit cancellation mechanism (such as unbinding the corresponding `offPress` method), then this JavaScript callback and the entire application sandbox context to which it is bound will be **permanently leaked**!

If you need to implement long-lifecycle callbacks across event loops (such as event subscriptions), you must combine the lifecycle mechanism of the **application sandbox** to manage C++ objects and safely unbind them when not in use, or directly use the dedicated `AsyncSession` facility (see [Asynchronous Function Development](./async.md)).
:::

For more complex asynchronous scenarios (such as needing to return a Promise, or requiring multiple callbacks), please refer to [Asynchronous Function Development](./async).

::: tip Complete API reference
This section only covers the most commonly used capabilities of the JsVM bridging layer.`JsVM` and `JsValue` also provide many interfaces not covered in this section, such as: JSON parsing and serialization (`parseJSON()`, `stringifyJSON()`), property enumeration (`properties()`), Promise operations (`newPromise()`, `promiseResolve()`/`promiseReject()`), and direct execution of JSCode (`eval()`, `importModule()`), etc. For complete interface description, please refer to the API documentation distributed with the SDK.
:::

### Export C++ objects

The previous examples are all "functions returning basic types or ordinary JavaScript objects", essentially operating JavaScript through the C++ API.But sometimes it is necessary to export a **C++ object to JavaScript** so that the script can continue to operate on the same underlying instance.

There are several different ways to implement this:

- **`vm.newMetaObject(object)`**: The most direct, automatically exposes `GX_PROPERTY` / `GX_METHOD` to JavaScript;
- **`vm.newObject(object)` + manual hanging function**: closer to "ordinary JS objects with native handles";
- **`vm.newProxy()`**: The most flexible, but the attribute interception logic is scattered and the maintenance cost is the highest.

In most business scenarios, it is recommended to use `newMetaObject()` first. Only consider the other two approaches if you definitely need to hand-write a layer of JavaScript shapes, or if you need to intercept very dynamic property access.

#### `newMetaObject()` export

This is the simplest way. First define a native object type, and then directly wrap it into a reflective JavaScript object.

The following example exports a read-write counter object. It must inherit from `PrimitiveObject` and be declared into the meta-object system with `GX_OBJECT`:

```cpp
#include "gx_jsvm.h"
#include "gx_object.h"

using namespace gx;

class NativeCounter final : public PrimitiveObject {
GX_OBJECT

public:
explicit NativeCounter(int initial = 0) : m_value(initial) {}

int value() const { return m_value; }
void setValue(int value) { m_value = value; }

GX_METHOD void reset() { m_value = 0; }

// Needs to be exposed to JavaScript as a "constructor".
static JsValue constructor(JsCtx ctx) {
int initial = ctx.argc() ? ctx.arg(0).asInt(0) : 0;
auto *counter = new NativeCounter(initial);
return ctx.vm().newMetaObject(counter);
}

GX_PROPERTY(int value, get value, set setValue)

private:
int m_value = 0;
};
```

::: type of tip GX_METHOD
Functions marked with `GX_METHOD` can have any `Variant` managed type parameters and return values that can be converted to and from `JsValue`, and can be references. For example: `int`, `const String &`, etc.

Don't forget, `JsValue` itself can also be used.
:::

Then export this "constructor" in the module factory function:

```cpp
static JsValue createCounterModule(JsVM &vm) {
JsValue mod = vm.newObject();
mod["createCounter"] = NativeCounter::constructor;
return mod;
}
```

The JavaScript side is used like this:

```js
import counter from '@vendor.counter'

const c = counter.createCounter(10)
console.log(c.value) // 10
c.value = 42
c.reset()
console.log(c.value) // 0
```

Here `c` looks like a normal JavaScript object, but underneath it is actually associated with a `NativeCounter` instance. Since `newMetaObject()` is used, JavaScript can directly read and write properties declared by `GX_PROPERTY`, and can also call methods exposed by `GX_METHOD`.

If you just need to "naturally expose a C++ object as a JavaScript object" (including properties and methods), this is usually enough.

#### Handle Applet context

`newMetaObject()` has a common limitation: `GX_METHOD` exported through the meta-object system is an ordinary C++ member function. It cannot get `JsCtx` / `JsCallContext`, so it cannot directly write `Applet::current(ctx.vm())` like a module function.

If your object method needs to access the current application context, for example:

- Parse application private URI;
- Read application permissions or configurations;
- Continue to bind other resources to the current sandbox within the object method;

Then it is more appropriate to let this object inherit `BindableObject` and bind it to the current `Applet` when the object is created. In this way, subsequent `GX_METHOD` can directly access the host application through `applet()`.

Example:

```cpp
#include "gx_applet.h"
#include "gx_bindableobject.h"
#include "gx_jsvm.h"

using namespace gx;

class NativeFile final : public BindableObject {
GX_OBJECT_KINDS(NoneKind)

public:
NativeFile(Applet *applet, const String &uri)
: BindableObject(applet), m_uri(uri) {}

GX_METHOD String resolvedUri() const {
auto *host = applet();
return host ? host->resolveUri(m_uri) : String();
}

static JsValue constructor(JsCtx ctx) {
auto *applet = Applet::current(ctx.vm());
if (!applet) return {};

String uri = ctx.argc() ? ctx.arg(0).toString() : String();
return ctx.vm().newMetaObject(new NativeFile(applet, uri));
}

private:
String m_uri;
};
```

::: warning sandbox security
Don't actually implement `resolvedUri()` which directly exposes the underlying resource path, this is just an example. In actual development, be sure to perform permission checks and access control to avoid leaking sensitive information to the JavaScript side.
:::

There is no difference from the ordinary `newMetaObject()` object when used on the JavaScript side:

```js
const file = native.createFile('internal://files/config.json')
console.log(file.resolvedUri())
```

In this example, `resolvedUri()` does not have a `JsCtx` parameter, but it can still access `applet()` because the object is already bound to the current application when it is created.

::: two prerequisites for warning `BindableObject`
There are two additional points to note when using `BindableObject`:

- `BindableObject` comes with `ExplicitDeleteKind` by default. This means that it will not be automatically destroyed because the JavaScript object is GCed. If you want it to return to GC behavior like a normal Native Object, you can override this default value with `GX_OBJECT_KINDS(NoneKind)` as in the example above.
- `BindableObject` must be bound to `Applet`, otherwise `applet()` will always be a null pointer and the context cannot be discussed. The simplest way is to call `BindableObject(applet)` in the constructor, or bind to the current `Applet` immediately after creation.
:::

::: important legacy behavior
Before the official version v0.8.0, the behavior of `PrimitiveObject::objectKinds()` is inconsistent with this document. Please do not refer to the implementation details of older versions.
:::

`BindableObject` is not a replacement for [`newMetaObject()` export](#newmetaobject-export), but is a specialized solution when object methods need to remember the application context to which they belong. Only introduce this concept when you really need to access `Applet` within `GX_METHOD`.

#### `newObject()` and export the method manually

Sometimes you don't want to expose the entire meta-object interface, but just want to hang the C++ object as an opaque handle to the JavaScript object, and then manually decide which methods can be called. At this point you can use `vm.newObject()` to export the object.

In this way, `GX_PROPERTY` and `GX_METHOD` are not automatically exposed, so you need to hook the methods to the object yourself:

```cpp
class CounterCore final : public PrimitiveObject {
GX_OBJECT

public:
explicit CounterCore(int initial = 0) : m_value(initial) {}

int value() const { return m_value; }
void add(int delta) { m_value += delta; }

private:
int m_value = 0;
};

static JsValue createManualCounter(JsCtx ctx) {
int initial = ctx.argc() > ? ctx.arg(0).asInt(0) : 0;

JsVM &vm = ctx.vm();
JsValue obj = vm.newObject(new CounterCore(initial));

obj["add"] = [](JsCtx ctx) -> JsValue {
auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
if (!counter)
return {};
counter->add(ctx.arg(0).asInt(0));
return {};
};

obj["get"] = [](JsCtx ctx) -> JsValue {
auto *counter = dyn_cast<CounterCore *>(ctx.thisObject().object());
if (!counter)
return {};
return counter->value();
};

return obj;
}
```

What you see on the JavaScript side is a normal object:

```js
const c = counter.createManualCounter(10)
c.add(5)
console.log(c.get()) // 15
```

The characteristic of this writing method is that the shape of the JavaScript API is completely decided by you, but each method must internally retrieve the underlying C++ pointer from the `this` object and use `dyn_cast` to check the type. Compared to `newMetaObject()`, there is more boilerplate code and it is easier to miss checks.

But it also has a direct benefit: these manually hung functions are essentially ordinary `JsCtx` callbacks, so the current application context can be obtained directly through `Applet::current(ctx.vm())` like module functions. This is also an important difference between it and `GX_METHOD`.

This method cannot yet export property accessors (getters/setters), but only fixed property values.

#### Use `newProxy()` to export objects

If you need to take over all behaviors such as property reading and writing, method lookup, and lazy generation of fields, you can also use `vm.newProxy()`.This method can implement very dynamic interfaces, such as forwarding to the underlying dictionary when accessing any attribute name, generating sub-objects on demand, and intercepting writes for verification.

But it also comes with obvious costs:

- The behaviors of reading properties, writing properties, and method calling are all scattered in the proxy logic;
- API shapes are no longer directly expressed by class definitions like `newMetaObject()`;
- Once the behavior is complex, it will be more troublesome to troubleshoot the problem.

Therefore, `newProxy()` is more suitable for a small number of very dynamic bridging scenarios, rather than replacing regular object exports.

#### Life cycle rules

The destruction rules of Native Object are not determined by `newMetaObject()` alone, but by `objectKinds()` of C++ objects:

- If the object contains `RootKind` and **does not** `ExplicitDeleteKind`, then the C++ object will also be automatically destroyed when the corresponding JavaScript object is recycled by GC;
- If the object is a child node of another object, or `ExplicitDeleteKind` is declared, its life cycle is still responsible for the C++ side.

For most "independently wrapped objects", directly inheriting `PrimitiveObject` without additionally declaring `ExplicitDeleteKind` can usually get the appropriate default behavior, that is, automatic destruction with GC.

If you are not familiar with these object life cycle markers, it is recommended to read the chapter about `PrimitiveObject` in [Object System](./object-system.md) before deciding whether to hand over the object to JavaScript GC management.

#### Retrieve Native Object from `JsValue`

Sometimes another Native Module function receives this object as a parameter, in which case the underlying C++ pointer can be temporarily retrieved from `JsValue`:

```cpp
static JsValue getCounterValue(JsCtx ctx) {
if (ctx.argc() < 1 || !ctx.arg(0).isObject())
return {};

auto *counter = dyn_cast<NativeCounter *>(ctx.arg(0).object());
if (!counter)
return {};
return counter->value();
}
```

`object()` only provides **temporary access** and does not transfer ownership. If you really need to "take" the object away from the JavaScript side, you should use the template form of `moveObject<T>()`:

```cpp
auto *counter = value.moveObject<NativeCounter>();
```

**Don't** write it like this:

```cpp
auto *counter = dyn_cast<NativeCounter *>(value.moveObject());
```

Once the types do not match, this code will lose object ownership after the transformation fails, causing a leak. The API documentation also clearly recommends using `moveObject<T>()` in preference to merging "type checking" and "ownership transfer" into one step.

::: warning When not to export Native Object
If you just want to return a simple result data, such as device information, one-time calculation results, and configuration snapshot, give priority to returning the JavaScript object constructed by ordinary `newObject()`.It is only worthwhile to introduce Native Object when JavaScript needs to continue to operate on the same C++ instance in the future.
:::

## Module definition and registration

After mastering the basic tools of the JsVM bridging layer, you can assemble C++ functions into a complete Native Module. A module consists of two parts: a **factory function**, which is responsible for creating the module object and mounting C++ functions on it; and a **registration macro**, which is responsible for registering the factory function into the framework's module system.

::: tip
If you are developing non-standard system extensions, it is recommended to give priority to using the [Library Loader](#library-loader) mechanism.
:::

### Module structure

Take the implementation of a device information module `@vendor.device` as an example:

```cpp
#include "gx_jsvm.h"

using namespace gx;

// C++ functions in the module
static JsValue getDeviceName(JsCtx ctx) {
return "MyDevice-Pro";
}

static JsValue getBatteryLevel(JsCtx ctx) {
int level = /* Read the power from the driver */ 85;
return level;
}

//Factory function: build module object and return
static JsValue createDeviceModule(JsVM &vm) {
JsValue mod = vm.newObject();
mod["getDeviceName"] = getDeviceName;
mod["getBatteryLevel"] = getBatteryLevel;
return mod;
}

// Register the module so that it is accessible in JavaScript at the @vendor.device path
GX_JSVM_MODULE(vendor_device, "vendor.device", createDeviceModule)
```

The `GX_JSVM_MODULE` macro accepts three parameters: C++ variable name, JavaScript module path (without `@` prefix), and factory function. The factory function is called when the module is imported for the first time, and the returned JsValue object is the module obtained by the JavaScript side.

On the JavaScript side, the application uses the module like this:

```js
import device from '@vendor.device'

const name = device.getDeviceName()
const battery = device.getBatteryLevel()
```

::: tip This is a Demo!
This seems pretty simple, but it ignores a big problem: most APIs are asynchronous!We should not read the power in the JavaScript execution context, that is, the UI thread, unless we are really doing a demo. For asynchronous APIs, see the [Asynchronous Function Development](./async.md) chapter for more suitable patterns and examples.
:::

### Enable module

Simply declaring the module is not enough, you also need to "install" it into the JavaScript engine when the framework is initialized. This is done via the `GX_JSVM_MODULE_IMPORT` macro:

```cpp
GX_JSVM_MODULE_IMPORT(vendor_device)
```

`GX_JSVM_MODULE` declares a global variable in the file scope, and `GX_JSVM_MODULE_IMPORT` finds and calls the `install()` method of this variable. The name parameter (first parameter) of the two macros must be the same.

A common approach is to group all `GX_JSVM_MODULE_IMPORT` calls into one function for easier management:

```cpp
void installVendorModules() {
GX_JSVM_MODULE_IMPORT(vendor_device)
GX_JSVM_MODULE_IMPORT(vendor_sensor)
GX_JSVM_MODULE_IMPORT(vendor_bluetooth)
}
```

Call `installVendorModules()` after `AppletKit` has been initialized to ensure that modules are available when the application starts.

## Library Loader

Native Module is suitable for implementing framework-level system APIs that are universally available to all applications. However, for **non-standard system customization functions**, such as vendor-specific data access, private SDK packaging, or the ability to only be open to specific authorized applications, it is more recommended to use the **Library Loader** mechanism.

Library Loader loads by name via the [`loadLibrary()`](/api/system-app.md#loadlibrary) method provided by the `@system.app` module:

```js
import app from '@system.app'

const lib = app.loadLibrary('custom-library')
lib.someFunction()
```

Compared with Native Module, Library Loader has two significant advantages:

- **No need for global registration**: Does not rely on `GX_JSVM_MODULE` macro and `GX_JSVM_MODULE_IMPORT`, module objects are created on demand when called;
- **Easy to simulator rollback**: The application side can detect whether the return value of `loadLibrary()` is `undefined` and gracefully downgrade to a script-implemented stub in a general simulator environment. However, the stub trick imported by such modules as `import lib from '...'` is more hacky and anti-pattern.

```js
import app from '@system.app'

//Try to load the native library and fall back to the script stub in the simulator
const nativeLib = app.loadLibrary('custom-library')
const lib = nativeLib || {
someFunction() { /* Simulator implementation */ }
}
```

Except for the registration method and the usage method on the JavaScript side, Library Loader is basically the same as Native Module in other aspects.

### Register Library Loader

On the C++ side, register a loader function via `AppletKit::setLibraryLoader()`.The loader receives the `Applet` instance that made the call and returns the library object (a `JsValue`):

```cpp
#include "gx_appletkit.h"
#include "gx_jsvm.h"

using namespace gx;

static JsValue getDeviceName(JsCtx ctx) {
return "MyDevice-Pro";
}

void installLibraries() {
AppletKit::instance()->setLibraryLoader(
"custom-library",
[](Applet *applet) -> JsValue {
JsVM &vm = JsVM::current();
JsValue lib = vm.newObject();
lib["someFunction"] = getDeviceName;
return lib;
}
);
}
```

`setLibraryLoader()` can be called after `AppletKit` is initialized. There is no need to register again every time the application is started.

The loader of Library Loader receives `Applet*`, so it can directly perform **application permission verification** at the entrance and refuse to provide functions to unauthorized applications without having to repeat the check inside each module function:

```cpp
AppletKit::instance()->setLibraryLoader(
"custom-library",
[](Applet *applet) -> JsValue {
// Permission check: Unified interception of unauthorized access at the entrance
if (!applet || !applet->permission(vendor::Permission::AccessCustomLib))
return vm.newError("permissions denied"); // Return undefined

JsVM &vm = JsVM::current();
JsValue lib = vm.newObject();
lib["someFunction"] = getDeviceName;
return lib;
}
);
```

If the loader returns `undefined` (i.e. the default constructed `JsValue()`), `app.loadLibrary()` also gets `undefined` on the JavaScript side, and the application can perform fallback processing accordingly.

::: tip
It is not recommended that the loader function throws an exception when the permission check fails, but returns `undefined` by default. In addition to making it easy to downgrade on the JavaScript side, this also avoids leaking module existence information if you don't want unauthorized applications to know that the library exists.
:::

## Collaborate with application sandbox

The module functions introduced in the previous chapters are all stateless - they receive parameters, return results, and do not hold any context. But many practical scenarios require the module to be associated with the currently running application: reading the application's resource path, language settings, or hosting a long-lived C++ object in the application sandbox. This requires using the capabilities provided by `Applet`.

### Get the current application context

Obtain the application instance to which the caller belongs through `Applet::current()`:

```cpp
#include "gx_applet.h"

static JsValue readPreference(JsCtx ctx) {
auto applet = Applet::current(ctx.vm());
// Since subsequent operations rely on applet, be sure to check whether the context is successfully obtained.
if (!applet) return JsValue();

//Read the application's private storage path
String storagePath = applet->resolveUri("internal://files/preferences.json");
// ...
}
```

`Applet` instances are automatically managed by the framework, and each application runs in its own independent JavaScript Realm.`Applet::current()` derives the corresponding application instance through the current Realm. Therefore, when the same module function is called in different applications, each independent context is obtained.

### Resource life cycle management

If a module function needs to allocate a long-lived C++ object (such as a background task that continuously monitors hardware status), **Never** use global variables or raw pointers to hold the resource across calls - this will allow the resource to escape tracking by the application sandbox, which will not only prevent the resource from being released after the application exits, but also lose the key security guarantees given by the sandbox.

There is a serious security requirement here: **Native Module must ensure that all operation paths that access C++ objects undergo strict ownership and type checking**, rather than just providing "legal paths" and leaving the possibility of bypassing it. The correct way to do this is to completely delegate the object life cycle to the `Applet` sandbox management, and force the use of `takeObject<T>()` for verification in **every** module function that receives an integer handle - this is an invariant that cannot be omitted, and will be explained below.

The following takes the function of continuously monitoring sensor status as an example to demonstrate this safe life cycle binding mechanism.

::: tip
The code in this section is actually a crude replacement for the `AsyncSession` principle in the [Asynchronous Function Development](./async.md) chapter, and is only used to demonstrate the concept. In actual business development, it is strongly recommended to directly use mature `AsyncSession` related facilities to handle asynchronous tasks. They are also implemented based on the methods introduced in this section at the bottom level.
:::

Suppose we have a sensor. The application needs to start listening during initialization, then read the latest data multiple times, and manually stop listening when it is not needed. First, we define the carrier of this background task:

```cpp
class SensorListener : public PrimitiveObject {
GX_OBJECT
public:
SensorListener() {
// Start the sensor and request the underlying driver hardware resources...
}
~SensorListener() override {
// Stop the sensor and release related hardware resources...
}
int latestValue() const { return m_value; }

private:
int m_value = 0;
};
```

#### Bind objects to the sandbox

Use `Applet::bindObject()` to bind the instance to the current application sandbox, returning an integer handle for the JavaScript side to hold:

```cpp
static JsValue startSensor(JsCtx ctx) {
auto applet = Applet::current(ctx.vm());
if (!applet) return {};

auto *listener = new SensorListener();
// Hand over the object to the Applet for management and obtain an integer handle (ID)
int bindId = applet->bindObject(listener);

// Return the ID to JavaScript as a unique credential for subsequent operations on the object
return bindId;
}
```

Since the object is now managed by the sandbox, even if the application exits during the task or is forcibly killed by the system, the sandbox will automatically clean up all bound objects when destroyed, thereby avoiding resource leaks.

#### Safely retrieve objects

When the JavaScript side needs to operate on a previously created object, it must pass `Applet::takeObject<T>()` to retrieve the instance according to the handle without any form of "naked conversion":

```cpp
static JsValue readSensor(JsCtx ctx) {
auto applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1) return {};

int bindId = ctx.arg(0).asInt();
auto *listener = applet->takeObject<SensorListener>(bindId);
if (!listener) return {}; // If the ID is invalid or the type does not match, return nullptr

return listener->latestValue();
}
```

`applet->takeObject<T>()` only accesses IDs belonging to the current sandbox (to prevent cross-application unauthorized access), and then verifies **type matching** through object meta information. A non-null pointer is returned only if both levels are passed.

:::danger must access the object through `takeObject<T>()`
An integer ID from JavaScript is completely untrustworthy on the C++ side - it could be forged, or an out-of-date reference. Lack of validation can lead to serious security vulnerabilities:

```cpp
// ❌ Never do this!
static JsValue readSensor(JsCtx ctx) {
auto bindId = ctx.arg(0).asInt();
// Only use the non-template version of takeObject + static_cast, bypassing type checking and sandbox bounds checking
auto *binded = applet->takeObject(bindId);
// Danger: static_cast has no runtime check, and bound here may not be a SensorListener at all!
auto *listener = static_cast<SensorListener *>(binded);
return listener->latestValue(); // Can cause arbitrary memory reading and writing
}
```
:::

#### Unbinding and Destruction

When you need to actively terminate the task from the C++ side and completely release the resources, first use `takeObject<T>()` to retrieve and verify the type, then use `unbindObject()` to release the hosting, and finally destroy it manually:

```cpp
static JsValue stopSensor(JsCtx ctx) {
Applet *applet = Applet::current(ctx.vm());
if (!applet || ctx.argc() < 1) return {};

int bindId = ctx.arg(0).asInt();
auto *listener = applet->takeObject<SensorListener>(bindId);
if (listener) {
applet->unbindObject(listener); // Unbind from the automatic management list
delete listener; // Manual destruction
}
return {};
}
```

The complete usage process of JavaScript front-end side:

```javascript
import sensor from '@vendor.sensor'

// Start and temporarily store credentials
const id = sensor.startSensor()
// ...read multiple times
const value = sensor.readSensor(id)
//The task ends and resources are released
sensor.stopSensor(id)
```

Due to the backing support provided by `bindObject`, even if the application forgets to call `stopSensor()`, all bound objects will be automatically released when the sandbox exits.


::: important must be automatically unbound
Since the JavaScript code is not trusted, it cannot be assumed to call functions that release resources. Sandbox leaks caused by JavaScript reference leaks are an effective attack method for malicious applications. Therefore, all objects bound to the sandbox must be automatically unbound when the sandbox is destroyed to ensure that no matter what JavaScript does, it does not cause resource leaks.

Any design that requires JavaScript side unbundling is dangerous and must be avoided.
:::

### Security Protection

Although there are many safety requirements highlighted above, this may not be enough to eliminate all risks. To further strengthen the security line, we recommend directly restricting access to extensions to trusted applications. You can directly check the permission ID or identity information of `Applet` in the module factory function and deny access that does not meet the conditions:

```cpp
static JsValue createDeviceModule(JsVM &vm) {
auto applet = Applet::current(vm);
if (!applet || !applet->permission(
vendor::Permission::AccessDeviceInfo)) {
// If there is no permission, return an empty object or throw an exception
return vm.newError("permissions denied");
}

//Only after authorization can you create module objects and expose functions
JsValue mod = vm.newObject();
mod["getDeviceName"] = getDeviceName;
// ...
return mod;
}
```

This strategy effectively blocks unauthorized access at the entrance. Even if the module function itself is not robust enough, an attacker cannot use it to obtain sensitive information or perform malicious operations.

Library Loader's entry permission check has been introduced in relevant documentation.

## Reflection and meta-object compiler

Standard C++ classes are "silent": once you get an object pointer, you cannot know at runtime what members it has, what their names are, and how to read and write them. This is not an obstacle for static C++ development that does not require scripting.

But Glyphix works differently. When the application page template writes `:value="progress"`, the responsive framework needs to find the corresponding property of the control according to the string `"value"` at runtime, and automatically refresh when the data changes. This ability to "understand its own structure while the program is running" is called Reflection and is not supported by standard C++.

Glyphix's solution is to add a **Meta Compiler** to the build process. It scans the source code before formal C++ compilation, generating metadata for classes that need to participate in the object system. Developers simply put the **`GX_OBJECT`** macro at the beginning of the class definition and the meta-object compiler will process the class - the framework can then read and write its properties or call methods by name, and access it from JavaScript.

You don't need to understand the internals of the meta-object system just yet. Just remember one rule: any class that requires reflection capabilities must be defined with the `GX_OBJECT` macro and inherit from `PrimitiveObject` or `Object`.

## `PrimitiveObject` and `Object`

The object system of the framework is divided into two levels:

**`PrimitiveObject`** is the root base class for all **managed objects**.Classes that inherit it have framework capabilities such as attribute reflection, dynamic transformation, and safe delayed destruction. But `PrimitiveObject` itself has no parent-child tree structure - it is just a "framework-aware C++ object".Types such as `AsyncSession` and `BindableObject` all inherit from it because these classes do not need to form a tree.

**`Object`** inherits from `PrimitiveObject`, with an additional **parent-child tree structure**: the `parent` pointer is passed in during construction, and when the parent object is destroyed, all child objects will also be destroyed recursively. The Widget Tree is organized through this mechanism.

::: tip analogy to other frameworks
If you have Qt development experience, you can compare Glyphix's meta-object system to Qt's MOC system: `GX_OBJECT` corresponds to `Q_OBJECT`.But there are also many differences. For example, Glyphix splits the capabilities of `QObject` in Qt into two layers; `Signal` is just an ordinary template class that does not rely on the meta-object compiler.

Other frameworks such as Unreal Engine's UCLASS also have similar reflection systems.
:::

Which base class you choose depends on whether your class needs to be part of a tree:

```cpp
// Need to participate in the object tree → inherit Object
class MySensor : public Object {
GX_OBJECT
public:
explicit MySensor(Object *parent = nullptr) : Object(parent) {}
};

// Only frame aware, not involved in the tree → Inherit PrimitiveObject
class MyNetworkSession : public PrimitiveObject {
GX_OBJECT_KINDS(ExplicitDeleteKind)
public:
MyNetworkSession() = default;
};
```

`GX_OBJECT_KINDS(ExplicitDeleteKind)` in the code is an additional declaration, which declares the meta-object class like the `GX_OBJECT` macro, but tells the framework that the life cycle of this object is the responsibility of the developer and will not be automatically recycled by JavaScript. Lifecycle-sensitive types such as `AsyncSession` use it.

## Properties and signals

The **`GX_PROPERTY`** macro is used to declare a property that is aware of the framework and associates the corresponding getter and setter. After declaration, the property can be driven by the framework's reactive system - its UI is automatically refreshed when the value changes, and the animation system can also interpolate it:

```cpp
class MyWidget : public Widget {
GX_OBJECT
public:
int value() const { return m_value; }
void setValue(int v) { m_value = v; update(); }

GX_PROPERTY(int value, get value, set setValue)

private:
int m_value = 0;
};
```

### Signal

**`Signal<>`** is an event notification mechanism and is directly declared as a class member."Emit" an event when it occurs, and other objects receive notifications through "connections" ([lambda expression](https://en.cppreference.com/w/cpp/language/lambda) is C++'s anonymous function syntax):

```cpp
class MyWidget : public Widget {
GX_OBJECT
public:
Signal<int> valueChanged;

void setValue(int v) {
m_value = v;
valueChanged(v); // emit signal
}
private:
int m_value = 0;
};

// Connect to member function
myWidget->valueChanged.connect(this, &MyClass::onValueChanged);

// Or connect to lambda
auto slot = make_slot([](int v) { /* Respond to changes */ });
myWidget->valueChanged.connect(slot);
```

::: Comparison of signals and slots between tip and Qt
Qt's classic signal and slot mechanism requires MOC generated code support, but `Signal<>` is a pure C++ template class and does not rely on the meta-object compiler. So it is not necessary to use the `Signal<...>` object in a specific class, you can use it anywhere.

Since `Signal` is a class, it will occupy memory space (even if there is no connection), so it is recommended to use event type enumeration and single signal member variable to save memory instead of declaring a `Signal` member for each event.
:::

### Full form of `GX_PROPERTY`
In addition to `get` / `set`, `GX_PROPERTY` also supports declaring associated change signals (`signal`), which is the standard interface for reactive frameworks to subscribe to property changes:

```cpp
class ProgressRing : public Widget {
GX_OBJECT
public:
int value() const { return m_value; }
void setValue(int v) {
if (m_value == v) return;
m_value = v;
update();
valueChanged(v);
}

Signal<int> valueChanged;

GX_PROPERTY(int value, get value, set setValue, signal valueChanged)

private:
int m_value = 0;
};
```

If a `signal` property is declared, its changes will be automatically passed to the JavaScript expression bound to the property through the reactive framework. This is the basis for two-way synchronization of control properties and application data.

The `signal` field in `GX_PROPERTY` does not depend on the parameter type of `Signal<T>`, the framework only cares about whether it exists and when it is emitted. Instead, a `get` field must be provided to let the framework read the property value on the JavaScript side.

## Guard pointers and memory safety

In the GUI framework, asynchronous scenarios can easily cause dangling pointer crashes. A typical case:
```cpp
void onNetworkResponse(const String &data) {
//The network request takes 2 seconds to return
// But within these 2 seconds, the user may have exited the current page and the label has been destroyed
this->label->setText(data); // Segmentation Fault!
}
```
All asynchronous scenarios such as timer callbacks and IO callbacks face the same risk. In a scriptable framework, this use case is structurally unavoidable, so a safe lifecycle observation mechanism must be provided.

### `Pointer<T>` guard pointer

Glyphix has built-in weak reference counting support for all derived classes of `PrimitiveObject`.Use `Pointer<T>` to hold non-ownership cross-object references. When the target object is destroyed, `Pointer<T>` will automatically be nulled and can be used safely by checking before dereferencing:

```cpp
Pointer<Label> m_label; //Declared as a member variable

// ...assignment after construction...
m_label = label;

// In any asynchronous callback that may cause label to be destroyed:
void onNetworkResponse(const String &data) {
if (!m_label)
return; // label has been destroyed, safe exit
m_label->setText(data); // Access is safe at this time
}
```

::: tip when to use
When holding a pointer across objects but not owning its lifetime, use `Pointer<T>` instead of a raw pointer `T *` to track the lifetime.`Signal`'s `connect` mechanism also relies on guard pointers - when the receiver (the object where the slot is located) is destroyed, the connection is automatically disconnected and no dangling callbacks are triggered.
:::

::: warning thread limit
Guard pointers do not support cross-thread access, they are basically limited to the UI thread, and they are not a zero-overhead abstraction. Each construction involves a reference counting operation.
:::

### `SharedRef<T>` Intrusive reference counting

For ordinary value objects that do not inherit from `PrimitiveObject` (such as custom data structures), the framework provides intrusive shared reference counting. By letting the value type inherit `SharedValue` and then using `SharedRef<T>` to hold it, you can obtain sharing semantics similar to [`std::shared_ptr`](https://en.cppreference.com/w/cpp/memory/shared_ptr) while avoiding additional control block allocation:

```cpp
class MyData : public SharedValue {
public:
int x = 0;
String name;
};

auto ref1 = make_shared<MyData>();
ref1->x = 42;

SharedRef<MyData> ref2 = ref1; //Increase the reference count and share the same object
```

`SharedRef` also supports copy-on-write (COW) semantics: before modifying the copied version, an independent copy is created to ensure that multiple holders do not interfere with each other. This mechanism uses atomic reference counting to achieve thread safety.

## Dynamic type conversion

Standard C++'s [`dynamic_cast`](https://en.cppreference.com/w/cpp/language/dynamic_cast) relies on RTTI (Runtime Type Information), while embedded environments are usually compiled with `-fno-rtti`.`dyn_cast` provides equivalent runtime-safe downcast capabilities using the meta-object system.

The target type `T` of `dyn_cast<T *>()` must satisfy two conditions:
1. Inherited from `PrimitiveObject`
2. Declared the `GX_OBJECT`/`GX_OBJECT_KINDS` macro

```cpp
PrimitiveObject *obj = getSomeObject();

// Safe downward transformation, if the transformation fails, return nullptr
auto *btn = dyn_cast<Button *>(obj);
if(btn)
btn->setText("OK");

// const version is also supported
const auto *constBtn = dyn_cast<const Button *>(obj);
```

::: warning `GX_OBJECT` is a prerequisite
The type checking of `dyn_cast` relies on the static meta-object information (`staticMetaObject`) of the target class. If the target class does not declare `GX_OBJECT`, necessary runtime type information is lacking and a compilation error occurs.
:::

In Native Module development, `dyn_cast` is particularly commonly used: the framework often passes objects in as base class pointers (`PrimitiveObject *` or `Object *`), and `dyn_cast` is needed to safely restore them to specific types before operating.

Considering that the sandbox security policy does not trust the object passed in by the script, we cannot assume that the runtime object pointer passed in is the correct type, so `dyn_cast` must be used to verify the type and safely access its members.

### Memory leak trap

Typical `dyn_cast` usage patterns imply a memory leak risk, such as:
```cpp
auto *session = dyn_cast<Session *>(takeObjectOwnership());
if (session) {
// Successful transformation, accessing session members and transferring ownership
}
```
The problem is that if the object returned by `takeObjectOwnership()` is not of type `Session`, `dyn_cast` will return `nullptr`, but the ownership of the original object has been transferred - which will cause a memory leak if there is no other mechanism to recycle the object.

When developing Native Module API, you sometimes encounter this problem, and related frameworks provide better APIs to avoid this situation. But developers should be aware of this potential risk and not be misled by the security of `dyn_cast`.

### Is `GX_OBJECT` necessary?

Not all classes that inherit from `PrimitiveObject` require `GX_OBJECT`.The function of the `GX_OBJECT` macro is to register the class with the meta-object system and enable capabilities such as reflection, property binding and `dyn_cast`.If your class:

- No need to expose to JavaScript
- No need for reflection mechanisms such as `GX_PROPERTY` and `GX_METHOD`
- No need to be safely cast by `dyn_cast`

Then you can omit `GX_OBJECT`, just inherit the base class and use C++ features normally:

```cpp
// Internal auxiliary class that does not require any meta-object capabilities, omit GX_OBJECT
class InternalBufferManager : public PrimitiveObject {
public:
explicit InternalBufferManager() = default;
void flush();
private:
// ...
};
```

Classes that omit `GX_OBJECT` still have the basic capabilities of `PrimitiveObject`, including `deleteLater()` and guard pointer support, but lose reflection and dynamic type recognition capabilities.

Another situation is that your final type requires meta-object capabilities, but some intermediate base classes do not, then the intermediate base classes do not need to declare `GX_OBJECT`.This will lose some runtime type information, but can reduce the code size.

::: tip
If you are not sure whether you need `GX_OBJECT`, it is generally recommended to add it conservatively.
:::

One last important difference is this: once the `GX_OBJECT` tag is used, the class must be located in a header file (`*.h`) and registered with the build system using the `glyphix_add_meta_objects()` CMake macro. Classes without `GX_OBJECT` do not have this requirement and can be defined directly in the `.cpp` file.

## Runtime type system

In all the previous discussions about `GX_PROPERTY`, there is one question that has never been answered:

```cpp
GX_PROPERTY(int value, get value, set setValue)
```

How does JavaScript know what `int` is?When JavaScript profile writes `widget.value = 42`, this `42` is JavaScript’s `number` type. And `setValue(int v)` accepts C++ `int`.What happened in between?Conversely, how does the `int` returned by `getValue()` become a `number` in JavaScript?

Without any glue code, the framework obviously needs to do some work behind the scenes to bridge C++ static types and dynamic script types. This is a fairly transparent process, and this section explains what happens in the middle.

### Universal type container `Variant`

The answer lies in `Variant`.It is a type erasure container that can hold any type of value and is the core bridge connecting the C++ static type system and JavaScript dynamic types.

Whenever the framework needs to cross this boundary, it takes the `Variant` path:

1. **Property reading and writing middle layer**: When the properties declared by `GX_PROPERTY` are read and written through the reflection API, the value is passed in `Variant`.The framework converts JavaScript's `JsValue` into `Variant`, and then converts `Variant` into the actual parameter type of the C++ setter; the direction is reversed when reading.
2. **Method call parameter marshalling**: The parameters and return values ​​of `GX_METHOD` are represented by `Variant` before being passed to C++.

```cpp
Variant v1; // Null
Variant v2{42}; // store int
Variant v3{3.14}; // store double
Variant v4{String("Hello")}; // Store String
// Variant must be explicitly constructed and does not support implicit conversion
// Variant v5 = 42; // Error, must write Variant v5{42};

// type checking
if (v2.is<int>()) { /* ... */ }
// It is not recommended to check the convertibility, but directly use to<T>() to determine whether it is an illegal value.
if (v3.convertible<double>()) { /* ... */ }

// Read by reference (fastest, requires exact type matching)
int n = v2.as<int>();
// Read by reference, return the default value if the type does not match
double d = v2.as<double>(0.0); // int != double, returns 0.0
// Read with type conversion (by value)
int fromDouble = v3.to<int>(); // 3.14 -> 3
String fromInt = v2.to<String>(); // 42 -> "42"
```

::: tip
This is not C++17's [`std::variant`](https://en.cppreference.com/w/cpp/utility/variant), but more like [`std::any`](https://en.cppreference.com/w/cpp/utility/any) which supports runtime type recognition and automatic type conversion.

Usually you don't need to manipulate `Variant` directly in business code, the framework automatically completes all conversions. You will only deal with it directly when implementing low-level framework extensions, writing common utility functions, or when you need to directly operate the runtime reflection API.
:::

### Built-in type mapping

The framework has built-in bidirectional mapping to JavaScript for common C++ basic types:

| C++ types | JavaScript types | Remarks |
|:---:|:---:|:---:|
| `int`, `float`, `double`, etc. | `number` | Direct mapping of numerical types |
| `bool` | `boolean` | |
| `String` | `string` | |
| Subclasses of `PrimitiveObject *` | JavaScript object references | Object lifecycle managed by the framework |
| `Color`, `Length` and other value types | `string` | Represented by a string in a specific format |
That's why after you write `GX_PROPERTY(int value, ...)`, the JS side can directly do `widget.value = 42`: `int` is in the built-in mapping table, and the framework knows how to convert the type.

:::note don't use C strings
`Variant` requires ownership of the storage type `T`, so non-owning types such as C strings (`const char *`), string slices (`String::View`), etc. cannot be stored in `Variant`.Please always use `String` to represent text data. If necessary, you need to explicitly convert it to `String` and store it in `Variant`.

If an unsupported string type is used, a compilation error will result.
:::

::: important
The built-in type map does not register a mapping related to `std::string`, so it is not recommended to store `std::string` in `Variant`.An unmapped type can be stored normally, but it is treated as an opaque C++ object and cannot be used in JavaScript.
:::

### Complex type reflection

For classes declared with `GX_OBJECT`, `GX_ENUM` and `GX_STRUCT` can also be used to export enumeration and structure member types so that they can also be used in a natural way in JavaScript. This type of export is automatic and does not require hand-written additional binding code.

#### Enum reflection `GX_ENUM`

When the parameter type of a property or method is a C++ enumeration, exposing it directly to JavaScript as an integer is both unintuitive and error-prone.`GX_ENUM` exports an enumeration as a string constant, allowing JavaScript to operate with human-readable strings instead of magic numbers:

```cpp
class ScrollArea : public Widget {
GX_OBJECT
public:
enum GX_ENUM ScrollBarStyle {
RemoveScrollBar GX_ALIAS("hidden"),
LinearScrollBar GX_ALIAS("line"),
DotsScrollBar GX_ALIAS("dots")
};

GX_PROPERTY(ScrollBarStyle indicator, set setScrollBar)
};
```

`GX_ENUM` is placed after the `enum` keyword to tell the meta-object compiler that this enumeration needs to be exported.`GX_ALIAS("...")` specifies a JavaScript-visible string name for each enumeration member - if omitted, the original name of the C++ member is used by default. Application developers use JavaScript like this:

```js
scroll.indicator = "hidden"; // Corresponds to RemoveScrollBar
scroll.indicator = "dots"; // Corresponds to DotsScrollBar
```

When the framework reads the `indicator` attribute, it converts the string `"dots"` into the `DotsScrollBar` enumeration value and then passes it to the setter; when reading, the enumeration value is converted back to a string. The entire process is completely transparent to the C++ side, and the C++ code always operates on specific enumeration types.

#### Structure parameter reflection `GX_STRUCT`

For method parameters, sometimes an operation requires multiple related configuration items. At this time, the parameters can be encapsulated into a structure and exported using `GX_STRUCT`, so that the JavaScript side can pass in an object literal:

```cpp
class Scroll : public ScrollArea {
GX_OBJECT
public:
struct GX_STRUCT ScrollOptions {
Length left;
Length top;
ScrollBehavior behavior;
};
struct GX_STRUCT IndexOptions {
int index;
ScrollBehavior behavior;
};

GX_METHOD void scrollTo(const ScrollOptions &options);
GX_METHOD void scrollBy(const ScrollOptions &options);
GX_METHOD void setIndex(const IndexOptions &options);
};
```

`GX_STRUCT` is placed after the `struct` keyword, and each field of the structure is automatically exported according to its type (also via built-in type mapping or nested `GX_ENUM`).The JS side can directly pass in the object:

```js
scroll.scrollTo({ left: 0, top: 200, behavior: "smooth" });
scroll.setIndex({ index: 3, behavior: "instant" });
```

What `scrollTo` on the C++ side receives is always a strongly typed `ScrollOptions` object, without any parsing on the C++ side.

::: warning Don’t forget to mark
When declaring `GX_PROPERTY` or `GX_METHOD`, if the related type is a custom enumeration or structure, be sure to mark `GX_ENUM` or `GX_STRUCT` correctly. Otherwise, the JavaScript side cannot use these properties or methods, and there will be no compilation error prompt.
:::

### Is there an "intermediate representation"?

When using `Variant` to bridge C++ and JavaScript, does the framework convert JavaScript objects into a common intermediate representation, such as some JSON-like serialization structure?

The answer is no.`Variant` directly stores a C++ object (including `JsValue`), which also includes all type information and operation semantics of the object. Type conversions and method calls are performed correctly based on the runtime type marking of the `Variant` value, without the need for a specific intermediate representation or serialization process.

# Platform font fallback

The Glyphix framework has a built-in font loading and fallback mechanism based on font-face / font-family. However, the target platform usually comes with a complete font pipeline (such as Windows DirectWrite, macOS CoreText), which has implemented system font fallback and related optimizations.
To take full advantage of the platform font pipeline, Glyphix allows you to take over font fallback: when a character cannot be covered by an in-frame font, hand it over to the platform to find and render the appropriate system font. This article is for Glyphix system developers and will take you step by step to complete the docking.

Public header files involved:
- `gx_unite.h`: Contains the UniTE public interface and the engine installation function `installEngine()`;
- `gx_shapingadapter.h`: This is the main interface;
- `gx_fontdriver.h`: Provides `FontDriver` packaging mechanism;
- `gx_fontloader.h`: Provides font loader interface.

## Overall idea

To display a piece of text on the screen, it will go through the following pipeline: the application text is handed over to the **Paragraph Layout Engine** for branching and positioning; each piece of text with the same script and the same direction is **shaped** into a glyph; when there are missing words, **Font Fallback** fills them in; the glyphs are then handed over to the **Font Driver** for rendering into bitmaps; and all fonts come from the registration, loading and reuse of the **Font Management** layer.

The three parts highlighted in the figure are the content covered in this article:
1. Fallback strategy `FontFallbackShaper`, used to find missing characters and fallback to shape;
2. The `PlatformFont` wrapper responsible for drawing platform fallback fonts, used in conjunction with `FontFallbackShaper`;
3. The `FontLoader` used to load the platform fallback font wrapper will be registered in the `FontManager`.

The remaining layers of the framework have been implemented. Text shaping (`ShapingAdapter`) usually does not need to be re-implemented, and the reference implementation can be directly reused.

### Preconditions

Before implementing the platform font fallback function according to this document, you need to:

- Enable the UniTE text engine (compared to the default lightweight engine, it supports complex script shaping and multi-level fallback).
- The target platform supports a complete font pipeline, which can provide advanced functions such as system font shaping and script mapping. This is typically a complex subsystem that most MCU RTOS platforms do not have.

::: important
Enabling UniTE and the full font pipeline requires more memory and firmware space than the default LiTE engine. And the performance of this engine is worse than that of lightweight LiTE. It needs to be evaluated whether it needs to be enabled for complete Unicode support and internationalization requirements.
:::

## Reuse shaping backend

`ShapingAdapter` is responsible for shaping characters into glyphs. The built-in `HarfBuzzShaper` (`gx_harfbuzz_shaper.cpp`) has implemented complete OpenType shaping. It calls HarfBuzz shaping, and then writes the glyph index, advance, and offset to the output according to the target pixel size.

`HarfBuzzShaper` relies on Freetype to read font files, so it is necessary to introduce both HarfBuzz and Freetype libraries. If these libraries already exist on the target platform, please ensure that the versions are consistent, otherwise linking or runtime errors may occur.

::: tip
Similar to HarfBuzz's Responsibilities, `ShapingAdapter` does not handle text runs containing different fonts, including the "font fallback" mechanism described below. Therefore, whenever the font used in shaping has missing characters, the `ShapingAdapter` implementation will return the `.notdef` glyph (index `0`) and be handled by the fallback strategy.
:::

## Implement fallback strategy

`FontFallbackShaper` is the core of fallback. The engine calls it once every time it shapes a section of text, requiring a glyph sequence that does not contain missing characters to be returned as the shaping result. Unlike `ShapingAdapter`, it is not just for shaping a single font-face, but is designed for two-level fallback.

### Two-level fallback cascade

`FontFallbackShaper::shape()` The fallback is divided into two levels according to "from near to far":

- **Level 1**: Use other fonts to complement each other within the current family. The framework is implemented, you just call `builtinShape()`.
- **Level 2**: Missing characters that cannot be filled in the first level are handed over to the platform system font. This level is up to you.
Missing characters appear as glyph index `0` in the data, that is `.notdef`.The return value of `shape()` `FallbackResult` uses bit flags to express the result: `result & NotNeeded` is true to indicate that there are no missing words and can be terminated directly; otherwise it is common to return `FullyResolved` (all processed) or `PartiallyResolved` (there are still remaining `.notdef`).

### `shape()` function skeleton

First call the first level; if there are no missing characters, return, otherwise enter the second level platform font fallback.`m_shaper` is the `ShapingAdapter` held by this fallback (usually `HarfBuzzShaper`).

```cpp
FallbackResult shape(GlyphRunBundle &storage,
TextSpan text,
FontDriver *font) override {
// First level: Use builtin API to handle fallback within the family
auto r = builtinShape(storage, text, font, &m_shaper);
if (r & NotNeeded)
return r; // There are no missing words, end
return resolveByPlatform(storage, text, font); // Second level, see below
}
```

`builtinShape()` is the only place that relies on `ShapingAdapter`. In this case you usually need to implement `PlatformFallbackShaper` as follows:
```cpp
class PlatformFallbackShaper : public FontFallbackShaper {
HarfBuzzShaper m_shaper; // Define member variables directly, no pointer reference required

public:
PlatformFallbackShaper() = default;
FallbackResult shape(GlyphRunBundle &storage,
TextSpan text, FontDriver *font) override;
};
```
Please note that `m_shaper` is just a private member variable of your platform fallback strategy and does not need to be exposed to external use at all. When `shape()` calls `builtinShape()` internally, just pass in `&m_shaper`.

::: tip
In extreme cases (such as the preliminary adaptation stage), you can ignore the fallback within the family, directly skip `builtinShape()`, and only handle the second-level platform fallback. At this time, the `m_shaper` member variable can be omitted.

Regardless, the `ShaperAdapter` concrete class generally cannot be defined as a local variable, as it may hold HarfBuzz's cached state, which would cause severe performance degradation if recreated for each shaping.
:::

### Get platform font

The second level needs to hand over the missing words to the platform and finally let the wrapper render it.`fallbackFont(font)` returns the wrapper registered at the end of family (see below).Its static type is `FontDriver *`. You need to convert it back to your own wrapper type to call your customized registration and query interface.

```cpp
// Casting can also be done with dyn_cast, but if there is only one wrapper type, static_cast is also safe
auto *wrapper = static_cast<PlatformFont *>(fallbackFont(font));
if (wrapper == nullptr)
return PartiallyResolved; // The last item of family has no wrapper and cannot continue.
```

::: warning must be implemented in pairs
Fallback strategies and wrappers go hand-in-hand: `static_cast` above requires `fallbackFont()` to return exactly your own wrapper type. It is important to ensure that the installed fallback and registered wrapper match each other.
:::

### Simple rollback and shaping

The most common and good starting situation is when the entire run can be shaped with the same platform font (that is, a system font file completely overwrites the script).At this time, press `storage.run().spec.script` to select the platform font, reshape the entire run once, write the same `faceId` in the entire section, **directly overwrite the first-level results**, without merging with the parsed glyphs.

Unite splits runs according to script. Latin and CJK in the same text are inherently different runs. When the main font is mainly Latin and encounters scripts such as CJK, Arabic, Devanagari, etc., the entire section of the run after `builtinShape()` is often `.notdef`, and the entire section is reshaped and overwritten without losing any parsed glyphs. Therefore, the vast majority of multi-language typesetting takes this path, and it is not a special case of degeneration.

```cpp
// Select the platform font according to the script (platform font handle, not FontDriver), and register the faceId
auto sysFont = platformFontForScript(storage.run().spec.script);
uint32_t faceId = wrapper->registerFont(sysFont);
// Your shaping step produces glyphCount glyphs (demonstrated here with the HarfBuzz product)
auto &run = storage.resize(glyphCount);
for (int i = 0; i < glyphCount; ++i) {
run.data.glyphIds[i] = GlyphIds::encodeFallback(gid[i], faceId);
run.data.xAdvances[i] = uint16_t(scale(pos[i].x_advance));
run.data.xOffsets[i] = int16_t(scale(pos[i].x_offset));
run.data.yOffsets[i] = int16_t(scale(pos[i].y_offset));
run.data.clusterMap[i] = static_cast<int>(info[i].cluster);
}
```

The `pos`, `info`, `gid` and `scale` fields come from your shaping step, demonstrated above using the HarfBuzz output.

::: tip platform shaping capabilities
The platform usually comes with its own shaping capabilities (such as DirectWrite, CoreText), and whether to reuse HarfBuzz depends on the specific platform; the HarfBuzz product in the demonstration can be replaced with the platform shaping output. RTL run (`spec.bidiLevel & 1`) needs to pass the direction to the shaper.
:::
The premise of this method is that the entire run is mapped to a single platform font. It **does not apply to Common script** (Emoji, symbols, etc.): different characters within the same run may belong to multiple platform fonts, requiring complex fallback below.

### Complex rollback shaping

When multiple platform fonts are required within a run, or only some clusters need to be rolled back, the simple solution no longer works. Considering that the specific rollback and merging algorithms depend on the platform API, this document only restricts the semantics that `GlyphRun` must satisfy after merging, and the implementation needs to handle it by itself:

- The first level of resolved glyphs is left **as is**, the second level only replaces clusters that are still `.notdef`.
- Each glyph slot is filled with `glyphIds`, `xAdvances`, `xOffsets`, `yOffsets`, `clusterMap`; fallback glyphs are marked with `encodeFallback(gid, faceId)`.
- `clusterMap[i]` is the offset of the source code point corresponding to the glyph relative to this run** (consistent with `spec.text`, range `[0, text.length())`), for drawing reflection and line-based cropping.
- Variable number of glyphs: adjust storage with `storage.resize()/reset()`, then write slot by slot.`GlyphRunBundle` will automatically update `run().glyphCount` internally.
- When the same source cluster is mapped to multiple glyphs, the sum of the order and advance must be correct; code points annexed by GSUB clustering should produce zero advance glyphs to avoid gaps or misalignments.
- `faceId` must be an ID registered by the wrapper and stable throughout the life cycle; the glyph order and shaping direction of RTL run must be consistent.
- Return value: `FullyResolved` will be returned if all are completed, and `PartiallyResolved` will be returned if there are still remaining items.

As long as the output meets the above constraints, the framework can render correctly. Whether to query the platform API in segments or reuse HarfBuzz font-by-font shaping can be selected by platform.

### Row height and cache

The line height depends on which font each glyph is actually drawn by.`builtinLineMetrics()` is responsible for the part of the glyphs within the family; glyphs with a fallback flag (`isFallback()`) query the wrapper for the riser and lower part of their system font to be incorporated. The fallback glyph is encoded by `encodeFallback` in `GlyphIds`, whose `fontIndex()` is the `faceId` written, and the corresponding platform font is retrieved from the wrapper accordingly.

```cpp
VerticalMetrics resolveLineMetrics(const GlyphIds *gids, int count,
FontDriver *font) const override {
// Process glyphs within family
VerticalMetrics m = builtinLineMetrics(gids, count, font);
// Handle platform fallback glyphs
auto *wrapper = static_cast<PlatformFont *>(fallbackFont(font));
if (wrapper == nullptr)
return m;
// For the glyphs of gids[i].isFallback(), ask the wrapper for asc/descent and merge into m
for (auto gid : utils::span<const GlyphIds>(gids, count)) {
if (!gid.isFallback())
continue; // Only handle fallback glyphs
uint32_t faceId = gid.fontIndex(); // Fallback fontIndex() of the glyph, that is, faceId
auto face = wrapper->fontForFaceId(faceId); // Platform font handle (non-FontDriver)
if (face == nullptr)
continue;
m.ascent = max(face->ascender(), m.ascent);
m.descent = min(face->descender(), m.descent);
}
return m;
}
```

It is also possible to aggregate fallback fonts for an entire line and query their asc/descent in one go, avoiding font-by-font queries in a loop.

`flush()` is used to free the system fonts cached by the wrapper:

```cpp
void flush(FontDriver *font) override {
if (auto *w = static_cast<PlatformFont *>(fallbackFont(font)))
w->releaseFonts();
}
```

::: tip
`flush()` is called by the framework when a paragraph is destroyed or memory is tight, where it cleans up platform resources held by the wrapper.
:::

## Fallback font `FontDriver` wrapper

The wrapper is responsible for rendering the glyphs shaped in the previous step into bitmaps. It inherits `FontDriver` and is constructed with the `PlatformFallback` flag so the framework knows it is a fallback font.

```cpp
class PlatformFont : public FontDriver {
public:
PlatformFont(const String &family, const FontAttribute &attr)
: FontDriver(family, attr, Vector | PlatformFallback) {}
// ... bitmapOf / metricsOf ...
protected:
void requestHandler(int) override {}
};
```

This font wrapper is not used to load a font file (like `FontDriverTTF` does).Its function is to hand over the fallback glyphs to the platform font pipeline for processing, and the internal implementation is opaque to Glyphix.

### Dual mode query

The `code` received by the wrapper has two meanings, distinguished by the `CodeAsGlyphId` bit:

- **Tagged**: Query by glyph index, the high bit carries `faceId`, and the low bit is the glyph index. After decoding, route to the corresponding platform font, and then use `glyphId` to query the corresponding `GlyphBitmap`.
- **Unmarked**: Unicode character query, search through the registered platform fonts according to codepoint, internally convert it to glyph index and then query.

The common `bitmapOf()` implementation is as follows:

```cpp
bool bitmapOf(uint32_t code, GlyphBitmap *bitmap) override {
if (code & CodeAsGlyphId) { // index by glyph
uint32_t faceId = (code >> 16) & 0x3ff;
uint32_t glyphId = code & 0xffff;
auto face = fontForFaceId(faceId); // Platform font handle (not FontDriver)
return face && face->bitmapOf(glyphId, bitmap);
}
//Unicode character search, here iterates through registered fonts, or you can use a more efficient mapping table
for (auto *face : registeredFonts()) {
uint32_t glyphId = face->glyphIndexOf(code);
if (face->bitmapOf(glyphId, bitmap))
return true;
}
return false;
}
```

::: tip
`fontForFaceId()` returns the platform font handle, **not `FontDriver`**; the above `face->bitmapOf(...)` and `face->glyphIndexOf(...)` are pseudo-codes for operating on this handle, which respectively mean "get `GlyphBitmap` by `glyphId`" and "get `glyphId` by code point".
:::

`metricsOf()` uses the same bimodal logic; `advancesOf()`, `baseline()`, etc. are also calculated from the platform font.`duplicate()` just copies the mapping table.

### `faceId` mapping

The wrapper maintains a `faceId` → platform font mapping for fallback policy registration and retrieval during rendering.

`faceId` is a $10$ integer ($[0, 1023]$), the meaning is completely defined by the implementation, the only requirement is **stability throughout the life cycle**.There are two common approaches:

- **Fixed by script**: directly use the `Script` enumeration value as `faceId`, the wrapper holds the corresponding platform font according to the script, and is written according to the script when registering, without the need for runtime allocation.
- **Allocation on demand**: Each time a new platform font is encountered, the next index is allocated and a growth table is maintained.

Example of fixing by script (`faceId` is the script value):
```cpp
PlatformFontHandle fontForScript(Script script) {
switch (script) {
case Script::Han: return sysHanFont;
case Script::Arabic: return sysArabicFont;
case Script::Latin: return sysLatinFont;
// ...
}
return sysDefaultFont;
}
```
You need to handle script → font mapping, `faceId` allocation and platform font object caching yourself.

::: tip
`faceId` is the contract between the fallback strategy and the wrapper: `PlatformFallbackShaper` uses it to encode the glyph, and `PlatformFont` uses it to decode back to the system font. The interpretation of `faceId` must be consistent at both ends and must be represented by a $10\rm bit$ integer.
:::

## Register wrapper

Finally let the framework include the wrapper into the family loader. Implement `FontLoader::load()`, return a wrapper for a common family name, and load it into `FontManager`:

```cpp
struct PlatformFontLoader : public FontLoader {
FontDriver *load(const String &face, const FontAttribute &attr) override {
if (face == "sans-serif")
return new PlatformFont(face, attr);
return nullptr;
}
};

CoreApp()->fontManager()->install(new PlatformFontLoader);
```

When the application requests a font in the form of `"<primary-face>,sans-serif"`, the framework merges the parts into the same family in comma order, and the wrapper becomes the bottom face as the last item, and `fallbackFont()` can get it.

`PlatformFont` and `PlatformFontLoader` are usually only registered as fonts with generic family names such as `sans-serif`, rather than a specific system font name. This allows applications to use the same family name on different platforms without knowing the specific fonts of the platform.

::: warning function limitation
The wrapper always relies on the application to write the family name in the above order before the last item of family. The mechanism to automatically guarantee this order is still under development.
:::

## Install and assemble

`installEngine()` in `gx_unite.h` connects your fallback strategy to the engine:

```cpp
unite::installEngine(*CoreApp()->typesetCore(),
std::make_unique<PlatformFallbackShaper>());
```

Complete assembly sequence:

1. `fontManager()->install(new PlatformFontLoader)`: Register the wrapper loader.
2. `installEngine(...)`: Install the fallback strategy that holds the shaping backend.
3. Request the font in the form of `"<primary-face>,sans-serif"`, layout and draw as usual.

## Notes

- advance/offset is always Q26.6 fixed point (value = pixels × 64).
- Uncompleted `.notdef` (glyph index $0$) is skipped during rendering, and blanks or tofu blocks will be displayed at the corresponding positions.
- `faceId` has only $10$ bits, and the upper limit of system fonts active at the same time for a single family is $1024$.
- The fallback strategy and wrapper must be implemented in pairs and keep the type consistent (depending on `static_cast`).
- Be sure to free the platform font cache held by the wrapper in `flush()`.

# SDK project configuration
Glyphix is ​​distributed to device manufacturers in the form of precompiled libraries. This article describes how to configure the build environment in the SDK project to develop Native Module, Native Widget or platform adaptation code based on it.

### Preconditions

Before you begin, make sure you have:
- CMake 3.14 or higher
- C++ compiler (GCC, Clang or MSVC) with C++14 support
- Glyphix meta-object compiler `meta` (matches the SDK, see below for details on how to obtain it)
- Cross-compilation toolchain (if you need to build embedded targets)

::: tip System Requirements
- MSVC toolchain requires Visual Studio 2022 or higher.
- Linux recommends using a distribution with a desktop environment, such as Ubuntu 22.04 or higher.
- Ubuntu 20.04 is not recommended because its package versions are usually out of date and new versions of software often need to be installed manually.
- The emulator and GUI examples cannot be run using environments without a graphical interface such as WSL and Docker.
- The current host environment only provides Linux precompiled libraries, and Windows and macOS precompiled libraries are not yet ready.
:::

## SDK package structure

The unzipped SDK contains the following directories:

```
glyphix-sdk/
├── libs/
│ └── <target-triple>/ # Precompiled libraries differentiated by target triples
│ ├── include/ # Glyphix header file (gx_*.h)
│ └── lib/ # Static library (libglyphix-core.a, etc.)
├── cmake/
│ ├── GlyphixSDK.cmake # SDK main configuration script
│ ├── meta.cmake # Meta object compiler integration (glyphix_add_meta_objects)
│ ├── cross-compile.cmake # Cross-compile tool chain loading
│ ├── arch/ # Compilation parameters for each architecture (mips-linux-gnu, cortex-m33, etc.)

```

### `libs/<target-triple>/`

The precompiled library of the SDK uses target triple as the directory name to distinguish the platform, for example:

- `x86_64-linux-gnu/`: 64-bit Linux host development/emulation
- `mips-linux-gnu/`: MIPS Linux embedded target
- `cortex_m55-none-gnu/`: Cortex-M55 bare metal target

The `include/` directory contains all Glyphix public header files, all prefixed with `gx_`.The `lib/` directory is a static library, and the core libraries include:

| Library file | Description |
|:---|:---|
| `libglyphix-core.a` | Core framework (object system, control tree, events, etc.) |
| `libglyphix-widgets.a` | Built-in widget library |
| `libglyphix-reactive.a` | Responsive framework (JavaScript bridging layer) |

## Preparation

### Configure the meta-object compiler

The `meta` meta-object compiler is distributed separately from the SDK and is provided as a standalone compressed package. After decompression, you will get two directories: `bin/` and `lib/`. **Both must be kept in the same directory**. The `meta` executable file depends on the runtime library in `lib/`.

On Linux and macOS, it is recommended to extract to `/usr/local` so that `meta` will automatically be in `PATH`:

::: code-tabs#bash

@tab Linux

```bash
sudo tar -xJf glyphix-meta-vX.X-linux-x86_64.tar.xz -C /usr/local
```

@tab macOS

```bash
sudo tar -xJf glyphix-meta-vX.X-darwin-arm64.tar.xz -C /usr/local
```

:::

You can also unzip it to any directory, and then add the `bin/` directory to `PATH`.After completion, confirm whether it is available through the following command:

```bash
meta --version
```

If you do not want to modify `PATH`, you can explicitly specify the full path of the executable file through `-DGX_META=/path/to/bin/meta` during CMake configuration.

## Configure CMakeLists.txt

### Minimum configuration

::: tip
The CMake configuration introduced in this section is similar to the standard example template of the Glyphix SDK project. You can directly refer to the SDK source files.
:::

The following is a minimal runnable `CMakeLists.txt`, showing the standard configuration skeleton of the project:

```cmake
cmake_minimum_required(VERSION 3.14)

# Must be loaded before project() so that the toolchain is in place when project() probes the compiler
include(cmake/cross-compile.cmake)

# Load Glyphix SDK (set header file path, link directory, glyphix::sdk target)

add_subdirectory(src) # your source code
```

Create the target and link the SDK in `src/CMakeLists.txt`:

```cmake
add_executable(my_app
main.cpp
my_module.cpp
my_widget.cpp
)

# Link to Glyphix SDK
target_link_libraries(my_app PRIVATE glyphix::sdk)
# Generate metadata for header files containing GX_OBJECT
glyphix_add_meta_objects(my_app
my_module.h
my_widget.h
)
```

### Register meta objects (`glyphix_add_meta_objects`)

The [Object System](./object-system) document mentions that any class that declares `GX_OBJECT` must be registered with the build system, and the meta-object compiler generates a `*_meta.cpp` file for it.`glyphix_add_meta_objects()` is the CMake function that does this:

```cmake
glyphix_add_meta_objects(<target> [header1.h header2.h ...])
```

It accepts a target name and a set of header paths as arguments. For each header file, the `meta` tool will generate the corresponding `*_meta.cpp` in the `meta/` subdirectory under the build directory, and automatically add it to the target source file list to participate in compilation.

**Example:** Assume the project has the following structure:

```
src/
├── CMakeLists.txt
├── main.cpp
├── sensors/
│ ├── step_counter.h # Contains GX_OBJECT
│ └── step_counter.cpp
└── widgets/
├── activity_ring.h # Contains GX_OBJECT
└── activity_ring.cpp
```

Corresponding `CMakeLists.txt`:

```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/../cmake/meta.cmake)

add_executable(my_app
main.cpp
sensors/step_counter.cpp
widgets/activity_ring.cpp
)
target_link_libraries(my_app PRIVATE glyphix::sdk)

glyphix_add_meta_objects(my_app
sensors/step_counter.h
widgets/activity_ring.h
)
```

::: tip Only send header files, not .cpp
`glyphix_add_meta_objects()` only needs to pass in the **header file** (`.h`) containing the `GX_OBJECT` declaration. The meta-object compiler reads macro declarations in header files to generate code without parsing implementation files. In contrast, classes containing `GX_OBJECT` cannot be defined in `.cpp` files.
:::

::: warning Don’t miss registration
If a class declares `GX_OBJECT` but is not registered through `glyphix_add_meta_objects()`, a **link error** will result (symbols such as `staticMetaObject` cannot be found).Whenever a new header file containing `GX_OBJECT` is added, remember to update `CMakeLists.txt` simultaneously.
:::

### `glyphix::sdk` interface target

`GlyphixSDK.cmake` defines the `glyphix::sdk` CMake interface library target, which encapsulates all link dependencies of the SDK.Just link this target in your `CMakeLists.txt`:

```cmake
target_link_libraries(my_target PRIVATE glyphix::sdk)
```

It is internally equivalent to:

```cmake
# Pseudocode - actually managed automatically by GlyphixSDK.cmake
target_include_directories(... ${GLYPHIX_INCLUDE_DIRS} wrapper/include)
target_link_libraries(... -Wl,--start-group ${glyphix-*.a} glyphix-wrapper -Wl,--end-group)
target_link_libraries(... m pthread dl) # UNIX system library
```

Using `-Wl,--start-group ... -Wl,--end-group` to wrap static libraries is to solve the problem of circular dependency linking between static libraries on embedded platforms.

::: tip Link order problem
If there is your own static library in the project (such as `add_library(my_module STATIC ...)`), it should be linked to `glyphix::sdk` **internal**, otherwise the scope of `--start-group` will not override it and may cause a link error. The method is to append your static library path to the `GLYPHIX_LIBS` variable in `GlyphixSDK.cmake` before the `glyphix-sdk` target is created, or directly let the final executable file link to both `my_module` and `glyphix::sdk` and manually specify `--start-group`.
:::

## Host build

The host builds sample programs for running Glyphix on a development machine, allowing you to quickly verify control and module logic without connecting to hardware.

```bash
mkdir build && cd build
cmake -G Ninja ..
cmake --build .
```

The SDK's `app/` directory contains multiple examples, and each subdirectory corresponds to an independent executable target. For example:

| Subdirectories | Build products | Description |
|:---|:---|:---|
| `app/emulator/` | `demo` | Emulator with graphical interface, relying on MiniFB window backend |
| `app/async/` | `async-demo` | Asynchronous service example without graphical interface, demonstrating Native Module and asynchronous callback |

`GlyphixSDK.cmake` will automatically detect the host's compiler triplet (via `gcc -dumpmachine` or `clang -dumpmachine`), and use this as a key to find the corresponding precompiled library in the `libs/` directory. For example, on an x86_64 Linux development machine, it will be automatically resolved to `libs/x86_64-linux-gnu/`.

If the automatically detected triplet does not match the actual library directory, you can specify it manually:

```bash
cmake -G Ninja -DTARGET_TRIPLE=x86_64-linux-gnu ..
```

If you only need to build a specific example, you can specify the target name:

```bash
cmake --build . --target demo
cmake --build . --target async-demo
```

## CMake cross compilation

For embedded targets, the target architecture needs to be specified via the `-DARCH` parameter. The SDK is preset with the following architecture configurations:

| `-DARCH` value | target platform | toolchain prefix |
|:---:|:---:|:---:|
| `mips-linux-gnu` | MIPS Linux | `mips-linux-gnu-` |
| `cortex_m33-gnu` | ARM Cortex-M33 (GNU) | `arm-none-eabi-` |
| `cortex_m7-gnu` | ARM Cortex-M7 (GNU) | `arm-none-eabi-` |

### MIPS Linux Example

```bash
export MIPS_TOOLCHAIN_DIR="/opt/mips-gcc720-glibc229"

mkdir build-mips && cd build-mips
cmake -G Ninja .. \
-DARCH=mips-linux-gnu \
-DMIPS_TOOLCHAIN_DIR="$MIPS_TOOLCHAIN_DIR" \
-DCMAKE_BUILD_TYPE=Release
cmake --build .
```

If the toolchain is already in `PATH` (i.e. `mips-linux-gnu-gcc` can be called directly), you can omit `-DMIPS_TOOLCHAIN_DIR` and CMake will automatically locate it.

### ARM Cortex-M Example

```bash
mkdir build-cm33 && cd build-cm33
cmake -G Ninja .. \
-DARCH=cortex_m33-gnu \
-DARM_TOOLCHAIN_DIR="/opt/arm-none-eabi-gcc" \
-DCMAKE_BUILD_TYPE=Release
cmake --build .
```

In cross-compilation, `GlyphixSDK.cmake` does not attempt to automatically detect triples - the architecture file (such as `cmake/arch/cortex_m33-gnu.cmake`) directly sets `TARGET_TRIPLE`, pointing to the correct library directory.

### Supported target architectures

The SDK only provides precompiled libraries for the architectures listed in the table above. If your target platform is not among them, you need to contact Glyphix to obtain the SDK package for the corresponding architecture. You cannot add support yourself based on the existing SDK.

## Other build systems

The SDK uses CMake as the main build system, and Glyphix will also provide support for other build systems for partner vendors. This is usually just pulling in the pre-built SDK libraries and headers, and adding the porting layer source files.

### Project restrictions

This solution is suitable for projects that only require standard SDK functionality. Once capabilities such as customized controls and Native Modules are required, the `meta` meta-object compiler must be introduced to generate the necessary binding code. Currently, CMake is the only supported build system.

There are several alternatives available:
1. Use the SDK CMake project to build the custom code, and then link the resulting library into your main project.
2. Use the SDK CMake project to build the custom code, and then include the generated source files (`*_meta.cpp`) into your main project.
3. Call the `meta` tool directly in your build system to generate binding code.

Among them, the Glyphix SDK itself is built through method 1.But it is not suitable for downstream vendors' internal development processes because it requires maintaining a separate project outside the main firmware project and linking the generated binary library back to the main project. This creates serious version management problems.

Method 3 is also generally not ideal because vendors usually don't want to introduce an external tool into the main project's build system.

### Recommended plan

Therefore, it is recommended to use method 2, which copies the source code. Although it requires manual operation, it is easy to review and integrate into the existing build process. You can build custom code in the SDK's CMake project, generate `*_meta.cpp` files, then copy these files into your main project and compile them in the main project's build system.

Another limitation of this approach is the need for custom source files to be successfully built within the SDK project environment. Specifically, this requires that it can be built independently of the main project, including:
- The include path and preprocessor definition need to be set correctly. The header file of the customized component cannot contain the header file unique to the main project.
- The cpp files of customized components should preferably be compiled and passed. Although this does not affect the generation of `*_meta.cpp` files, it can facilitate rapid iteration and debugging in the host environment.

::: tip
This is not a problem for most [custom controls](widget.md).It may be more troublesome for [Native Module](native-module.md). It should be noted that the header file declaring `GX_OBJECT` should not include the main project-specific header file.
:::

# Control registration and framework integration

In [Control Development Guide](./widget.md), we implemented a C++ control class. But at this time it is just an ordinary C++ object, and application developers cannot use it directly in the page code. This article describes how to register a control with the framework so that it becomes a component that can be used in your app. Many concepts in this document involve [Object System](./object-system.md). It is recommended to read the relevant content first.

## Running environment

Control registration relies on a set of **running environment objects**.They are necessary dependencies for the reactive framework to run. They must be explicitly created in `main()` or platform startup code, and their life cycle should cover the entire application running period:

```cpp
Application app(/* platform */);
JsVM vm;
Window window;
AppletKit kit(&window, "pkgs.db");
```

These objects are responsible for the running environment of the entire application:
- The `Application` framework application object is responsible for all underlying services and maintaining the event loop. At the end of initialization, call `app.exec()` to enter the event loop;
- `JsVM` is an embedded JavaScript engine that hosts the running of the responsive framework and must be created before `AppletKit`;
- `Window` is the top-level window, used as the rendering output target;
- `AppletKit` is the application (Applet) manager, responsible for application life cycle and control registration.

::: warning do not omit these objects
`vm`, `window`, `kit`, etc. are RAII objects, and the framework manages the running environment through their construction/destruction. Even if you don't see a direct call to `vm` in the code, its existence alone is required - destroying it early or not creating it will cause the framework to not work.
:::

`Window window` can sometimes be replaced by `Wigdet window`, etc. The difference is that `Window` draws an opaque background by default, while `Widget` draws a transparent background by default.

## Register control
The registration of the control is done through `AppletKit::installWidget<T>()`, which is called after `AppletKit` is instantiated and before `launch()` starts the first application:

```cpp
//Register custom control (before launch)
kit.installWidget<ProgressRing>(); // No parameters, registered with class name, written as <progress-ring> in the template
kit.installWidget<MySpecialChart>("SpecialChart"); // or register with a custom name (see below)

kit.launch("com.example.app"); // Launch the application
return app.exec(); // Enter the event loop
```

::: tip Built-in controls are registered by default
The built-in controls such as buttons and labels that come with the framework are registered by `installBuiltinWidgets()`.As long as the SDK is built with the CMake option `GX_BUILTIN_BINDINGS` enabled (default `ON`), it will be called automatically when `AppletKit` is constructed, without manual handling. You only need to call `kit.installBuiltinWidgets()` yourself if you explicitly turn off this option.
:::

After registration, the framework will automatically export its properties, events, methods, and the enumeration and structure types they use based on the `GX_OBJECT` metadata of the control class, making them available at the application layer.

### Used in application pages

After successful registration, application developers can use it in page templates like built-in controls:

```xml
<!-- Take the progress-ring component as an example -->
<progress-ring
class="ring"
:value="progress"
@completed="onDone">
</progress-ring>
```

Here `:value="progress"` binds the `value` property of the control to the application data `progress`; `@completed` listens to the `completed` event exposed by the control. The framework automatically converts JavaScript values ​​​​to C++ properties and back, and developers do not need to write any "bridging code".

### Custom component name

By default, controls are registered with class name. If the class name is not suitable as a component name directly, you can specify a custom name when registering:

```cpp
// Register VendorWaveformGraph as WaveformGraph and write <waveform-graph> in the template
kit.installWidget<VendorWaveformGraph>("WaveformGraph");
```

Custom names should use PascalCase format, consistent with the C++ class name style.

### C++ ↔ UX naming conversion

The component tag name corresponds to the name when registered (default is the **class name** declared by `GX_OBJECT`, or a custom name specified when registering).It is customary to use dashes (kebab-case) to write in templates. The ux packaging tool is responsible for name conversion during compilation**:

- Tag name: kebab-case in the template ↔ PascalCase of the registered name. For example, `<progress-ring>` corresponds to the class `ProgressRing`.The same goes for custom registration names.
- Attribute name: kebab-case in template ↔ camelCase in C++.For example, `ring-color` corresponds to the attribute `ringColor`.

That is to say, the runtime framework matches exactly the original name (camelCase / PascalCase) declared in C++, and the dash writing is just a writing convention on the template side, which is converted by the ux tool and then docked.

The same label PascalCase and attribute camelCase as C++ can also be used in ux components, see [Component Naming Specification](/tutorials/name-spec.md).

## Properties and events export

Properties declared with `GX_PROPERTY` will be automatically exported, the rules are as follows:

- The attribute name is the attribute name in the frame component, and they correspond directly to each other.
- Properties declared with setters (`set xxx`) can be assigned values by the application
- Properties declared with getter (`get xxx`) can be read by the application
- When signal(`signal xxxChanged`) is declared, the signal of property change will be passed to the binding

For example, the following complete property declaration:

```cpp
class ProgressRing : public Widget {
GX_OBJECT
public:
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
GX_PROPERTY(Color ringColor, get ringColor, set setRingColor)
GX_PROPERTY(bool showLabel, get showLabel, set setShowLabel)
// ...
};
```

Corresponding usage at the application layer:

```xml
<progress-ring
:value="jobProgress"
ring-color="#409EFF"
:show-label="true">
</progress-ring>
```

The attributes in the template are written with dashes (kebab-case), corresponding to the camelCase attribute names in C++: `ring-color` → `ringColor`, `show-label` → `showLabel` (the conversion is completed by the ux packaging tool, see above).`:value` and `:show-label` are dynamic bindings (values ​​are expressions), while literals like `ring-color="#409EFF"` are static assignments.

### Event export

Component events are exported through properties with change signals instead of directly exporting `Signal<>` members. Exporting an event requires two steps:

1. Declare a `Signal<...>` member (used internally by C++);
2. Reference it in the `signal` field of a `GX_PROPERTY`.

The key rule is: the event name monitored by the application side is the attribute name, not the name of the signal member.

### Attribute change event with value

```cpp
class ProgressRing : public Widget {
GX_OBJECT
public:
int value() const;
void setValue(int v);

Signal<int> valueChanged; // Internal signal, this name is not visible to the application
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
};
```
The application side uses `@property name` to listen for changes, so `@value` (property name) is written here instead of `@value-changed`: Although the signal member is called `valueChanged`, the event name seen by the application is always the property name `value`.

```xml
<progress-ring :value="progress" @value="onProgressChanged"></progress-ring>
```

This is completely consistent with the built-in controls of the framework. For example, the value change signal member of `Slider` is called `changed`, but the application side still monitors the property name `value` (`@value` or two-way binding `::value`).

### Pure event with no value

For events that do not carry a value and only represent "something happened" (such as "completion"), use `invalid_t` as the attribute type to declare an attribute that only has a signal and no read-write value:

```cpp
Signal<> completed; // Emitted when progress is completed
GX_PROPERTY(invalid_t completed, signal completed)
```

The application side can listen like this (no event value):

```xml
<progress-ring @completed="onDone"></progress-ring>
```

You cannot declare a `GX_PROPERTY` as a `void` type even if it has no `get`/`set` at all, so use `invalid_t` as a placeholder type. If you want the event to carry a value, you must declare it as a concrete type and provide a `get` method - the parameter type of `Signal<T>` does not automatically become the event value, but always comes from the property's getter.

::: warning `Signal<>` does not automatically become an event
If you only declare a `Signal<>` member and do not reference it with the `signal` field in any `GX_PROPERTY`, this signal cannot be monitored on the application side using `@some-event`.The framework will only expose the "property change signal", that is, the `signal` field as an event, and the event name always comes from the property name.
:::

## Method export

Member functions declared with `GX_METHOD` are exported as component methods and can be called by applications in JavaScript:

```cpp
class ProgressRing : public Widget {
GX_OBJECT
public:
GX_METHOD void reset(); // No parameter method
GX_METHOD void animateTo(int target); // Method with parameters
};
```

Different from properties and events, methods are not used through template tags. Instead, they first use [`$element()`](../framework/component/component-apis.md#element) to obtain the native component object and then call it on it. The corresponding template needs to set `id` to the component:

```xml
<progress-ring id="ring" :value="progress"/>
```

```js
onReady() {
const ring = this.$element('ring'); // 'ring' is the id of the component in the template
ring.reset();
ring.animateTo(80);
}
```

The parameters and return values of the method are automatically marshalled by the framework via `Variant`, without the need for hand-written conversion code (see [Object System](./object-system.md#Runtime Type System) for details on type bridging).Note that `$element()` must be called during and after the [`onReady()`](../framework/component/life-cycle.md#onready) life cycle. For details, see [Native Component](../framework/component/native-component.md).

## Enumeration and structure types

When the type of attribute or method parameter is a custom C++ enumeration or structure, it can be exported together with `GX_ENUM` / `GX_STRUCT` annotation. When [Register Control](#Register Control), the framework will automatically install the corresponding type conversion, without the need for hand-written binding code. Enumerations are represented as string constants on the JavaScript side, and structures are represented as object literals:

```cpp
class ProgressRing : public Widget {
GX_OBJECT
public:
// Be careful to define an alias for the value, otherwise the JavaScript side will use
// 'Solid' / 'Dashed' names instead of expected 'solid' / 'dashed'
enum GX_ENUM LineStyle {
Solid GX_ALIAS("solid") = 0,
Dashed GX_ALIAS("dashed"),
};
// Pay attention to writing default values in the structure to avoid undefined fields when creating on the JavaScript side.
struct GX_STRUCT Range { int min = 0; int max = 100; };

GX_METHOD void setRange(const Range &range);

GX_PROPERTY(LineStyle lineStyle, get lineStyle, set setLineStyle)
};
```

```xml
<progress-ring line-style="dashed"/>
```

```js
this.$element('ring').setRange({ min: 0, max: 100 });
```

For complete semantics such as enumeration aliases, structure field mapping, nested types, etc., see [Object System · Complex Type Reflection](./object-system.md#Complex Type Reflection), which will not be expanded here.

::: warning Don’t forget to mark
When attributes or methods use custom enumerations/structures, be sure to mark `GX_ENUM` / `GX_STRUCT`, otherwise the JavaScript side cannot be used and there will be no compilation error prompt.
:::

## Accommodate child controls (container type controls)

If the control needs to accommodate sub-content declared by the application, you only need to implement it as a container control: the C++ side is responsible for the layout of the sub-controls, and the framework will automatically create the sub-components nested in the template as sub-controls and mount them below it. Glyphix does not have named slots like HTML, and nested tags in the template will directly become child controls of the control.

There are two ways to implement the layout of the container (see the "Layout and Size" section of the [Control Development Guide](./widget.md) for details):

- Use the framework's ready-made layout classes, such as `setLayout(new FlexLayout())` in the constructor;
- Or override `layoutEvent()`, where iterate over `children()` and manually set the geometry of each child control.

At the application layer, just use it like a nested subtag (here `card-panel` is a container control implemented and registered by the developer, and `text` is a built-in control):

```xml
<card-panel>
<text>Title</text>
<progress-ring :value="progress"/>
</card-panel>
```

## A complete example

The following defines a simple number display control and registers it as a frame component:

```cpp
// number_display.h
#pragma once
#include "gx_widget.h"
#include "gx_color.h"

class NumberDisplay : public Widget {
GX_OBJECT
public:
explicit NumberDisplay(Widget *parent = nullptr);

int value() const { return m_value; }
Color textColor() const { return m_color; }

void setValue(int v);
void setTextColor(const Color &c);

bool event(Event *event) override; // The only virtual function that needs to be overridden

Signal<int> valueChanged; // Internal signal; the application side listens through the property name value

GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
GX_PROPERTY(Color textColor, get textColor, set setTextColor)

protected:
// paintEvent / sizeHint are not virtual functions and cannot be overridden.
void paintEvent(PaintEvent *event);
Size sizeHint() const;

// EventDispatch needs to access the protected handler function
friend struct EventTraits<NumberDisplay>;

private:
int m_value = 0;
Color m_color{0, 0, 0};
};
```

```cpp
// number_display.cpp
#include "number_display.h"
#include "gx_format.h"
#include "gx_painter.h"
#include "gx_widgetevent.h" // EventDispatch

NumberDisplay::NumberDisplay(Widget *parent)
: Widget(parent) {}

bool NumberDisplay::event(Event *event) {
// Distribute events to paintEvent; declaring PaintEvent can check for omissions at compile time
return EventDispatch<Widget, PaintEvent>{}(this, event);
}

void NumberDisplay::setValue(int v) {
if (m_value == v) return;
m_value = v;
update();
valueChanged(v);
}

void NumberDisplay::setTextColor(const Color &c) {
if (m_color == c) return;
m_color = c;
update();
}

Size NumberDisplay::sizeHint() const {
return Size(60, 30);
}

void NumberDisplay::paintEvent(PaintEvent *) {
Painter p(this);
p.setBrush(m_color); //The text color is determined by the brush (Brush), not the brush
p.setFont(Font(20));
p.drawText(rect(), format("{}", m_value), AlignCenter);
}
```

Register:

```cpp
kit.installWidget<NumberDisplay>();
```

Application layer uses:

```xml
<number-display
:value="count"
text-color="#333333"
@value="onCountChanged">
</number-display>
```

At this point, the entire process from C++ implementation to application use is complete: the `<number-display>` tag is converted to the registered name `NumberDisplay` by the ux tool and is recognized.

Whenever the application data `count` changes, the `:value` binding will call `NumberDisplay::setValue()`; when the control internally emits the `valueChanged` signal, the framework triggers an event named `value` (the event name is the property name), thereby calling the application's `onCountChanged`.If you want `count` to be synchronized in both directions with the control, you can use `::value="count"` instead.

# Custom Widget practice

`slider-demo` is a complete example included with the Glyphix SDK, showing how to implement a **custom control**: `WaveSlider` from scratch in C++.This control adds water ripple filling effect and click ripple effect based on the standard `Slider`. The example also involves `StyleEngine` customization, directly using C++ to build the UI interface, etc.

This article takes this example as a clue, combined with the core concepts in the [Control Development Guide](./widget.md), to completely demonstrate all the steps required to customize a new Widget.

## Example structure

The file structure of the example is as follows:

```
app/slider-demo/
├── CMakeLists.txt
├── main.cpp # Application entry, build UI directly with C++
├── styleengine.h/.cpp # Customize StyleEngine
└── waveslider.h/.cpp # Implementation of WaveSlider control
```

Compile and run the `slider-demo` target directly to see the effect without cooperating with the front-end project.

### Build instructions

After [Configuring the SDK](sdk-setup.md#Preparation), use the following commands to build and run the example:

```bash
mkdir build && cd build
cmake .. && cmake --build . -j
bin/slider-demo
```

::: important host system
This example must be built and run on a Linux system with desktop environment support.
:::

## Build UI directly in C++

In `main.cpp`, the application's UI is completely built with C++ code in the constructor, similar to Qt Widgets or LVGL: child controls are created through `new` and the parent control pointer is passed in, without the need for declarative templates.

```cpp
int main() {
Application app(new BSPPlatform(500, 500));
app.setFont(Font(GX_EXAMPLE_ASSETS "/roboto.ttf", 32));
app.setStyleEngine(new MyStyleEngine);

Window window;
window.setFlowLayout(true);

MyWidget widget(&window);
StyleModifier(&widget)->setSize(
Length::fromPercent(100), Length::fromPercent(100));
StyleModifier(&widget)->setMargin(Margin(10));
return app.exec();
}
```

`Application` receives a platform backend object (`BSPPlatform`) and resolution.`Window` is the root control. After `setFlowLayout(true)` is enabled, its child controls will be automatically arranged according to the flow layout.

`setStyleEngine` mounts a custom style engine, which is not required (otherwise the default style is used).You only need to provide your own implementation if you need to customize the appearance of the control (such as the transformation of `Switch` below).

### `MyWidget` class

`MyWidget` inherits `ScrollArea`, creates and adds child controls in the constructor:

```cpp
class MyWidget : public ScrollArea {
public:
explicit MyWidget(Widget *parent = nullptr) : ScrollArea(parent) {
addItem(&m_switch);
addItem(&m_label);
addItem(&m_slider);
// ...
}
// ...
private:
Label m_label;
Switch m_switch;
Slider m_slider;
};
```

Child controls are declared as member variables and are automatically initialized during construction (the parent control is created in `addItem`).The life cycle of member variables is managed by `MyWidget`, and there is no need to manually `delete`.

`ScrollArea` provides out-of-the-box scrolling, inertia, rebound and other capabilities, and `MyWidget` does not require any hand-written scrolling logic.

::: tip The function of `addItem()`
Under normal circumstances, you can directly hang the child control to the parent control through `setParent()`, but there is actually a special content container (`contentWidget()`) inside `ScrollArea`. Ordinary elements cannot be added directly to `ScrollArea`, but must be added to the content container through `addItem()`.

For simple containers, `setParent()` and `addItem()` have the same effect; but for special containers such as `ScrollArea`, you must use `addItem()` to add elements.
:::

### Signal connection

Controls synchronize their status through signal connections:

```cpp
m_slider.changed.connect(this, &MyWidget::onSlider);
m_switch.checked.connect(this, &MyWidget::onSwitch);

// Bidirectionally synchronize the values ​​of two Sliders
waveSlider->changed.connect<AbstractSlider>(&m_slider, &Slider::setValue);
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);

// Switch the waveform mode of WaveSlider
m_switch.checked.connect(waveSlider, &WaveSlider::setWaveMode);
```

::: tip Signal usage
The syntax for signal connection is `signal.connect(receiver, &Type::method)`.When the signatures of `Slider::setValue` and `WaveSlider::setValue` are not exactly the same, you can declare a common base class (`AbstractSlider`) through template parameters to disambiguate.

When you are not sure about the actual type of a slot function, you can check it through IDE prompts. For example, when checking `Slider::setValue`, the IDE usually prompts:
```cpp
public method
void setValue(int value) in class AbstractSlider
```
This shows that `setValue` is actually declared in `AbstractSlider`.You need to specify `AbstractSlider` when connecting to eliminate ambiguity:
```cpp
m_slider.changed.connect<AbstractSlider>(waveSlider, &WaveSlider::setValue);
```
:::

### Use StyleModifier to set styles

`StyleModifier` is a tool for setting control styles programmatically in C++. The effect is equivalent to configuring through style attributes in the template:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setMargin(Style::Margin{Length::fromAuto(), 20});
m->setColor(Color{"#35a7ff"});
```

`setColor` sets the foreground color for `WaveSlider`, which will be read in `paintEvent` and used to draw the progress fill color.
## Customize StyleEngine

The built-in [`Switch`](/components/switch.md) is a fully functional switch control, but its default appearance is similar to [Fluent 2](https://fluent2.microsoft.design/components/web/react/core/switch/usage), which may not suit the visual style of a specific device or brand.

`StyleEngine` is the mechanism to solve this problem. Device manufacturers can implement their own `StyleEngine` to customize the appearance of all built-in controls while retaining their interaction logic without modifying the framework code.

The customized `Switch` is not just about changing the theme color. On the contrary, the entire set of switch animations (slider displacement, color transition, compression and scaling) can be realized through **programmed interpolation** instead of pre-recorded sequence frame pictures. This means:

- The motion effects are completely smooth, and the frame rate is consistent with the rendering system;
- Color and size can be overridden by application developers through style attributes. `StyleEngine` provides default values that can be overridden;
- No need to prepare different image materials for each resolution.

### Responsibilities of `StyleEngine`

`StyleEngine` is the core of the Glyphix style system and is responsible for three things:

1. **Provide palette** (palette): a global color variable, similar to CSS custom properties, which can be read by all built-in controls and custom controls.
2. **Paint control appearance** (paint): The visual effects of the framework's built-in controls (such as `Switch`, `Slider`) are all entrusted to `StyleEngine::paint()` for drawing, and developers can override them in derived classes to achieve completely different appearances.
3. **Recommended size** (size hint): The recommended size of the control in different style states, for reference by the layout system.

### Definition MyStyleEngine

Inherit `StyleEngine` and override `sizeHint()` and `paint()`:

```cpp
class MyStyleEngine : public StyleEngine {
public:
MyStyleEngine();
Size sizeHint(StyleOption::Type type, const Widget *widget) const override;
void paint(Painter &painter, Widget *widget, StyleOption &option) override;
};
```

Set the palette in the constructor:

```cpp
MyStyleEngine::MyStyleEngine() {
setPalette(SwitchDark, Color(0xff565656));
setPalette(SwitchLight, Color(0xff2f5cff));
setPalette(SwitchThumb, Color(0xffffffff));
}
```

`SwitchDark`, `SwitchLight`, `SwitchThumb` are predefined semantic color keys in the `StyleEngine` enumeration. Different theme engines can give them different colors, and controls are always read by key name rather than hard-coded color values.

### Override `sizeHint()`

`sizeHint()` tells the framework the recommended size for built-in controls in a given style state. Taking `Switch` as an example, its width and height should be proportional to the font pixel size:

```cpp
Size MyStyleEngine::sizeHint(StyleOption::Type type, const Widget *widget) const {
// Customized Switch size ratio can be different from built-in strategy
if (type == StyleOption::OptionSwitch) {
float f = widget->font().pixelSize();
int d = int(round(f));
return {int(round(f * SwitchAspectRatio)), d};
}
return StyleEngine::sizeHint(type, widget); // The remaining types are handed over to the base class
}
```

Be sure to call `StyleEngine::sizeHint(type, widget)` at the end of the function to fall back to the default implementation, otherwise other types of widgets will get zero size.

### Override `paint()`

`paint()` is distributed to the corresponding drawing logic through the `option()` type of `StyleOption`. Unprocessed types also need to be rolled back:

```cpp
void MyStyleEngine::paint(Painter &painter, Widget *widget, StyleOption &option) {
switch (option.option()) {
case StyleOption::OptionSwitch:
drawSwitch(this, painter, widget, static_cast<StyleOptionSwitch &>(option));
break;
default:
StyleEngine::paint(painter, widget, option);
}
}
```

`StyleOptionSwitch` is a derived class of `StyleOption` that adds Switch-specific status fields. It carries two key animation progress values:

- `option.transition`: Switch transition progress, `0.0` is closed state, `1.0` is open state, and the intermediate value indicates that the animation is in progress.
- `option.scale`: The scaling factor when pressed, used to draw the press feedback effect.

Use these two values to achieve smooth state transitions in `drawSwitch`:

```cpp
// Interpolate between on and off colors
color = color.blend(checked.background().color(), option.transition);

// The position of the thumb indicator moves as the transition progresses
float pos = option.transition * (box.width() - size - len);
```

`StyleEngine` is responsible for driving the animation. Developers only need to interpolate according to the progress value in `paint()` to get a complete transition effect.

::: tip Customize only some controls
The default `StyleEngine` implements the drawing logic of all built-in controls, some of which are quite complex. If you are not satisfied with the appearance of only some of the controls, you should only rewrite the drawing logic of these controls in the derived class, and the other controls directly fall back to the base class implementation.

Priority should be given to catering custom colors via a palette, and only overriding `paint()` when a completely different visual effect is required.
:::

### VectorPath draws a rounded capsule shape
The default `Switch` background and thumb are both rounded capsule shapes. In the example, `VectorPath` is used to draw two arcs. This is a more flexible method than `drawRoundedRect` and is suitable for scenarios where the arcs at both ends need to be controlled separately:

```cpp
static void indicatorBar(Painter &p, const RectF &rect) {
float radius = rect.height() * 0.5f;
float x1 = rect.left() + radius;
float x2 = rect.right() - radius;
float y = rect.top() + radius;
VectorPath path;
path.arcTo(PointF(x1, y), radius, radius, 90, 270); // Left end semicircle
path.arcTo(PointF(x2, y), radius, radius, -90, 90); // Right end semicircle
p.fillPath(path);
}
```

When two arcs are connected end to end, `arcTo` automatically connects the line in the path, without the need for additional `lineTo`.

## WaveSlider: Complete Practice of Custom Controls

`WaveSlider` is the core of this example, showing the complete development process of custom controls. Similar to the `StyleEngine` customization above, the design goal of `WaveSlider` is also to superimpose new visual effects without destroying existing capabilities:

- **Wave Fill** mode: the progress area is filled with dynamic waves instead of the ordinary rectangular progress bar;
- **Click Ripple** Effect: When pressed, diffuse oscillation is produced, causing the wave to briefly intensify and then recover;
- **`waveMode` property**: can switch between wave mode and normal mode at runtime, and supports application layer binding and attribute animation;
- **Complete fallback compatibility**: When the wave mode is turned off, `WaveSlider` directly calls `Slider::paintEvent()` to fall back to the default appearance, reusing all the capabilities of the parent class such as drag and drop, `value`/`changed`, etc., without changing any code on the application side.

### Class definition and inheritance

`WaveSlider` inherits from `Slider` (rather than directly inheriting `Widget`), and can reuse `Slider`’s existing gesture drag logic, `value`/`minimum`/`maximum` and other attributes, as well as the `changed` signal:

```cpp
// waveslider.h
#include "gx_slider.h"
#include "gx_valueanimation.h"

class WaveSlider : public Slider {
GX_OBJECT
public:
explicit WaveSlider(Widget *parent = nullptr);
~WaveSlider() override = default;

GX_NODISCARD bool isWaveMode() const { return m_waveMode; }
void setWaveMode(bool enabled);
bool event(Event *event) override;

GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
// ...
};
```

`GX_OBJECT` must be placed at the beginning of the class definition, it triggers the meta-object compiler to generate metadata for this class.`GX_PROPERTY` exposes `waveMode` to the property system so that it can be driven by application layer binding (such as `<wave-slider :wave-mode="enabled"/>`) and property animation.

### Member variables

The runtime state of the control is stored in member variables:

```cpp
private:
bool m_waveMode = false; // Whether it is currently in wave mode
float m_rippleProgress = 1.0f; // Ripple progress [0, 1], initially 1 (indicating inactive)
float m_waveOffset = 0.0f; // Waveform phase offset [0, 1], driven by animation
ValueAnimation<float> m_animation; // Wave loop animation
ValueAnimation<float> m_rippleAnimation; // Ripple animation
friend struct EventTraits<WaveSlider>; // Allow event dispatchers to access protected methods
```

`ValueAnimation<float>` is directly used as a member variable (not a pointer), and the life cycle is managed by `WaveSlider` without manual `delete`.

### Constructor: initialize animation

The constructor configures two animations and sets the direction:

```cpp
WaveSlider::WaveSlider(Widget *parent) : Slider(parent) {
// Wave animation: infinite loop, one complete cycle per second
m_animation.setRepeat(AbstractAnimation::Infinity);
m_animation.setValueLimits(0.f, 1.f);
m_animation.setDuration(1000);
m_animation.value.connect(this, &WaveSlider::onWaveAnimation);
m_animation.start();

// Ripple animation: played once when pressed, lasting 800ms
m_rippleAnimation.setValueLimits(0.f, 1.f);
m_rippleAnimation.setDuration(800);
m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);

setVertical(true); // Vertical slider
}
```

`m_animation` runs after startup, advancing `m_waveOffset` from $0$ to $1$ and looping back to $0$ each frame. This value ultimately translates into a phase shift in the waveform, allowing the wave to continue to flow.

`m_rippleAnimation` is only triggered when pressed and stops after playing once. `Infinity` is not set. The callbacks of the two animations only do one thing each: update the state variable and call `update()` to request redraw.

```cpp
void WaveSlider::onWaveAnimation(float value) {
m_waveOffset = value;
update();
}
void WaveSlider::onRippleAnimation(float value) {
m_rippleProgress = value;
update();
}
```

### Event handling

#### Configure EventDispatch

[`EventDispatch`](widget.md#processing events) is used in `event()` to route events. The template parameter lists the event types actually processed by the current control, which serves as a compile-time check:

```cpp
bool WaveSlider::event(Event *event) {
return EventDispatch<Widget,
GestureEvent, PaintEvent>{}(this, event);
}
```

#### Handling Gestures: Triggering Ripples

`gestureEvent()` intercepts the start moment of `Press` gesture to trigger ripples, and delegates the rest to `Slider` gesture processing (implementing drag and drop adjustment):

```cpp
bool WaveSlider::gestureEvent(GestureEvent *event) {
if (!event->isHitTest() && event->gesture()->type() == Gesture::Press) {
auto g = static_cast<PressGesture *>(event->gesture());
if (g->isStarted())
startRipple(g->clientPoint());
}
return Slider::gestureEvent(event); // Continue to hand over the event to Slider for processing
}

void WaveSlider::startRipple(const Point &) {
m_rippleProgress = 0.f; // Start from the beginning
m_rippleAnimation.start(); // Replay
}
```

When `isHitTest()` is `true`, it means that this is a hit test (used by the framework to detect whether the event should fall on this control) and does not represent real user interaction and should be skipped.

::: tip about `isHitTest()`
Hit testing is a preliminary step in event distribution. `gestureEvent()` will also be called during the hit testing phase, but it should not have any side effects (such as starting animations) at this time. Always check `!event->isHitTest()` first and then process the interaction logic.
:::

#### Style reading interface

`paintEvent()` will read the style data corresponding to the control. Here we first introduce the two involved interfaces:

- `style()` / `style(Styles::Xxx)` returns the `Style` object of a certain style pseudo-class of the current control, from which attributes such as color and background can be read;
- `se->palette(StyleEngine::Xxx)` reads the global palette color from `StyleEngine` as the default value when the control does not set a custom color.

The two work together to implement the logic of "use custom colors when there is custom configuration, otherwise fall back to the theme default color":

```cpp
auto contentStyle = style(Styles::Content);
p.setBrush(contentStyle.hasProperty(style::Background)
? contentStyle.background()
: se->palette(StyleEngine::ProgressRange));
```

### Drawing implementation

`paintEvent()` is the core of WaveSlider. Decide which drawing path to take based on `m_waveMode`:

```cpp
void WaveSlider::paintEvent(PaintEvent *event) {
discard(event); // PaintEvent itself does not carry useful information, explicitly discard it to eliminate compilation warnings

if (!isWaveMode())
return Slider::paintEvent(event); //Normal mode: directly call the parent class to draw

auto se = App()->styleEngine();
RectF box = rect();
float radius = min(box.width(), box.height()) * 0.5f;
float progress = sliderRange ? float(value() - minimum()) / float(sliderRange) : 0.f;

Painter p(this);

// Draw background (empty track)
p.setBrush(/* background color */);
p.fillRoundedRect(box, radius);

//Draw wave fill (progress area)
p.setBrush(/* foreground color */);
VectorPath path;
buildWaveFillPath(path, box, radius, progress, m_waveOffset, m_rippleProgress);
if (!path.isEmpty())
p.fillPath(path);
}
```

The entire drawing is divided into two steps: first use `fillRoundedRect` to draw a complete background rounded rectangle, and then use `fillPath` to draw a waveform fill above it. The two layers are superimposed to form a "rippled progress bar".

#### Waveform path generation

`buildWaveFillPath()` is a standalone helper function (not inside the class) responsible for constructing a wave path given geometric constraints:

```cpp
static void buildWaveFillPath(VectorPath &path, const RectF &box, float radius,
float progress, float waveOffset, float rippleProgress)
```

Its core logic is divided into three steps:

1. **Calculate water level and amplitude**: `waterLevel` rises from the bottom in proportion to `progress`; the amplitude depends on the width-to-height ratio and is limited to a range far enough away from the top and bottom arcs to avoid the waveform crossing the boundary.
2. **Sampling Waveform**: Sample evenly from left to right, and calculate the $y$ value for each $x$ coordinate.
The waveform consists of three parts superimposed: regular sine wave (`m_waveOffset` controls the phase) + ripple gain (`m_rippleProgress` controls the damped oscillation) + rounded constraint (ensures that the path does not exceed the boundaries of the rounded rectangle).
3. **Closed Path**: From the top of the waveform to the bottom of the rounded rectangle and back along the bottom edge, forming a closed polygon for `fillPath` to fill.

The algorithm details are a teaching effect demonstration. In actual products, they can be replaced with any customized path generation logic according to design requirements.

::: tip The efficiency of path drawing
The number of sample points (`sampleCount`) is proportional to the width of the control (approximately one point every `4px`), and the performance cost is acceptable at typical screen resolutions. If you have a weak CPU, you can reduce the sampling density or use the Bezier curve approximation instead.
:::

### waveMode property

The implementation of `setWaveMode()` is simple: update member values and mark redraw when the state changes:

```cpp
void WaveSlider::setWaveMode(bool enabled) {
if (m_waveMode != enabled) {
m_waveMode = enabled;
update();
}
}
```

The declaration of the `GX_PROPERTY` macro makes `waveMode` a framework-visible property:

```cpp
GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
```

The `signal` field is not declared here because it is typically consumer-driven value change rather than interactive triggering.

### Production-level optimization

The implementation of `WaveSlider` is mainly for teaching demonstrations and lacks some optimizations, such as:
- The wave animation always plays, even when `waveMode` is turned off and in `update()`, which triggers `paintEvent()` repeatedly;
- Only supports vertical slide bars and does not adapt to horizontal mode (determined by product requirements);
- Fixed drawing capsule shaped tracks, actual product may need to use rounded rectangles or other shapes.

## Collaboration between various departments

The following is the collaboration relationship between the components in `slider-demo` at runtime:

```
User presses the screen
├─ WaveSlider::gestureEvent() detects Press.isStarted()
│ └─ startRipple() resets m_rippleProgress and starts m_rippleAnimation
└─ Slider::gestureEvent() continues processing and adjusts the value according to the contact position
└─ changed signal emission → MyWidget::onSlider() updates Label text

Rendering loop per frame
├─ m_animation continues to advance m_waveOffset (0→1 cycle)
│ └─ update() → paintEvent() redraws the waveform with the new offset
└─ m_rippleAnimation advances m_rippleProgress (0→1 stops after playing)
└─ update() → paintEvent() repaint ripple decay with new rippleProgress

Switch switch
└─ waveSlider->setWaveMode(true/false)
└─ update() → paintEvent() switches to normal mode or wave mode
```

Each signal connection is established once in the constructor of `MyWidget`, and then the runtime is completely driven by events and signals, with no direct calls between controls.

## Summary of key patterns

Through `slider-demo`, the typical patterns for implementing custom controls in Glyphix can be summarized:

| Requirements | Practice |
|---|---|
| Inherit existing controls and reuse their interaction logic | Inherit the corresponding base class (such as `Slider`), and control the fallback to the base class in `EventDispatch` |
| Custom drawing | Implement `paintEvent()`, call `Slider::paintEvent()` when `isWaveMode()` is `false`, fallback |
| Continuously looping animation | `ValueAnimation::setRepeat(Infinity)` |
| Trigger animation once | Save state variables, call `anim.start()` in `gestureEvent()` to replay |
| Expose properties to the application layer | `GX_PROPERTY` macro, with getters/setters and optional signals |
| Read user color matching or theme color | `style().hasProperty()` returns to `se->palette()` after checking |
| Customize the appearance of global controls | Inherit `StyleEngine`, override `paint()` and `sizeHint()` |

These modes are described in detail in [Widget Development Guide](widget.md), and `slider-demo` is their comprehensive practice.

## Comparison with other GUI frameworks

::: important Positioning of C++ control development
The mainstream development method of Glyphix is to build the interface with declarative templates through [`.ux` single-file components](../tutorials/quick-orientation.md).The purpose of C++ control development is to implement the underlying control library on the device side (such as `WaveSlider` customized by the device manufacturer). These controls will then be used by the front-end application layer through templates and data binding. It is possible to build a complete UI directly in C++ (such as the demonstration in `main.cpp`) in the framework, but it is not a recommended workflow**, and the related tool chain support (debugging, hot update, layout preview) is not as complete as the application layer.

Therefore, when evaluating the overall development efficiency of Glyphix, the front-end application layer should be used as the benchmark; the C++ control development experience discussed in this section only represents the development scenario of the underlying control library.
:::

The mental model of Glyphix's C++ control development is closer to Qt Widgets than to LVGL: the signal mechanism, property macros, inherited extensions, `paintEvent` naming and division of responsibilities all basically correspond to Qt Widgets, and developers with a Qt background can quickly establish intuition.

LVGL developers need to convert from C handle style to C++ OOP style. The gap is relatively larger, but the core paradigms such as control tree organization and `update()` redraw triggering are common. This section uses `slider-demo` as a reference to explain the similarities and key differences between each framework.

### Similarities

Whether it is Qt Widgets, LVGL or Glyphix, they share a proven core paradigm of UI frameworks:

- **Control Tree**: The UI is organized in a parent-child tree structure, and the coordinates of child controls are relative to the parent control.`MyWidget(&window)` is semantically equivalent to Qt's `new QWidget(&parent)` and LVGL's `lv_obj_create(parent)`.
- **Custom drawing**: Achieve the appearance of the control by "overriding" the drawing method. Qt rewrites `paintEvent(QPaintEvent *)`, LVGL registers the `LV_EVENT_DRAW_MAIN` callback, and Glyphix implements `paintEvent(PaintEvent *)`. The three design ideas are consistent.
- **Signal/Slot Mechanism**: Status changes are transmitted between controls through signals, and the receiver responds with member functions.
- Glyphix: `m_slider.changed.connect(this, &MyWidget::onSlider)`;
- Qt: `connect(&slider, &QSlider::valueChanged, this, &MyWidget::onSlider)`;
- LVGL: Implement similar functions through event callback functions.
- **Inheritance reuse**: Implemented through inheritance when extending existing controls.`WaveSlider: public Slider` reuses all the drag and value logic of the parent class, and only rewrites the drawing part, which is consistent with the design of most OOP GUI frameworks.
- **Redraw on demand**: Call `update()` when the state changes to mark the dirty area, and the framework will redraw it uniformly in the next frame instead of drawing it immediately. Mainstream frameworks adopt this strategy to avoid repeated drawing within the frame.

### Differences from Qt Widgets

#### Event distribution

Qt distributes events through virtual function rewriting. Each event method is `virtual`, and subclasses use `override` to cover it:

```cpp
//Qt
class MySlider : public QSlider {
void paintEvent(QPaintEvent *event) override { ... }
void mousePressEvent(QMouseEvent *event) override { ... }
};
```

Glyphix's `paintEvent()`, `gestureEvent()` and other event processing functions are not virtual functions** and cannot be added with `override`. Event routing is completed by `EventDispatch` at compile time:

```cpp
//Glyphix
bool WaveSlider::event(Event *event) {
return EventDispatch<Widget, GestureEvent, PaintEvent>{}(this, event);
}
// paintEvent and gestureEvent are ordinary member functions without override
```

This is to avoid indirect jumps of virtual functions, which has performance advantages in high-frequency event processing of embedded devices; at the same time, the template parameter list serves as a compile-time document and missing item check. If you declare to handle `PaintEvent` but forget to implement `paintEvent()`, the compiler will report an error instead of silently falling back to the base class.

#### Object and attribute system

Qt uses the `Q_PROPERTY` macro with MOC (Meta Object Compiler) to generate attribute metadata; Glyphix uses `GX_PROPERTY` with `GX_OBJECT`. The mechanism is similar, but the generation method and runtime interface are different:

```cpp
//Qt
Q_PROPERTY(int value READ value WRITE setValue NOTIFY valueChanged)
//Glyphix
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

Both support animation driving through property name strings (`QPropertyAnimation` / `PropertyAnimation`).However, when implementing the control itself, Glyphix recommends using `ValueAnimation<T>` directly to avoid the cost of property name lookup and avoid conflicts with application layer-driven property animations.

#### Signals and Slots

As described in [Object System](object-system.html#signal-signal), Glyphix also has a signal mechanism, but it is closer to boost::signals2 and does not rely on MOC to generate code. This is an intentional design, because the [build system](sdk-setup.md#Other build systems) of the Glyphix ecosystem is relatively fragmented, and we assume that no meta-object compiler is used downstream at all.

#### Style and appearance customization

There are two ways to customize the appearance of Qt controls: `QStyle` subclassing (more complex) or QSS style sheets (CSS-like strings, runtime parsing).Glyphix uses `StyleEngine`: the vendor implements a `StyleEngine` subclass, draws the appearance of all built-in controls in C++ code in `paint()`, and provides recommended sizes in `sizeHint()`.This method is suitable for global system-level style customization, rather than local style adjustment of individual controls.

When setting the style of a single control, Glyphix uses the `StyleModifier` auxiliary object to assign values programmatically instead of using CSS strings:

```cpp
StyleModifier m(waveSlider);
m->setSize(120, 300);
m->setColor(Color{"#35a7ff"});

// Also supports inline style strings
waveSlider->setStyle(Style{"background-color: #35a7ff; color: #cce;"});
```

Glyphix's style and layout properties are set more through style properties rather than calling control methods directly. This is because C++ is mainly targeted at the development of underlying control libraries and is not directly oriented to application development.

#### Memory and life cycle

Under Qt's parent-child control ownership model, the parent control is responsible for destroying the child control after `new QWidget(parent)`.Glyphix also supports this mode (`new WaveSlider` followed by `addItem()`), and it is also recommended to declare child controls as member variables (such as `m_label`, `m_slider` in `MyWidget`). The life cycle is automatically managed with the host object, without manual `delete`, and does not rely on the parent-child tree destruction mechanism.

### Differences from LVGL

#### Programming model

LVGL is a framework implemented in C. Controls are operated through `lv_obj_t *` handles. Function naming usually follows the `lv_<type>_<operation>()` convention:

```c
// LVGL
lv_obj_t *slider = lv_slider_create(parent);
lv_slider_set_value(slider, 50, LV_ANIM_ON);
lv_obj_add_event_cb(slider, my_event_cb, LV_EVENT_VALUE_CHANGED, NULL);
```

Glyphix is a native C++ OOP framework. Methods are called through objects, and `this` naturally carries context:

```cpp
//Glyphix
auto *slider = new Slider(parent);
slider->setValue(50);
slider->changed.connect(this, &MyWidget::onSlider);
```

For LVGL developers, the main change here is not the capability itself, but the way of expression: before, you called functions outside the object handle, but now you organize state, events, and drawing logic inside the control class. The type system will also help you avoid misuse of some handle types at compile time.

#### Event system
LVGL's event processing usually receives multiple events through a single callback function, and uses `lv_event_get_code()` to enumerate branches within the callback:

```c
// LVGL
static void event_cb(lv_event_t *e) {
lv_event_code_t code = lv_event_get_code(e);
if (code == LV_EVENT_PRESSED) { ... }
else if (code == LV_EVENT_VALUE_CHANGED) { ... }
}
```

Glyphix distributes event types to independent processing functions. Different events are completely isolated, and the parameters also carry data of the correct type:

```cpp
//Glyphix
bool WaveSlider::gestureEvent(GestureEvent *event) { ... }
void WaveSlider::paintEvent(PaintEvent *event) { ... }
```

Additionally, Glyphix's `isHitTest()` mechanism has no exact equivalent in LVGL.LVGL can handle similar problems with `LV_EVENT_HIT_TEST`, but usually you still need to branch yourself in the same callback.

::: tip Glyphix internal event distribution mechanism
`EventDispatch` is also a switch-case distribution internally, but we do not recommend developers to hand-write switch branches. Instead, they always use the fixed `EventDispatch<Widget, ...>{}(this, event)` mode to facilitate code review.
:::

#### Animation

LVGL animation is configured through the `lv_anim_t` structure, and the target value is passed through the function pointer and `void *` user data:

```c
// LVGL
lv_anim_t a;
lv_anim_init(&a);
lv_anim_set_exec_cb(&a, anim_cb);
lv_anim_set_var(&a, obj);
lv_anim_set_values(&a, 0, 100);
lv_anim_set_time(&a, 800);
lv_anim_start(&a);
```

Glyphix's `ValueAnimation<T>` determines the interpolation type at compile time through template parameters, and eliminates `void *` conversion through signal connections:

```cpp
//Glyphix
m_rippleAnimation.setValueLimits(0.f, 1.f);
m_rippleAnimation.setDuration(800);
m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);
```

`ValueAnimation<T>` has built-in interpolation support for composite types such as `Color`, `Point`, and `Transform`. However, LVGL natively only supports integer ranges, and composite types need to implement interpolation callbacks by themselves.

#### Vector path drawing

LVGL's drawing API is mainly based on basic primitives such as rectangles and arcs. Vector path support (`lv_draw_vector`) is a newly added capability, and the interface is relatively low-level. Glyphix's `VectorPath` is a standard path construction interface. `moveTo`, `lineTo`, `arcTo`, `conicTo`, and `cubicTo` completely cover common curve types. The waveforms in `WaveSlider` completely rely on this interface implementation without introducing additional graphics libraries.

#### Memory and life cycle

Both support object tree management: child controls are hung under the parent control, and when the parent object is destroyed, the child objects will also be destroyed together.

Glyphix can also write sub-controls, animations and runtime states directly as class members and let C++'s RAII automatically manage them. For example, `m_label`, `m_slider` in `MyWidget`, and the two `ValueAnimation<float>` in `WaveSlider` can be constructed and destroyed along with the host object, instead of having to organize the state mainly around handles, `user_data` and callback context like LVGL.

# Control Development Guide

In Glyphix, all visible UI elements are widgets. The framework has built-in common controls such as buttons, labels, pictures, and scrolling areas, but equipment manufacturers often need to develop customized controls based on their own product features. For example, smart watches may require special list animations due to their smaller circular screens, while instrument devices may need to customize specialized chart controls. This document describes how to implement a new control in C++.

## Control Basics

`Widget` is a rectangular area. It has basic properties such as position, size, visibility, transparency, etc. It can receive events and is responsible for drawing its own content. Controls are organized in a tree structure: a parent control contains several child controls, and the coordinates of the child controls are relative to the parent control.

Each control has a **logical update cycle**: when the state of the control changes (for example, the data is updated), call `update()` to mark it as "requiring redrawing", and the framework will redraw all marked controls uniformly in the next rendering frame instead of redrawing immediately - this avoids multiple repeated drawings in the same frame.

### Control and component system

A UI control is usually implemented as a C++ class, inherits from `Widget`, and conforms to standard C++ object-oriented design. Glyphix's reactive framework and component system supports directly exposing these C++ controls as native components and using them in a templated and declarative manner.

This design makes the control development on the C++ side and the use of front-end components relatively independent, and maintains the development methods used by both parties. For example, in C++, you can build interfaces in a way like LVGL or Qt Widgets, without having to accept the declarative style popular in front-end frameworks.

### Comparison with other frameworks

The Glyphix control system is similar in design to traditional C/C++ UI frameworks such as Qt Widgets or LVGL.So you will find that the way and knowledge system of developing a new control is very similar to these frameworks:
- Create a new control class by inheriting `Widget`;
- There are core mechanisms such as layout system, event system, and drawing system;
- Implement data binding and event notification through attribute system and signal mechanism;
- It has geometric concepts such as coordinate system and size, and supports nested control tree structure.

::: tip It is not recommended to use C++ controls to develop UI
Glyphix is not designed to develop UI directly on the C++ side, so we will not provide relevant documentation and examples.
:::

## Create custom controls

This section takes a ring progress bar control (`ProgressRing`) as an example to explain step by step the various elements required to develop a custom control.

::: tip control comprehensive example
The [slider-demo](./widget-slider-demo.md) example included with the SDK is a complete practice of all the knowledge points in this document, including inheriting existing controls, drawing, event handling, property declaration, `ValueAnimation` animation, and `StyleEngine` customization. It is recommended to read this document after reading it.
:::

### Define control class

Create a new control, inherit `Widget`, add the `GX_OBJECT` macro at the beginning of the class definition, and override the `event()`** virtual function as the entry point for event processing:

```cpp
// progressring.h
#include "gx_widget.h"

class ProgressRing : public Widget {
GX_OBJECT
public:
explicit ProgressRing(Widget *parent = nullptr)
: Widget(parent), m_value(0) {}

int value() const { return m_value; }
void setValue(int v);
bool event(Event *event) override;

GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
Signal<int> valueChanged;

protected:
void paintEvent(PaintEvent *event);

// EventDispatch needs to access the protected method and declare friends
friend struct EventTraits<ProgressRing>;

private:
int m_value; // [0, 100]
};
```

`GX_OBJECT` is essential, it triggers the meta-object compiler to generate metadata for this class so that the control can be correctly perceived by the framework's property system, animation system and component system (see [Object System](./object-system.md) for details).

### Draw controls

Include `gx_widgetevent.h` in the `.cpp` file, implementing `event()` and `paintEvent()`:

```cpp
// progressring.cpp
#include "progressring.h"
#include "gx_widgetevent.h"

bool ProgressRing::event(Event *event) {
return EventDispatch<Widget>{}(this, event);
}

void ProgressRing::paintEvent(PaintEvent *event) {
Widget::paintEvent(event);
Painter p(this);
// ...see drawing chapter for details
}
```

Custom drawing is completed by implementing `paintEvent()`; when constructing `Painter`, pass in the `this` pointer to obtain the drawing context associated with the current control, and then call various drawing methods to draw. For a complete description of the `Painter` API, see the [Painting](./painting.md) chapter.

### Handle events

Glyphix's event system **does not rely on virtual function inheritance** to distribute events. `paintEvent()`, `gestureEvent()` and other methods are not `virtual`. **Don't** add `override` when declaring them (compilation errors will be reported).The framework routes calls to the correct handler function by event type at compile time via `EventDispatch`.

The only virtual function that needs (and must) be overridden is **`event()`**, where it delegates to `EventDispatch`:

```cpp
bool ProgressRing::event(Event *event) {
return EventDispatch<Widget>{}(this, event);
}
```

The first template parameter of `EventDispatch` is usually the **direct base class** (that is, the class that `ProgressRing` inherits from, in this case `Widget`).It will check at compile time whether the current class directly declares the corresponding processing function, and if so, it will call it, otherwise it will automatically fall back to the base class implementation. When the return value of the handler function is `bool`, it indicates whether the event has been consumed; when it returns `void`, it is deemed to have been consumed.

::: tip Base class selection tips
There are some optimization techniques for selecting the base class parameter of `EventDispatch`. You can usually choose a direct base class, but you can also use a higher-level ancestor class, which will cause subtle code size and performance differences. But generally there is no need to get too entangled, and there is no need to worry about misuse and errors - as long as the compilation passes, event distribution will work correctly.
:::

::: important
When the term "overriding `xxxEvent()`" is mentioned below, please note that only a member function with the same signature as the base class event handling function but **non-virtual** is declared in the derived control class. This is not a virtual function, cannot be overridden, and does not rely on the virtual function mechanism to distribute events.

The IDE may prompt you to change these member functions to virtual functions, but ignore this prompt.
:::

If you want to handle gesture input, declare `gestureEvent()` and implement it in your class:

```cpp
//Add a statement in the protected area of the header file:
bool gestureEvent(GestureEvent *event);

// Implemented in .cpp:
bool ProgressRing::gestureEvent(GestureEvent *event) {
if (event->type() == Event::Press) {
// ...
return true; // Returning true means that the event has been consumed and will no longer be passed to the parent control.
}
return false;
}
```

Event types that can be handled:

| Method signature | Trigger timing |
|---|---|
| `bool gestureEvent(GestureEvent *)` | Gesture events, including Press, Pan, Swipe, etc. |
| `bool wheelEvent(WheelEvent *)` | Wheel or knob input (such as watch crown) |
| `bool keyEvent(KeyEvent *)` | Entity key |
| `void resizeEvent(ResizeEvent *)` | Control size changes |
| `void moveEvent(MoveEvent *)` | Control position changes |
| `bool focusEvent(FocusEvent *)` | Focus change |
| `void paintEvent(PaintEvent *)` | Redraw request |
| `bool layoutEvent(LayoutEvent *)` | Layout request |
| `void tickEvent(TickEvent *)` | Frame-by-frame tick (needs to actively call `requestNextTick()` to enable) |

If some event handling functions are **must be implemented** for the current control, they can be declared in the template parameters of `EventDispatch`. If they are omitted or the signatures do not match, a compilation error will be reported:

```cpp
bool MyButton::event(Event *event) {
// If paintEvent or gestureEvent is not declared correctly, compilation fails
return EventDispatch<Widget, PaintEvent, GestureEvent>{}(this, event);
}
```

::: tip declares necessary event handling functions
Although `EventDispatch<Widget>` can be used to automatically distribute all events, it is **strongly recommended** to explicitly declare the event types that the current control needs to handle, so that omissions or clerical errors can be checked as much as possible at compile time, and the burden of manual review can be reduced.
:::

### Properties and signals

Use the `GX_PROPERTY` macro to expose properties to the framework so that they can be bound by the application layer and can also be used as targets for property animations:

```cpp
// Declare the value attribute, the getter is value(), and the setter is setValue()
// The signal field is associated with a change signal for the responsive framework to subscribe to.
GX_PROPERTY(int value, get value, set setValue, signal valueChanged)
```

Once declared, the `value` attribute can:
- Directly bound by the application layer template (such as `<progress-ring :value="progress"/>`)
- Smooth transitions by the property animation system (when the property type supports interpolation)

Call `update()` in the setter to trigger redrawing and send a signal to the outside at the appropriate time:

```cpp
void ProgressRing::setValue(int v) {
if (m_value == v) return;
m_value = v;
update(); // Mark the next frame for redrawing
valueChanged(v); // emit signal
}
```

`Signal<T>` is an ordinary template member variable, emitted directly like a function call. Use `Signal<>` for parameterless signals, and do not pass parameters when calling. For the complete semantics of properties and signals, see the relevant chapters in [Object System](./object-system.md).

### Layout

After the control is instantiated, manually specify the position and size through `setGeometry()`; if the parent control uses automatic layout, override `sizeHint()` to declare the expected size of the control:

```cpp
Size ProgressRing::sizeHint() const {
return Size(80, 80);
}
```

For container controls that need to manage the layout of child controls themselves, complete the geometry calculation of the child controls in `layoutEvent()`, or mount the layout class (such as `FlexLayout`) provided by the framework through `setLayout()`.For details, see the [Layout and Size](#Layout and Size) chapter.

## Draw

### Painter initialization

Construct `Painter` in the `paintEvent()` member function of the control to start drawing:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
Painter p(this);
// All subsequent drawing is completed through p
}
```

The drawing coordinate system takes the upper left corner of the control as the origin, $+x$ to the right, $+y$ to the bottom, and the unit is pixels.`rect()` returns the local rectangle `(0, 0, width(), height())` of the current control, which is the most commonly used reference area when drawing.

If the control has frame-managed style properties such as background color set by applying layer styles or `StyleModifier`, you can call the base class to handle these backgrounds before drawing custom content:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
Widget::paintEvent(event); // First draw the background managed by the frame (if any)
Painter p(this);
// ...
}
```

When the base class is not called, the background style managed by the framework will be ignored, and the control will be completely responsible for all visual presentation by its own `paintEvent`.

### Drawing status

`Painter` maintains a set of current drawing states, and each draw call uses the current state until the next modification.

#### Brush

The brush determines the fill class methods (`fillRect`, `fillRoundedRect`, `fillPath`, etc.), and the color used for the text:

```cpp
p.setBrush(Color(200, 200, 200)); // RGB gray
p.setBrush(Color{"#35a7ff"}); // Hexadecimal string
p.setBrush(Color::White); // Predefined constants
p.setBrush(Color(0xff4486ff)); // ARGB hexadecimal integer (0xff is fully opaque)
```

#### Pen

The brush determines the color and line width used by the stroke class methods (`drawRect`, `drawArc`, `drawLine`, etc.):

```cpp
Pen pen(Color(64, 156, 255));
pen.setSize(6); // Line width 6px
p.setPen(pen);
```

#### Other status

```cpp
p.setFont(Font(18)); // 18px font size, affects drawText()
p.setOpacity(127); // Transparency [0, 255], affecting all subsequent drawings
```

All states only act on the current `Painter` instance, and the `Painter` constructed by different controls are completely independent and do not interfere with each other.

### Basic Shape

#### Rectangle

```cpp
p.setBrush(Color::White);
p.fillRect(rect()); // Fill the entire control area
p.fillRect(Rect(10, 10, 60, 20)); // Fill the specified rectangle

p.fillRoundedRect(rect(), 8.0f); // Rounded corner fill, corner radius 8px
p.drawRoundedRect(rect(), 8.0f); // Rounded stroke (no fill, use Pen color)
```

When the corner radius is equal to half the smaller value of width and height, the rectangle becomes a capsule shape, which is very common in buttons and progress bars:

```cpp
float radius = min(box.width(), box.height()) * 0.5f;
p.fillRoundedRect(box, radius);
```

#### Straight line

```cpp
p.drawLine(Point(0, cy), Point(width(), cy)); // Horizontal dividing line
```

#### Arc

`drawArc` specifies an arc with center coordinates and radius, `startAngle`/`endAngle` is in degrees, $0°$ corresponds to $3$ o'clock direction, increasing clockwise:

```cpp
float cx = width() / 2.0f;
float cy = height() / 2.0f;
float radius = min(cx, cy) - 4.0f;

// Draw a complete arc (background ring), going around from -90° (12 o'clock)
Pen bgPen(Color(200, 200, 200));
bgPen.setWidth(6);
p.setPen(bgPen);
p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f);

//Draw the progress arc (clockwise from 12 o'clock to the corresponding position of progress)
if (m_value > 0) {
Pen fgPen(Color(64, 156, 255));
fgPen.setWidth(6);
p.setPen(fgPen);
p.drawArc({cx, cy}, radius, -90.0f, -90.0f + 360.0f * m_value / 100.0f);
}
```

The arc's visual thickness is determined by the current `Pen`'s linewidth.

### Vector path `VectorPath`

For complex shapes that cannot be described by rectangles and arcs, use `VectorPath` to construct arbitrary outlines, and then render them through `fillPath()` or `drawPath()`.

```cpp
#include "gx_vectorpath.h"
```

`VectorPath` works like a "brush trajectory": use `moveTo` to write down, `lineTo` straight line segments, `arcTo` arc segments to describe the outline in sequence, and finally rendered uniformly by `Painter`.

#### Straight line segment path

```cpp
VectorPath path;
path.moveTo(x0, y0); // Put pen to paper (no drawing)
path.lineTo(x1, y1); // Straight line to (x1, y1)
path.lineTo(x2, y2);
path.lineTo(x0, y0); // Return to the starting point to form a closed triangle

p.fillPath(path, Color(64, 156, 255)); // Fill the enclosed area
```

`fillPath()` automatically treats a path as a closed area, even if it does not end up explicitly returning to the starting point.`drawPath()` uses the current `Pen` to draw the path outline without filling it.

#### Arc segment path

The parameters of `arcTo` are the center of the circle, the $x/y$ radius (the two are not equal for ellipses), the starting angle and the sweep angle (angle system, clockwise is positive):

```cpp
//Draw a horizontal capsule shape: left semicircle + right semicircle, arcTo automatically connects the two segments with a connecting line
float r = rect.height() * 0.5f;
float x1 = rect.left() + r;
float x2 = rect.right() - r;
float y = rect.top() + r;

VectorPath path;
path.arcTo(PointF(x1, y), r, r, 90.0f, 270.0f); // Left end semicircle (counterclockwise from 9 o'clock to 3 o'clock)
path.arcTo(PointF(x2, y), r, r, -90.0f, 90.0f); // Right end semicircle (counterclockwise from 3 o'clock to 9 o'clock)
p.fillPath(path);
```

`arcTo` will automatically insert a straight line between the current end point of the path and the starting point of the new arc, so the two arcs are naturally connected from beginning to end, without the need for additional calls to `lineTo`.

#### Curve

Use `conicTo` or `cubicTo` to construct quadratic or cubic Bezier curve segments, and use `moveTo` and `lineTo` to describe complex contours:

```cpp
VectorPath path;
path.moveTo(x0, y0);
// Quadratic Bezier curve, (cx, cy) is the control point
path.conicTo(cx, cy, x1, y1);
// Cubic Bezier curve, (cx1, cy1) and (cx2, cy2) are control points
path.cubicTo(cx1, cy1, cx2, cy2, x2, y2);
// Fill the path with the specified brush
p.fillPath(path, brush);
```

#### Combination path example

By combining multiple instructions, you can build arbitrarily complex shapes. Taking the wave-filled area in `WaveSlider` as an example, the path contains the top wavy polyline and the bottom rounded edge:

```cpp
VectorPath path;
path.moveTo(leftX, waveY(leftX));
for (int i = 1; i <= sampleCount; ++i) {
float x = leftX + (rightX - leftX) * float(i) / sampleCount;
path.lineTo(x, waveY(x)); // Top wave outline
}
path.lineTo(rightX, bottomEdge(rightX)); // Drop to the right
for (int i = sampleCount - 1; i >= 0; --i) {
float x = leftX + (rightX - leftX) * float(i) / sampleCount;
path.lineTo(x, bottomEdge(x)); // Bottom edge (return along the bottom of the rounded rectangle)
}
path.lineTo(leftX, waveY(leftX)); // Return to the starting point
p.fillPath(path);
```

### Text

`drawText()` arranges and draws text within a rectangle. The text color is determined by the current `Brush` and the font is set by `setFont()`:

```cpp
p.setFont(Font(18));
p.setBrush(Color(50, 50, 50));
p.drawText(rect(), format("{}%", m_value), AlignCenter);
```

::: tip format string
`format()` is the formatting function provided by the framework. The syntax is similar to [`std::format`](https://en.cppreference.com/w/cpp/utility/format/format) and can be used across platforms.
:::

Alignment flags can be freely combined:

| Logo | Meaning |
|---|---|
| `AlignLeft` | Horizontal left alignment |
| `AlignHCenter` | Center horizontally |
| `AlignRight` | Horizontal right alignment |
| `AlignTop` | Vertical top alignment |
| `AlignVCenter` | Vertically centered |
| `AlignBottom` | Vertical bottom alignment |
| `AlignCenter` | Horizontal + vertical centering (equivalent to `AlignHCenter \| AlignVCenter`) |

The `font()` method returns the font currently inherited by the control from the style system. Using it during drawing can make the control automatically follow the application font size changes:

```cpp
p.setFont(font()); // Use the style font inherited by the control instead of a fixed font size
```

`drawText()` also supports more complex text layouts, such as multi-line text, automatic word wrapping, etc. See the API documentation for details.

### Pictures

`drawImage()` draws the image into the specified rectangle:

```cpp
Image img{"file://path/to/icon.png"};
p.drawImage(widget->rect(), img); // Draw the image to the specified area without automatic scaling
```

In actual use, images usually come from the resource system, and the loading method depends on the platform and packaging configuration.

### Complete example

The following is the complete `paintEvent` of `ProgressRing`, which combines the above drawing capabilities:

```cpp
void ProgressRing::paintEvent(PaintEvent *event) {
// If the control has a background style managed by the framework, call the base class first
// Widget::paintEvent(event);

Painter p(this);

float cx = width() / 2.0f;
float cy = height() / 2.0f;

//Draw a gray background circle

bgPen.setWidth(6);
p.setPen(bgPen);
p.drawArc({cx, cy}, radius, startAngle, startAngle + 360.0f);

//Draw a colored progress arc
if (m_value > 0) {
Pen fgPen(Color(64, 156, 255));
fgPen.setWidth(6);
p.setPen(fgPen);
p.drawArc({cx, cy}, radius,
startAngle, startAngle + 360.0f * m_value / 100.0f);
}

// Draw the percentage number in the center of the circle
p.setFont(Font(18));
p.setBrush(Color(50, 50, 50));
p.drawText(rect(), format("{}%", m_value), AlignCenter);
}
```

## Layout and size

Override `sizeHint()` to tell the layout system the "expected size" of the control. When the parent control uses automatic layout, the layout system will refer to this value to allocate space:

```cpp
Size ProgressRing::sizeHint() const {
return Size(80, 80); // It is recommended to display 80×80px
}
```

If the height of the control changes with the width (such as a proportionally scaled picture), override `heightForWidth()`:

```cpp
int AspectWidget::heightForWidth(int width) const {
return width; // square ratio
}
```

For situations where you need to manually manage the layout of the child control, override `layoutEvent()` and set the geometry of the child control there:

```cpp
bool ContainerWidget::layoutEvent(LayoutEvent *event) {
// Arrange child controls from top to bottom
int y = 0;
for (auto *child : children()) {
auto *w = dyn_cast<Widget *>(child);
if (w && w->isVisible()) {
w->setGeometry(0, y, width(), w->sizeHint().height());
y += w->height();
}
}
return true;
}
```

You can also use the ready-made layout classes provided by the framework (such as `FlexLayout`, `StackLayout`) and mount them through `setLayout(new FlexLayout())`.

::: tip Use ready-made layout classes
Unless you want to make a container control with a special layout, it is recommended to use the layout class provided by the framework to manage the layout of child controls. In this case, there is no need to override `layoutEvent()`.

Implementing a complete layout algorithm is relatively complex and requires processing multiple aspects of interaction such as `sizeHint()`, as well as performance optimization.
:::

## animation

The framework provides three types of animation mechanisms: **style animation**, **property animation** and **`ValueAnimation`**.Style animation and property animation are mainly used in the **application layer** (that is, the side using the control), and when implementing custom controls, `ValueAnimation` is most commonly used directly.

### ValueAnimation

`ValueAnimation<T>` is an animation class that interpolates any type `T`.Each frame it will calculate the interpolation result based on the current progress and emit it through the `value` signal. You just need to connect the signal to your own update logic:

```cpp
#include "gx_valueanimation.h"

//Declare animation objects in control members, generally using pointers to dynamically create and destroy them when needed
ValueAnimation<int> *m_animation = nullptr;
```

```cpp
// Initialize and start somewhere
m_animation = new ValueAnimation<int>;
m_animation->setValueLimits(0, 100); // Interpolate from 0 to 100
m_animation->setDuration(800); // 800 milliseconds
m_animation->value.connect(this, &MyWidget::onAnimationValue);
m_animation->start();
// Frame callback: receive the interpolation calculated for each frame
void MyWidget::onAnimationValue(int v) {
m_currentValue = v;
update(); // trigger redraw
}
```

The `finished` signal is emitted when the animation ends. If you do not need to manually manage the life cycle, you can use the `DeleteOnStop` strategy to allow the animation to be automatically destroyed after playing:

```cpp
// The animation object does not require external access and will be automatically destroyed after new.
auto *anim = new ValueAnimation<int>;
anim->setValueLimits(0, 100);
anim->setDuration(500);
anim->value.connect(this, &MyWidget::onValue);
anim->start(AbstractAnimation::DeleteOnStop); // Automatically delete after playing
```

The framework has built-in interpolation support for the following types: `int`, `float` (and other numeric types), `Color`, `Point`, `Pen`, `Brush`, `Length`, `Transform`, etc.

Other common configurations:

```cpp
// infinite loop playback
anim->setRepeat(AbstractAnimation::Infinity);

// Play back and forth alternately (forward play→reverse play→forward play...)
anim->setDirection(AbstractAnimation::Alternate);

//Set the easing curve
#include "gx_easecurve.h"
anim->setEaseCurve(easing::make_curve<easing::Ease>());
```

### Style animation and attribute animation

**Style Animation** (`StyleAnimation`) defines the transition effect in a manner similar to CSS transition. It is automatically played by the framework when the style state of the control switches. It is mainly used in the style configuration of application layer components.

**Property Animation** (`PropertyAnimation`) drives the properties declared by `GX_PROPERTY` through the property name string. It is often used in the application layer to animate control properties:

```cpp
#include "gx_propertyanimation.h"

auto *anim = new PropertyAnimation(widget, "value");
anim->setStartValue(Variant{0});
anim->setStopValue(Variant{100});
anim->setDuration(1000);
anim->start(AbstractAnimation::DeleteOnStop);
```

When implementing the control itself, you usually don't need to use property animation because `ValueAnimation` is more straightforward and doesn't have the overhead of looking up properties by name.

## Text display control

When implementing controls with text content, in addition to basic drawing logic, you also need to deal with issues such as text measurement, layout caching, and style linkage.`Label` is the most typical text control in the framework, and its implementation can be used as a reference template for similar controls.

### Use `updateLayout()`

`update()` only marks the control as requiring **redraw** and does not affect the layout system. When the text content changes, the expected size of the control (`sizeHint()` return value) usually changes accordingly. At this time, `updateLayout()` must be called at the same time to trigger the layout recalculation of the parent control:

```cpp
void MyTextWidget::setText(const String &text) {
if (m_text == text)
return;
m_text = text;
update(); // trigger redraw
updateLayout(); // Notify the parent layout to recalculate (because sizeHint has changed)
}
```

The consequence of just calling `update()` is: the text content has been updated, but the control size is still the value calculated from the old text, and the layout will be messed up.

### Text measurement and `sizeHint()`

`FontMetrics` is the core tool for text measurement, use it to implement `sizeHint()` and `heightForWidth()`:

```cpp
#include "gx_fontmetrics.h"

Size MyTextWidget::sizeHint() const {
if (m_text.empty())
return Size{0, int(font().pixelSize() * 1.2f)};
FontMetrics fm(font());
//Single line of text: measure width directly
return Size{fm.width(m_text), int(font().pixelSize() * 1.2f)};
}
```

For multi-line text that supports automatic line wrapping, you also need to implement `heightForWidth()` to tell the layout system the height of the control under a given width:

```cpp
int MyTextWidget::heightForWidth(int width) const {
if (width == 0) return 0;
FontMetrics fm(font());
float lineHeight = font().pixelSize() * 1.2f;
// boundingRect calculates the actual bounds of the text at a given width
return fm.boundingRect(m_text, width, 1024 * 1024, 0, 0, lineHeight).height();
}
```

If the control is strictly single-line (does not wrap with width), `heightForWidth()` returns `-1` to indicate no reliance on width:

```cpp
int SingleLineWidget::heightForWidth(int) const { return -1; }
```

### Responsive to style and size changes

When style attributes such as font and color change, the measurement results of the text will also change. Override `styleEvent()` to respond to style changes, call the base class implementation, refresh the cache related to the style, and then trigger layout updates:

```cpp
void MyTextWidget::styleEvent(StyleEvent *event) {
// The base class must be called first, it will update the internal style data
Widget::styleEvent(event);
// After the font and other styles are changed, the return value of sizeHint may change.
updateLayout();
}
```

Similarly, if there is width-dependent text wrapping calculation when the control size changes, an update needs to be triggered in `resizeEvent()`:

```cpp
void MyTextWidget::resizeEvent(ResizeEvent *event) {
Widget::resizeEvent(event); // Call base class
update(); // Redraw content after size change
}
```

::: important
Base class implementations of event handling functions such as `styleEvent()` and `resizeEvent()` usually have side effects that cannot be omitted and must be called. The timing of the call depends on your logic needs: in most cases, call the base class first and then execute your own logic.
:::

### Override `event()`

List all event types that need to be processed, such as `StyleEvent` and `ResizeEvent`, into the template parameters of `EventDispatch` to obtain compile-time checks:

```cpp
bool MyTextWidget::event(Event *event) {
return EventDispatch<Widget,
PaintEvent, ResizeEvent, StyleEvent>{}(this, event);
}
```

### Fluid layout and inline elements

`setFlowLayout(true)` sets the **container control** to flow layout mode. The effect is similar to CSS block-level flow. The framework will automatically arrange child elements in rows without creating an independent layout object through `setLayout()`.`Label` enables this mode in its constructor, allowing itself to be used as a `SpanLabel` container (embedding multiple sub-labels with different styles):

```cpp
Label::Label(Widget *parent) : Widget(parent) {
setFlowLayout(true);
}
```

`setInlineWidget(true)` is a setting for **child elements**, marking the control as an inline element, so that it can be embedded in the text flow of the parent container like text to participate in typesetting. For example, to embed an icon control within a row of rich text:

```cpp
auto *icon = new ImageBox(label);
// As an inline element mixed with text. ImageBox is already inline by default, this is just an example.
icon->setInlineWidget(true);
```

When `Label` is used as a `SpanLabel` container that holds inline child elements, the layout system will automatically coordinate the `Label`'s own text measurement logic and the arrangement of the child elements when used as a container. Both share the same layout mechanism, and developers do not need to manually intervene in this process.

## AbstractScrollArea and scrollable controls

When a control requires scrolling behavior, there is no need to implement gesture recognition, inertial scrolling and rebound effects from scratch. You can directly inherit `AbstractScrollArea` to obtain these capabilities. The framework's built-in `ScrollArea` (list scrolling) and `TextField` (single-line text input) are implemented based on it.

### Basic structure

Controls that inherit `AbstractScrollArea` follow a fixed structure: the control itself is the "viewport", and there is a content widget inside that is responsible for carrying the actual content. When scrolling, the content widget moves instead of the viewport itself.

Initialization is completed in the constructor:

```cpp
// myticker.h
#include "gx_abstractscorllarea.h"

class MyTicker : public AbstractScrollArea {
GX_OBJECT
public:
explicit MyTicker(Widget *parent = nullptr);
bool event(Event *event) override;

protected:
bool layoutEvent(LayoutEvent *event);
friend struct EventTraits<MyTicker>;
};
```

```cpp
// myticker.cpp
#include "myticker.h"
#include "gx_widgetevent.h"

MyTicker::MyTicker(Widget *parent) : AbstractScrollArea(parent) {
setDirection(Horizontal); // Horizontal scrolling
setDamping(5); //Adjust damping (the larger the value, the stronger the friction)

auto *content = new Widget; // Create content control
setContentWidget(content);
}

bool MyTicker::event(Event *event) {
return EventDispatch<AbstractScrollArea, LayoutEvent>{}(this, event);
}
```

Setting the base class parameter of `EventDispatch` to `AbstractScrollArea` (instead of `Widget`) allows events (gestures, scroll wheels, resize, etc.) that are not handled by the current class to automatically fall back to the implementation of `AbstractScrollArea`, thus retaining complete scrolling behavior.

### Configure scrolling parameters

```cpp
setDirection(Vertical); // Vertical scrolling (default)
setDirection(Horizontal); // Horizontal scrolling
setDamping(3); // Lower damping: stronger inertia, sliding farther
setDamping(20); //Higher damping: weak inertia, close to no inertia
setScrollBar(true); //Display scroll bar
setBouncesPolicy(SnapType::SnapEdge); // Edge bounce policy
```

`AbstractScrollArea` also provides `scrollTo(x, y, behavior)` to control the scroll position programmatically, and the `behavior` is `Instant` (jump immediately) or `Smooth` (with animation).

::: tip inertial damping
For controls such as `TextField` that require precise control of the scrolling position, a higher damping value is usually set to weaken the inertia; while for controls such as `ScrollArea` that are mainly focused on browsing, you can set a lower damping value to obtain a smoother scrolling experience.

Don’t set the damping too low, otherwise long-distance scrolling may cause content cache failure and freezes.
:::

### Call the base class in event dispatch

Sometimes it is necessary to do additional processing on an event and then transfer control to the default implementation of `AbstractScrollArea`.A typical approach is to call the base class method directly in the handler function:

```cpp
// TextField approach: forward gestures to the scroll area only when there is text
bool TextField::gestureEvent(GestureEvent *event) {
if (text().empty()) // Ignore directly if there is no text
return false;
// Leave the rest to the base class scrolling logic
return AbstractScrollArea::gestureEvent(event);
}
```

In this mode, the base class parameter of `EventDispatch` uses `Widget`, and the current class decides by itself when to call which base class method:

```cpp
bool TextField::event(Event *event) {
// Use Widget as the base class and completely control the calling timing of AbstractScrollArea behavior by yourself
return EventDispatch<Widget, GestureEvent, ResizeEvent>{}(this, event);
}
```

### Event filtering of content controls

The content control is responsible for layout and hosting child controls, but some of its events (such as layout requests) sometimes require container interception and custom processing. Register the container as an event filter for the content control via `setEventFilter(this)`, and then override `eventFilter()` to handle the events of interest:

```cpp
//Register in the constructor
content->setEventFilter(this);

//Intercept the layout request of the content control
bool MyTicker::eventFilter(Object *receiver, Event *e) {
if (receiver == contentWidget() && e->type() == Event::Layout) {
auto *lv = static_cast<LayoutEvent *>(e);
if (lv->isLayoutRequest()) {
// Custom layout logic...
return true; // Return true to prevent the event from continuing to be delivered
}
}
// Leave the rest to the base class
return AbstractScrollArea::eventFilter(receiver, e);
}
```

::: tip
Unhandled events should fall back to `AbstractScrollArea::eventFilter()`, which is responsible for interacting with internal mechanisms such as scroll bars.
:::

### Set up inline controls

Calling `setInlineWidget(true)` allows the control to participate in inline layout, which is suitable for scenes embedded in the text flow. This is how `TextField` is processed so that it can be embedded inline like text.

### ScrollArea and derived classes

`ScrollArea` is a derived class of `AbstractScrollArea`. It adds **index navigation** (`index()`/`setIndex()`), **adsorption mode** (snap) and **visual effects** (visual effect) based on scrolling. It is the preferred base class for lists, revolving doors and other scenes.`Swiper` further adds functions such as paging (`pageLength`) and indicator (indicator) on top of `ScrollArea`, which is suitable for carousel images and other modes.

These classes generally do not require further derivation, and most customization needs can be achieved through configuration parameters and mounting peripherals without subclassing.

#### Visual Effects VisualEffect

`ScrollArea` supports mounting a `VisualEffect` object through `setVisualEffect()`, and applying transparency, scaling, displacement and other visual transformations to each sub-control before drawing it to achieve dynamic effects during scrolling. The framework has the following built-in effects:

| Class name | Effect |
|---|---|
| `FisheyeVisualEffect` | Fisheye effect, the center element is enlarged and the edges are reduced |
| `FadeVisualEffect` | Edge fades, the farther away from the center of the viewport, the lower the transparency |
| `CollapseVisualEffect` | Collapse effect, elements gather and shrink at the upper (or lower) edges |
| `BlendVisualEffect` | Progressively interpolated transition between two effects |

```cpp
#include "gx_visualeffect.h"

scrollArea->setVisualEffect(make_shared<FisheyeVisualEffect>());
```

If you need custom effects, inherit `VisualEffect` and implement the `resolve()` method.`resolve()` receives the target sub-control, the viewport rectangle and the center point of the sub-control, and returns a `PaintModifier`, in which properties such as `opacity`, `scale` and `translate` can be set.

The complete parameter description of `ScrollArea` and `Swiper`, and how to implement custom `VisualEffect`, will be introduced separately in [Scroll Area](./scroll-area.md).

## Control tree and life cycle

When creating a control in C++, a parent-child relationship is established through the `parent` parameter of the constructor:

```cpp
// When parent is destroyed, child will also be destroyed.
auto *parent = new Widget(window);
auto *child = new ProgressRing(parent);
child->setGeometry(10, 10, 80, 80);
```

Whether you manually `delete` the parent control, or the framework cleans up the control tree when the app exits, all child controls are automatically destroyed. You don't need to `delete` the child control in the destructor.

If you need to delay destruction (for example, inside an event handling function), you can use `deleteLater()`, which will destroy the object after the current event processing is completed, avoiding problems such as "destroying itself in the callback".

In the reactive framework, the control tree is maintained by the component framework. When customizing development, you only need to [register the control class](./widget-export.md).
