# TODO: Оптимизация и миграция формата карт под STM32 (Cortex-M3)

Данный документ описывает план рефакторинга бинарного формата векторных карт (на базе реверс-инжиниринга DT G1) для адаптации под жесткие ограничения целевой платформы (отсутствие FPU, мало RAM, 2-битный дисплей).

## 1. Рефакторинг глобального заголовка файла
Оригинальный формат файлов (`.idx`, `.mlp`) использует 32-байтный заголовок `YZL` с избыточными данными для смарт-часов.
- [ ] **Удалить аппаратную проверку MD5.** Оригинальный формат резервирует 16 байт под контрольную сумму. На STM32 постоянный пересчет хэша при потоковом чтении с SD-карты неоправданно расходует процессорное время и ресурсы шины SPI.
- [ ] **Изменить сигнатуру и структуру.** Перепроектировать заголовок под нужды проекта `purrgo`.
  - Сократить размер заголовка до минимально необходимого (например, 12-16 байт).
  - Заменить магическую сигнатуру `YZL` на специфичную для проекта (например, `PRGO`).
  - Оставить только критичные поля: версия формата, суммарный размер `Payload Size`, начальное смещение на корень первого SQT-блока.

## 2. Исключение вычислений с плавающей точкой (`float`)
Программная эмуляция плавающей точки (SoftFP) на Cortex-M3 вызовет недопустимую задержку при проверках пересечений (Frustum Culling) и расчетах проекции.
- [ ] **Заменить типы в структурах Data Node и Nav Node.** Текущие BBox (Bounding Box) в `.idx` занимают 16 байт (`float[4]`). Их необходимо заменить на целочисленные `int32_t[4]`.
- [ ] **Внедрить масштабирование $10^7$.** Координаты в BBox должны масштабироваться умножением на `10000000` на этапе компиляции (в Python-скрипте). Это обеспечит нативную совместимость с целочисленной математикой навигационного ядра WGS84 в `geo.c` и `map_projection.c`.
- [ ] **Обновить С-структуры парсера.** В функции `parse_node()` необходимо заменить распаковку `<ffff` на `<iiii` (целочисленное чтение). Исключить любые кастования `(int32_t)(f_xmin * 10000000.0f)` на стороне микроконтроллера.

## 3. Ревизия структуры узлов (R-Tree / SQT)
- [ ] **Оптимизация поля `Type` (Код объекта).** В Data Node поле `Type` (4 байта) сейчас хранит сырые коды классов OSM (например, 5114). Его необходимо перепрофилировать под новый 5-уровневый `road_style_t` (MAJOR, NORMAL, MINOR, UNPAVED, PATH) и небольшое количество типов landuse и poi. Это позволит сократить поле до 1 байта.
- [ ] **Оптимизация поля `v3_jump`.** В Nav Node поле `v3_jump` используется для быстрого пропуска блоков (Culling). Требуется исключить из формата +8 байт компенсации префетча, специфичные для старой аппаратной платформы смарт-часов. Значение `v3_jump` должно содержать точный физический размер дочернего поддерева в байтах для передачи в `purrgo_fs_seek`.

## 4. Ограничения секции геометрии (`.mlp`) и потоковое чтение
- [ ] **Принудительная фрагментация геометрии (Chunking).** Ограничение RAM не позволяет загружать огромные массивы координат `points[]` в память. Офлайн-конвертер на PC должен принудительно фрагментировать длинные магистрали и крупные полигоны на сегменты с фиксированным лимитом точек (например, не более 128 вершин в одном Data Node, что потребует 1024 байта под статический буфер).
- [ ] **Паттерн потокового чтения.** C-парсер должен выполнять чтение вершин по одной координате за цикл (буфер 8 байт: 2 x `int32_t`), проецировать их в экранные координаты на лету и сразу отрисовывать линию, избегая переполнения RAM.
