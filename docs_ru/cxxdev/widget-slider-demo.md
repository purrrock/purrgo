## Настройка StyleEngine

Встроенный [`Switch`](/comComponents/switch.md) представляет собой полнофункциональный элемент управления Fluent 2](https://fluent2.microsoft.design/comComponents/web/react/core/switch/usage), fluent2.microsoft.design/comComponents/web/react/core/switch/usage) может не соответствовать внешнему стилю конкретного устройства или бренда.

StyleEngine — это механизм решения данных проблем. StyleEngine для настройки внешнего вида всех встроенных элементов управления, сохраняя при этом логику их взаимодействия без изменения кода платформы.

Настраиваемый «Переключатель» предназначен не только для изменения цвета темы. Напротив, весь набор переключения анимаций (размещение ползунка, переход, увеличение цвета и масштабирование) может быть реализован посредством **программированной интерполяции** вместо заранее измененных кадров по последовательностям изображений. Это означает:

- Эффекты движения полностью плавные, частота кадров соответствует системе рендеринга;
- Цвет и размер могут быть переопределены разработчиками приложений с помощью атрибутов стиля.
- Нет необходимости готовить разные графические материалы для каждого разрешения.

### Обязанности `StyleEngine`

StyleEngine — это ядро системы стилей Glyphix, отвечающее за три вещи:

1. **Обеспечить палитру** (палитра): глобальная переменная цвета, аналогичная пользовательским свойствам CSS, которую можно читать все встроенные и пользовательские элементы управления.
2. **Внешний вид элемента управления рисованием** (рисование). элементы управления фреймворка (такие как «Переключатель», «Ползунок») для рисования возлагаются на «StyleEngine::paint()», совершенно другой внешний вид.
3. **Рекомендуемый размер** (подсказка по размеру): рекомендуемый размер элемента управления в различных состояниях и стилях для справки в макете системы.

## WaveSlider: полная практика настройки элементов управления

WaveSlider — WaveSlider элементы управления. наложение новых визуальных эффектов без ущерба существующим условиям:

- Режим **Wave Fill**: область прогресса совершенствуется движениями волнами вместо обычного прямоугольного индикатора выполнения;
- Эффект **Click Ripple**: при повышении давления диффузные колебания, в результате чего волна на короткое время меняется, а затем восстанавливается;
- Свойство **`waveMode`**: может переключаться между волновым режимом и обычным режимом во время выполнения, а также поддерживает привязку уровней приложения и анимацию атрибутов;
- **Полная резервная совместимость**: когда волновой режим отключен, WaveSlider напрямую вызывает Slider::paintEvent() родительского класса, такие как перетаскивание, значение/изменение и т. д. д., без изменения какого-либо кода стороны приложения.

}
```Весь рисунок делится на два этапа: сначала используйте fillRoundedRect, чтобы изобразить полный фоновый прямоугольник со скругленными углами, а затем используйте fillPath, чтобы изобразить заливку формы волн над ними.

#### Генерация сигнала пути

`buildWaveFillPath()` — отвечающая за построение волнового пути с учетом геометрических ограничений:```cpp
static void buildWaveFillPath(VectorPath &path, const RectF &box, float radius,
                              float progress, float waveOffset, float rippleProgress)
```Его основная логика разделена на три этапа:

1. **Рассчитать уровень воды и амплитуду**: `waterLevel` поднимается снизу пропорционально `прогрессу`; амплитуда зависит от соотношения ширины к высоте и ограничена диапазоном, достаточно далеким от верхней и нижней дуг, чтобы форма волны не пересекала границу.
2. **Выборка сигнала**: равномерно производите выборку слева направо и вычисляйте значение $y$ для каждой координаты $x$.
   Форма волны состоит из трех наложенных друг на друга частей: обычная синусоидальная волна (m_waveOffset управляет фазой) + усиление пульсаций (m_rippleProgress управляет затухающими колебаниями) + ограничение округления (гарантирует, что путь не выходит за границы скругленного прямоугольника).
3. **Закрытый путь**: от верха формы сигнала до низа скругленного прямоугольника и обратно вдоль нижнего края, образуя замкнутый многоугольник для заполнения «fillPath».

Детали алгоритма представляют собой демонстрацию обучающего эффекта. В реальных продуктах их можно заменить любой настраиваемой логикой генерации пути в соответствии с требованиями проекта.

::: подсказка Эффективность прорисовки пути
Количество точек выборки («sampleCount») пропорционально ширине элемента управления (примерно одна точка на каждые «4 пикселя»), а затраты на производительность приемлемы при типичном разрешении экрана. Если у вас слабый процессор, вы можете уменьшить плотность выборки или вместо этого использовать аппроксимацию кривой Безье.
:::

### свойство waveMode

Реализация `setWaveMode()` проста: обновляйте значения членов и отмечайте перерисовку при изменении состояния:```cpp
void WaveSlider::setWaveMode(bool enabled) {
    if (m_waveMode != enabled) {
        m_waveMode = enabled;
        update();
    }
}
```Объявление макроса GX_PROPERTY делает waveMode видимым для платформы свойством:```cpp
GX_PROPERTY(bool waveMode, get isWaveMode, set setWaveMode)
```Поле «сигнал» здесь не объявлено, поскольку обычно это изменение значения, управляемое потребителем, а не интерактивный запуск.

### Оптимизация на уровне производства

Реализация WaveSlider предназначена в основном для обучающих демонстраций и не имеет некоторых оптимизаций, таких как:
- Волновая анимация воспроизводится всегда, даже если waveMode выключен и находится в режиме update(), что многократно запускает PaintEvent();
- Поддерживает только вертикальные ползунки и не адаптируется к горизонтальному режиму (определяется требованиями продукта);
- Исправлено рисование дорожек в форме капсул; в реальном продукте может потребоваться использовать закругленные прямоугольники или другие формы.

## Сотрудничество между различными отделами

Ниже приведены отношения сотрудничества между компонентами слайдера-демо во время выполнения:```
用户按下屏幕
    ├─ WaveSlider::gestureEvent() 检测到 Press.isStarted()
    │       └─ startRipple() 重置 m_rippleProgress 并启动 m_rippleAnimation
    └─ Slider::gestureEvent() 继续处理，根据触点位置调整 value
            └─ changed 信号发射 → MyWidget::onSlider() 更新 Label 文字

每帧渲染循环
    ├─ m_animation 持续推进 m_waveOffset (0→1 循环)
    │       └─ update() → paintEvent() 用新 offset 重绘波形
    └─ m_rippleAnimation 推进 m_rippleProgress (0→1 播完停止)
            └─ update() → paintEvent() 用新 rippleProgress 重绘涟漪衰减

Switch 切换
    └─ waveSlider->setWaveMode(true/false)
            └─ update() → paintEvent() 切换为普通模式或波形模式
```Каждое сигнальное соединение устанавливается один раз в конструкторе MyWidget, а затем среда выполнения полностью управляется событиями и сигналами, без прямых вызовов между элементами управления.

## Сравнение с другими фреймворками графического интерфейса

::: важное Позиционирование разработки средств управления на C++
Основной метод разработки Glyphix — создание интерфейса с помощью декларативных шаблонов с помощью [`.ux` однофайловых компонентов](../tutorials/quick-orientation.md). Целью разработки элементов управления на C++ является реализация базовой библиотеки управления на стороне устройства (например, WaveSlider, настроенной производителем устройства). Эти элементы управления затем будут использоваться на уровне внешнего приложения через шаблоны и привязку данных. В рамках платформы можно создать полный пользовательский интерфейс непосредственно на C++ (например, демонстрация в `main.cpp`), но это не рекомендуемый рабочий процесс**, а поддержка соответствующей цепочки инструментов (отладка, горячее обновление, предварительный просмотр макета) не такая полная, как на уровне приложения.

Поэтому при оценке общей эффективности разработки Glyphix в качестве эталона следует использовать уровень интерфейсных приложений; Опыт разработки элементов управления C++, обсуждаемый в этом разделе, представляет собой только сценарий разработки базовой библиотеки элементов управления.
:::

Ментальная модель разработки элементов управления C++ в Glyphix ближе к Qt Widgets, чем к LVGL: механизм сигналов, макросы свойств, унаследованные расширения, именование `paintEvent` и разделение обязанностей - все это в основном соответствует Qt Widgets, и разработчики с опытом Qt могут быстро догадаться.

Разработчикам LVGL необходимо перейти от стиля дескриптора C к стилю ООП C++. Разрыв относительно больше, но основные парадигмы, такие как организация дерева управления и запуск перерисовки update(), являются общими. В этом разделе используется слайдер-демо в качестве справочного материала для объяснения сходств и ключевых различий между каждой структурой.

### Сходства

Будь то Qt Widgets, LVGL или Glyphix, они разделяют проверенную базовую парадигму UI-фреймворков:

- **Дерево элементов управления**: пользовательский интерфейс организован в виде древовидной структуры «родитель-потомок», а координаты дочерних элементов управления указаны относительно родительского элемента управления. `MyWidget(&window)` семантически эквивалентен `new QWidget(&parent)` в Qt и `lv_obj_create(parent)` в LVGL.
- **Пользовательский рисунок**: внешний вид элемента управления можно получить, «переопределив» метод рисования. Qt переписывает `paintEvent(QPaintEvent *)`, LVGL регистрирует обратный вызов `LV_EVENT_DRAW_MAIN`, а Glyphix реализует `paintEvent(PaintEvent *)`. Три дизайнерские идеи совпадают.
- **Механизм сигналов/слотов**: изменения состояния передаются между элементами управления посредством сигналов, а приемник отвечает функциями-членами.
  - Glyphix: `m_slider.changed.connect(this, &MyWidget::onSlider)`;
  - Qt: `connect(&slider, &QSlider::valueChanged, this, &MyWidget::onSlider)`;
  - LVGL: реализация аналогичных функций с помощью функций обратного вызова событий.
- **Повторное использование наследования**: реализуется посредством наследования при расширении существующих элементов управления. `WaveSlider: public Slider` повторно использует всю логику перетаскивания и значений родительского класса и перезаписывает только часть рисования, что соответствует дизайну большинства платформ ООП с графическим интерфейсом.
- **Перерисовка по требованию**: вызовите `update()`, когда состояние изменится, чтобы отметить грязную область, и платформа будет перерисовывать ее равномерно в следующем кадре, а не рисовать ее немедленно. Основные фреймворки используют эту стратегию, чтобы избежать повторного рисования внутри фрейма.

### Отличия от виджетов Qt

#### Распространение событий

Qt распределяет события посредством переписывания виртуальных функций. Каждый метод события является виртуальным, и подклассы используют для его покрытия переопределение:```cpp
//Qt
класс MySlider: public QSlider {
    void PaintEvent(QPaintEvent *event) переопределить { ... }
    void mousePressEvent(QMouseEvent *event) переопределить { ... }
};
````paintEvent()`, `gestureEvent()` не могут быть добавлены с помощью `override`. компиляции:```cpp
//Глификс
bool WaveSlider::event(Event *event) {
    return EventDispatch<Widget, GestureEvent, PaintEvent>{}(this, event);
}
// PaintEvent иgestEvent — обычные функции-члены без переопределения
```Это сделано для того, чтобы избежать непрямых переходов виртуальных функций, которые имеют в то же время параметры шаблона списка, служащие документом времени компиляции и проверки отсутствующих элементов. компилятор сообщил о Нург вместо того, чтобы молча вернуться в базовый класс.

#### Система объектов и атрибутов

Qt использует макрос `Q_PROPERTY` с MOC (компилятором метаобъектов) для генерации атрибутов метаданных; Глификс GX_PROPERTY с GX_OBJECT. выполнение соответствия:```cpp
//Qt
Q_PROPERTY(целое значение READ значение WRITE setValue NOTIFY valueChanged)
//Глификс
GX_PROPERTY(целое значение, получить значение, установить setValue, значение сигналаChanged)
```Оба используют анимацию через строки имен свойств (QPropertyAnimation/PropertyAnimation). Самый элемент управления Glyphix рекомендует использовать ValueAnimation<T>` напрямую, чтобы избежать затрат на поиск свойств имени и избежать последствий со свойством анимации, управляемой слоем приложения.

#### Сигналы и слоты

Glyphix также имеет механизм сигналов, но он ближе к boost::signals2 и не использует MOC для генерации кода. (sdk-setup.md#Другие системы сборки) экосистемы Glyphix вскоре фрагментирована, и мы предполагаем, что ни один компилятор метаобъектов вообще не используется в будущем.

#### Настройка стиля и внешнего вида

Qt: создание подклассов `QStyle` (более Glyphix использует StyleEngine: C++ C++ Paint() и обеспечивает рекомендуемые размеры в SizeHint(). Стиль на уровне настройки системы, а не для локального стиля отдельных элементов управления.

StyleModifier для установки стиля одного элемента управления CSS:```cpp
StyleModifier m (waveSlider);
м->setSize(120, 300);
m->setColor(Color{"#35a7ff"});

// Также поддерживает строки встроенного стиля
waveSlider->setStyle(Style{"цвет фона: #35a7ff; цвет: #cce;"});
```Glyphix Glyphix Glyphix вызовы методов управления. Управление библиотеками и не ориентировано непосредственно на разработку приложений.

#### Память и жизненный цикл

В ответ на модель владения родительско-дочерним элементом управления Qt родительский Glyphix также после `new QWidget(parent)`. поддерживают этот режим («new WaveSlider», за которым следует «addItem()»), а также рекомендуется объявить дочерние элементы управления как переменные-члены (например, «m_label», «m_slider» в «MyWidget»). Цикл автоматически управляется с помощью хост-объекта, без ручного «удаления» и независимо от механизма уничтожения родительско-дочернего дерева.

### Отличия от LVGL

#### Модель программирования

LVGL — это платформа, реализованная на C. Элементы управления управляются через дескрипторы `lv_obj_t*`.```с
// ЛВГЛ
lv_obj_t *slider = lv_slider_create(родитель);
lv_slider_set_value (ползунок, 50, LV_ANIM_ON);
lv_obj_add_event_cb (слайдер, my_event_cb, LV_EVENT_VALUE_CHANGED, NULL);
```Glyphix — это собственный ООП-фреймворк C++. ответственность в своем контексте:```cpp
//Глификс
auto *slider = новый слайдер (родительский);
слайдер->setValue(50);
слайдер->changed.connect(this, &MyWidget::onSlider);
```Для разработчиков основным изменением LVGL здесь является не сама возможность, а способ выражения: раньше вы вызываете функции вне дескриптора объекта, а теперь вы вызываете состояние, события и логику отрисовки внутри управляющего класса. Избегайте неправильного использования некоторых типов дескрипторов во время компиляции.

#### События системы

Обработка событий LVGL обычно получает несколько событий через функцию функции обратного вызова и использует lv_event_get_code() для повторения ветвей в обратном вызове:```с
// ЛВГЛ
static void event_cb(lv_event_t *e) {
    код lv_event_code_t = lv_event_get_code (e);
    если (код == LV_EVENT_PRESSED) { ... }
    иначе если (код == LV_EVENT_VALUE_CHANGED) { ... }
}
```Glyphix полностью изолированы, а параметры также не содержат данных типа:```cpp
//Глификс
bool WaveSlider::gestureEvent(GestureEvent *event) { ... }
void WaveSlider::paintEvent(PaintEvent *event) { ... }
```ЛВГЛ. LVGL может решить подобные проблемы с помощью `LV_EVENT_HIT_TEST`, но обычно вам все равно приходится разветвляться тем же обратным вызовом.

::: подсказка Внутренний механизм распределения событий Glyphix
«EventDispatch» также является распределенным трибутивом для переключателей-дисплеев, но мы не рекомендуем разработчикам писать ветки переключателей вручную. фиксированный режим EventDispatch<Widget, ...>{}(this, event)` для облегчения проверки кода.
:::

#### Анимация

LVGL-анимация на воздействие через текстуру lv_anim_t, целевое значение применяется через функцию указателя и пользовательские данные void *:```с
// ЛВГЛ
lv_anim_t а;
lv_anim_init(&а);
lv_anim_set_exec_cb(&a, anim_cb);
lv_anim_set_var (& а, объект);
lv_anim_set_values(&а, 0, 100);
lv_anim_set_time(&а, 800);
lv_anim_start(&а);
````ValueAnimation<T>` Glyphix преобразования преобразования `void *` через сигналы соединения:```cpp
//Глификс
m_rippleAnimation.setValueLimits(0.f, 1.f);
m_rippleAnimation.setDuration(800);
m_rippleAnimation.value.connect(this, &WaveSlider::onRippleAnimation);
````ValueAnimation<T>` поддерживает интерполяцию для составных типов, таких как `Color`, `Point` и `Transform`. Однако LVGL изначально поддерживает только целочисленные диапазоны, а составные типы должны самостоятельно реализовывать обратные вызовы интерполяции.

#### Рисование векторного пути

API рисования LVGL в основном основан на базовых примитивах, таких как прямоугольники и дуги. Поддержка векторного пути (`lv_draw_vector`) — это новая добавленная возможность, а интерфейс относительно низкоуровневый. VectorPath от Glyphix — это стандартный интерфейс построения пути. `moveTo`, `lineTo`, `arcTo`, `conicTo` и `cubicTo` полностью охватывают распространенные типы кривых. Формы сигналов в WaveSlider полностью основаны на реализации этого интерфейса без введения дополнительных графических библиотек.

#### Память и жизненный цикл

Оба поддерживают управление деревом объектов: дочерние элементы управления подвешиваются под родительский элемент управления, и при уничтожении родительского объекта дочерние объекты также будут уничтожены вместе.

Glyphix также может писать субэлементы управления, анимацию и состояния времени выполнения непосредственно как члены класса и передавать их RAII C++ для автоматического управления. Например, `m_label`, `m_slider` в `MyWidget` и два `ValueAnimation<float>` в `WaveSlider` могут быть созданы и уничтожены вместе с хост-объектом, вместо того, чтобы организовывать состояние в основном вокруг дескрипторов, `user_data` и контекста обратного вызова, как LVGL.
