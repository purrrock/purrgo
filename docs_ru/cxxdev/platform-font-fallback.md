
# Резервный шрифт платформы

Фреймворк Glyphix шрифте/семействе шрифтов. шрифтов (например, Windows DirectWrite, macOS CoreText), в которых реализован резервный системный шрифт и соответствующая оптимизация.

Glyphix позволяет вам взять резервный шрифт: если символ не может быть покрыт внутрикадровым шрифтом, передайте его платформу, чтобы найти и отобразить соответствующий системный шрифт. проведет вас к завершению стыковки.

Задействованные общедоступные заголовочные файлы:
- `gx_unite.h`: InstallEngine()`;
- `gx_shapingadapter.h`: основной интерфейс;
- `gx_fontdriver.h`: обеспечивает механизм реализации FontDriver;
- `gx_fontloader.h`: обеспечивает интерфейс загрузчика шрифтов.

## Общая идея

Чтобы отобразить фрагмент текста на экране, он выполняет следующий этап: приложение текста в **Paragraph Layout Engine** для ветвления и наклона; шрифтом и в одном направлении **формируется** в глиф; если есть пропущенные слова, **Font Fallback** выполнит их; шрифты вызываются при регистрации, загрузке и повторном использовании слоя **Управление шрифтами**.

Три части, выделенные на рисунке, представляют собой содержание, рассматриваемое в этой статье:
1. Резервная стратегия FontFallbackShaper, используемая для поиска недостающих символов и возврата к форме;

Остальные уровни структуры реализованы. Формирование текста («ShapingAdapter») обычно не требует повторной реализации, и эталонную реализацию можно напрямую использовать повторно.

### Предварительные условия

Прежде чем реализовать функцию резервного шрифта платформы согласно этому документу, вам необходимо:

- Включите текстовый движок UniTE (по сравнению с облегченным движком по умолчанию, он поддерживает сложное формирование сценариев и многоуровневый откат).
- Целевая платформа поддерживает полный конвейер шрифтов, который может предоставлять расширенные функции, такие как формирование системных шрифтов и сопоставление сценариев. Обычно это сложная подсистема, которой нет на большинстве платформ MCU RTOS.

::: важно
Для включения UniTE и полного конвейера шрифтов требуется больше памяти и места для прошивки, чем для механизма LiTE по умолчанию. И характеристики этого двигателя хуже, чем у легкого LiTE. Необходимо оценить, нужно ли его включать для полной поддержки Unicode и требований интернационализации.
:::

## Повторное использование бэкэнда формирования

ShapingAdapter отвечает за преобразование символов в глифы. Встроенный HarfBuzzShaper (gx_harfbuzz_shaper.cpp) реализовал полное формирование OpenType. Он вызывает формирование HarfBuzz, а затем записывает индекс глифа, его продвижение и смещение в выходные данные в соответствии с размером целевого пикселя.

«HarfBuzzShaper» использует Freetype для чтения файлов шрифтов, поэтому необходимо использовать библиотеки HarfBuzz и Freetype. Если эти библиотеки уже существуют на целевой платформе, убедитесь, что их версии согласованы, в противном случае могут возникнуть ошибки компоновки или выполнения.

::: совет
Подобно обязанностям HarfBuzz, ShapingAdapter не обрабатывает текстовые фрагменты, содержащие разные шрифты, включая механизм «резервного шрифта», описанный ниже. Таким образом, всякий раз, когда в шрифте, используемом при формировании, отсутствуют символы, реализация ShapingAdapter вернет глиф .notdef (индекс 0) и будет обработана резервной стратегией.
:::

## Реализация резервной стратегии

FontFallbackShaper — это основа резервного соединения. формирует фрагмент текста, требующий, чтобы в результате формирования результата была возвращена последовательность глифов, не содержащая пропущенных символов. предназначен не только для формирования одного шрифта, но и для двухуровневого отката.

### Двухуровневый резервный каскад

`FontFallbackShaper::shape()`

- **Уровень 1**: используйте другие шрифты, дополняющие друг друга в современном семействе. Фреймворк реализован, вы просто вызываете `builtinShape()`.
- **Уровень 2**: недостающие символы, которые невозможно заполнить на первом уровне, передаются системному шрифту платформы. Этот уровень зависит от вас.

Отсутствующие символы отображаются в данных как индекс глифа «0», то есть «.notdef». Возвращаемое значение `shape()` `FallbackResult` использует битовые флаги для выражения результата: `result & NotNeeded` имеет значение true, что указывает на отсутствие пропущенных слов и может быть продолжено напрямую; в «Частично решено» (все еще сохраняется «.notdef»).

### Простой откат и кадры

Самая распространенная и хорошая стартовая ситуация — когда весь прогон можно оформить на одном и тем же шрифте платформы (то есть файл системного шрифта полностью перезаписывает скрипт). изменить форму всего дальше, написать один и тот же `faceId` во всех разделах, **напрямую перезаписать результаты первого уровня**, без слияний с разобранными глифами.

Разделение Unite происходит в соответствии со сценарием. Латиница и CJK в одном и том же тексте — это по своей сути разные прогоны. скриптами, такими как CJK, арабский, деванагари и т. д. д., весь раздел после `builtinShape()` часто имеет `.notdef`, и весь раздел изменяется и перезаписывается без потери каких-либо проанализированных глифов. Поэтому подавление большинства многоязычных наборщиков идет по этому пути, и это не является серьезным случаем вырождения.```cpp
// Выбираем шрифт платформы согласно скрипту (дескриптор шрифта платформы, а не FontDriver) и прописываем faceId
auto sysFont = PlatformFontForScript(storage.run().spec.script);
uint32_t faceId = оболочка->registerFont(sysFont);
// На этапе формирования создаются глифы glyphCount (здесь показано на примере продукта HarfBuzz)
auto &run = Storage.resize(glyphCount);
for (int i = 0; я <glyphCount; ++i) {
    run.data.glyphIds[i] = GlyphIds::encodeFallback(gid[i], faceId);
    run.data.xAdvances[i] = uint16_t(scale(pos[i].x_advance));
    run.data.xOffsets[i] = int16_t(scale(pos[i].x_offset));
    run.data.yOffsets[i] = int16_t(scale(pos[i].y_offset));
    run.data.clusterMap[i] = static_cast<int>(info[i].cluster);
}
```Поля `pos`, `info`, `gid` и `scale` HarfBuzz.

::: возможности формирования наконечника платформы
Платформа обычно имеет собственные возможности формирования (например, DirectWrite, CoreText) и возможность повторного использования HarfBuzz зависит от конкретной платформы; осуществить формирование платформы. Запуск RTL (`spec.bidiLevel & 1`) должен передать форму направления.
:::

Суть этого метода заключается в том, что весь прогон отображается на одном шрифте платформы. Это **не относится к общему шрифту** (эмодзи, символы и т. д.): разные символы в одном и том же наборе могут быть характерны для стандартных шрифтов платформы, что требует сложного резервного соединения ниже.

### Сложность проведения отката

Когда для выполнения требуется несколько платформ шрифтов или требуется откат только для кластеров, простое решение некоторые не работают. слияние документации с платформой API, это ограничение устанавливает только семантику, которой GlyphRun должен соответствовать после слияния, и обработка должна обрабатываться сама:

- Первый уровень разрешенных глифов остается **как есть**, второй уровень заменяет только кластеры, которые все еще имеют `.notdef`.
- Каждый слот глифа заполняется `glyphIds`, `xAdvances`, `xOffsets`, `yOffsets`, `clusterMap`; запасные глифы отмечены `encodeFallback(gid, faceId)`.
- `clusterMap[i]` — это смещение точек исходного кода, соответственно глифу, этого запуска** (согласно `spec.text`, диапазон `[0, text.length())`), для отражения изображения и обрезки на основе линий.
- Storage.resize()/reset()`, затем запишите слот за слотом. GlyphRunBundle автоматически обновит run().glyphCount внутри.
— Когда один и тот же исходный кластер состоит из нескольких глифов, больший порядок и продвижение должно быть логичным; кодовые точки, конечные с помощью кластеризации GSUB.
- `faceId` всего жизненного цикла;
- Возвращаемое значение: «FullyResolved» будет возвращено, если все выполнено, и «PartiallyResolved» будет возвращено, если еще остались элементы.

Если данные выходного дня соответствуют соответствующим ограничениям, платформа может корректно использовать Google. ХарфБазз.

### Высота строки и кеш

`builtinLineMetrics()` отвечает за часть глифов внутри модуля; оболочку для включения стояка и нижней части системного шрифта. Код создается с помощью encodeFallback в GlyphIds, чей FontIndex() является буквенным FaceId, а платформа соответствующего шрифта извлекается соответствующим образом.```cpp

                                   FontDriver *font) const override {

    ВертикальныеМетрики м = встроенныеЛинейные Метрики (гиды, количество, шрифт);
    // Обработка запасных символов платформы
    auto *wrapper = static_cast<PlatformFont *>(fallbackFont(font));
    если (обертка == nullptr)
        вернуть м;
    // Для символов gids[i].isFallback() запрашиваем оболочку по возрастанию/спуску и сливаем их в m
    for (auto gid: utils::span<const GlyphIds>(gids, count)) {
        если (!gid.isFallback())
            продолжить; // Обрабатываем только запасные глифы
        uint32_t faceId = gid.fontIndex(); // Резервный FontIndex() глифа, то есть FaceId
        авто лицо = оболочка->fontForFaceId(faceId); // Дескриптор шрифта платформы (не FontDriver)

            продолжить;
        m.ascent = max(face->ascender(), m.ascent);
        m.descent = min(face->descender(), m.descent);
    }
    вернуть м;
}

## Оболочка запасного шрифта `FontDriver`

Обертка отвечает за рендеринг глифов, сформированных на предыдущем этапе, в растровых изображениях. шрифт.```cpp
класс PlatformFont: public FontDriver {
публика:
    PlatformFont(const String &family, const FontAttribute &attr)
        : FontDriver(семейство, attr, Vector | PlatformFallback) {}
    // ... bitmapOf / metricsOf ...
защищено:
    void requestHandler(int) переопределить {}
};
```ФонтДрайверTTF). Функция — предоставление резервных глифов конвейерной платформы шрифтов для обработки, внутренняя часть непрозрачна для Glyphix.

### Запрос двойного режима

КодАсГлифИд:

- **С тегами**: запрос по индексу глифа, старший бит содержит `faceId`, младший бит – это индекс глифа. для запроса соответствующего GlyphBitmap.
- **Не отмечено**: запрос символов Юникода, поиск среди зарегистрированных шрифтов платформы по кодовому результату, преобразование результатов в индексные глифы и последующий запрос.

Общая реализация `bitmapOf()` выглядит следующим образом:```cpp
bool bitmapOf(uint32_t code, GlyphBitmap *bitmap) переопределить {
    if (code & CodeAsGlyphId) { // индекс по глифу
        uint32_t faceId = (код >> 16) & 0x3ff;
        uint32_t glyphId = код & 0xffff;
        авто лицо = FontForFaceId (faceId); // Дескриптор шрифта платформы (не FontDriver)
        return face && face->bitmapOf(glyphId, растровое изображение);
    }
    //Поиск символов Юникода, здесь выполняется перебор зарегистрированных шрифтов, или вы можете использовать более эффективную таблицу сопоставления
    for (auto *face: RegisteredFonts()) {
        uint32_t glyphId = face->glyphIndexOf(код);
        если (face->bitmapOf(glyphId, растровое изображение))
            вернуть истину;
    }
    вернуть ложь;
}
```::: совет
`fontForFaceId()` возвращает описание шрифта платформы, **а не `FontDriver`**; приведенные выше `face->bitmapOf(...)` и `face->glyphIndexOf(...)` "получить `GlyphBitmap` по `glyphId`" и "получить `glyphId` по кодовой точке".
:::

`metricsOf()` использует ту же бимодальную логику; `advancesOf()`, `baseline()` и т. д. шрифт платформы. `duulate()` просто копирует таблицу диаграммы.

### Сопоставление `faceId`

Оболочка конфигурации шрифтов `faceId` → платформа для регистрации и резервной политики во время рендеринга.

`faceId` — значение числа $10$ ($[0, 1023]$), смысл полностью определённая реализация, определение масштаба — **стабильность на протяжении всего жизненного цикла**. Есть два комплекта:

- **Управляется сценарием**: значение перечисления `Script` используется непосредственно как `faceId`, включает соответствующий шрифт платформы в соответствии со сценарием и записывается в соответствии со сценарием при регистрации, без необходимости выделения во время выполнения.
- **Распределение по приборам**: каждый раз, когда обнаруживается новый шрифт платформы, выводится следующий индекс и сохраняется рост таблицы.

Пример исправления скриптом (faceId — значение скрипта):```cpp
PlatformFontHandle fontForScript (сценарий сценария) {
    переключатель (скрипт) {
    случай Script::Han: return sysHanFont;
    случай Script::Arabic: return sysArabicFont;
    случай Script::Latin: return sysLatinFont;
    // ...
    }
    вернуть sysDefaultFont;
}
```FaceId` и кэширование объекта шрифта платформы.

::: совет
`faceId` — это контракт между резервной стратегией и оболочкой: `PlatformFallbackShaper` использует его для кодирования глифа, а `PlatformFont` использует его для обратного декодирования в системный шрифт. Интерпретация `faceId` целым числом $10\rm bit$.
:::

## Установка и сборка

`installEngine()` в `gx_unite.h` подключает ваш запасной перерыв к движку:```cpp

```Полная последовательность сборки:
