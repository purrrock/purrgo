
# Процесс установки приложения

Glyphix — это платформа приложений для встраиваемых устройств. После того, как устройство покидает завод, конечному пользователю или производителю все равно необходимо добавлять приложения на устройство — точно так же, как при установке приложений на телефон. Но на микроконтроллерах с ограниченными ресурсами, что именно означает «установка приложения» и как платформа находит и запускает его, не так хорошо известно, как на мобильных телефонах.

В этом документе описывается полный процесс установки → запуска → удаления пакета приложения на устройстве, а также объясняется, как конфигурация каталога влияет на поиск, обновление и удаление приложений.

## «Установить приложение» на устройстве

Приложение Glyphix поставляется в виде файла .pkg — это контейнер ресурсов, доступный только для чтения и содержащий манифест приложения («manifest.json»), код JavaScript, изображения и другие ресурсы. Во время работы приложения распаковка не производится, а фреймворк считывает файлы непосредственно из `.pkg` по требованию.

**Установка** приложения по существу выполняет две задачи: помещает файл `.pkg` в каталог на устройстве, которое будет сканироваться платформой, и регистрирует имя его пакета в базе данных пакетов. После регистрации платформа может найти соответствующий `.pkg` по имени пакета и запустить его. **Удалить** — это обратная операция: удалите файл `.pkg`, очистите данные, сгенерированные приложением, и выйдите из базы данных.

::: формат пакета ресурсов подсказки
При запуске используйте полный файл ресурсов `.pkg`, а не распакованный каталог. Этот режим пакета также распространен в игровых движках, поскольку пакет ресурсов приложения будет только читать, но не записывать. Пакетный режим может уменьшить фрагментацию файловой системы и избежать чрезмерного занятия кучей мелких файлов индексного дескриптора файловой системы.
:::

Здесь участвуют две роли, и это руководство ориентировано на последнюю:
- **Разработчик приложений**: пишите приложения на JavaScript, создавайте файлы `.pkg` с помощью команды `gx build` и доставляйте их.
- **Разработчик платформы**: интегрируйте среду выполнения Glyphix на устройстве, настройте каталог, в котором хранится приложение, и вызовите интерфейс установки и запуска на C++. Вы получаете файл `.pkg`, и цель состоит в том, чтобы заставить его работать.

::: совет
В этом руководстве предполагается, что у вас уже есть рабочий скелет платформы Glyphix («Application» + «JsVM» + «AppletKit»). Если вы еще этого не сделали, обратитесь к примерам `examples/emulator`, которые входят в состав SDK.
:::

## Подготовка

Перед началом работы убедитесь, что соблюдены следующие условия:

- Рабочая платформа Glyphix. Минимальный скелет выглядит следующим образом, и все последующие операции выполняются в этом контексте.
- Файл `.pkg` для установки. Вы можете получить его у разработчика приложения или создать образец приложения самостоятельно, используя gx build. В этом руководстве предполагается, что имя файла — «com.example.demo.pkg», а имя пакета — «com.example.demo» (имя пакета записано в файле [`manifest.json`](/framework/application/manifest.md#package) приложения).
— Перезаписываемый раздел на устройстве, используемый для хранения файлов .pkg и данных времени выполнения приложения. `/data` используется ниже для обозначения этого раздела.

Простой скелет платформы Glyphix выглядит так (это не псевдокод, все просто):```cpp
#include "gx_application.h"
#include "gx_appletkit.h"
#include "gx_jsvm.h"
#include "gx_widget.h"

using namespace gx;

int main() {
    Application app{new MyPlatform}; // 平台适配，需按设备接入
    JsVM vm;                         // JavaScript 运行时
    Widget window;                   // 所有应用的父窗口
    AppletKit kit(&window, "/pkgs.db"); // 第二个参数是包数据库路径
    // ...本教程的配置与安装代码写在这里
    return app.exec();
}
```::: Второй параметр подсказки `AppletKit`
Он указывает на файл «базы данных пакетов» (например, `/pkgs.db`). `AppletKit` использует его для записи информации об установленных приложениях. Вы можете получить объект PackageDatabase через kit.database(ADBT_Applet) для запроса списка установленных приложений, который будет использоваться позже.
:::

## Сообщаем фреймворку, где разместить приложение

Перед установкой любого приложения вы должны сначала сообщить Glyphix расположение двух каталогов: **каталог пакета приложения** (файлы хранилища `.pkg`) и **каталог данных приложения** (данные хранилища, генерируемые при запуске приложения). У этих двоих разные обязанности, поэтому не путайте их.

### Каталог пакета приложения

Каталоги пакетов приложений управляются EnvPath::packages(). Это список, каждая запись в котором указывает на каталог, в котором хранится `.pkg`. Этот список несет в себе одновременно несколько семантик, и их понимание является основой для всех последующих конфигураций:

- **Поиск**: когда платформе необходимо загрузить ресурс типа `pkg://com.example.demo/...`, она просматривает список **с начала назад** и ищет `com.example.demo.pkg` в каждом каталоге. Будет загружен первый хит.
- **Установка**: при вызове интерфейса установки новый пакет **фиксально записывается в последний каталог** в списке.
- **Удалить**: при удалении выполните сканирование спереди назад и удалите пакет из первого каталога, содержащего пакет.

Поскольку установка всегда приходится на конец списка, а поиск и удаление начинаются с начала списка, порядок каталогов в списке определяет их роль: каталог в начале подходит для приложений, которые «поставляются с завода и не хотят быть перезаписанными»; каталог сзади подходит для приложений, которые «впоследствии устанавливаются пользователем».

::: важное предварительное условие
Перед вызовом интерфейса установки список packages() должен иметь хотя бы один каталог, а последний каталог в списке (цель установки) должен существовать и быть доступен для записи. В противном случае установка завершится неудачно.
:::

Метод настройки заключается в добавлении каталогов в список на этапе инициализации платформы:```cpp
#include "gx_environment.h"
using namespace gx;

// 在 Application 构造之后、安装/启动之前调用
EnvPath::packages().emplace_back("/data/apps");
```### Каталог данных приложения

Когда приложение запущено, ему требуется доступное для записи пространство для хранения кеша, файлов, временных данных и т. д. Эти каталоги настраиваются с помощью EnvPath::setEntry(role, path)`, где каждая роль соответствует определенной цели. Их смысловой контракт таков:

| Роль | Значение | Типичный путь |
|:---|:---|:---|
| `AppletCache` | Кэш приложения с возможностью записи, инфраструктура может очищать и перестраиваться при нехватке места | `/данные/кэш` |
| `AppletFiles` | Частные файлы приложения, сохраненные, не очищенные автоматически | `/данные/файлы` |
| `AppletMass` | Большое хранилище файлов (например, медиа-ресурсы), большая емкость | `/данные/масса` |
| `AppletTemp` | Временные файлы, которые можно очистить после выхода из приложения | `/данные/темп` |
| `AppletStorage` | Постоянное хранилище приложений | `/данные/хранилище` |
| `LoggingDirectory` | Каталог журналов платформы | `/журналы` |

**Изоляция данных**. Платформа создает независимые подкаталоги для каждого приложения в указанном выше каталоге по имени пакета. Например, личные файлы приложения com.example.demo попадают в каталог /data/files/com.example.demo/. Вам не нужно вручную управлять этими подкаталогами, платформа автоматически создает и очищает их во время установки и удаления.

Кроме того, существует специальная роль GlobalPackage, которая указывает на глобально общий файл .pkg (например, /global.pkg). Все приложения могут читать общедоступные ресурсы, такие как шрифты и значки, через протокол `pkg:///...`. Он не принадлежит приложению и обычно записывается вместе с прошивкой.

Пример конфигурации:```cpp
EnvPath::setEntry(EnvPath::AppletCache,   "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles,   "/data/files");
EnvPath::setEntry(EnvPath::AppletMass,    "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp,    "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
```::: время подсказки
`EnvPath` сбрасывается до конфигурации по умолчанию при создании `Application`, поэтому пользовательскую настройку следует выполнять сразу после создания `Application` и перед любыми вызовами `installPackage`/`launch`. Поздняя настройка может привести к неожиданному поведению.
:::

### Пример конфигурации

При объединении двух типов каталогов необходимо провести последовательную интерпретацию выглядит следующим образом:```cpp
Приложение-приложение;
// Каталог пакета приложения: хотя бы один каталог, доступный для записи.
EnvPath::packages().emplace_back("/data/apps");
// Каталог данных приложения: настраивается в соответствии с фактическим разделом устройства
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");

JsVM виртуальная машина;
Окно виджетов;
Комплект AppletKit(&window, "/pkgs.db");
```## Установить приложение

Перед вызовом installPackage вам необходимо обеспечить:

1. Список EnvPath::packages()
2. Создан AppletKit
3. Устанавливаемый файл `.pkg` уже существует в файловой системе устройства (например, в `/tmp/com.example.demo.pkg`).
4. Должен быть настроен идентификатор поставщика/продукта устройства; проверка идентификатора устройства.

### Установка звонка

Интерфейс установки — «AppletKit::installPackage(fileUri, policy)», первый параметр — путь к файлу «.pkg», второй — политика «NormalVerify»):```cpp
автоматический статус = kit.installPackage("/tmp/com.example.demo.pkg");
if (статус != AppletKit::ValidPackage) {
    LogError() << "установка не удалась:" << AppletKit::packageStatusMessage(status);
    возвращаться;
}
LogInfo() << "установить ок";
```Возвращаемое значение — PackageStatus, которое имеет несколько результатов анализа:

| Статус | Значение |
|:---|:---|
| `ДействительныйПакет` | Установка прошла успешно |
| `FileNotExists` | Путь к файлу `.pkg` не существует |
| `ИнвалидПакет` | Пакет поврежден или явно не читается |
| `НедействительнаяВерсия` | Версия не соответствует политикам проверок |
| `InvalidDevice` | Идентификатор поставщика устройства/продукта не соответствует |
| `FileIOError` | или недостаточно места |

Стратегия проверки PackageVerify устанавливает, наконец, строгую систему при установке пакета:

| Политика | Проверка версии |
|:---|:---|:---|
| `NormalVerify` (по умолчанию) | Новая версия не должна быть ниже установленной | Требуется |
| `UpgradeOnly` | Должна быть строго выше установленной версии | Требуется |
| `ИгнорироватьВерсию` | Пропустить | Требуется |
| `NoVerify` | Пропустить все, если пакет легален | Пропустить |

::: совет
Если вы столкнулись с InvalidDevice или InvalidVersion во время первой установки и отладки, вы можете временно использовать AppletKit::NoVerify в процессе установки, а затем восстановить официальную отставку.
:::

### Что будет делать установка?

`installPackage` определяет следующие внешние эффекты:

- Убедитесь, что файл `.pkg` легален, и проверьте версию и идентификатор устройства в соответствии с выбранной политикой.
- Если приложение с таким же именем запущено, оно сначала будет закрыто, чтобы избежать работы с файлами или анализом данных.
- Скопируйте файл `.pkg` в последний каталог в списке `packages()` с именем `<имя-пакета>.pkg`. имя уже существует, оно будет перезаписано.
- Зарегистрируйте приложение в базе пакета данных, записав путь его установки и URI доступа `pkg://<имя-пакета>`.
— Если манифест приложения объявляет URI схемы (например, регистрирует себя в качестве обработчика метода ввода `ime`), зарегистрируйте и ее.
- Откорректировать поддержку пакета, чтобы другие части платформы не были известны о новом приложении.

::: важная проверка возможности посылки
`AppletKit::installPackage()` Производителям оборудования необходимо самостоятельно создать соответствующую функцию, проверить файл `.pkg` перед вызовом `installPackage()` и обеспечить согласованность защиты от отключения питания файловой системы, отката и т. д. д. в процессе установки. будет завершено только при условии, что файл `.pkg` легален, доступен для чтения и записи.
:::

## Удаление приложения

Интерфейс удаления — `AppletKit::removePackage(package)`. ли пакет файлов и удален:```cpp
if (!kit.removePackage("com.example.demo"))
    LogError() << "не удалось удалить: пакет не найден";
```Последствия удаления внешних гарантий:

- Если приложение запущено, сначала завершите его.
- Удалите файл `.pkg` из первого каталога в список `packages()`, содержащий пакет.
- Удалите приложения подкаталогов в каждом каталоге данных (`<имя-пакета>/` в `AppletCache`/`AppletFiles`/`AppletTemp`/`AppletStorage`).
- Замените приложение регистрации из пакета данных базы данных.

проверьте после удаления:

- `/data/apps/com.example.demo.pkg` в каталоге установки исчез.
- Данные подкаталогов, такие как `/data/files/com.example.demo/`, были очищены.
- `kit.installedApplets()` больше не содержит `"com.example.demo"`.

## Дополнительно: каталог предустановленных системных приложений.

На многих устройствах необходимо наличие двух типов приложений: системные приложения, которые предустановлены на заводе и не могут быть удалены, и пользовательские приложения, которые впоследствии включают пользователя и могут быть удалены. Этого многоуровневого расположения можно добиться с помощью двух каталогов, воспользовавшись последовательной семантикой списка пакетов().

### Сценарии использования

обычно за основу берутся флэш-памяти, доступные только для чтения, и пользователи не должны их удалять или перезаписывать. раздел доступен для записей, и их можно добавлять или удалять в любое время. каталогов используется только один каталог, последующее обновление приложения или управление удалением усложнятся.

### Рекомендуемая планировка

Packages(), packages, packages, packages чтение идет первым, каталог, доступный для записей пользователя, последний:```cpp
EnvPath::packages().emplace_back("/system/apps"); // Предустановлено только для чтения, ставится впереди
EnvPath::packages().emplace_back("/data/apps"); // Доступная для записи пользовательская установка, размещаемая после
```#Каталог пакетов приложений) на первом этапе, семантика трех операций в этом макете следующая:

- **Поиск** сбоку назад, с предустановленными каталогами сбоку и заводскими приложениями, запускаемыми первыми, чтобы обеспечить стабильную загрузку.
- **Установка** записывает последний каталог в списке, который является пользовательской областью.
- **Удалить** верхнюю часть назад, первый из каталога, пакет.

### Механизм защиты: белый вызывающая звонковую сторону

Последовательная семантика лишь определяет способ хранения приложения и запускает процесс определения и не может будить пользователей удалять предустановленные приложения. Встроенный код <code>AppletKit&#8203;::&#8203;removePackage</code>, в последовательностях которого белый список имен предустановленных пакетов, который перехватывается перед вызовом `removePackage`: если в белом списке появляется белый список, удаление отклоняется.

На боковой стороне установка белого списка не требуется. приложения, предустановленные настройки и т. д. д.) сами контролируют легитимность имен пакетов, за которые этот уровень не отвечает; маскировки прямого разрешения (см. «Известные ограничения» ниже) обновления предустановленных приложений во время выполнения не могут вступать в силу, и нет необходимости дополнительно предотвращать перезаписанные установки. `kit.installPackage`.

Собственный способ удаления слоя```cpp
#include "gx_hashset.h"

класс PackageManager {
публика:
    PackageManager (предустановлен AppletKit &kit, HashSet<String>)
        : m_kit(комплект), m_preinstalled(std::move(предустановленно)) {}

    автоматическая установка (const String &packageUri) {
        вернуть m_kit.installPackage(packageUri);
    }

    bool uninstall(const String &packageName) {
        если (m_preinstalled.count(имяпакета)) {
            LogWarning() << "отказаться от удаления защищенного пакета:" << packageName;
            вернуть ложь;
        }
        вернуть m_kit.removePackage(имяпакета);
    }

    AppletKit&m_kit;
    HashSet<String> m_preinstalled;

```::: подсказка Монтаж только для чтения и внесение в белый список
Монтирование предварительно смонтированных разделов только для чтения по-прежнему рекомендуется (во избежание случайной записи), но это не зависит от защиты от размонтирования. Даже если предустановленный каталог доступен для записи, белый список заблокирует его перед вызовом `removePackage`.

Поле разрешений `EnvPath::Entry` не участвует в принятии решения о каталоге пакета приложения, а только ограничивает доступ кода JavaScript к каталогу данных приложения.

### Восстановить заводские настройки

Воспользовавшись разделением предустановленного каталога и каталога пользователя, восстановления заводских настроек можно добиться, удалив все файлы `.pkg` в каталоге пользователя и сбросив `pkgs.db`; предустановленные пакеты в системном каталоге не затрагиваются. Установка во время выполнения фиксированно записывается в `packages().back()` (каталог пользователя) и никогда не перезаписывает предварительно установленную копию в системном каталоге. Таким образом, после очистки каталога пользователя и сброса базы данных предустановленные приложения по-прежнему можно нормально анализировать и загружать с помощью `pkg://`.

При желании можно «удалить обновления предустановленных приложений» — то есть удалить обновленную копию предустановленного приложения в пользовательском каталоге и откатить его до заводской версии в системном каталоге. Эта возможность в настоящее время только возможна и еще не получила официальной поддержки.

### Известные ограничения

Следующее поведение платформы требует, чтобы собственный бизнес-уровень активно избегал или обращал на это внимание:

1. **Обновление предустановленных приложений в магазине приложений невозможно**. Текущее разрешение ресурса `pkg://<name>` выполняет прямой обход по списку `packages()`, в то время как установка во время выполнения всегда записывает `packages().back()` (каталог пользователя). Если вы попытаетесь обновить предустановленное приложение посредством установки во время выполнения, новая версия появится в пользовательском каталоге, но будет скрыта старой версией в системном каталоге из-за прямых обращений и никогда не вступит в силу. Эту возможность обновления еще предстоит реализовать.
2. **При удалении нет понятия «защищено»**. `removePackage` находит только в соответствии с «первым успешным удалением» и удалит пакет в любом каталоге без каких-либо различий. Отметки "является ли это предустановленным пакетом" нет. Перехват белого списка должен быть реализован собственным вызывающим объектом, и платформа не предоставляет такого решения.
3. **Удаление пакета набора номера не привело к очистке базы данных**. `removePackage` только выполняет выход из таблицы приложений (`ADBT_Applet`) и не очищает записи базы данных пакета набора номера (`ADBT_Dial`), оставляя устаревшие записи. Это обязательный элемент фреймворка. Если встроенная логика удаления должна поддерживать набор номера, ее необходимо обрабатывать самостоятельно.
4. **Поле разрешений в записи каталога пакета приложения недействительно**. Разрешение `EnvPath::Entry` не участвует в решениях по поиску/установке/удалению списка `packages()` и ограничивает только доступ кода JavaScript к каталогу данных приложения. Его нельзя использовать для выражения «Установка в этот каталог запрещена».

## Шаблон инициализации платформы

Ниже приведена полная конфигурация EnvPath для трех типичных сценариев, которую можно скопировать напрямую и настроить в соответствии с путем устройства. Вся настройка должна быть выполнена после создания приложения и до <code>AppletKit&#8203;::&#8203;launch</code>/`installPackage`.

### Эмулятор хоста

Самая простая конфигурация, приложение для хранения в одном каталоге:

```cpp
os::chroot(".");
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::packages().emplace_back("/apps");
```### Встроенная цель (один раздел)

Устройство только с одним доступным для записи разделом, где приложения и данные расположены совместно:```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");
EnvPath::packages().emplace_back("/data/apps");
```### Устройства с предустановленными разделами

Отделите предустановленный раздел только для чтения раздела, доступного для записей пользователя:```cpp
EnvPath::setEntry(EnvPath::GlobalPackage, "/system/global.pkg");
EnvPath::setEntry(EnvPath::AppletCache, "/data/cache");
EnvPath::setEntry(EnvPath::AppletFiles, "/data/files");
EnvPath::setEntry(EnvPath::AppletMass, "/data/mass");
EnvPath::setEntry(EnvPath::AppletTemp, "/data/temp");
EnvPath::setEntry(EnvPath::AppletStorage, "/data/storage");

// Чувствителен к порядку: предварительно установленные каталоги только для чтения идут первыми, каталоги, доступные для записи пользователем, идут последними
EnvPath::packages().emplace_back("/system/apps");
EnvPath::packages().emplace_back("/data/apps");
```После завершения настройки вы можете настроить шаги второй и третий, чтобы установить и запустить приложение. При первом запуске пакета убедитесь, что `.pkg` появляется в `/data/apps`, `launch` возвращает непустое значение, а затем постепенно восстанавливает формальную проверку проверок и предустановленный макет.
