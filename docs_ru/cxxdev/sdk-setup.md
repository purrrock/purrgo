
# Конфигурация проекта SDK

Глификс. Native Module, Native Widget или В этой статье рассматривается, как настроить среду сборки в проекте SDK для адаптации кода платформы.

### Предварительные условия

Прежде чем начать, убедитесь, что у вас есть:
- CMake 3.14 или выше
- Компилятор C++ (GCC, Clang или MSVC) с поддержкой C++14.
- Компилятор мета-объекта Glyphix `meta` (соответствует SDK, подробности о том, как его получить, см. ниже)
- Набор инструментов для кросс-компиляции (если вам нужно создавать встроенные цели)

::: подсказка Системные требования
- Для набора инструментов MSVC требуется Visual Studio 2022 или более поздняя версия.
- Linux Ubuntu 22.04 Ubuntu 22.04.
- Программное обеспечение Ubuntu 20.04 часто приходится держать вручную.
— Примеры эмулятора и графического пользовательского интерфейса невозможно запускать в средах без графического интерфейса, таких как WSL и Docker.
— Linux, предварительно скомпилированные библиотеки Windows и macOS еще не готовы.
:::

## Структура пакета SDK

Разархивированный SDK содержит следующие каталоги:```
глификс-SDK/
├── библиотеки/
│ └── <target-triple>/ # Предварительно скомпилированные библиотеки, дифференцированные по целевым тройкам
│ ├── include/ # Заголовочный файл Glyphix (gx_*.h)
│ └── lib/ # Статическая библиотека (libglyphix-core.a и т. д.)
├── cmake/
│ ├── GlyphixSDK.cmake # Сценарий основной конфигурации SDK
│ ├── Meta.cmake # Интеграция компилятора метаобъектов (glyphix_add_meta_objects)
│ ├── cross-compile.cmake # Загрузка цепочки инструментов кросс-компиляции
│ ├── Arch/ # Параметры компиляции для каждой архитектуры (mips-linux-gnu, cortex-m33 и т.д.)
│ └── цепочка инструментов/ # Файлы цепочки инструментов CMake для каждой цепочки инструментов
├── оболочка/ # Уровень адаптации платформы (хостовая реализация сети, файловой системы и т. д.)
├── app/ # Пример входа в приложение (эмулятор, асинхронный режим и т. д.)
└── поставщик/ # Сторонняя библиотека зависимостей
```### `libs/<target-triple>/`

Предварительно скомпилированная библиотека SDK использует целевую тройку имени в качестве каталога, чтобы различать платформу, например:

- `x86_64-linux-gnu/`: разработка/эмуляция 64-битного хоста Linux.
- `mips-linux-gnu/`: встроенная цель MIPS Linux.
- `cortex_m55-none-gnu/`: голая металлическая цель Cortex-M55.

Glyphix, все с префиксом `gx_`. `lib/` статическая библиотека, и основные библиотеки включают в себя:

| Файл библиотеки | Описание |
|:---|:---|
| `libglyphix-core.a` | Основная структура (система объектов, дерево управления, события и т. д.) |
| `libglyphix-widgets.a` | Встроенная библиотека виджетов |
| `libglyphix-reactive.a` | Адаптивный фреймворк (промежуточный слой JavaScript) |
| `libglyphix-platform.a` | Интерфейс уровня абстракции платформы |
| `libglyphix-service.a` | Уровень системного обслуживания |

::: подсказка предварительно скомпилированной библиотеки поставщика
Дистрибутив SDK также содержит некоторые предварительно скомпилированные дополнительные библиотеки, такие как `libfreetype.a` и т. д. д. Не можете использовать предварительно скомпилированную компоненту и выполнять сборку непосредственно из исходного кода.
:::

## Подготовка

### Настройте компилятор метаобъекта

Компилятор метаобъектов `meta` предоставляется отдельно от SDK и автономного видео. После распаковки вы получите две директории: `bin/` и `lib/`. храниться в одном каталоге**. `lib/`.

В Linux и macOS рекомендуется заменить файл в `/usr/local`, чтобы `meta` автоматически попадала в `PATH`:

::: вкладки кода#bash

@tab Linux``` баш
sudo tar -xJf glyphix-meta-vX.X-linux-x86_64.tar.xz -C /usr/local
```@tab macOS``` баш
sudo tar -xJf glyphix-meta-vX.X-darwin-arm64.tar.xz -C /usr/local
```:::

ПУТЬ. После подтверждения, он доступен с помощью следующей команды:``` баш
мета-версия
```Если вы не хотите изменять PATH, вы можете указать полный путь к исполняемому файлу через -DGX_META=/path/to/bin/meta во время настройки CMake.

## CMakeLists.txt

### Минимальная конфигурация

::: совет
CMake, CMake, CMake, CMake, CMake, CMake, CMake Glyphix SDK.
:::

CMakeLists.txt, показывающий стандартный скелет проекта:```cmake
cmake_minimum_required (ВЕРСИЯ 3.14)

# Должен быть загружен перед project(), чтобы цепочка инструментов была на месте, когда project() проверяет компилятор
включить(cmake/cross-compile.cmake)

проект (my_glyphix_app)
установить (CMAKE_CXX_STANDARD 14)

# Загрузите Glyphix SDK (установите путь к заголовочному файлу, каталог ссылок, цель glyphix::sdk)
включить(cmake/GlyphixSDK.cmake)

add_subdirectory(vendor) # Сторонние зависимости (если есть)
add_subdirectory(src) # ваш исходный код
```Создайте цель и ввяжите SDK в `src/CMakeLists.txt`:```cmake
add_executable(my_app
  main.cpp
  мой_модуль.cpp
  my_widget.cpp
)

# Ссылка на Glyphix SDK
target_link_libraries (my_app ЧАСТНЫЙ глификс::sdk)

# Генерируем метаданные для файлов заголовков, содержащих GX_OBJECT
glyphix_add_meta_objects(my_app
  my_module.h
  my_widget.h
)
```### Регистрация метаобъектов (`glyphix_add_meta_objects`)

В документе [Object System](./object-system), зарегистрированном в сборке системы, и компиляторе мета-объекта последовательно для него файл `*_meta.cpp`. `glyphix_add_meta_objects()` — это функция CMake, которая делает это:```cmake
glyphix_add_meta_objects(<цель> [header1.h header2.h ...])
```Он принимает целевое имя и набор способов ввода заголовков в качестве аргументов. Инструмент заголовка «meta» генерирует соответствующий файл «*_meta.cpp» в подкаталоге «meta/» сборки каталога и автоматически добавляет его в список целевых исходных файлов для участия в компиляции.

**Пример:** предполагается, что проект имеет такую ​​структуру:```
источник/
├── CMakeLists.txt
├── main.cpp
├── датчики/
│ ├── Step_counter.h # Содержит GX_OBJECT
│ └── Step_counter.cpp
└── виджеты/
    ├── Activity_ring.h # Содержит GX_OBJECT
    └── Activity_ring.cpp
```Соответствующий `CMakeLists.txt`:```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/../cmake/meta.cmake)

add_executable(my_app
  main.cpp
  датчики/step_counter.cpp
  виджеты/activity_ring.cpp
)
target_link_libraries (my_app ЧАСТНЫЙ глификс::sdk)

glyphix_add_meta_objects(my_app
  датчики/step_counter.h
  виджеты/activity_ring.h
)
```::: совет отправлять только файлы заголовков, а не .cpp
`glyphix_add_meta_objects()` `GX_OBJECT`. Генерация кода без анализа файлов реализации. Сохраняется в файлах .cpp.
:::

::: предупреждение Не пропустить регистрацию
Если класс объявляет `GX_OBJECT`, но не зарегистрирован через `glyphix_add_meta_objects()`, возникает нет **ошибка ссылки** (невозможно найти такие символы, как `staticMetaObject`). CMakeLists.txt.
:::

### Цель интерфейса `glyphix::sdk`

`GlyphixSDK.cmake` ссылается на SDK. Просто внесите эту цель в свой CMakeLists.txt:```cmake
target_link_libraries (my_target ЧАСТНЫЙ глификс::sdk)
```Это внутренне эквивалентно:```cmake
# Псевдокод — на самом деле автоматически управляется GlyphixSDK.cmake
target_include_directories(... ${GLYPHIX_INCLUDE_DIRS} оболочка/включение)
target_link_libraries(... -Wl,--start-group ${glyphix-*.a} glyphix-wrapper -Wl,--end-group)
target_link_libraries(... m pthread dl) # системная библиотека UNIX
```-Wl,--start-group ... -Wl,--end-group` для упаковки статических библиотек Позволяет решить проблему циклического связывания зависимостей между статическими библиотеками на встроенных платформах.

::: подсказка Проблема с порядком ссылок
Если в проекте есть статическая библиотека вашей консоли (например, `add_library(my_module STATIC ...)`), она должна запустить группу ошибок компоновки. переменная GLYPHIX_LIBS в GlyphixSDK.cmake --start-group.
:::

## Сборка хоста

Хост создает примеры программ для запуска Glyphix на машине разработки, которая позволяет быстро проверять логику управления и модуля без подключения к оборудованию.``` баш
сборка mkdir && сборка компакт-диска
cmake -G Ниндзя ..
cmake --build.
```Каталог `app/` SDK целевому исполняемому файлу. Например:

| Подкаталоги | Строительные продукты | Описание |
|:---|:---|:---|
| `приложение/эмулятор/` | `демо` | интерфейсе MiniFB |
| `приложение/async/` | `асинхронная демонстрация` | интерфейса, демонстрирующий Native Module и асинхронный циклический вызов |

GlyphixSDK.cmake используйте его в качестве ключа для настройки предварительной скомпилированной библиотеки в каталоге libs/. `libs/x86_64-linux-gnu/`.

Если автоматический обнаруженный триплет не соответствует фактическому каталогу библиотеки, вы можете управлять им вручную:``` баш
cmake -G Ninja -DTARGET_TRIPLE=x86_64-linux-gnu ..
```Если вам нужно построить только конкретный пример, вы можете указать целевое имя:``` баш
cmake --build. --целевая демонстрация
cmake --build. --target асинхронная демонстрация
```## Кросс-компиляция CMake

Для встроенных параметров «-DARCH». В SDK предварительно настроена следующая конфигурация конструкции:

| значение `-DARCH` | целевая платформа | префикс инструментальной цепочки |
|:---:|:---:|:---:|
| `mips-linux-gnu` | МИПС Linux | `mips-linux-gnu-` |
| `cortex_m33-gnu` | ARM Cortex-M33 (GNU) | `arm-none-eabi-` |
| `cortex_m7-gnu` | ARM Cortex-M7 (GNU) | `arm-none-eabi-` |

### Пример MIPS Linux```bash
export MIPS_TOOLCHAIN_DIR="/opt/mips-gcc720-glibc229"

mkdir build-mips && cd build-mips
cmake -G Ninja .. \
  -DARCH=mips-linux-gnu \
  -DMIPS_TOOLCHAIN_DIR="$MIPS_TOOLCHAIN_DIR" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```Если цепочка инструментов уже находится в PATH (т. е. mips-linux-gnu-gcc можно вызвать напрямую), вы можете опустить -DMIPS_TOOLCHAIN_DIR, и CMake автоматически найдет ее.

### Пример ARM Cortex-M```bash
mkdir build-cm33 && cd build-cm33
cmake -G Ninja .. \
  -DARCH=cortex_m33-gnu \
  -DARM_TOOLCHAIN_DIR="/opt/arm-none-eabi-gcc" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build .
```При кросс-компиляции `GlyphixSDK.cmake` не пытается автоматически обнаруживать тройки — файл архитектуры (например, `cmake/arch/cortex_m33-gnu.cmake`) напрямую устанавливает `TARGET_TRIPLE`, указывая на правильный каталог библиотеки.

### Поддерживаемые целевые архитектуры

SDK предоставляет только предварительно скомпилированные библиотеки для архитектур, перечисленных в таблице выше. Если вашей целевой платформы среди них нет, вам необходимо связаться с Glyphix для получения пакета SDK для соответствующей архитектуры. Вы не можете добавить поддержку самостоятельно на основе существующего SDK.

## Другие системы сборки

SDK использует CMake в качестве основной системы сборки, а Glyphix также обеспечит поддержку других систем сборки для партнеров-поставщиков. Обычно это просто извлечение предварительно созданных библиотек и заголовков SDK и добавление исходных файлов уровня переноса.

### Ограничения проекта

Это решение подходит для проектов, которым требуется только стандартная функциональность SDK. Если требуются такие возможности, как настраиваемые элементы управления и собственные модули, необходимо ввести компилятор метаобъектов для генерации необходимого кода привязки. В настоящее время CMake — единственная поддерживаемая система сборки.

Доступно несколько альтернатив:
1. Используйте проект SDK CMake для создания пользовательского кода, а затем свяжите полученную библиотеку с основным проектом.
2. Используйте проект SDK CMake для создания собственного кода, а затем включите сгенерированные исходные файлы (`*_meta.cpp`) в свой основной проект.
3. Вызовите инструмент `meta` непосредственно в вашей системе сборки, чтобы сгенерировать код привязки.

Среди них сам Glyphix SDK создается с помощью метода 1. Но он не подходит для внутренних процессов разработки последующих поставщиков, поскольку требует поддержки отдельного проекта вне основного проекта прошивки и связывания сгенерированной двоичной библиотеки обратно с основным проектом. Это создает серьезные проблемы с управлением версиями.

Метод 3 также, как правило, не идеален, поскольку поставщики обычно не хотят вводить внешний инструмент в систему сборки основного проекта.

### Рекомендуемый план

Поэтому рекомендуется использовать метод 2, который копирует исходный код. Хотя для этого требуется ручное управление, его легко просмотреть и интегрировать в существующий процесс сборки. Вы можете создать собственный код в проекте CMake SDK, сгенерировать файлы `*_meta.cpp`, затем скопировать эти файлы в свой основной проект и скомпилировать их в системе сборки основного проекта.

Еще одним ограничением этого подхода является необходимость успешной сборки пользовательских исходных файлов в среде проекта SDK. В частности, для этого необходимо, чтобы его можно было построить независимо от основного проекта, включая:
- Путь включения и определение препроцессора должны быть установлены правильно. Файл заголовка настроенного компонента не может содержать файл заголовка, уникальный для основного проекта.
- Файлы cpp настроенных компонентов желательно скомпилировать и передать. Хотя это не влияет на генерацию файлов `*_meta.cpp`, это может облегчить быструю итерацию и отладку в среде хоста.

::: совет
Это не проблема для большинства [пользовательских элементов управления](widget.md). Это может быть более проблематично для [Native Module](native-module.md). Следует отметить, что файл заголовка, объявляющий GX_OBJECT, не должен включать в себя основной файл заголовка, специфичный для проекта.
:::
