## ResultSession одиночного запроса

`async::ResultSession<T>`, например, чтение файла или инициирование сетевого запроса. асинхронный шаблон, который работает как вызов асинхронной функции.

### Рабочая модель

Полный жизненный цикл ResultSession выглядит следующим образом:

1. **Создать**: функция модуляции создает сеанс через `async::make<ResultSession<T>>(applet)`, и этот сеанс автоматически привязывается к текущему `Applet`.
2. **Конфигурация**: session->client()` чистый C++, необходимый для задачи.
3. **Отредактировать**: вызовите `session->request(resolver)`, чтобы отправить задачу и мгновенно вернуть `Promise` в JavaScript.
4. **Выполнение**: Платформа перенаправляет метод клиента `resolve()` **асинхронному исполнителю** (по умолчанию — пул фоновых потоков) для выполнения.
5. **Возврат**: после возврата `resolve()` результат **автоматически переносится обратно в поток Promise`.
6. **Очистка**: сеанс сеанса объекта автоматически уничтожается после составления отчета или автоматически очищается при выходе из апплета.

:::Требования к выполнению важных классов клиентов
Клиентский класс (т. е. параметр шаблона `T`) работает в асинхронном режиме и не должен хранить JavaScript, включая любые объекты, специфичные для потока пользовательского интерфейса, такие как `JsValue`, `Applet*` и т. д. д.

Клиентский класс должен занимать свое место **модуль обработки данных на чистоте C++**, независимо только от типа данных, String, int или пользовательскую структуру и т. д. д.), и выполняющий всю работу в методеsolve(). Между потоком пользовательского интерфейса и асинхронными обрабатываются платформой автоматически.
:::

#### Накладные расходы на преобразование во время выполнения

`js_cast()` показывает обратный результат в потоке пользовательского интерфейса и не запускается в асинхронном потоке. Затраты времени на преобразование постоянно происходят в потоке пользовательского интерфейса. структура должна быть достаточно быстрой, чтобы избежать зависимости кадра. затраты каждого типа следующие:

- **Типы с нулевыми издержками**: `int`, `double`, `bool`, ``String`, ``const char *` напрямую сопоставляются конструктором через `JsValue`, без дополнительных копий кучи. js_cast<T> js_cast<T> уязвимости.
- **Линейный тип стоимости**: `std::vector<T>` должен включать `setIndex()` поэлементно, а стоимость пропорциональна количеству элементов. фиксированными, предпочтительнее использовать оператор JsValue() для ручного создания объекта JS, который более эффективен и легче читается, чем массив.
- **Совет обходит дерево**: JsonValue рекурсивно обходит все дерево во время преобразования и включает JavaScript один за другим. Это самый дорогой из изменяемых типов. JsValue() JsValue() JsValue() JsValue() затратно на создание самого JsonValue.
- **Пользовательская структура**: если вы используете специализацию `operator JsValue()` или `js_cast()`, производительность преобразования зависит от стоимости преобразования каждого типа элемента, то есть сложность построения объекта.

#### Нет уровня средней сериализации

Асинхронные платформы требуют передачи данных между некоторым потоком JSON и другими форматами с десериализованными потоками пользовательского интерфейса. Это сделано для достижения передачи «типа стирания» между потоками, но за счет того, что каждый вызов должен иметь еще худшую возможность создания нескольких копий данных (сериализованных промежуточных данных, исходных данных и т. д.).

Асинхронная платформа** не входит на средний уровень сериализации. ** Результаты перемещаются между потоками как собственные значения C++ через `async::Result<T>`, полностью минуя процесс сериализации:```
поток пользовательского интерфейса рабочего потока
solve(Result<MyType>{...}) → js_cast(result.value()) → JsValue (JavaScript)
                  ↑
             Прямое перемещение памяти, без строк JSON
````js_cast()` C++ с потоком представления движка JavaScript, не работает как протокол связи между потоками.

Если вы твердо решите использовать JsonValue в качестве параметра типа Result<T> для раздувания шаблона кода), тогда вы будете вести накладные расходы на **конструкцию и обход дерева** для `JsonValue` вместо строки сериализации. древовидную структуру в памяти, а не текстовый формат.

#### Поток обратного вызова и `fulfill()`

Обратный вызов таймаута (третий аргумент функции make_timeout()) **всегда результат** в потоке пользовательского интерфейса, поскольку он запускается таймером («Таймер»), события таймера отправляются основным циклом событий.

session->fulfill()`: session->fulfill()`: session->fulfill()`:

| Метод | Вызываемая нить | Анализ на сессии |
| --- | --- | --- |
| `решить(результат)` | Любая тема | потоком пользовательского интерфейса |
| `выполнить(результат)` | **Только поток пользовательского интерфейса** | Распространяйте результаты напрямую, **не удаляя** сеанс |

make_timeout() — это ответственность самого таймера за удаление сеанса после завершения обратного вызова. Он также доказывает событие отключения сеанса, образующее **двойное освобождение** с таймером «удаления», что приводит к неопределенности в постановлении. `fulfill()` только выдает результаты и не затрагивает жизненный цикл сеанса, поэтому это единственный безопасный выбор в обратных вызовах.

`fulfill()` принимает `async::Result<R>` или напрямую `async::Status` (сокращение от указанного значения результата):```cpp

    s->fulfill(async::Result<String>{"partial", async::Status(206)});
    // ❌ Не вызывайте s->resolve(), это сформирует двойной выпуск с сеансом удаления по таймеру
});
```::: совет
Правило определения простое: кому принадлежит сеанс и кто несет ответственность за его удаление?
- **Обычный путь**: `handle->resolve()` автоматически берет на себя управление сеансом, и сеанс удаляется после обработки событий Consume.
- **Обратный вызов по истечении времени**: таймер берет на себя управление сеансом и удаляется после завершения обратного вызова. используйте только `fulfill()`.
:::

### Автоматическая очистка при выходе из приложения

Когда «Аплет» удаляется (например, пользователь закрывает приложение и система освобождает ресурсы), все асинхронные сеансы, рекомендованные к «Аплету», будут автоматически очищаться:

- Вызывается метод `unbind()` сеанса, который закрывает сеанс и освобождает ссылку `Promise`.
- Если используется make_timeout, таймер также будет отключен, внутренний сеанс будет удален.
- «Обещание» на стороне JavaScript никогда не будет разрешено или отклонено, но сама среда JavaScript в настоящее время уничтожается, так что это безопасно.

Это означает, что вам не нужно вручную контролировать и менять асинхронные задачи — гарантии фреймворка, которые не могут произойти следующее:
— Публикация в боевом приложении приводит к доступу к вышестоящему указателю.
- Выполнение обратных вызовов в расширенном двадцати JavaScript.
— Утечка асинхронного сеанса после выхода из приложения.

В частности, когда фоновый поток вызывает `resolve()` для получения результата в потоке Applet()`. Апплет()`. В результате уничтожения Applet() возвращает nullptr, платформа безопасно выдает результат, не выполняя никаких операций JavaScript.

«Сигнал» поддерживает два режима доставки, управляемые вторым параметром:```cpp

### значения Тип сигнала

Параметр типа `T` для `Signal<T>` следует точно тем же правилам преобразования, что и `ResultSession`: при запуске сигнала платформа преобразует значение C++ в параметр обратного вызова JavaScript с помощью того же механизма `js_cast()`. Встроенные типы, такие как int, bool, String, JsonValue и т. д., можно использовать напрямую; если вам нужно передать пользовательскую структуру или перечисление, обратитесь к методам в разделе [Типы значений и преобразование JavaScript](#Типы значений и -javascript-преобразование).

## Инструкции по безопасности потоков

Модель потокобезопасности асинхронных платформ следует следующим правилам:

- **`resolve()` является потокобезопасным**: `ResultSession::resolve()` и `SingleTimer::resolve()` можно вызывать из любого потока. Они доставляют результаты в поток пользовательского интерфейса через систему событий и не работают напрямую с объектами JavaScript.
- **`JsValue` не является потокобезопасным**: `JsValue` управляет жизненным циклом на основе подсчета ссылок, а его операции подсчета ссылок не являются атомарными. `JsValue` нельзя создавать, копировать, уничтожать или получать к нему доступ в асинхронном потоке. Вот почему клиентские классы не должны содержать JsValue.
- **Разрешение Promise выполняется в потоке пользовательского интерфейса**: независимо от того, из какого потока вызывается `resolve()`, окончательный обратный вызов `Promise` всегда выполняется в потоке пользовательского интерфейса, обеспечивая безопасность операций пользовательского интерфейса.
- **`async::Signal` уведомления отправляются в потоке пользовательского интерфейса**: хотя `async::Signal::operator()` можно вызывать в разных потоках, обратные вызовы JavaScript всегда выполняются в потоке пользовательского интерфейса.

Если клиентскому классу необходимо поделиться состоянием с потоком пользовательского интерфейса (например, предоставить флаг отмены), используйте атомарные операции, такие как [`std::atomic`](https://en.cppreference.com/w/cpp/atomic/atomic) или мьютекс для защиты общих данных:```cpp
class CancellableClient {
public:
    void cancel() { m_cancelled.store(true); }

    async::Result<String> resolve() {
        for (int i = 0; i < 100 && !m_cancelled.load(); ++i) {
            // 执行分步任务，定期检查取消标志
            processChunk(i);
        }
        if (m_cancelled.load())
            return async::Status(499);  // 客户端取消
        return std::move(m_result);
    }

private:
    std::atomic_bool m_cancelled{false};
    String m_result;
};
```В частности, многие типы значений платформы Glyphix могут безопасно передаваться между потоками в этой асинхронной среде, например:
- `String`: может быть назначен и доступен напрямую в нескольких потоках без дополнительного механизма синхронизации.
- `JsonValue`: этот класс также является типом значения и имеет те же функции безопасности потоков, что и `String`.
- `ByteArray`: аналогичен `String`, поддерживает межпоточное использование.
- `SharedRef<T>`: интеллектуальный указатель с подсчетом ссылок сам по себе может передаваться между потоками, но безопасность потока управляемого объекта `T` зависит от его определения.
— Несобственные типы, такие как String::View, нельзя использовать в потоках.

Вот почему во всех предыдущих примерах мы всегда захватываем и передаем такие типы, как String, непосредственно в асинхронный контекст, и для их использования не требуется никакой специальной обработки. Для защиты нет необходимости использовать механизмы синхронизации, такие как мьютекс.

::: важно
Вышеупомянутые типы потокобезопасности на самом деле зависят от конкретной модели памяти асинхронной платформы, а это означает, что они не являются автоматически потокобезопасными во всех сценариях. Асинхронная структура в этом документе гарантирует это, но ее нельзя обобщать на все ситуации.
:::
