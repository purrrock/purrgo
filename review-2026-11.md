## Находки

### [Высокая] Диагностический режим трек-логгера включён по умолчанию

`src/core/nav/track_logger.c:26-28`:

```c
#ifndef PURRGO_TRACK_DIAG
#define PURRGO_TRACK_DIAG 1
#endif
```

Последствия сборки без явного `-DPURRGO_TRACK_DIAG=0`:

- **прошивка** (`stm32u5-debug/release`): корневой `CMakeLists.txt:73-76` при опции OFF (значение по
  умолчанию) макрос **не определяет вовсе**, срабатывает fallback `1`. Логгер пишет **каждую эпоху
  GNSS** (~0,9 МБ/ч по комментарию в `track_logger.c:24`) с маской `pg:rej` в `<extensions>` — рост
  записи на SD, энергопотребление, размер трека, и пользовательские GPX не соответствуют
  документации;
- **PC-сборки и эмулятор** — то же самое (define добавляет только `tests/host/CMakeLists.txt:12-13`,
  который подключается лишь при `PURRGO_BUILD_TESTS=ON`);
- **host-тесты** защищены явно (`tests/host/CMakeLists.txt:13`, `run.sh:30`), поэтому CI зелёный и
  проблему не ловит;
- документация утверждает обратное: `CMakeLists.txt:70-71` («Для штатной работы выключено»),
  `docs/development.md:78` (в таблице параметров `ON` — «включить», подразумевая, что OFF — рабочее
  состояние).

Судя по комментариям в `run.sh:23-26` и `tests/host/CMakeLists.txt:8-11`, default `1` — сознательное
**временное** состояние «для полевого теста» (снятие кривых разряда по `pg:vbat` — см. TODO P1, пункт
о кривых щелочных/NiMH/Li-FeS2). Риск в том, что состояние забыто в коде и не имеет «предохранителя»:
через документированную опцию `-DPURRGO_TRACK_DIAG=ON/OFF` выключить его нельзя (OFF ничего не
определяет), а чек-лист P4 («Проверить track logging») пройдёт с диагностическим режимом и не заметит.

**Рекомендация**: вернуть fallback `0`, полевой тест включать только `-DPURRGO_TRACK_DIAG=ON`
(опция уже добавляет `=1`); в P4 добавить пункт «штатная запись трека в релизной сборке»; пока не
сняты кривые разряда щелочных/NiMH/Li-FeS2 — решение за владельцем ([решение] в TODO).

### [Средняя] Дрейф `docs/eink.md`: EXTI BUSY показан как «не реализовано»

`docs/eink.md:89-94` в списке «Не реализовано» первой строкой называет «прерывание EXTI по BUSY
вместо опроса», но пробуждение по спаду BUSY давно работает: `stm32/port/display/eink_wake.c`
(arm/disarm, вектор `EXTI2_IRQHandler`, static_assert на линию PB2) и используется в цикле сна
(`stm32_app.c:215-224`); в `TODO.md` пункт отмечен `[x]`. Файл `eink_wake.c` не упомянут и в таблице
файлов `docs/eink.md`. Читатель документа получит неверную модель энергопотребления и, например,
начнёт «оптимизировать» уже сделанное.

**Рекомендация**: обновить `docs/eink.md` (перенести EXTI BUSY из «не реализовано» в описание,
добавить `eink_wake.c` в таблицу); пункты про SPI DMA и 1-bit серый пересверить с текущим состоянием
(TODO P2/Dисплей).

### [Средняя] Дрейф комментария в `hardware_config.h` (PSMOO)

`include/purrgo/hardware_config.h:70-74`: «Режим PSMOO … не поддержан намеренно: между фиксами
приёмник молчит…». Ниже по тому же файлу (строки 118-190) PSMOO полностью описан и включён по
умолчанию для режима TRACKER (`PURRGO_GNSS_TRACKER_PSMOO 1`), профиль трекера реализован в
`gnss_receiver.c`/`gnss_io.c`. Первая половина комментария — устаревший текст эпохи до введения
профиля трекера.

**Рекомендация**: переписать блок строк 52-91 с учётом PSMOO (или сократить его до ссылки на
раздел трекера и `docs/gnss-ubx.md`).

###  [Средняя] `app_fsm.c` — концентрация ответственности

884 строки: маршрутизация кнопок по экранам, таймауты фикса GNSS, retry-политика логгера, вход/выход
в режимы (читалка, трекер), «shown_*»-дифференцирование данных для перерисовки, sun-таймеры.
Код корректный и хорошо прокомментированный, но каждый новый экран утяжеляет один файл и один
`switch` (`purrgo_app_handle_button`, строки 341+).

**Рекомендация** (Backlog, без спешки): выделить (а) таблицу соответствия «состояние → кнопка →
действие», (б) отдельный модуль политики логгера (`logger_retry`), (в) модуль «заметных изменений
данных» (shown_*) с host-тестами — тестировать станет проще, файлы меньше.

###  [Низкая] CI-сборка прошивки без `-Werror`

`PURRGO_WERROR` включён только в пресете `linux-gcc-test` (`CMakePresets.json:92`); job
`build-stm32u5` (`ci.yml:54-65`) собирает `stm32u5-release` без него, поэтому новые предупреждения
arm-gcc в коде прошивки CI не останавливают (clang-tidy informational, cppcheck прошивку не
обходит — только `sd_spi.c`, `ci.yml:93-94`).

**Рекомендация**: добавить `PURRGO_WERROR=ON` в job `build-stm32u5` (или в пресеты `stm32u5-*`),
предварительно убедившись, что прошивка собирается чисто под arm-none-eabi-gcc; затем расширить
cppcheck на HAL-free модули `stm32/port` (`gnss_link.c`, `gnss_diag.c`, `sd_power.c` — они уже
тестируются на хосте и не тянут HAL).

### [Низкая] Мелкие дефекты кода

- Дублирующиеся `#include`: `app_fsm.c:3` и `:12` (`purrgo/map_controller.h`), `map_idx.c:9` и `:14`
  (`string.h`) — следы слияний;
- `stm32_app.c:458`: комментарий `//обработка кнопок` дублирует соседний канонический и выпадает из
  стиля остального кода;
- смешение языков комментариев (рус/англ) даже внутри одного файла — само по себе не проблема, но
  для новых модулей стоит держаться русского (фактический стандарт проекта).

**Рекомендация**: разовая чистка техдолга, без отдельного приоритета.

###  [Низкая] Ручная бухгалтерия слоёв карты в `map.c`

`map_context_t` (13 указателей файлов + 8 флагов missing + 7 флагов включённости) и
`map_close_all_files()` (`map.c:76-114`) перечисляют слои вручную; добавление слоя (например,
waterways уже показало схему) требует правок в шести местах. Аналогичную ручную синхронизацию
делает `docs/architecture.md` раздел «Layer drawing order».

**Рекомендация** (Backlog): таблица дескрипторов слоёв `{имя, флаг конфига, idx/mlp/db, missing,
порядок отрисовки}` — один цикл закрытия/открытия, порядок отрисовки из тех же данных; снизит и
рассинхрон с документацией.
